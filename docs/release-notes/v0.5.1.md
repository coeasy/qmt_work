## 一、大 QMT 模式：结论与证据

**模式识别链路完全正确**（真机只读取证，光大 QMT @ `P:\stock\gd_qmt`）：

| 检查点 | 实测 |
|---|---|
| 运行进程 | `['XtItClient.exe']`（**无** `miniquote.exe`） |
| `_probe_quote_service` | `client_type=full`、`trade_ports=[58600]`、`quote_ports=[]` |
| `discover()` 首选候选 | `client_mode=full`、`mode_source=process`、`client_path=…\userdata` |
| `_effective_trade_dir(auto)` | `(…\userdata, "full")` |
| 策略桥实跑（QMT 内置 py3.6.8） | `ok=true`、`PROBE ok=true`、actions=14、exit=0 |

**但交易链不通，根因已确证**（推翻此前「PID 白名单」「极简模式没勾」两条假设）：
客户端主日志 `XtClient_20261009.log`（17.2 MB / 103 592 行）里，授权串
`mdl_auth_xtquant=0`、`mdl_auth_gt_ipc_pair=0`，配套
`CIPCManager::init, not auth:mdl_auth_gt_ipc_pair` +
**`The XtQuantServer is not allowed to start.`**，而三个 `strict_connection_check` 全为 `0`。

⇒ **券商未给该资金账号下发 xtquant 模块授权，客户端根本不启动量化服务**。
要走通只剩两条路：① 找券商开通 xtquant 模块授权；② 走**路径 B 策略桥**（客户端内置 Python，不受该授权限制）。

## 二、本版修复（按「断链 / 孤儿 / 假告状」分类）

### 2.1 ★ 诊断会「早上判对、晚上静默失效」（真 bug）

`read_client_auth_flags` 只读日志**头部 512 KB**、拒绝行只在**尾部 256 KB** 找；
而授权串实测偏移 **1 573 933 B**、拒绝行在 1.81 MB / 15.54 MB —— 两个窗口全落空，
结果是 `found=false`、`reason=""`：**不报错也不判错，只是不判**。

改为 `_scan_marker_lines` 全文件按块扫描（1 MiB/块 · 上限 64 MiB · 跨块残行拼接 ·
utf-8↔gb18030 容错）+ 记**绝对偏移**再按窗口读原文（不假定授权串永远单行），
授权取**最后一次**下发。取证耗时 0.09 s / 0.23 s。

### 2.2 ★ 诊断「假告状」：把「服务未授权启动」误报成 PID 白名单

`"not allowed" in ln` 会命中 `The XtQuantServer is not allowed to start.`，
于是让用户去做「加 PID 白名单」这种**完全无关**的操作。
现按 `_PID_DENY_RE`（必须含 `pid`）分流为四档
（`xtquant_server_blocked` / `pid_not_allowed` / `strict_check` / `xtquant_module_unauthorized`），
各带**不同的处置首句**（前两档明确告诉用户「别往哪查」）。

### 2.3 孤儿逻辑清零

| 类别 | 处置 |
|---|---|
| 生产代码孤儿函数 5 个 | `_stock_name_map` / `starts_with_initials` 删除；`get_request_id`、`instrument_type_label` 改为**被复用的单一路径**；`reset_name_cache` 由测试真实调用 |
| 孤儿配置 `qmt_agent_bundle_timeout` | **只声明不读取**，而拉取处硬编码 `timeout=30.0` ⇒ 改了环境变量毫无效果，且注释声称的默认 10 s 与真实行为矛盾。已接线（默认值对齐真实行为 30 s），并锁「0 / 负数必须回退」 |
| 载荷断链 `trade_surface` | agent 已算出的「下单接口面」此前只落在 `probe_result.json` 被脚本消费，**界面拿不到** ⇒ 用户只读到「下单能力：不可用」却不知缺哪个入口。已贯通：后端随诊断下发 + 前端新增「下单接口面」一行 + 2 条护栏 |
| 模块 / 路由断链 | 41 个 router 全部注册（0 断链）；256 个模块零孤儿 |

### 2.4 循环面：22 个 `while True` 逐个定性

全部为「可取消的常驻协程 / 有界的翻页循环 / daemon 线程」，**无真死循环**。
并按本仓已知坑复核停止路径：引擎 `start()` 先 `await stop()` 保证幂等、
资金流采集 `cancel → await → 仅当仍是自己才置 None`、reaper 有停机路径且有守卫用例。

### 2.5 文档断链（新增 CI 门禁）

`docs/BROKER_ONBOARDING.md` 长期写着「`POST /api/v1/brokers/profiles/hotplug`」——
**该端点从未存在**（热插拔实际是 `POST /api/v1/brokers` 的内部自动行为），
读者按文档调用只会 404。新增 **`scripts/check_doc_endpoint_links.py`** 并接进 CI：
文档里声明的每个 REST 端点都必须能在契约里查到（已做可证伪自检：临时插入 2 条假端点被抓出，
`...` 与 `{check|pull}` 这类省略写法被正确跳过）。

### 2.6 无效历史文档删除

`docs/G4_统一数据面使用指南.md` —— 它描述的前端 topic 总线（`lib/dataHub.js` 的
`subscribe/peek/invalidate`）在前端重写为 `frontend-next` 后**已不存在**，
且策略表数值也已与后端 `_TOPIC_POLICIES` 漂移。删除并摘掉 2 处链接、登记删除理由；
同时修正 `backend/app/routes/datahub.py` 的模块 docstring（它仍在宣称策略表是
「前端数据总线的单一真源」，属**代码注释侧的同一处断链**）。

其余文档漂移一并修正：G6 补**资源组互斥**（此前只写 kind 配额）、G8 的前端文件名
（`Screen.jsx` → `ScreenPanels.tsx`）、`项目规划.md` 里不存在的门禁脚本名、
大小 QMT 说明 §7.1 重写（两种 `rc=-1` 日志特征对照）+ 新增 §7.10。

### 2.7 其它
