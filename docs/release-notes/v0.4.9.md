# v0.4.9（R26）大小 QMT 贯通审计 + 涨跌额符号口径统一

> 发布日期：2026-10-05 ｜ 上一版本：v0.4.8
> 主题：**回答「大小 QMT 核心功能是否真的打通」**。
> 本轮逐条走读大 QMT（XtItClient + agent 文件桥）与小 QMT（极简 MiniQMT +
> `userdata_mini`）两条链路的「识别 → 判活 → 取数 → 下单 → 重连 → 停机」，
> 再做全仓前后端贯通对账（路由 / 载荷 / 事件 / 声明）。共修掉 **8 处**问题，
> 其中 **1 处是有真实业务后果的真缺陷**（策略取 K 线走错连接）。

---

## 一、先回答「能否达到工业级」

| 维度 | 结论 | 证据（本轮实测） |
|---|---|---|
| **大 QMT 判活诚实性** | ✅ 达到 | `BigQmtBridge.is_connected()` = 「本轮有过真实往返」且未连续无应答；文件桥不拿「连接」概念说谎；`pump_running()` 判的是任务本身而非连接状态 |
| **小 QMT 交易目录分流** | ✅ 达到 | `_effective_trade_dir()` 按 `mini`/`full`/`both` 与目录存在性解析，`both` 优先 `userdata`（否则「行情正常、交易取不到数据」） |
| **重连有界性** | ✅ 达到 | 退避 `min(2^n, 60s)`，判定 `needs_action` 后降频到 300s；循环出口由 `_stopped` / `cfg.active` 双条件保证；静态门禁 `check_unbounded_waits` 违规 0 |
| **失败语义（零 mock）** | ✅ 达到 | 全仓 AST 扫描「`except` 内返回 `ok=True`/`code=0`/`accepted=True`」**命中 0 处**；桥侧拿不到的能力（财务 / L2）**抛错**而非返回空 dict |
| **取数用对连接** | ⚠️ 本轮修复 | 策略侧 `_fetch_kline` 漏传 `broker_id` ⇒ 取 K 线走**活跃**连接而非 run 绑定的连接（见 §2.1） |
| **能力矩阵诚实性** | ⚠️ 本轮修复 | `_infer_capabilities` 的 `client_type` 是哑形参，docstring 却称它参与推导（见 §2.2） |
| **前后端贯通** | ✅ 达到 | 运行时 OpenAPI 唯一路径 **214 == 契约 214**（双向差集 0）；前端 api 层 126 个路径模板**全部**命中契约；WS 事件 34/34 有消费 |

> 一句话：**主干是工业级的**——判活不撒谎、失败不粉饰、重连有上界。
> 本轮抓到的问题集中在「**参数传了但没用**」这一族，它不会让程序崩，
> 但会让「我以为配的是 A、实际走的是 B」，属最阴的一类。

## 二、本轮修掉的 8 处问题

| # | 类别 | 位置 | 问题 | 修法 |
|---|---|---|---|---|
| 1 | **真缺陷 P1** | `engines/strategy_runtime.py::_fetch_kline` | 收了 run 绑定的 `bridge`，**从不使用**；内部无条件 `fetch_kline_cached(code, period, count)` ⇒ 其内部 `get_bridge(None)` 恒取**活跃**连接。多连接下「信号用 A 券商的 K 线算、订单下到 B 券商」 | 把 `run["conn_id"]` 透传为 `broker_id`；`conn_id` 为空时行为与修正前**完全一致**。同目录 `engines/algo.py` 一直传 `job["conn_id"]`，可见此处是漏接 |
| 2 | 孤儿形参 P2 | `xtquant_client/xtp/env.py::_infer_capabilities` | `client_type` 形参**从未被使用**，而 docstring 首行写「由客户端类型 / 账户类型推导能力矩阵」——读者会以为极速版/完整版影响这份矩阵 | 删除该形参并重写 docstring，说明**为什么不按 client_type 裁能力**（瞬态下会把「暂时没有」写成「没有」，正是「假绿灯」的反向形态） |
| 3 | 孤儿形参 P2 | `gateway/kline_cache.py::_where` | `code`/`period`/`adjust` 三个形参**从未被使用**（SQL 用 `?` 绑定，值由调用方 tuple 给）⇒ M6 不变量「读路径必须按 adjust 过滤」只靠**调用方参数顺序**保证，形参却像已经过滤过 | 改为 `_read_sql(...)` **同源构造 `(sql, params)`**，4 处调用点一并改；M6 由该函数唯一保证，调用方不可能再写错顺序 |
| 4 | 孤儿属性 P2 | `xtquant_client/xtp/adapter.py` | `_order_status_cache` 仅在 `__init__` 声明，**全仓零读写**（状态归一已改成无状态纯函数） | 删除（`_name_cache` 真被 `instrument.py` 使用，保留） |
| 5 | 孤儿形参 P3 | `xtquant_client/xtp/trading.py::_order_status` | `oid` 形参未使用（状态词表只由状态码裁决） | 删除形参；带着订单号会让人误以为「不同订单有不同归一结果」 |
| 6 | 孤儿形参 P3 | `engines/strategy_runtime.py::_normalize_params` | `codes` 形参未使用（参数规范化只按策略类型裁剪） | 删除形参 |

| 8 | 孤儿 + 重复真源 | `frontend-next/src/app/routes.tsx::DEFAULT_PAGE`、`stores/workspace.ts` | `DEFAULT_PAGE` 声明后**无人引用**，而字面量 `"dashboard"` 在 `workspace.ts` 里**又硬写了两次** ⇒ 改默认页要动三处，漏一处就「初始页是 A、分屏兜底是 B」 | `DEFAULT_PAGE` 成为唯一真源；顺带删掉 `Dashboard.tsx::__dashPrice`（注释写「供测试断言使用」，实测 src/tests **零引用**——docstring 在说谎）与 `format.ts::fmtTime`（src 0 / tests 0） |

## 四、沉淀

1. **「参数传了但没用」是本仓的高频缺陷族**，且比崩溃更难发现：本轮 5 处
   （#1/#2/#3/#5/#6）全是同一个形态——形参存在、调用方也传了、函数体不看它。
   建议后续新增/重构函数时，用 AST 扫一遍「形参零使用」再提交。
2. **零消费 ≠ 死代码**。#7 的 `fmtSigned` 一度被当死代码删除，实际是**漏接**：
   函数写好了、没接到展示位。删之前先问一句「这功能本该出现在哪」。
3. **docstring 会撒谎**：`__dashPrice` 写「供测试断言使用」、`_infer_capabilities`
   写「由客户端类型推导」、`kline_cache._where` 的形参看着像已过滤 —— 三处都是
   注释/签名与实现脱节。**签名与注释也是判据**，审计要一并核。
4. **「只被自己的测试引用」要警惕**：测试给不存在的消费者背书，会让套件变绿而
   守卫为零。判断一个导出该不该留，看的是**生产代码**有没有消费者。
5. **新增门禁 `scripts/check_frontend_orphans.py`**（11 → 12 条，已接 CI）：
   后端早有 `audit_orphan_modules`（零引用模块），前端一直缺对应物 —— 于是
   「导出了没人用」只能靠人肉审计（本轮一次就扫出 9 个）。这条门禁的判据刻意
   保守：**消费者含 `tests/`**（不认测试会制造假告警），且裁定表**反腐烂**
   （条目对应的符号消失、或有了真实消费者，一律报红，逼人删条目）。配 10 条
   回归用例，每个「必须报红」的分支都有证伪用例。
