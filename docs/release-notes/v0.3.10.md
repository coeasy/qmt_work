# v0.3.10 · R39 发布阻断缺陷：安装包内嵌构建者密钥

> 发布日期：2026-09-30 · 上一版本 v0.3.9（发布说明见 [`v0.3.9.md`](v0.3.9.md)）
>
> 本轮由**重建 v0.3.9 安装包的收尾核对**触发：产物目录里发现 `data/master.key`，
> 追查后确认它是**发布阻断级**缺陷 —— 已构建的 0.3.9 安装包内含一把固定的主密钥。

## 一、缺陷（两个 bug 互相掩盖）

### Bug A：安装包里带着构建者的密钥

| 项 | 内容 |
|----|------|
| 现象 | `backend/dist/qmt_work/data/master.key`（以及 `app.db` / `logs/` / `qmt_work_config.json`）在打包前就存在，被 electron-builder 一并封进 `qmt_work-Setup-0.3.9.exe` |
| 来源 | **不是构建本身，而是「构建后自检」**（Step 4）——它在 `backend/dist/qmt_work/` 里**原地跑了一次后端**，后端于是在 exe 同目录写出运行期状态 |
| 触发链 | 首次全量构建（09:18 自检写入）→ 因 `latest.yml` 版本闸门未过**只重跑了 Step 3 打包**（09:28）→ 上一轮自检的密钥被第二次打包收进安装包 |
| 后果 | ① 所有安装共享同一把主密钥（且正是构建者本机加密数据所用的密钥）；② 密钥是数据库敏感字段（LLM API Key 等）加密的唯一凭据 |

### Bug B：干净的只读安装**首次启动会崩**（被 Bug A 掩盖）

`core/crypto.py` 把主密钥固定放在 `exe_dir()/data/master.key`。打包态 `exe_dir()` 指向
`resources/backend/qmt_work/`，而桌面壳明确按「资源目录只读」设计（见 `electron/main.cjs`
把 `QMT_DB_PATH` / `QMT_LOG_DIR` / `QMT_PORT_FILE` 全部重定向到 `userData`）。

| 项 | 内容 |
|----|------|
| 后果 | 装到 `Program Files` 时该目录不可写 ⇒ `_load_master_key()` 写文件抛 `OSError` ⇒ **后端崩在 `core.crypto` 导入期** |
| 为何一直没暴露 | 因为 Bug A 顺手把密钥「带」进了包 —— 文件已存在、读得到，就走了「读回」分支，**写失败路径从未被执行** |
| 判据 | 「绿灯是另一个 bug 遮出来的」：`crypto.py` 的口径与 `run.py` 的单实例锁、`.qmt_work.port`、`wal.jsonl`、`bars_cold.db`（**全部跟随 `settings.db_path.parent`**）不一致，密钥是唯一的例外 |

> 该缺陷 2026-08-14 曾手工清理过一次（当年把密钥从 `_internal/data` 挪到 `exe_dir()/data`，
> 以为「与 app.db 同目录」），但**从未在流水线里设防** ⇒ 2026-09-30 复发。

## 二、修复

| 层 | 修改 |
|----|------|
| 代码（根治） | `core/crypto.py`：主密钥改为 `<settings.db_path 的父目录>/master.key`，与 `.qmt_work.lock` / `.qmt_work.port` / `wal.jsonl` / `bars_cold.db` **口径统一**；`QMT_DB_PATH=:memory:` 或相对路径退回旧位置 |
| 兼容（升级不丢数据） | 新位置不存在但旧位置（`exe 同目录/data/master.key`）存在时，**复制**旧密钥到新位置再使用 —— 老库里已加密的密文仍可解密；旧文件保留，降级回 0.3.9 也能开 |
| 健壮性 | 密钥文件过短（写入中断）不再采信，重新生成；迁移写失败时降级为「继续用旧文件」而不是让整个后端起不来；用 `QMT_MASTER_KEY` 注入密钥时不再空跑一次权限加固 |
| 构建（防复发） | `build_all.sh` / `build_all.bat` 新增 **`purge_dist_runtime_state`**：打包前清掉 `backend/dist/qmt_work` 与上一轮 `win-unpacked` 里的 `data/ logs/ export/ kline_data/ qmt_work_config.json` |
| 构建（硬门禁） | 新增 **`verify_no_runtime_state_in_package`**：打包后断言包内**没有**上述任一运行期状态，命中即 `fail`（不再产出带运行期状态的安装包） |
| 测试护栏 | `tests/test_crypto.py` 新增 4 例：密钥路径跟随主库目录 / `:memory:` 回退 / 旧位置升级迁移 / 短文件重生成 |

## 三、验证

- `tests/test_crypto.py` **14 passed**；`test_config_paths` 11、`test_paths_guard` 16、
  `test_db_backup_policy` 46（路径与备份策略相关面）全部 passed
- 构建门禁**双分支实测**（`.sh` 与 `.bat` 各自独立跑）：
  - 产物被污染 → 清理两棵树（`backend/dist` + `win-unpacked`）后门禁通过；
  - 跳过清理（模拟清理失败/被占用）→ **硬门禁 `exit 1`** 并给出可操作修法；
  - 干净产物 → 通过。
- 产物核对：`backend/dist/qmt_work/` 只剩 `_internal/` 与 `qmt_work.exe`；
  `frontend-next/dist-electron/win-unpacked/` 下**无 `master.key` / `app.db` / 配置 / 日志**

## 四、升级说明

- **从 0.3.5～0.3.9 升级**：首次启动会把旧位置的 `master.key` 自动复制到新位置
  （`%APPDATA%\qmt_work\master.key`，与 `app.db` 同目录），**已保存的加密配置无需重新填写**。
- **全新安装**：不再随包分发密钥，首次启动在用户目录随机生成一把，**每台机器各不相同**。
- 老安装包内嵌的那把密钥仅在本机开发环境使用过；如曾把 0.3.9 安装包分发给他人，
  建议其重新安装 0.3.10（旧包内密钥对所有装过 0.3.9 的机器是同一把）。
- 可用 `QMT_MASTER_KEY`（base64 或 ≥32 字符明文）显式指定密钥，优先级最高。
