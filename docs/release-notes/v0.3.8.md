# v0.3.8 发布说明

> 发布日期：2026-09-29
> 版本真源：仓库根 `VERSION`（0.3.8）· `frontend-next/package.json`
> 上一版：v0.3.7
> 主题：**GitHub 发布后自动构建安装包**（断链闭环）＋ **三遍深度审计 30 处修复** ＋ 文档全面回归真实

---

## 1. 一句话

修好了「GitHub 发布 → 自动构建安装包」这条链路上**三处静默断链**（CI 里没有嵌入式
Python 运行时、产物上传路径指向空目录、构建脚本在缺运行时的情况下**假装成功**），
并完成三遍独立审计：修复 **30 处**真实缺陷（4 个 Critical / 9 个 High / 其余 Medium·Low），
其中 **10 类 WS 事件长期推不到前端**（三个引擎同步调用 async 回调）与
**停机漏停两个会真实下单的引擎**为最严重两项。文档按真实功能全面校准。

## 2. GitHub 发布后自动构建（断链闭环）

| # | 问题 | 影响 | 修复 |
|---|---|---|---|
| C1 | `backend/runtimes/`（嵌入 Python，**336 MB**）被 `.gitignore` 排除 | 本地构建会打进包；**CI 里根本不存在** ⇒ 桥接运行时缺失 | `backend/tools/fetch_runtimes.py` 新增 `--with-deps`（装 `cryptography / pydantic / pydantic-settings / psutil` 等桥接闭包依赖）与 `--strict`（缺一即非 0 退出）；`release.yml` 构建前先备运行时 |
| C2 | `build_exe.py` 缺 `runtimes/` 时**只打印一行「跳过」继续构建** | 产出一个**装完也连不上券商**的安装包，CI 全绿 | 新增硬闸门：`QMT_BUILD_REQUIRE_RUNTIMES=1`（CI 恒开）时运行时缺失 → **非 0 退出并阻断发布**；`_verify_bridge_imports` 由「跳过」改为「失败」 |
| C3 | `build-client.yml` 上传 `frontend-next/release/*` | electron-builder 产物实际在 `frontend-next/dist-electron/` ⇒ **上传的资产一直是空的** | 修正上传路径，并补齐 `*.zip` / `*.exe` / `latest*.yml` 匹配 |

> 判据：本地以 `QMT_BUILD_REQUIRE_RUNTIMES=1` 模拟「无 runtimes」的 CI 环境，
> 构建**必须**以非 0 退出（已实测拦下）。

现在 `release.yml` 的链路是：**备运行时 → 前端 build → 后端 EXE（带硬闸门）→
打包（zip + NSIS）→ 产物结构核验 → 上传 Release 资产**。

## 3. 三遍审计修复清单

### 3.1 Critical（4）

| # | 文件 | 问题 | 修复 |
|---|---|---|---|
| A | `app/routes/trade.py` + `tools/position.py` | `POST /trade/target` 导入 `tools.position.order_target_position`，而该符号**只是嵌套闭包**（模块级不存在）⇒ 路由一调用就 `ImportError` | 抽出模块级 `order_target_position_impl`，路由与 MCP 工具共用 |
| B | `engines/{algo,limitup,condition_order}.py` | 三引擎的 `_emit` **同步**调用 `self._on_event(event)`，而接线传进来的是 `ws_manager.broadcast`（`async`）⇒ 只创建协程、**永不 await** ⇒ **10 类事件永远推不到前端**（下单/拆单/条件单/涨停/打板…），且每次 GC 冒一条 never-awaited 警告。**静态护栏只扫 `gateway/`，所以长期没拦住** | 全部改走唯一出口 `core.emit.emit_event`；护栏 `tests/test_emit_event.py` 由「只扫 gateway、正则匹配行」升级为 **AST 全量扫描 + 扩到 `engines/`**，并用注入探针验证护栏真能拦下违规 |
| C | `app/bootstrap/shutdown.py` | 停机**漏停** `algo_engine` 与 `strategy_runtime` —— 两者都能**真实下单**；停机后仍在运行的拆单/策略任务会继续发单到券商 | 停机序列中于 `db.close()` **之前**显式 `stop()`；`strategy_runtime` 补 `stop_all()` |
| D | `datasource/cold_store.py` + `app/bootstrap/phase_db.py` | 冷仓搬移 `while True` **无上限**（每批搬完不判总量），且跑在启动期线程里 ⇒ 一旦某批反复满足条件就**起不来也退不出**（TD-25 同族） | 加上限（`max_batches`）与无进展退出；调用点改 **daemon 线程 + 有界等待**（超时即放弃本次搬移，冷仓回退主库表） |

### 3.2 High（9）

| # | 文件 | 问题 | 修复 |
|---|---|---|---|
| E | `sync/__init__.py` | 账户快照循环的**间隔计算与 `sleep` 在 `try` 之外**：`runtime_config.snapshot_interval` 取到非法值（None/负/字符串）时 `sleep` 抛错 → **打死整个快照循环**，账户/持仓/成交静默停更 | 间隔与 sleep 移入 `try`，非有限值回退默认；异常路径留痕 |
| F | `sync/__init__.py` | `_batch_buf` / `_batch_rows` **无上限**；且 `_batch_loop` 单窗口异常**直接打死循环** ⇒ 消费端一死，生产端无界堆积到 OOM | 两缓冲改 `deque(maxlen=20000)`；循环体整体 `try/except` + 退避，`CancelledError` 正确上抛 |
| G | `xtquant_client/gateway.py` | `bridge.call` **无超时**，`run_in_executor(max_workers=4)` 被挂死的券商调用占满后，**所有后续券商调用级联冻结** | `call` / `call_locked` 加 30s 硬超时（`QMT_BRIDGE_CALL_TIMEOUT` 可调） |
| H | `engines/algo.py` | POV 算法单**无 `max_idx`**（Iceberg 有，POV 漏了）⇒ 无成交量回报时可**无限重复下单** | 补同源有界退出（`max(slices*5, 20)`） |
| I | `app/routes/config.py` | 手动备份 `asyncio.to_thread` **非 daemon 且无超时**（TD-25 同族）⇒ 理论上一旦备份阻塞，进程退不出去 | daemon 线程 + 有界等待（`QMT_MANUAL_BACKUP_TIMEOUT`） |
| J | `app/bootstrap/phase_engines.py` | `AlertEngine` 在 `phase_db` 创建时 `ws_manager` **尚未初始化** ⇒ `_on_event` 为 None ⇒ **`alert` 事件是死路径** | `ws_manager` 就绪后补接 `alert_engine._on_event` |
| K | `gateway/wal.py` | `_maybe_checkpoint` / `_apply` **静默吞** `except Exception: pass` ⇒ 崩溃恢复失败却报成功；损坏行无计数 | 补计数与告警日志；WAL 损坏行写入 `_corrupt_lines` 供读路径告警 |
| L | `app/runtime/jobs.py` | 派发循环 `_dispatch_loop` **无异常保护**；队列里悬垂的 job id 会 `KeyError` ⇒ 派发器一死，**所有定时任务永久停在 queued** | 派发体加 `try/except` + 退避；取 ready 时剔除悬垂 id |
| M | `sync/__init__.py`（`_batch_loop`） | 保留策略写在 `if not items: continue` **之后** ⇒ 空闲窗口（盘后/周末）永不清理 | 清理块移出该判断，`prune_tick` 始终递增 |

## 6. 升级注意

- **无破坏性变更**。REST / MCP 签名未变；WS 仅**新增** `alert` 通道（原为死路径）。
- 新增可选环境变量（均有默认值，可不设）：
  `QMT_BRIDGE_CALL_TIMEOUT`(30) · `QMT_MANUAL_BACKUP_TIMEOUT`(120) ·
  `QMT_DB_CLOSE_TIMEOUT`(5) · `QMT_COLD_MIGRATE_TIMEOUT`(60) · `QMT_BUILD_REQUIRE_RUNTIMES`(CI 置 1)。
- 数据库迁移 **28**（新增 `moneyflow_cache(ts)` 索引）自动执行，幂等。
- 新增的保留策略会在运行约 6 分钟后首次触发，日志形如
  `account_snapshot retention: 清理 N 行（保留 90 天）`。若需更长历史，请调大 `keep_days`。
