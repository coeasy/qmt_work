## 二、大 QMT 全量接入（新增能力）

**背景**：完整版大 QMT 不允许外部进程直连 xtquant（授权串 `mdl_auth_xtquant=0`，
端口不监听），只能用 QMT **内置 Python 3.6** 跑一个策略脚本，经目录（file）/redis/zmq
与平台通信。此前平台只支持 miniQMT，大 QMT 属于「装得上、连不上」。

**实现**

| 层 | 落点 | 说明 |
|---|---|---|
| 协议/方言 | `connectors/dialects/{base,bigqmt_v1,xtquant_v1,ptrade_v1}.py` | canonical `Ops`（17 个）↔ 各方言 wire action；`is_write_op()` 唯一判定写操作 |
| 传输 | `connectors/transports/{base,file_signal,http_gateway,lowlatency,inprocess,semantics}.py` | `_TRANSPORTS` 为唯一注册表；文件桥语义（轮询 → 事件，realtime=DEGRADED） |
| 连接器 | `connectors/generic.py`、`connectors/registry.py` | 请求-响应 / 超时 / 重试 / probe；`connector_key`（如 `qmt.big.bridge.file`）解析 |
| 桥 | `connectors/bigqmt_bridge.py` | **双槽位本体**：`Connection.bridge` 与 `Connection.adapter` 是**同一对象**；事件泵、行情订阅对账、`is_connected()` 存活判据 |
| 网关面 | `connectors/bigqmt_gateway.py` | canonical op → 旧 `XTQuantGateway` shape 的适配（`_BigQmtGateway`） |
| 策略端 | `agent_bigqmt/{BIGQMT_AGENT,qmt_api}.py` + `scripts/gen_qmt_agent_bundle.py` | py3.6 标准库 only；单文件 bundle 一键部署；启动即写自检 + 心跳 |
| 前端 | `src/domains/system/Brokers.tsx`、`src/domains/system/bigqmtProbe.ts` | 连接表单（模式选择 / 桥目录 / token）+ 大 QMT 诊断面板（注入函数捕获、ContextInfo 方法面、桥目录一致性、四类根因） |

**关键设计取舍（都有事故来源，详见 [`BIG_QMT_COMPAT_PLAN.md`](../BIG_QMT_COMPAT_PLAN.md) §9.6）**

- **`is_connected()` 必须是「现在可用」，不是「曾经连上」**：文件桥没有连接概念，
  唯一诚实证据是**一次真实请求/响应往返**。刻意**不**用 `agent_status.json` 心跳新鲜度
  —— `handlebar` 只在行情推进时被调用，收盘后心跳自然过期，拿它当判据会在非交易时段
  把健康连接误报成掉线并触发重连风暴。
- **`SUB_QUOTE` 必须真的下发**：曾只写了一句 `log.debug` 就当订阅成功，界面价格永远
  停在种子值而所有指标全绿（教科书式「绿灯是另一个 bug 遮出来的」）。
- **诚实报错，不装作支持**：桥上没有的接口（财务 / L2 逐笔）抛 `BrokerError` 并给出
  替代路径，绝不返回 `{}` 冒充「这家公司没有数据」。

## 三、三轮审计修复

### 第 1 轮（14 项）

`PositionSnapshot.raw` 丢失致持仓静默变 `[{}]`；`ConnectorError/TransportError/UnsupportedOp`
游离于 `BrokerError` 之外致桥故障全变 500；`_rebuild` 缺 `Rejected/Expired/Timeout/Unsupported`；
`_FUNC_TO_CAPS` 写了单数 `position`；`QmtConnector` 把「未连接」压成 400（应 503）；
`get_kline` 位置传参跨重排签名；`XTQuantGateway.place_order` ABC 比实现窄；两处
`except RuntimeError` 收不住；**`SUB_QUOTE` 从未下发**；替身 `meta()` 在 dispatch 前计算；
DB 备份 WAL 指纹两种口径不可比；**agent `seq` 回卷静默吞事件**（file 桥 + redis 孪生）；
**`check_execution_architecture` Gate 1 常驻红**（CI 里没人读的门禁）；
`_live_db_backup` fixture 每轮白写约 5.6 GB（磁盘满的真凶）。

### 第 2 轮（6 项）

- **wire action 五方对账门禁**：`_OP_TO_ACTION` / `Ops` / agent `_ACTIONS` /
  agent `execute()` 派发链 / 契约替身，五处注释都写「必须同步」却**没有任何东西在核**。
  新增 AST 对账（5 例）：自述↔路由、方言↔agent、替身↔真身、扫描器自证、方言覆盖率 + 模板缺口登记。
- **`is_connected()` 存活判据**：90 s 空闲才探活 / 5 s 短超时 / 30 s 退避 / 连续 2 次无应答才判死；
  诊断面上浮 `agent_unresponsive` / `liveness_failures` / `last_agent_ok_age_s` / `available`（7 例，含**泵真的在调探活**的接线断言）。
- **指标「生产者缺失」（TD-27）**：6 个 `record_*` 全仓零调用而 `/metrics` 照样输出 0；
  trace 环形缓冲生产者与消费者**都**缺席。接线 5 处（`runtime_mode` 走注入回调以守住分层）
  + 删除半落地功能 + 新增 `tests/test_metrics_wiring.py` 8 例（**扫描时排除 `tests/`**）。
- 文档与代码不符 3 处；两处死定义（`register_transport` / `_size_str`）删除。

### 第 3 轮（3 项 + 文档订正）

- **TD-28 新功能顶穿文件体积上限**：存活判据把 `connectors/bigqmt_bridge.py` 顶到 51.8 KB
  （CI Gate 4 上限 50 KB）⇒ 按**依赖方向**拆出 `connectors/bigqmt_gateway.py`，**51.8 KB → 40.6 KB**，
  零行为变化。刻意**不**用「删注释绕过上限」。
- **TD-29 冻结基线门禁匹配过宽 + 基线腐烂**：`check_appcontext.py` 用正则
  `from core\.state import .*`，把「取常量 `MSG_NO_BROKER`」也算成单例引用 ⇒ 改 **AST 判定**；
  顺带暴露 1 条产线代码直取 `core.state.state`（`gateway/easytrader_facade.py`），
  已改走 `core.context.active_context_or_none()`（与路由 `Depends(get_ctx)` 同源）。
- **TD-31 后端上浮的诊断字段前端一个都没消费**：第 2 轮为修假绿灯专门上浮的
  `available` / `agent_unresponsive` / `liveness_failures` / `last_agent_ok_age_s`
  在 `frontend-next/` 里 **grep 命中为 0**（连类型都没声明）—— 用户在诊断面板上
  仍问不出「**现在**还可用吗」。与 TD-27 同族（生产者/消费者不配对），成因是
  **响应载荷字段不在任何门禁视野里**（契约漂移门禁只核路径 + 查询参数）。
  已补齐：类型声明 → 探针纯函数三态判定（`warn`/`ok`/`unknown`，**agent 从未应答不报红**）
  → 面板新增「可用性」行 → 提示行兜底 → **8 条用例**（含「元数据全正常但不可用必须判 warn」那一格）。
- **文档订正**：4 处写 `ci_reconcile.py --fix`（脚本只认 `--update`）；
  `BIG_QMT_COMPAT_PLAN.md` §4.2 是规划稿、与实机落地差得远 ⇒ 新增 **as-built 对照表**。
