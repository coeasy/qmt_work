R31：QMT 客户端升级后交易连不上 —— 「严格连接校验」根因闭环 + 前后端贯通

**背景**

用户反馈：**QMT 客户端升级一个小版本后，平台再也连不上正在使用的客户端。**

按要求做**三遍独立审计**（① 报障根因定位 ② 全链路断链 / 孤儿逻辑 / 死循环复核
③ 全量回归与发布验证），每遍确认的问题必须**全部修完**才进下一遍。
完整报告见 `docs/2026-09-28_第31轮_客户端升级连不上根因与前后端贯通.md`。

本轮最值得记录的一点：**根因不在平台侧，但平台连「把根因送到用户眼前」都没做到。**
后端其实已经把完整诊断（客户端日志证据 + 官方四步排查）构造出来了，
却在前端默认 15s 超时处被 abort —— 用户只看到「请求超时」。
所以本轮近一半工作量花在**让真话能到达屏幕**。

---

**① 真实根因：客户端启用了「量化连接严格校验」（券商侧授权，平台无法改写）**

铁证（客户端日志 `XtMiniQmt_20260928.log`）：

```
quant session 5, pid 5580 not allowed, return
[quant]XtQuantServer:: connect ret error-1
```

授权串在 09-23 → 09-28 之间发生变化：

| 授权项 | 09-23 | 09-28 |
|---|---|---|
| `mdl_auth_xttrader_strict_connection_check` | 0 | **1** |
| `mdl_auth_xtdata_strict_connection_check` | 0 | **1** |
| `mdl_auth_xtquant_no_pid_check` | 0 | 0 |

即：客户端开始对调用进程做 **PID 白名单校验**，拒绝外部进程的 xtquant 交易连接。

**影响面是隔离的**：行情（xtdata）完全正常，只有交易 `connect()` 返 `rc=-1`
（mini / full / auto 三种模式均如此）。该开关由**券商服务端下发的模块授权**控制，
**平台侧无法自行改写** —— 只能精确识别并引导用户处理。故本轮把
「自动读授权串 + 定位客户端日志 + 把证据与处置步骤写进错误文案」做到位。

> 附带修掉的定位缺陷：极速版客户端日志前缀是 `XtMiniQmt_*`（原只认 `XtClient_*`，
> 属孤儿逻辑 ⇒ 证据恒丢失）；授权串只写在日志**头部**（原只读尾部 ⇒ 解析恒为空）；
> 日志选择原按 mtime（`XtMiniQuote_*` 行情线程高频写 ⇒ 恒最新 ⇒ 恒选错），
> 改为按 `_log_rank`（交易主 2 > 辅助 1 > 行情 0）排序。

**② 前后端断链：精心构造的根因永远到不了界面（本轮最高价值）**

`http.ts` 的 `DEFAULT_TIMEOUT = 15_000`，而 `brokerApi.connect` **没有覆盖它**。
后端一次 connect 最坏要跑「桥接子进程冷启动 + 候选数据目录(≤2) × session(6)
逐个 `XtQuantTrader.connect()`」≈ **45s**（`_CONNECT_RETRY_BUDGET`），
加子进程启动余量接近 60s。于是 15s 就被 abort，后端那份带着客户端日志证据、
官方四步排查的诊断**永远到不了界面**，用户只看到「请求超时（15s）」。

修法：

- `connect` / `test` 显式 `timeout: 120_000`；
- `auto-detect` `60_000` + `retry: 0`（实测全盘扫描 + 逐个探 xtquant 可导入性 ≈ 25s，
  默认 15s 会把「正在发现」误报成「发现失败」，`retry` 还会把 25s 级扫描白跑两遍）；
- `version-info` `60_000`；
- 新增回归测试 `frontend-next/tests/brokerConnectBudget.test.ts`（假时钟 + 永不 resolve
  的 fetch，断言 16s / 60s 处**不得** abort、120s 处超时才触发，且 fetch 只被调用 1 次）。

**③ 桥接启动同步阻塞 ⇒ 真实错误被「握手超时」掩盖**

旧实现 `adapter.start()` 同步跑完才进读循环。交易路径要串行尝试「候选目录 × session」
最多 12 次 `connect()`（实测约 38s），期间读循环根本没起来，父端 30s 握手窗口内收不到
`_ping` 响应 → 判「桥接子进程握手失败：`_ping` 调用超时」并 kill 子进程 →
**真实根因在产出前就被丢弃**。

修法：`adapter.start()` 移入后台线程，读循环立刻就绪；`_ping` 语义收窄为
「IPC 就绪」（回 `{alive, connected:false, starting:true}`）；新增 `_wait_ready`
承载启动结果；父端 `_READY_TIMEOUT = 100s`（**必须大于** 45s 重试预算，否则
「重试还没跑完，父端就判就绪超时」，同一种掩盖会换个地方重现）。

**④ 失败路径「先写 IO 再发布状态」⇒ 启动态永不释放（300s → 41.87s）**

`except` 分支里同步写 stderr（错误摘要 + 完整 traceback，可达数 KB），而它写在
`state["starting"] = False` **之前**。父端若不持续排空 stderr，管道缓冲写满即阻塞在
`stderr.write`，启动态永不释放 → 一个**已经完成**的启动失败被报成「就绪等待超时」。

修法：**先发布结果，再做任何 IO**；stderr 改写走 daemon 线程（`_stderr_async`）。
实测（不排空 stderr 条件下）：`_wait_ready` 返回耗时 **300.30s → 41.87s**。

**⑤ 错误语义纠偏：内部 bug 不再伪装成「券商不可用」**

`app/routes/broker.py` 原把**一切**异常映射成 `503 券商不可用`。于是「平台自己的
代码缺陷」被如实报成「券商连不上」，用户被引导去重装客户端 / 联系券商 ——
排查方向彻底带偏。真实案例：`datasource` 层 `except BrokerError` **未导入
`BrokerError`**，真出错时抛 `NameError`，在旧口径下会显示成「券商不可用」。

修法：非 `BrokerError` ⇒ **500** + 显式带出异常类型 + `log.exception` 留完整栈；
同时**补上缺失的导入**（这是真实 bug，不是门禁噪声）。

**⑦ 健康监控：退避按失败性质分档**

对「严格连接校验 / 未开通程序化交易」这类**非自愈**根因，旧实现仍按 `min(2^n, 60)`
每 60s 无意义地重拉桥接子进程（每次 spawn + 45s 预算 + 客户端日志持续刷 `not allowed`）。

修法：`BrokerError.needs_action`（**基于文案**判定 —— 异常对象过不了进程边界，
只能靠 `error` 文本 + `error_type`）命中后，退避上限提到 **300s**，
`health_status` 标成 `needs_action`，前端提示「需人工处理」而不是笼统的「错误」；
且**不**把该状态降级成 `disconnected`（否则抹掉「必须人工处理」这一关键信息）。
`last_error` 统一走 `brief_error()` 取**单行结论句**（不再把 2KB 多行诊断塞进列表、
并在句中截断成无意义碎片）。

**用户需要做什么（客户端升级后连不上）**

1. 在客户端日志里搜 `not allowed` —— 命中即确认是「严格连接校验」；
2. 联系券商，为该资金账号申请**程序化交易 / 外部策略接入**授权，
   并要求关闭「xtquant 严格连接校验」（或把平台进程加入 PID 白名单）；
3. 或：把平台后端进程完整路径加入客户端「设置 → 量化接口 / 白名单」，
   也可用**极简模式**重新登录客户端后再连接；
4. 客户端刚升级时**重登一次**客户端，重新拉取券商下发的授权串。

> **本问题只影响交易通道，行情（xtdata）不受影响，行情功能可继续使用。**
