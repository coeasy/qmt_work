## 一、P0：守护装配漏 `await` ⇒ 自动连接在打包客户端上从未生效

### 1.1 现象（打包产物 fresh-profile 复测，28/31）

`live_autoconnect_e2e.py --packaged`（v0.5.3 `win-unpacked/qmt_work.exe`，
exe_mtime=20:23、src 新于 exe 的文件数 0 ⇒ 包即当前代码）+ 清空后的 fresh
profile：**路径 B 轮询 150s 未出现**，连接列表只有路径 A 一条
（`connected=false`，rc=-1 授权封死）。dev 端同一份代码 33/33 ⇒
**dev 全绿 ≠ 交付物全绿**。

### 1.2 根因（日志实锤）

```
live_client_pkg.log:49: RuntimeWarning: coroutine
  '_install_auto_connect_guard' was never awaited
  (app\bootstrap\phase_watchdogs.py:297)
```

v0.5.3（40b53a8）把守护装配从 `setup()` 里的内联 `asyncio.create_task(...)`
抽成 `async def _install_auto_connect_guard(app)`，**调用点忘了写 `await`** ⇒
协程对象创建后永不执行 ⇒ **守护任务从未创建** ⇒ 「启动预算 8s 被路径 A 慢失败
烧掉 ⇒ 守护首轮立即接力气探文件桥」整条链路静默停摆。而 `has_intent` 为真时
（存在持久化的活跃连接，如二次启动）`setup()` 自身的自动连接块也会被跳过 ⇒
**没有任何机制再去建桥** —— 用户报的「客户端没有自动连接大 qmt」在打包客户端上
原样复现。

单测全绿的原因：`test_guard_installed_only_when_switch_on` 直接
`asyncio.run(pw._install_auto_connect_guard(app))` **测了单元、没测接线**。

### 1.3 为什么 v0.5.3 的 dev 33/33 是假绿灯（本节最重要的复盘）

19:05 那跑用的 profile **不 fresh**：桥连接 `841ae96f08cc` 是上一轮遗留的
**持久化连接**，启动时由 `start_persistent_connections` 直接恢复
（dev 日志 19:04:47 `broker connection started: 大QMT桥接·文件（自动连接）
connected=True`，早于路径 A 的 8s 延迟消息 19:04:55）——与守护毫无关系。
带着脏 profile 跑，「自动连接修复了没有」根本测不出来。

⇒ e2e 脚本 **hermetic 化**：开跑前先杀自带 profile 的进程、再清空自有
profile 目录（只删 `output/order_e2e/` 下自管产物），每跑都是 fresh 库。

### 1.4 修复

- `phase_watchdogs._install_auto_connect_guard`：**改回同步函数**。
  `asyncio.create_task` 本身就是同步调用，该函数没有任何需要 `await` 的动作；
  同步化从根上消灭「忘了 await」这个 bug 类（async 化它没有任何收益）。
- 双回归锁（`backend/tests/test_autoconnect.py`）：
  1. **行为锁** `test_guard_installer_is_sync_contract_and_wiring`：与 setup()
     同形的调用（循环内、不 await）必须真的建出 `app.state._broker_acg`；
  2. **AST 锁**：模块里该函数必须保持 `def`（非 `async def`），且任何调用点
     不得位于 `await` 之下。
- **反向验证（可证伪）**：临时把函数改回 `async def`，两把锁同时红；还原后全绿。
