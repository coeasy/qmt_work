**⑨ `build_all.bat` 不产出任何产物却退出码 0（本轮最严重）**

实测 `build_all.bat --nsis` 在**几秒内** exit 0，而构建 NSIS 安装包至少需要十几分钟。
核对日志，全部输出只有 6 行：横幅 + `[build] keeping previous dist output; ...`。
**Step 1/2/3 的 echo、`build complete` 横幅、产物路径全部没有。**

根因两层叠加：

1. **LF 行尾**：该文件在 git 里一直是 `i/lf w/lf`。`cmd.exe` 逐行读取 .bat，
   LF-only 会让**括号块**（`for` / `if`）解析错位，报
   `'x' is not recognized as an internal or external command` /
   `) was unexpected at this time`。
   **实测对照**：同一份内容转 CRLF 后，同一条 `for /d` 通配在 `chcp 936` 与 `chcp 437`
   下都正常 ⇒ **编码（UTF-8 中文注释）不是变量，行尾才是**。
2. **顶层流程落进子程序**：`:clean_dist` / `:clean_static` / `:verify_static` /
   `:verify_packaged_static` 四个 helper 放在**文件中部**、以 `goto :eof` 结尾
   （语义 = 返回调用点），却**没有任何 `goto` 跳过它们**。顶层自上而下执行时落进第一个
   helper 的体内，执行它的 `goto :eof` —— 顶层 `goto :eof` 就是**结束整个脚本**。
   该结构自 HEAD 起就存在 ⇒ **`build_all.bat` 从来没能构建过任何东西**；
   历次 v0.3.x 的包实际是用 `build_all.sh`（Git Bash）产出的 ——
   这也解释了为什么 `.sh` 里有 `--backend-only` 的缺陷修复记录，而 `.bat` 里完全没有。

修法：文件整体转 **CRLF** 并在头部写明「禁止对本文件做 LF 归一化」（附症状原文）；
第一个 helper 前加 `goto :main`、最后一个 helper 后加 `:main`，让子程序只能经 `call` 进入；
并补齐两处**只在 `.sh` 有、`.bat` 缺**的发布闸门：

- `call :verify_static` 的失败必须吃掉 —— 它用 `exit /b 1` 返回，而在 `call` 语境下
  那只是**返回调用点**，脚本会继续往下跑，于是「静态产物不完整」被降级成一句提示，
  残缺前端被打进 EXE（白屏）且 exit code 仍是 0。
- `.bat` 缺 **`latest.yml` 硬核对**：`latest.yml` 只由 NSIS target 写出，缺失时客户端
  「检查更新」**静默失效且界面无任何提示**。现按 `.sh` 口径补齐（存在性 +
  `version` 与仓库根 `VERSION` 一致 + `path` 指向的安装包在位）。
- `.bat` 缺 **MCP 协议端到端**（Step 4.5）：REST 自省能列出 127 个工具**不等于**
  Agent 真能连上。现按 `.sh` 口径补齐（无 `bash` 时降级为 skip 并打印原因）。

> 教训：**「脚本退出码 0」不足以证明它做了事。**

**⑩ ⑨的修法只落在工作区：仓库里仍是 LF（blob 没变）**

⑨ 把工作区的 `build_all.bat` 转成 CRLF，但 `git ls-files --eol build_all.bat` 仍是
`i/lf w/crlf`，且本仓库 `core.autocrlf=false`、**没有 `.gitattributes`**
⇒ 工作区的 CRLF 只是本地状态。**新克隆 / CI / GitHub 源码包 / 协作方**拿到的仍是
**LF-only** 的 `.bat` ⇒ ⑨ 的整个缺陷**原样复现**（构建静默空转、退出码 0）。
只改工作区，等于把「Windows 一键构建不可用」留在了发布物里。

修法：新增 `.gitattributes`，只针对「行尾会决定脚本能否运行」的文件（不做全仓 eol 策略）：
`build_all.bat text eol=crlf`、`build_all.sh text eol=lf`、
`scripts/verify_packaged_mcp_boot.sh text eol=lf`（CRLF 会让 shebang 变成 `/bin/bash\r`）。

> 这里**刻意用 `text eol=crlf` 而不是 `-text`（直接存 CRLF 字节）**：
> `eol=crlf` 由 git 在**检出时强制**写成 CRLF，即使将来有人用 LF 编辑器改了这个文件并提交，
> 下一位 Windows 用户拿到的**仍然**是可运行的版本；`-text` 只是「存什么给什么」，
> 一旦被 LF 污染就**没有任何机制**再纠正。这类缺陷的代价是「静默无产物」，必须选能自我纠正的那种。

**⑪ CI 环境下 electron-builder 自行开启 GitHub 发布 ⇒ 构建 `exit 1` 且 `latest.yml` 丢失**

⑨ 修复后第一次真正跑完 Electron 打包：`Setup.exe`(236 MB) 与 `zip`(297 MB) **都已落地**，
脚本却 `exit 1`，且 `dist-electron/latest.yml` **不存在**。

```
  • building        target=nsis file=dist-electron\qmt_work-Setup-0.3.5.exe archs=x64
  • building block map  blockMapFile=dist-electron\qmt_work-Setup-0.3.5.exe.blockmap
  ⨯ Cannot cleanup:
Error: GitHub Personal Access Token is not set, neither programmatically, nor using env "GH_TOKEN"
```

根因（**读 electron-builder 源码确认，不是猜**）：
`app-builder-lib/out/publish/PublishManager.js` L46~L63 —— 发布策略**未显式指定**且
环境变量 `CI` 为真、当前提交又没有 git tag 时，electron-builder **自行**把策略推断成
`onTagOrDraft` 并置 `isPublish = true`（日志里那句
`artifacts will be published if draft release exists  reason=CI detected` 就是它），
于是**在产物全部生成之后**去 `new GitHubPublisher(...)` ⇒ 缺 `GH_TOKEN` 抛错 ⇒
进入 `Cannot cleanup` ⇒ 退出码 1，同时收尾的 update-info 任务被整段跳过 ⇒ **`latest.yml` 不落盘**。
本机构建环境里 `CI=true`，因此**每次** `build_all.bat --nsis` 都必踩。

修法：两个构建脚本的 electron-builder 调用**一律显式 `--publish never`**。
依据（同文件 L158~L163）：`latest.yml` 的写出条件是
`event.isWriteUpdateInfo && target != null && …`，**与 `isPublish` 无关**；
包内 `resources/app-update.yml`（L86~L89）同理
⇒ `--publish never` 只关掉「上传」，**不会削掉自动更新清单，也不会削掉更新源配置**。
上传资产是 `scripts/publish_release.py` 的职责，构建脚本**任何情况下都不发布**。

> ⑨ 与 ⑪ 是一对：一个「退出码 0 但其实什么都没做」，一个「做完了却报失败」，
> 都发生在**产物生死**这一层，而且都**只在退出码上表现出来** ——
> 只看退出码的 CI 会同时误判这两种情况。⑫ 是同一家族的第三个。

**⑫ `echo` 里的裸括号把 `if` 块提前闭合 ⇒ 最后两道闸门一次都没跑**

⑪ 修好后重跑 `build_all.bat --desktop-only --nsis`：Step 3 与 `latest.yml` 硬核对**全部通过**，
脚本却在 Step 4 之前停住，退出码 **255**：

```
[build] electron done
  latest.yml: version=0.3.5 path=qmt_work-Setup-0.3.5.exe

. was unexpected at this time.
```

**后果**：Step 4（构建后自检：拉起打包后的客户端跑 REST / WS / 窗口）与
Step 4.5（MCP 协议端到端真握手）**一次都没执行** —— 而这两步恰好是「产物到底能不能用」的判据。
与 ⑨ 同类：**构建看起来跑完了，把关的那一段被跳过了**。

根因（`cmd.exe` 的块语法）：括号块内遇到 `(` 会当成嵌套块开始、`)` 当成它的结束，
`)` 之后只允许接 `else` 或换行。Step 4 自检块里原来这一行：

```bat
echo [warn] self-check did not fully pass (see output). artifacts exist, please review.
```

被解析成 `(` 开块 → `)` 闭块 → 紧随其后的 `. artifacts exist…` 成了块外多余 token。
**同一写法在块外完全合法**（`echo` 只是把括号原样打印），只有落进括号块才炸 —— 肉眼极易漏掉。
同文件其余带括号的行都恰好躲开：`^(…^)` 转义、被引号包住
（`"C:\Program Files (x86)\NSIS\makensis.exe"`）、或用了全角 `（）`（非 ASCII，cmd 不认）。

定位方式（可复现）：把可疑块原样拷进 `output/_p*.bat`（CRLF）单跑，再逐行二分 ——
三次运行即锁定到 `(see output).` 这一行。

修法：改为 `^(see output^).`。标尺：**括号块内的 `echo` 文本，ASCII 括号必须 `^(` / `^)`
转义，或改用全角 `（）`**。复验：`build_all.bat --desktop-only --nsis` 以 `exit 0` 跑完并打印
`build complete` 横幅。

**⑬ `where bash` 命中 WSL 启动器 ⇒ MCP 端到端假报失败、构建 `exit 1`**

⑫ 修好后脚本终于跑到尾：Step 4 自检 **28/28 通过**，Step 4.5 却失败：

```
[build] Step 4.5: MCP end-to-end (packaged backend, real handshake)
适用于 Linux 的 Windows 子系统没有已安装的分发版。
[warn] MCP end-to-end failed. Agent may not connect; please review.
```

⇒ `VERIFY_RC=1` ⇒ 整个构建 `exit 1`，**而产物完全正常**。
与 ⑨ / ⑪ 方向相反，这是第三个变体：**闸门本身出错，把一次成功的构建判为失败**。

根因：`C:\Windows\System32\bash.exe` 在 Windows 10/11 上是 **WSL 启动器**，
未安装 WSL 发行版时**依然在 PATH 上**，于是 `where bash` 照样命中，
但一执行就打印上面那句并返回非 0。原实现用 `where bash >nul` 判断「有没有 bash」
⇒ 定位到 WSL 桩 ⇒ 把桩的报错当成「MCP 端到端失败」。
本机 PATH 上另有 `P:\db\PortableGit\bin\bash.exe` 与 `WindowsApps\bash.exe`（同为桩），
只有 `C:\Program Files\Git\bin\bash.exe` 是真 bash。

修法：不再信 `where`，改为**实测**——按已知安装位置依次探 Git 安装目录，
都没有再遍历 `where bash` 的每一行并实跑 `--version`，**必须回 `GNU bash`** 才采纳；
一个都没有则 `[skip] no usable bash (Git Bash) found` 并说明 WSL 桩为何不算。
`build_all.sh` 无此问题：它本身就跑在 bash 里，`bash` 必然解析到真 bash。

> 教训：**「工具存在」与「工具可用」是两件事。**
> 用 `where` / `command -v` 判命令可用性时，凡是有「同名桩 / 启动器」历史的命令
> （`bash`、`python`、`node` 都有其例），都必须**实跑一次版本探测**再采信。

**⑭ 窗口被遮挡 ⇒ `PrintWindow` 取到空白合成层 ⇒ 渲染判据假失败、构建 `exit 1`**

⑬ 修好后，同一份产物出现了**无法解释的分裂**：「窗口已实际渲染（非纯色空窗）」
检查在首次完整构建时 **PASS**（83 色 / 40298 bytes），此后连续两次 **FAIL**
（1 色 / 6406 bytes）⇒ 构建 `exit 1`。而报告里其余 **27/28 全绿**、
客户端日志显示 `GET /` 与全部 `assets/*.js` 均 200、`WebSocket /api/v1/ws [accepted]`
握过两次、`POST /api/v1/market/quotes` 正常返回 —— 页面显然好着呢。

根因：截图走 `capture_screen.capture_window()` 的
`PrintWindow(hwnd, memDC, PW_RENDERFULLCONTENT)`，取的是**窗口的 GDI 合成层**。
窗口被其它窗口**完全遮挡**时，Chromium 判定不可见、**停止出帧**、不再维护合成层，
拿到的就是未合成的空白客户区。**同一时刻**渲染进程内部完全正常：

```
CDP  -> {"nodes":200,"textLen":473,"rootKids":1,"ready":"complete",
         "text":"...平安银行 000001.SZ 11.30 -0.44% / 贵州茅台 600519.SH..."}
窗口  -> {'distinct_colors': 1,   'dominant_share': 1.0}    bytes=6406
整屏  -> {'distinct_colors': 405, 'dominant_share': 0.5495} bytes=243678
```

整屏图目视确认：客户端窗口被浏览器 / 记事本 / 资源管理器**完全盖住**。
即**判据本身失效** —— 闸门没测到任何真实问题，却把一次成功的构建判为失败。

修法（判据从「OS 位图」换成「渲染进程自证」）：

- `frontend-next/electron/main.cjs` 新增 `startRenderProof()`（仅 `TEST_MODE`）：
  由**渲染进程自己**周期性 `executeJavaScript` 取 `{nodes, textLen, rootKids, readyState}`
  落盘到 `<userData>/render-proof.json`（取样 30s，覆盖懒加载分片就绪）。
- `scripts/client_start_test.py` 新增权威判据 **「页面 DOM 已实际渲染（非空壳）」**
  （`nodes >= 50 && textLen >= 100`）；并新增 `window_occluded()`
  （`WindowFromPoint` + `GetAncestor(GA_ROOT)`），遮挡时**明确跳过**像素判据、打印
  `[skip] 窗口被其它窗口遮挡，像素判据不适用`，且**不再空等 30s**。
  像素判据保留为**第二条独立证据**（不遮挡时仍要求 ≥50 色）。
- `render-proof.json` 加入陈旧状态文件清单，避免误用上次运行的取样。

复验：`28/28 通过`、`exit 0`，报告含
`[PASS] 页面 DOM 已实际渲染（非空壳） -> 节点 132 / 正文 232 字符 / root 子节点 1 / readyState=complete`。

> 教训：**「取到的位图」不等于「页面渲染了」。**
> 任何经由 OS 合成层观察 GUI 的判据，都必须先回答「此刻该层是否被维护」；
> 否则它测的是窗口管理器的状态，而不是被测程序的健康度。

**⑮ `Edit` 工具只把改动行写成 LF ⇒ `.bat` 行尾混排 ⇒ 括号块被 cmd 撕裂（★ 最隐蔽）**

⑭ 修好后重跑构建：脚本**全程跑通**、产物**全部产出**、`BUILD_EXIT=0`、
Step 4 自检 `28/28`、Step 4.5 `MCP end-to-end passed` ——
但 stderr 多出 3 行**没人能解释**的解析噪声：

```
'），' is not recognized as an internal or external command,
'）才是执行期取值。同理' is not recognized as an internal or external command,
'）.' is not recognized as an internal or external command,
```

定位过程中有一次被排除的错误假设值得记下来：
先猜「中文 UTF-8 字节按 GBK 解读时第二字节撞上 cmd 语法字符（`^|&<>()`）」
⇒ 写探针逐行检验 ⇒ **命中 0 处，假设被排除**；
又把原样 4 行 `REM` 与 `build_all.bat` 的 415~464 行分别提出来单独跑 ⇒ **两者都干净、复现不出来**。
转机是用 PowerShell **逐字节**统计 `build_all.bat` ⇒ `CRLF=478 bareLF=6`，
**裸 LF 恰好落在第 458~463 行**，即**刚被 `Edit` 工具改动过的块内行**；
对照失败那次构建，噪声指向第 450~453 行 —— 完全吻合。
「复现不出来」恰好反证了这一点：那些探针文件是用别的方式落盘的，行尾是齐的。

根因：`Edit` 工具**只把它实际改动的那几行写成裸 LF**，其余行保持 CRLF，
文件由此变成**混排行尾**；而 cmd.exe **逐字节**读 `.bat`，读到 `\n` 即认为该行结束
⇒ `if (...)` / `for (...)` 的括号块**在 LF 处被撕裂**，块内后半段文本被当成新命令执行。

**为什么危险**：被撕裂的这次恰好只是注释（无副作用），所以**没有任何一条闸门会红**。
一旦被撕裂的是有效语句（`if` 条件、`set`、`call`），后果就是 ⑨ 的翻版：
**静默空转、退出码 0**。肉眼看不出来，`git diff` 也不显眼。
同一个「行尾」坑本轮已踩三次 —— ⑨（入库即 LF）/ ⑩（检出未生效）/ ⑮（编辑引入混排），
**三种不同的引入方式，同一个后果**。

修法：

1. 整文件行尾**归一化**为全 CRLF：`CRLF=488 bareLF=0 bytes=24398`；
2. 把**块内**中文 `REM` 全部改为**纯 ASCII 短注释**或**提到块外**
   （块外不受括号块撕裂影响），并在文件头写下这条标尺；
3. **新增第 5 项门禁** `scripts/ci_reconcile.py::check_line_endings()`：
   解析 `.gitattributes` 的 `eol=crlf` / `eol=lf` 规则，**逐字节**扫描工作区文件，
   与声明不符（含混排）即报红并**打印确切行号**（最多 20 个）。

复验（含证伪）：人为把 `build_all.bat` 第 100 行改成裸 LF ⇒ 门禁正确报红
`build_all.bat 要求 eol=crlf，但第 100 行 不符 → ...`；恢复后
`[✓] .gitattributes 声明的行尾与工作区一致`、`RECONCILE OK, EXIT=0`；
重跑构建 stderr **零解析噪声**。

> 教训：**「退出码 0」不等于「脚本被完整解析」。**
> 当一段脚本的语义由**行边界**决定（`.bat`、`Makefile`、YAML 缩进块）时，
> 行尾就是语法的一部分，必须与内容一样进门禁 —— 靠人眼与 `git diff` 一定会漏。

> 本轮在**构建脚本自己**这一层连续撞到**五个坑**（⑨ 静默空转 / ⑪ 做完却报错 /
> ⑫ 尾部中止 / ⑭ 闸门假失败 / ⑮ 闸门假通过），它们都**不改变产物的字节内容**，
> 因此不会被任何单元测试或前端测试捕获 —— 只有**真的把构建实跑到尾**才会现形。
> 结论：发布前必须实跑一次完整构建，不能只跑门禁；而**闸门的可信度本身也要审计**
> —— 既不接受「看着像失败」，也不接受「退出码 0」。

**① 发布包内缺 openpyxl ⇒ Excel 导出静默降级**

`to_excel()` 用 `df.to_excel(..., engine="openpyxl")`，而 `engine` 是**字符串**，
PyInstaller 静态分析看不见它；PyInstaller 6.22.1 又**没有** `hook-openpyxl`（实测只有 `hook-pandas*`）。
于是源码环境正常，**用户装的包**里没有 openpyxl ⇒ 导出**永远是 CSV**。

修法：`backend/build_exe.py` 的 `HIDDEN` 显式声明 `"openpyxl", "et_xmlfile"`。

> **★ 收尾复核更正了一个错误的判据**：本条原先写「构建后核对
> `backend/dist/qmt_work/_internal/openpyxl/` 存在」。**这是错的** —— PyInstaller 把
> **纯 Python 模块**作为 `PYMODULE` 收进 PYZ，而 PYZ **内嵌在 `qmt_work.exe` 里**，
> 不会在 `_internal/` 下生成 `openpyxl/` 目录（只有带 `.pyd` 的包如 `numpy` / `pandas`
> 才以目录形式出现）。按目录判定会**两头都错**：正常打包被误判成「缺陷仍在」；
> 而 `--add-data=backend/runtimes;runtimes` 又带进一份
> `runtimes/cp311/Lib/site-packages/openpyxl`（客户端运行时的**数据副本**，
> 不在冻结应用 `sys.path` 上），把真缺的包误判成「在」。
> 唯一可信的判据是**跑一次真实导出**。收尾时按完整重建（`build_all.bat --nsis`，
> 会重跑 Step 2 重建后端 EXE）实测：
> `POST /api/v1/market/export {"format":"xlsx"}` → `{"format":"xlsx","path":"…\\_verify_xlsx.xlsx"}`，
> 产物 4905 bytes、首两字节 `PK` ⇒ **openpyxl 真的可用**。
> 附带一条构建顺序规则：`--desktop-only` 会**跳过 Step 2**、直接使用上一轮的
> `backend/dist`；发布前必须跑**完整**构建。

> 叠加效应值得记一笔：本轮另一处修复刚把「产物不存在」的行为改成「如实报 csv」（见 ②），
> **两处叠加后反而更难发现** —— 信封诚实了，用户还是拿不到 xlsx。
> **诚实降级 ≠ 能力完整，两者必须一起修。**

**② 导出端点的信封描述了不存在的产物**

`POST /market/export` 恒返回 `format` 与 `fallback_csv` 字样，而 `to_excel()` 的降级判据
只覆盖 **pandas 导入失败**：pandas 装好、openpyxl 缺失时，`df.to_excel` 在**写入阶段**抛
`ImportError` ⇒ 端点走 `except Exception` ⇒ **500**，与文档承诺的「回退 CSV」不符；
且调用方若按 `path` 取文件必然失败。

修法（两处，各管一段）：

- `app/export/__init__.py::to_excel()`：把 `to_excel`/`to_csv` 调用一并纳入 `try`，
  捕获写阶段 `ImportError` ⇒ 降级返回 CSV 内容，且**降级时不落盘**
  （绝不把 CSV 内容写进 `.xlsx` 路径造成「伪 xlsx」）。
- `app/routes/analysis.py::market_export()`：**以真实产物为信封** ——
  `path.exists() and path.stat().st_size > 0` 才报 `format="xlsx"`；
  否则报 `format="csv"` + `content` + `filename`。**绝不返回不存在的 path**。

**③ 自动更新永远装不上**

Electron 文档明确 `app.exit()` **立即终止且不发出** `before-quit` / `will-quit` / `quit` 事件；
而 electron-updater 的「退出时自动安装」正挂在 `app.once("quit", …)`。
`electron/main.cjs::fullShutdown()` 原来用 `app.exit(0)` 收尾 ⇒
**用户点了「重启安装」，程序退了，版本号没变。**

修法：

```js
setTimeout(() => { app.quit(); }, 300);   // 走正常退出序列 ⇒ 触发 quit ⇒ 安装
setTimeout(() => { app.exit(0); }, 8000); // 兜底：正常序列被异常阻塞时才硬退
```

此刻 `quitting` / `shuttingDown` 均已置位，`win.on("close")` 与 `before-quit` 都会放行，
不会二次拦截。JS 单线程 ⇒ 安装包同步拉起期间那个兜底定时器**不会插进去打断安装**。

**④ `updater.cjs` 的孤儿 IPC 与「点了没反应」**

原实现用 `webContents.send("update-status"/"update-progress")` 通知渲染层，
而 `preload.cjs` **从未暴露**任何更新通道、渲染层**从未订阅** ⇒
**孤儿逻辑**：消息发进真空。且托盘「检查更新」在无更新时只写日志 ⇒
用户点了**界面毫无反应**，无法区分「已是最新」和「功能坏了」。

修法（整体重写 `updater.cjs`）：去掉全部 `webContents.send`，改**原生对话框**；
新增 `_manual` 标记，**只有**托盘手动检查才弹窗，启动静默检查绝不打扰；
`_manual = true` 必须在 `if (_checking) return;` **之前**置位（否则「正有一次静默检查在飞」时
用户点菜单会被早退吞掉）；`_info()` 兼容 `_win` 已销毁。

**⑤ `QMT_UPDATE_URL` 死旋钮 + `build_all.bat` Node 探测硬编码**

| 缺陷 | 后果 | 修法 |
|------|------|------|
| `QMT_UPDATE_URL` 环境变量 | **死旋钮**：更新源由 `electron-builder.yml` 的 `publish` 段决定（据此生成包内 `resources/app-update.yml`，运行期只读它），环境变量**根本不起作用** ⇒ 改它的人以为改了源 | `.bat`/`.sh` 删除该旋钮，改**校验 `electron-builder.yml` 存在**并在汇总里打印 `update src` |
| `build_all.bat` 硬编码 `node\versions\22.22.2` | 实际托管目录是 `22.22.2-3`（带补丁后缀）⇒ 探测不到托管 node ⇒ 静默退回 PATH 上任意 node（乃至没有 node）⇒ 构建结果与 `build_all.sh` 不一致 | 改**通配探测**（与 `.sh` 对齐） |

**⑥ A 股交易日历把「周末休市」当交易日**

内置 `WORKDAYS` 把交易所休市通知里的「周末休市」日（如 2026-01-04 周日、2026-10-10 周六）
当**调休补班交易日** —— 这些日期全社会上班，但**证券交易/清算照休**。三条链路同时错：
`is_trading_day()` 在周末返回 True ⇒ `/market/session` 声称「今天是交易日」；
`TradingSession.is_active()` 周末盘中为 True ⇒ **引擎整天高频空转打源**；
`prev/next_trading_day()` 把周末补班日当参照日 ⇒ 条件单续期算错。
另 `_CALENDAR_MAX_YEAR = 2027` 但 2027 只填了元旦 1 天，`coverage().exact=True` 属**虚假精度**。

修法：`WORKDAYS` 内置清空（仅保留 runtime_config `market.calendar.workdays` 作为非常规扩展口）；
按沪深北交易所 2025-12-22 通知补齐 2025/2026 休市段（★ 2026-02-23、2026-05-04/05 原缺）；
`_CALENDAR_MAX_YEAR` 改 2026。

**⑦ `/market/session` 契约自相矛盾**

响应体同时给出 `trading_day` 与 `phase`，但两者来自**两个不同的判定源**：
前者走 `is_trading_day_exact()`（券商日历 > 内置表，**权威**），后者走 `TradingSession` 自己判定。
共用同一张表时恰好一致，但**中秋这类「工作日休市」**上会分裂：
返回 `trading_day=False` 却 `phase="closed"` ⇒ 界面显示「已收盘」而不是「休市」——
对用户是**误导性的确定感**：以为只是今天收盘了，其实是根本不开市。

修法：`session_snapshot()` 以权威 `trading_day` 强制归一（`if not trading_day: phase = "holiday"`），
让契约由**构造**保证，而不是靠两个来源碰巧一致。

**⑧ 客户端 `site-packages` 长期污染后端进程（本轮根因最深的一处）**

`_load_xtquant_from()` 把客户端 `bin.x64\Lib\site-packages` **插进 `sys.path` 后就再也不摘除**。
该目录属于**另一个 Python 运行时**（客户端内嵌解释器），捆着大量按那个版本编译的旧库。实测症状：

> 客户端捆绑的 `defusedxml` 在 py3.11 上构造 `XMLParser` 直接
> `TypeError: __init__() takes 1 positional argument`；
> 而 openpyxl 是**首次导出 Excel 时才 import** 的 ⇒
> **「连过券商之后，Excel 导出开始报错」**，前因后果完全看不出来。

更甚者，环境探测（`probe_environment`）也会调本函数 —— 一次探测就**永久**改变整个后端进程的
import 解析顺序；导入失败时旧实现同样把路径留在 `sys.path`。

修法：注入改为**临时** —— `_added` 标记 + `finally` 摘除（成功失败都摘）；
`import xtquant.xtdata` 之后再注册的 xtquant 子模块经包 `__path__` 解析、不依赖 `sys.path`，
故摘除不影响可用性。客户端 `bin` 目录的 **PATH** 强化保留（DLL 解析靠 PATH）。

> 它同时解释了「dev 环境 Excel 导出正常、连过券商后开始报错」与
> 「同一进程里另一次完全无关的导入莫名 TypeError」两个看似无关的现象。
