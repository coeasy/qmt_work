# QMT Work 多行情源与定时数据同步完整架构方案 V7

> 日期：2026-09-09  
> 仓库：`coeasy/qmt_work`  
> 基线：V6「多数据源独立运行与 QMT 完全解耦架构完善方案」  
> 状态：V7 为 V6 的完整增强版，后续数据面、任务调度、历史行情同步与无 QMT 运行改造以本方案为准。  
> 核心目标：**QMT 可选、多行情源并存、研究链独立、历史数据每天自动更新、任务可持久化恢复、数据可追溯/可对账/可复现。**

# 1. 最终产品原则

QMT Work 后续必须遵守以下四条一级架构原则：

1. **QMT 是 Connector / Provider 之一，不是 Core 的宿主依赖。**
2. **行情数据源与交易执行源完全解耦。**
3. **历史研究数据以本地统一数据仓为核心，不依赖实时逐股远程查询。**
4. **每日历史行情同步属于系统级基础设施任务，不是一个可有可无的手工按钮。**

最终定位：

```text
插件化多数据源、多交易连接、本地优先的量化研究与交易平台
```

而不是：

```text
必须连接 QMT 才能工作的 QMT 外壳
```

# 4. 当前必须优先修正的真实问题

这些问题应进入 P0/P1，而不是以后再说。

## P0-1 LocalStore “最近 N 根”查询语义存在正确性风险

当前 `LocalStore.get_bars()` 是：

```sql
ORDER BY dt ASC
LIMIT ?
```

但方法说明是“取最近 N 根”。

当某标的数据超过 N 根后，上述 SQL 会取**最早 N 根**，不是最近 N 根。

这可能直接影响：

- 条件选股；
- 指标；
- 因子；
- 回测默认窗口；
- 最新涨跌幅；
- 策略研究。

必须修成语义明确的查询：

```text
内层 DESC LIMIT N
外层 ASC
```

或提供：

```text
get_latest_bars(...)
get_bars_range(...)
```

两个明确 API。

必须补测试：仓中 1000 根时 `limit=250` 必须返回最新 250 根且最终升序。

---

## P0-2 当前 local_bars 无 source / batch / version，多源会互相覆盖

当前主键：

```text
(code, period, adjust, dt)
```

然后：

```text
INSERT OR REPLACE
```

接入多个历史行情源后：

```text
BaoStock 同一天
↓
eltdx 同一天
↓
腾讯同一天
```

可能直接覆盖前一个来源。

后果：

- 无法知道当前值来自哪个 Provider；
- 无法比较源差异；
- 无法复现某次回测；
- 无法发现某个 Provider 修改了历史数据；
- 无法做源级回滚。

必须升级为“原始层 + 标准层”。

推荐：

```text
raw_market_bars
  provider_id
  provider_symbol
  code
  period
  trade_date/time
  payload/raw fields
  fetched_at
  sync_batch_id
  checksum

canonical_bars
  instrument_id
  period
  trade_date/time
  OHLCVA
  primary_provider
  provenance_json
  quality_state
  dataset_version
```

即：

> 原始数据不互相覆盖；Canonical 层才根据策略选主值。

## P0-3 显式 source 与复权 K 线的路由语义需要重新锁死

当前 `get_kline()` 对 qfq/hfq 会优先进入“跳过 broker、遍历补充源”的分支。

未来必须保证：

```text
source=auto
```

才允许自动换源。

而：

```text
source=baostock
source=qmt
source=eltdx
```

必须严格使用指定源；该源不支持该复权方式时返回：

```text
UNSUPPORTED_CAPABILITY
```

绝不能静默换成另外一个数据源。

否则回测/研究无法复现。

## P0-4 交易日历不能等同“法定工作日/调休工作日”

当前日历实现包含 `WORKDAYS` 调休补班日，并把周末补班日视作可交易日。

证券交易所会话日历必须成为独立 SSOT：

```text
ExchangeCalendarPort
```

来源优先：

```text
交易所/可靠市场日历 Provider
↓
本地持久化交易日历
↓
显式 degraded
```

禁止：

```text
国务院普通工作日表
→ 直接推导交易所开市日
```

还必须支持：

- 临时休市；
- 半日市（未来市场扩展）；
- 不同市场/交易所独立日历；
- 数据日历版本与来源。

## P0-5 当前 JobRuntime 并不持久化

当前 `JobRuntime` 的：

```text
_jobs
_queue
_running
_seq
```

全部是内存变量。

但是前端任务页面文案写着“重启后历史任务保留”。

这是明确的契约漂移。

必须二选一：

1. 先修文案，真实描述为进程内任务；
2. V7 正式落地 Durable JobRuntime，使文案成为事实。

V7 选择第 2 条。

## P0-6 当前 MarketSync 不是“全市场每日历史同步”

现有 `MarketSync`：

- 默认 `market.sync.enabled=False`；
- 仅进程运行时生效；
- 只刷新 `kline_cache.all_series()` 中已经存在的代码；
- 不负责完整 LocalStore 全市场历史仓；
- 客户端关闭时不会执行；
- `_last_run_date` 只存在内存；
- 使用本机 `time.strftime`，没有固定 `Asia/Shanghai`；
- 一天只按本地状态判断一次；
- 任务结果没有持久化 run manifest。

因此不能把它当成 V7 的每日数据同步系统。

它可以被迁移成 Scheduler 的一个兼容任务，最终取消独立循环。

即使部分标的失败，仍可能存在一个“最近同步时间”。

多源平台必须改为：

```text
  market
  period

  provider
  expected_count
  success_count
  valid_no_data_count

  failed_count
```

前端不能仅看到：

```text
今天 18:30 已同步
```

而要看到：

```text
2026-09-09 日线：4992/5006 完整，9 停牌无数据，5 待修复
```

# 8. UI 实时行情与历史同步必须走不同优先级通道

一个重要潜在问题是：

> 每日全市场同步不能把实时 UI 行情请求或实盘风控报价挤死。

因此 Provider 侧建立预算分区：

```text
interactive lane     最高
risk pricing lane    最高且独立
stream lane          常驻
scheduled sync lane  中
backfill lane         低
repair lane           低
```

实现：

- Provider 级 token bucket；
- Capability 级并发上限；
- bounded worker pool；
- scheduler jitter；
- retry backoff；
- 429/限频自动降速。

当前 `sync_many()` 一次创建全市场大量 coroutine，后续改为固定 worker pool，避免全市场规模扩大后队列内存膨胀。

# 10. 复权体系必须重新设计

多行情源以后不能把 Provider 已算好的 qfq/hfq 当成永远不变事实。

原因：

- 不同源复权因子可能不同；
- 新增除权除息后历史前复权值会变化；
- 数据源可能修订 corporate action。

推荐：

```text

+
CorporateAction / AdjustmentFactor
↓
Canonical Adjustment Engine
↓

```

短期仍可保留 Provider-adjusted bars，但必须记录：

```text
provider
adjustment_policy
factor_version
sync_batch_id
```

正式研究默认使用平台统一 adjustment policy。

# 14. Job 状态机

统一：

```text
scheduled
   ↓
queued
   ↓
running
   ├── succeeded
   ├── partial
   ├── failed
   ├── canceled
   └── interrupted
```

失败后：

```text
retry_wait
  ↓
queued
```

要求：

- 所有状态持久化；
- 每个运行有唯一 run_id；
- 重启后 running 任务先标 interrupted，再按策略恢复；
- 不再使用会重置的 `sync-0001` 作为全局唯一标识；
- heartbeat 检测僵尸任务；
- 支持 cooperative cancellation；
- `to_thread()` 长任务不能只取消外层 Future，要有停止 token/分片边界。

# 16. “每天必须同步”真正的保证方式

仅在 FastAPI/Electron 进程里跑 scheduler 不能保证每天执行，因为：

```text
用户关机
客户端退出
进程崩溃
升级重启
```

都会错过。

因此 V7 采用三层保证。

## 第一层：进程内 Durable Scheduler

客户端/backend 运行时按计划触发。

## 第二层：OS 级系统触发

打包一个无 UI 的数据维护入口：

```text
qmt-work-worker run-system-schedules
```

平台安装时可注册：

- Windows Task Scheduler；
- macOS launchd；
- Linux systemd timer。

即使桌面主界面没有打开，也能完成系统级 EOD 数据维护。

## 第三层：Startup Catch-up

每次后台或桌面启动时：

```text
读取 ExchangeCalendar
↓
检查最近应完成的 trade_date
↓
发现缺口
↓
自动生成 catch-up job
```

因此最终语义是：

> 至少一次执行 + 幂等写入 + 缺口自动补偿。

而不是追求脆弱的“恰好一次”。

# 17. 系统内置必须存在的定时任务

## 17.1 `system.market.eod_history_sync` —— 强制系统任务

用途：每天交易结束后同步全市场历史行情。

# 26. 本地存储容量与性能风险

日线全市场放 SQLite 可以先继续使用，但：

- 长历史；
- 1m/5m；
- tick；
- 多 Provider Raw；
- 多版本 DatasetSnapshot；

规模会快速扩大。

V7 不要求立即替换 SQLite，而是先抽：

```text
HistoricalStorePort
MetadataStorePort
```

推荐长期分层：

```text
SQLite
  配置 / schedule / job / metadata / index

Parquet + DuckDB（或等价列式层）
  大规模历史 bars / raw provider data / research scan
```

必须通过阈值与 benchmark 决定迁移，不做无证据的大重写。

# 31. Retry 策略

```text

AUTH
UNSUPPORTED
DATA_INVALID
STORAGE
INTERNAL
```

# 41. Scheduler readiness 与 degraded 语义

# 56. 明确不做的事情

1. 不把 QMT 删除；它仍是重点 Connector。
2. 不让某一个公共行情库成为新的单点依赖。
3. 不用“大量 if provider == xxx”污染业务层。
4. 不用 mock 掩盖 Provider 真实缺失。
5. 不把所有 Provider 强迫成万能接口。
6. 不允许 `INSERT OR REPLACE` 直接抹掉多源历史证据。
7. 不用普通法定工作日代替交易所日历。
8. 不把每日同步只实现成 Electron 打开时的 `setInterval`。
9. 不追求不可实现的跨崩溃“恰好一次”，采用 at-least-once + idempotency + lease。
10. 不立即把 SQLite 全部换掉，先抽 StorePort、测量后迁移。
11. 不让回测读取会动态变化的 `source=auto` 数据集合。
12. 不因 Provider 不可用让整个 Core 失去 Ready。
13. 不让第三方 Data Provider 获得 Execution 权限。
14. 不降低现有 CI、安全、交易风控和零 mock 门禁。
