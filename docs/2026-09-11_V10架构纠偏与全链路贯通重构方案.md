## 2. 架构不合理之处

### 2.1 分层违反（P2/P9/P12）

```
core/context.py:70    → from app.runtime.jobs import get_runtime      ← 反向
core/context.py:76    → from datasource.registry import get_manager   ← 反向
core/context.py:82    → from gateway.execution import get_execution_service ← 反向
core/context.py:96    → from gateway.trading_session import default_session   ← 反向
core/state.py:7       → from xtquant_client.manager import BrokerManager      ← core → xtquant
gateway/market_sync.py:137 → from app.runtime.jobs import JobSpec, get_runtime ← 反向
xtquant_client/bridge_client.py:297 → from gateway.metrics import get_metrics  ← 反向
```

**根因**：`AppContext.from_state()` 是「从全局 state 反射构建上下文」的桥接设计，它必须读 app/datasource/gateway 的单例。这违反了 core 无依赖的分层约定。

### 2.2 AppContext 死代码（P1）

- `app.state.ctx = AppContext.from_state(state)` 在 lifespan 中构建
- `get_ctx(request)` 依赖函数已定义
- **grep `Depends(get_ctx)` 全仓零命中**（不含定义处的注释）
- `check_appcontext.py` 冻结了 35 个直接引用 state 的模块基线——说明项目有意识推动迁移但尚未执行

### 2.3 选股性能瓶颈（P3）

```python
# bars_provider.py:107-117 —— 逐只循环
def _local_batch(codes, store, ...):
    for c in codes:
        out[c] = store.get_bars(c, period, adjust, count)  # 每只 1 次 SQL
```

全市场 5000+ 只 → 5000 次 SQL 串行往返。虽然功能正确，但违反 V9 §J.10 「本地向量化 ≤3s」的性能目标。

### 2.4 前端能力门控缺失（P4）

| 组件 | 交易动作 | can("trading") | 风险 |
|---|---|---|---|
| Trade.jsx | 下单/撤单/条件单/调仓 | ✅ | — |
| AccountsGrid.jsx | 批量下单 | ❌ | 无券商连接时可点按钮（后端会 503，但 UX 差） |
| Algo.jsx | 算法单提交 | ❌ | 同上 |
| QuickTrade.jsx | 快速下单 | ❌ | 同上 |
| OrderTicketModal.jsx | 下单 | ❌ | 同上 |
| Rebalance.jsx | 再平衡 | ❌ | 同上 |

### 2.5 前端 WS 事件词汇（P6）

- `shared/events.js` 定义 `WS_EVENTS` 常量表（标注「单一真源」）
- `lib/events.js` 定义 `EVENT_TYPES` 常量表（另一套命名）
- **两套常量表零引用**，所有组件直接写裸字符串（如 `"quotes"`, `"order"`, `"deal"`）

### 2.6 Electron 安全（P7）

| 安全项 | 状态 |
|---|---|
| contextIsolation | ✅ |
| nodeIntegration | ❌（正确禁用） |
| CSP | ❌ 缺失 |
| 导航白名单 | ❌ 缺失 |
| openExternal URL 校验 | ❌ 无 |

## 3. 重构方案

### 3.1 总体原则

- **正确性 > 安全 > 能力 > 性能**（D11 铁律不变）
- **不回退功能**：任何重构不得降低当前已贯通的链路能力
- **破坏性变更允许**（D8）：REST/WS/表结构/前端契约可一次到位
- **不商用**（用户确认）：`commercial_mode=false`，eltdx 全程可用
- **测试先行**：每个改动项必须先写测试再改代码

### 3.2 Phase 分解

| A1 | `core/context.py` 的 `from_state()` 改为**接收显式参数**而非反向 import：`AppContext(db=state.db, runtime_config=..., job_runtime=..., ...)`，由 `main.py` lifespan 显式注入所有依赖 | — |
| A2 | `core/state.py:7` 的 `from xtquant_client.manager import BrokerManager` 改为**延迟加载**（函数内 import），消除 core → xtquant_client 顶层依赖 | — |

## 4. 实施顺序与依赖

```
Phase A (core 纠偏 + AppContext 迁移)  ←── 最高优先，解除架构债
  │
  ├── Phase B (SQL pivot)            ←── 独立，可并行
  ├── Phase C (能力门控)              ←── 独立，可并行
  ├── Phase F (补测试)               ←── 依赖 A 的 AppContext
  │
  └── Phase D (前端 TS 化)           ←── 工作量最大，C 完成后启动
        │
        └── Phase E (Electron 安全)  ←── 独立，可并行

Phase G (shim 清理)                  ←── 最后做，全绿后清理
```

**建议节奏**：
1. **第一轮**：A + B + C 并行（后端纠偏 + 选股性能 + 前端门控）
2. **第二轮**：D + E + F 并行（前端 TS 化 + Electron 安全 + 补测试）
3. **第三轮**：G（shim 清理）
