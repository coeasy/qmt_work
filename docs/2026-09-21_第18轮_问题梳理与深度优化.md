## 二、A1 详解：GPU 自愈「隔次启动失败」（头号真缺陷）

### 2.1 现象与定位过程

排查起点是「客户端第 1 次启动崩、第 2 次正常、第 3 次又崩」，
而 `gpu-verdict.json` 当时**已经是 `{"ok":false}`** —— 按设计第 3 次应该直接进安全模式，不该崩。

三次连续启动的日志证据（`output/_clientrun/repro_{a,b,c}.log`）：

| 次 | 启动时读到 | 实际模式 | 结果 | 结束后写盘 |
| --- | --- | --- | --- | --- |
| 1 `repro_a` | 无判定 | 正常 | **崩**（`GPU 子进程崩溃 2/2` + `renderer process gone`） | `{"ok":false}` |
| 2 `repro_b` | `false` | 安全模式 | 正常起（**0 条 GPU 崩溃行**，`backend ready on 21118`） | **`{"ok":true}`** ← 被改回去 |
| 3 `repro_c` | `true` | 正常 | **又崩** | `{"ok":false}` |

### 2.2 根因

`frontend-next/electron/main.cjs` 里「确认 GPU 可用」的那段**漏判了 `SAFE_MODE`**：

```js
// 修复前
app.on("ready", () => {
  setTimeout(() => {
    if (gpuRestarted) return;          // ← 只挡了「已判定为坏」
    try { writeGpuVerdict(true); } catch {}
  }, GPU_CRASH_WINDOW_MS + 500);
});
```

安全模式下**压根没用过 GPU**（已 `disableHardwareAcceleration()` + `swiftshader`），
跑满崩溃窗口当然是「不崩」，于是被误判成「GPU 好了」并写回 `ok=true`；
下一次启动读回 `true` ⇒ 回到正常模式 ⇒ **再崩一次**。这就是「隔次」。

⚠️ 这类**接线错误**用纯函数单测抓不住 —— 判据（`!restarted`）本身没错，
错的是**没把 `SAFE_MODE` 接上去**。只有真的连续启动几次才能证伪。

### 2.3 修法

```js
app.on("ready", () => {
  if (SAFE_MODE) return; // 安全模式没用过 GPU，无权宣称 GPU 可用
  setTimeout(() => { ... }, GPU_CRASH_WINDOW_MS + 500);
});
```

安全模式不写盘 ⇒ 判定**保持 `false`** ⇒ 30 天后自然过期再重探一次，
才是「装好驱动后能自己恢复」的闭环。

### 2.4 配套：让崩溃路径可观测（`QMT_CLIENT_NO_MODAL`）

崩溃收尾会弹 `dialog.showMessageBoxSync(...)`，而它是**同步阻塞**的 ——
在非交互会话（自动化 / 远程 / 无桌面）里无人可点，进程一直挂在对话框上，
「崩溃后到底写了什么判定」变得**不可观测**。

而 `QMT_CLIENT_TEST_MODE` 会**顺带强制安全模式**，于是想复现「正常模式崩一次」这条路径就没有开关可用。
因此把「免模态框」从 TEST_MODE 里**拆出来**：

```js
const NO_MODAL = TEST_MODE || process.env.QMT_CLIENT_NO_MODAL === "1";
```

### 2.5 回归护栏（新增）

`scripts/verify_gpu_safe_mode_persistence.py` —— **不 mock、不读源码，直接跑打包产物三次**：

| 次 | 期望结果 | 期望判定文件 |
| --- | --- | --- |
| 1 | 本机无 GPU ⇒ 崩 | 写成 `{"ok":false}` |
| 2 | 安全模式**必须起来** | **仍是 `false`** ← ★ 核心断言 |
| 3 | 仍进安全模式**必须起来** | 仍是 `false` |

- 若第 1 次就正常起来并写 `ok=true` ⇒ 本机 GPU 正常 ⇒ **SKIP**（不是失败）。
- 修复前表现：第 2 次起来但把判定改成 `true`，第 3 次**崩** ⇒ 本用例红。

## 三、A2 / A3 详解：自检脚本的进程归属

### 3.1 现象

`scripts/client_start_test.py` 用 `--user-data-dir=output/client_test/profile` 把**数据**
与用户真实客户端隔离，却又按**镜像名**把**所有** `qmt_work.exe` 杀掉。
于是「跑一次自检」= 「用户正开着的客户端被静默杀掉」——
实测现象是跑完自检后手动启动的客户端不见了，**一度误判成「客户端自己崩了」**。

**隔离了数据却不区分进程归属，是自相矛盾。**

### 3.2 修法：按 profile 收敛清理范围

新增 `pids_of_profile(image, profile)`：查 `Win32_Process.CommandLine`，
只命中命令行里带**本脚本隔离 profile** 的进程。

```python
def pids_of_profile(image: str, profile: Path) -> set[int]:
    marker = str(profile).replace("\\", "/").lower()
    ps = ("Get-CimInstance Win32_Process -Filter \"Name='%s'\" | "
          "ForEach-Object { $_.ProcessId.ToString() + [char]9 + $_.CommandLine }" % image)
    ...
    if pid_s.isdigit() and marker in cmd.replace("\\", "/").lower():
        pids.add(int(pid_s))
```

⚠️ 查询失败时**刻意不退回**「按镜像名全杀」：宁可少杀（最坏是撞单实例锁、本次测试报红，
人一看就知道）也不要误杀用户正在用的客户端。

依据：Electron 的 `requestSingleInstanceLock()` 按 **userData 目录**区分实例，
所以按 profile 精确清理就足以保证「上次残留不撞锁」。

### 3.3 正向验证（实测）

带已知 profile 启动打包客户端，实测：

```
pids_of(全部)               = [9188, 10944, 17216, 17648, 19964]   # 5 个
pids_of_profile(真 profile) = [9188, 10944, 17216, 17648]          # 4 个（排除 19964）
pids_of_profile(假 profile) = []
命中判定 = PASS
```

⇒ 修复前会把这 5 个**全杀**（含用户客户端），修复后只动自己的 4 个。

### 3.4 A3：顺带修掉的断言口径错

`teardown()` 里「关闭后零残留进程」用 `pids_of(image)` 统计 ——
**只要用户自己开着客户端，这条断言就必然 FAIL**（把别人的进程算成「我没清干净」）。
改为按 profile 统计后，「零残留」才真正表达「本脚本起的那棵树清干净了」。

## 四、A5 详解：备份跳过判断会被纯 WAL 检查点打断（已修）

### 4.1 怎么发现的

后端全量测试出现 **1 个失败**：
`tests/test_db_backup_policy.py::test_run_endpoint_skip_chain_survives_its_own_audit_row`。

| 跑法 | 结果 |
| --- | --- |
| 全量（第 1 次） | **1 failed**, 1513 passed, 11 skipped |
| 该用例单跑 | **1 passed** |
| 该文件单跑（37 例） | **37 passed** |
| 全量（第 2 次） | **1515 passed, 10 skipped**（与基线完全一致） |

⇒ 顺序固定（无 `pytest-randomly` / `xdist`）、跑 3 次红 1 次 ⇒ **时序相关的偶发**。
（当时的记录写着「本轮未动任何后端源码」；A5 的**修复**是在随后单独一轮里做的，
见 4.4~4.7。）

### 4.2 机制

跳过判据 `DBBackup._covered_by()` 比较的是主库与 `-wal` 的 **`(size, mtime_ns)`**：

```python
for tag, suffix in (("db", ""), ("wal", "-wal")):
    fp[tag] = [int(st.st_size), int(st.st_mtime_ns)]
```

而**一次纯粹的 WAL 检查点**（把 WAL 内容写回主库并截断 WAL）会同时改变
`app.db` 与 `app.db-wal` 的 size 和 mtime，**却不改变任何逻辑数据** ——
于是「主库没变」被误判成「变了」⇒ 跳过失效 ⇒ 白复制一份整库。

端点的写入顺序本身是**对的**（审计行经 `after_create` 回调写在采指纹之前，
`insert()` 是同步 `commit()`，见 `core/db.py:336-342`），
所以问题只在**指纹口径对文件形态过度敏感**。

**第一次只加诊断的理由（当时是对的）**：改指纹语义的风险方向**双向且不对称** ——
改松了只是浪费一次复制（可恢复），**改紧了是静默丢备份（不可恢复）**。
在没有稳定复现的前提下动它，等于拿数据安全换省一次复制。于是先加诊断：

```python
diag = (f"记下的指纹(备份时) = {recorded_fp}  备份名={recorded_name}\n"
        f"  当前指纹(判定时)   = {inst._source_fingerprint()}\n"
        "  两者不等即说明两次调用之间主库 / -wal 被写过；"
        "注意纯 WAL 检查点也会造成这种差异（无逻辑数据变化）")
```

### 4.3 复现（先有夹具，再谈修法）

用真实 SQLite（`journal_mode=WAL`）+ 真实 `DBBackup` 写夹具，**不 mock**：

```
第 1 次 backup_once → action=created
记下的指纹          db=[4096, ...885100]   wal=[45352, ...884800]
执行 PRAGMA wal_checkpoint(TRUNCATE)：逻辑行数 2000 → 2000（未变 ✓）
检查点后的指纹      db=[36864, ...886000]  wal=[0,     ...885500]
指纹变化的部分 = ['db', 'wal']
第 2 次 backup_once → action=created   ← ★ 缺陷：应 skipped
备份份数 = 2（应 1），白复制整库 36864 字节
```

### 4.4 ★★ 显而易见的那条修法被实测**否决**

第一反应是「采指纹前先跑一次 `wal_checkpoint(TRUNCATE)`，让文件形态归一化」。
**实测不成立**：一次**无内容可合并**的检查点照样会更新 `-wal` 的 mtime
（size 恒为 0，mtime 每次都变）⇒ 指纹每次判断都算「变了」⇒ **永远跳过不了**
⇒ 每次点击都白复制一份整库 —— **比原缺陷更糟**（原缺陷只在真的发生检查点时重复）。

> 这正是「先要夹具、再改语义」的价值：没有这个夹具，这条修法看起来毫无问题，
> 上线后会把「偶发重复备份」变成「每次点击都重复备份」。

### 4.5 测量：哪种信号既对检查点免疫、又对真写入敏感

把 SQLite 暴露的全部候选信号在一串操作下逐条打出来（`output/_a5_signal_matrix.py`）：

| 步骤 | db (size, mtime) | wal (size, mtime) | page_count | hdr_ctr | dv_ro |
| --- | --- | --- | --- | --- | --- |
| 1 基线 | (4096, T1) | (45352, T1) | 9 | 1 | 2 |
| 2 **纯检查点** | (36864, T2) | (0, T2) | 9 | 2 | 3 |
| 3 **空操作检查点** | (36864, T2) ← **没变** | (0, T3) ← 变了 | 9 | 2 | 4 |
| 4 原地 UPDATE | (36864, T2) | (4152, T3) | 9 | 2 | 5 |
| 5 再检查点 | (36864, T5) | (0, T5) | 9 | 2 | 6 |
| 6 小 INSERT | (36864, T5) | (4152, T6) | 9 | 2 | 7 |

**没有任何单一信号同时合格**：`page_count` 对检查点免疫但连原地 UPDATE 都看不见
（页数不变）；`hdr_ctr` 只在检查点时才动（方向正好相反）；`data_version`
连空操作检查点都算变化。

**但矩阵第 2→3 行给出了出路**：空操作检查点时**主库的 (size, mtime) 完全没动**，
动的只有 `-wal` 的 mtime。⇒ 归一化后**只认主库**即可。

### 4.6 修法（设计 v2，先验证设计再改产品代码）

```
1. 采指纹前 best-effort 跑 PRAGMA wal_checkpoint(TRUNCATE)；
2. 检查点**确实成功**（busy=0 且 -wal 归零）⇒ 指纹只取主库 (size, mtime_ns)
   —— 此刻全部已提交数据都在主库里，主库足以代表逻辑内容；
   -wal 只留 size（恒 0）作痕迹，**剔除它的 mtime**（空操作检查点会扰动它）；
3. 检查点**没成功**（有活跃读者持有旧快照 ⇒ busy）⇒ 退回今天的口径
   （主库 + -wal 的 size 与 mtime）—— 宁可多备份，绝不漏备份。
```

设计先在探针里验四件事（`output/_a5_design_check.py`），**全过才动产品代码**：

| 性质 | 含义 | 结果 |
| --- | --- | --- |
| P1 | 纯检查点后指纹不变（原缺陷消除） | ✓ |
| P2 | 空操作检查点后指纹不变（否则走向反面） | ✓ |
| P3 | 真写入必变（原地 UPDATE / 小 INSERT / 删行 / 批量 INSERT 四种） | ✓ 4/4 |
| P4 | 降级路径仍检出真写入（不漏备份） | ✓ |
| P5 | 归一化恢复后指纹稳定（不会「永远跳过不了」） | ✓ |

> ⚠️ P4 的**探针本身写错过一次**：我一开始断言「有活跃读者 ⇒ 检查点必然失败」，
> 实测第一次仍成功（只有「读者持有**旧快照**之后又发生写入」才让 WAL 无法归零）。
> 改断成为「凡进入降级路径，真写入必须被检出」—— 这才是真正要保证的性质。

实现落在 `backend/gateway/db_backup.py`：新增 `_wal_path()` 与 `_normalize_wal()`，
`_source_fingerprint()` 改为「先归一化、再按是否归一化成功决定口径」。
用应用自己的写连接跑检查点（`self.db.execute`）—— 它就是写入方，不会与自己的写锁相争
（`_rw.write()` **不可重入**，但 `backup_to` 在返回前已释放锁，`_source_fingerprint`
在其之后调用 ⇒ 无嵌套）。

## 五、A4 详解：客户端窗口探针的确定性

`tests/verify_client_window_live.mjs` 要「点左侧自选股里的 600519」，
而自选股是**用户数据** —— 可能为空、可能被上一轮审计清空过。
此前直接把「环境没准备好」报成「左侧面板 0 行」，**连累下游 5 条断言一起红**。

改法：**先记原值 → 写入固定标的 → reload 让 store 重读 → 跑断言 → 原样写回 → 再 reload**，
整段包在 `try / finally` 里，异常也不会留下副作用：

```js
const origWL = await page.evaluate((k) => localStorage.getItem(k), WL_KEY);
await page.evaluate(([k, v]) => localStorage.setItem(k, JSON.stringify(v)), [WL_KEY, WL_SEED]);
await page.reload({ waitUntil: "domcontentloaded" });
try { /* …26 条断言… */ } finally { /* 还原 + reload */ }
```

## 九、教训

1. **「安全模式没崩」不等于「GPU 好了」** —— 判定必须问「这一次到底有没有真的用过它」。
   这类**接线错误**（判据没错、只是没接上）纯函数单测抓不住，必须有端到端护栏。
2. **隔离了数据却不隔离进程，等于没隔离** —— 清理范围要跟**归属**走，不要跟**名字**走。
3. **报 FAIL 之前先怀疑探针**（本项目已多次印证）：探针依赖用户数据 ⇒ 探针必须先摆现场。
4. **flaky 先当真缺陷查**，但**改它之前先算清风险方向**：
   A5 那种「改紧了会静默丢备份」的地方，宁可先只加诊断，也不要凭猜测动语义。
5. **构建中途发现要改代码，别等它跑完**；**构建前先腾空 `backend/static`**
   （vite `emptyOutDir` 删 139 个文件会撞删除护栏，`clean_static_assets` 只报不删）。
6. **只比 `qmt_work.exe` 大小会误判「没重新打包」** —— 应用代码在 `resources/app.asar` 里，
   改 `electron/**` **不改变外壳 EXE 的体积**（本轮两次构建的 EXE 字节数完全相同）。
   判据要看 `app.asar` 里有没有新字符串，或看它的时间戳。
7. **CDP 端口就绪 ≠ 应用页就绪**：刚启动时窗口里还是 `about:blank`（标题「正在启动」），
   而 `about:blank` 的 origin 是 **opaque** ⇒ 碰 `localStorage` 会抛
   `DOMException: Access is denied`。探针必须**等到 URL 变成 `http://127.0.0.1:<port>/`**
   再动存储；同理，`/json/version` 通了 **不等于** 后端 `/api/v1/live` 通了。
8. **本环境会在命令结束时回收进程树**：用 `DETACHED_PROCESS` 起的客户端，会在该次工具调用
   结束后被回收（日志**戛然而止、无任何崩溃记录、无 crashpad 转储** ⇒ 不是产品崩了）。
   所以「启动客户端 + 用它做验证」**必须写在同一条命令里**（见 `output/_clientrun/verify_all.sh`）。
9. **★ 刚打包完的第一次冷启动会让「窗口已渲染」假失败**（见 §8.7）：同一份产物
   首跑 40 色 / 12.2s 判红，**紧接着重跑 93 色 / 1.0s 判绿**。
   遇到窗口类断言失败，**先看截图再下结论** —— 截图里界面全在，就说明是断言抢跑，不是回归。
   诊断时别只盯「颜色数」这一个代理指标（§8.7 已加主色占比作辅助诊断）。
10. **诊断代码不能把自检本身弄挂**：往探针里加诊断输出时，务必用 try/except 兜住
   —— 实测 `capture_screen` 是局部导入的，在 `main()` 里直接引用会 `NameError`，
   把一次「27/28」变成「脚本崩掉、退出码 1」（后者更糟：连失败项清单都拿不到）。

## 十、收尾复查发现：仓库行尾一致性（A6）

### 10.1 怎么发现的

收尾核对 `git diff --stat` 时，`frontend-next/electron/main.cjs` 显示 **1595 行**改动 ——
而本轮对它只有 3 处编辑（`NO_MODAL` 拆开关 / `if (SAFE_MODE) return;` / 启动日志加 `noModal=`）。
数字对不上 ⇒ 说明 diff 里混进了**整文件级**的变化。

### 10.2 判据（必须两条一起看）

```bash
git ls-files --eol -- <file>                    # i/crlf  w/lf      ← 索引与工作区不一致
git diff --stat -- <file>                       # 1595 行           ← 假
git diff --ignore-cr-at-eol --stat -- <file>    # 117 增 / 8 删     ← 真
```

`i/crlf w/lf` 的含义是：**索引里存的是 CRLF，工作区已被翻成 LF**。本仓 `core.autocrlf=false`、
**没有 `.gitattributes`** ⇒ git 按字节存储，工作区行尾必须与索引一致，否则整个文件都算「改动」。

写文件工具（Write/Edit）不会保留原行尾，会把**整文件**翻转。所以改这类文件后必须按字节复原：

```python
b = path.read_bytes()
b = b.replace(b"\r\n", b"\n")                      # 先归一
b = b.replace(b"\n", b"\r\n")  # 或保持 \n          # 再按索引目标展开
path.write_bytes(b)
```

### 10.4 ★ 为什么这 3 个后端文件「git 说没改」

`git status` / `git diff` **看不见** `i/lf w/crlf` 这类错配：索引里缓存的文件尺寸还停在
CRLF 时代（`quote_bus.py` = 6987），与工作区当前尺寸一致 ⇒ git 认为 stat 未变、**不再重算哈希**
⇒ 报「干净」。只有当文件被重新 `add`（刷新索引）时，这个 156 字节的差异才会突然以
「整文件改动」的形式炸出来。

这正好解释了硬约束里那条为什么写成「**`git ls-files --eol` 加 `git diff --stat`**」：

- 只看 `git diff --stat` ⇒ 漏掉那 3 个潜伏文件；
- 只看 `git ls-files --eol` ⇒ 知道不一致，但不知道影响面（是幻影 diff 还是真改动）。
