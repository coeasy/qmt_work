## 1. 第一轮：根因定位

### 1.1 现象与初步证据

用户机器（广发 `gd_qmt`）表现为「客户端在跑、行情正常，但平台连不上」。

**客户端侧日志**（`<数据目录>/log/XtMiniQmt_20260928.log`）出现：

```
quant session 5, pid 28844 not allowed, return
[quant]XtQuantServer:: connect ret error-1
```

**客户端授权串**（日志头部 `receive module auth string` 之后）：

| 授权键 | 升级前 | 升级后 | 影响 |
|---|---|---|---|
| `mdl_auth_xttrader_strict_connection_check` | 0 | **1** | 交易侧对调用进程做严格校验 |
| `mdl_auth_xtdata_strict_connection_check` | 0 | **1** | 行情侧同上 |
| `mdl_auth_xtquant_no_pid_check` | 0 | 0 | **不豁免 PID 校验** |

**影响面隔离验证**（隔离数据目录 + 真实客户端）：

| 通道 | 接口 | 结果 |
|---|---|---|
| 行情 | `xtdata.get_trading_dates` / `get_instrument_detail` / `get_market_data_ex` | **全部正常** |
| 交易 | `XtQuantTrader.connect()`（`mini` / `full` / `auto` 三种模式） | **均 `rc=-1`** |

> 因此「**行情能看、就是连不上券商 / 下不了单**」是本根因的特征症状。

### 1.2 结论

该开关由**券商服务端下发的模块授权**控制，平台侧无法改写 ⇒ 只能精确引导用户
联系券商申请授权 / 加白名单。于是第一轮的目标变为：**把这个根因自动识别出来并如实透出**，
同时修掉所有让根因「到不了用户眼前」的连带缺陷。

## 2. 第一轮修复

### 2.1 P0-2 / P0-3 桥接启动时序

**修前**：`bridge_server` 在读循环之前**同步**执行 `adapter.start()`。

```
父端 _ping（握手 30s 窗口）
   └─ 子进程正卡在 start() ≈ 38s（2 目录 × 6 session × ~3.1s）
        ⇒ 父端收不到响应 ⇒ 判「桥接子进程握手失败：_ping 调用超时」并 kill 子进程
        ⇒ 真实错误（rc=-1 + 客户端日志证据）在产出前被丢弃
```

**修后**：启动转入后台线程，读循环立即可用；`_ping` 语义收窄为「IPC 就绪」，
启动结果改由新方法 `_wait_ready` 承载。

```
_ping       → {"alive": true, "connected": false, "starting": true}     立即返回
_wait_ready → 等 start() 结束 → ok=false + 完整根因文案（或 ok=true + connected）
```

**预算链（三处必须配套）**：

| 环节 | 常量 | 值 |
|---|---|---|
| 子进程内交易重试总预算 | `XTPQuantAdapter._CONNECT_RETRY_BUDGET` | 45 s |
| 父端等待启动结果 | `bridge_client._READY_TIMEOUT` | 100 s |
| 父端握手（仅 IPC） | `bridge_client._HANDSHAKE_TIMEOUT` | 30 s |

### 2.2 P0-3 的深挖：一次被「就绪超时」掩盖的**已完成**失败

修完 2.1 后端到端实测仍然「`_wait_ready` 跑满 300s 才返回」，与直接测量
（`adapter.start()` 只用 43.58s）严重不符。逐阶段计时探针结果：

```
[    0.72] load_xtquant_from(导入 xtquant)
[    2.81] probe_quote_service / effective_trade_dir
[   43.59] running_client_exes  ← 重试循环在此前结束（~40.8s / 12 次 connect）
[   43.64] diagnose_trade_connect
[   43.64] adapter.start() FAILED 用时 43.58s
```

⇒ 子进程内 `start()` 只花 43.58s，那多出来的 ~256s **不在 `start()` 里**。

**真因**（`bridge_server._start_worker` 的旧写法）：

```python
except Exception as exc:
    state["init_error"] = _safe_err(exc)     # ① 已写入
    _write(stdout, {...})                     # ② 事件已发出
    stderr.write(f"...{tb}")                  # ③ ← 多 KB 写 stderr，可能阻塞
finally:
    state["starting"] = False                 # ④ ← 永远到不了
```

父端若未持续排空 stderr（或排空线程卡顿），管道缓冲写满即**阻塞在 ③**，
⇒ 启动态永不释放 ⇒ 父端把一次**已经完成**的启动失败报成「就绪等待超时」，
而 `init_error` 明明已经产出。

**验证**：同一子进程、同样条件，只加一个 stderr 排空线程，`_wait_ready` 立刻
在 **40.98s** 返回完整根因文案。

**修法**（结构性，不靠「调用方记得排空」）：

```python
err = None
try:
    adapter.start()
except Exception as exc:
    err = (_safe_err(exc), _err_type(exc), traceback.format_exc())
finally:
    if err is not None:
        state["init_error"], state["error_type"] = err[0], err[1]
    state["starting"] = False          # ★ 先发布结果
if err is not None:
    _write(stdout, {...})              # 再做 IO
    _stderr_async(...)                 # stderr 写进 daemon 线程，永不阻塞主流程
```

**回归验证**（故意**不排空** stderr 复现阻塞条件）：

| 版本 | `_wait_ready` 返回耗时 | 结果 |
|---|---|---|
| 修前 | 300.30 s（预算耗尽） | 报「就绪等待超时」，根因丢失 |
| 修后 | **41.87 s** | `ok=false` + 完整根因文案 ✔ |

### 2.3 P0-4 日志读取（孤儿逻辑）

| 项 | 修前 | 修后 |
|---|---|---|
| 日志前缀 | 只认 `XtClient_*` | `XtClient_*` / `XtMiniQmt_*` / `XtMiniQuote_*` |
| 选择依据 | 只按 `mtime` | `_log_rank`（交易主 2 > 辅助 1 > 行情 0） |
| 读取窗口 | 只读尾部 256KB | 授权串在**头部** ⇒ 新增 `_head_text` 先读头 |

> 为什么必须改选择依据：`XtMiniQuote_*` 由行情线程高频写入，`mtime` **恒最新**，
> 只按 mtime 会稳定选中行情日志 ⇒ 交易证据**恒丢失**（且看起来「很正常」）。

### 2.4 P1-1 新诊断：`diagnose_trade_connect`

读客户端日志 + 授权串，产出结构化结论（`reason` / `title` / `evidence` / `steps`），
其中 `evidence` 是**客户端日志原文**。接入 `adapter.start()` 的失败路径后，
报错文案新增 **`### ★ 客户端侧根因（优先按此处理）`** 段，并把结论置于
「官方四步排查」之前（后者是通用清单，前者是本次真实原因）。

### 2.5 P1-2 discovery 运行态一致

`discover_accounts` 的数据目录顺序改为**运行进程优先**（跑 `XtMiniQmt.exe` 就先试
`userdata_mini`），并给候选打 `mode_source = process|layout`；`autoconnect` 的
generic 分支加守卫，**不得用静态布局结论覆盖运行态判定**。

## 3. 第二轮：全链路审计

### 3.1 P0-5 断链：前端 15s 超时把诊断挡在门外 ★本轮最关键

| 环节 | 事实 |
|---|---|
| 后端 | 一次 `connect` 最坏约 45s + 子进程冷启动 ⇒ 接近 60s |
| 前端 | `http.ts` 的 `DEFAULT_TIMEOUT = 15_000`，而 `brokerApi.connect` **未覆盖超时** |
| 后果 | 15s 时 `AbortController` 触发 ⇒ 用户只看到「请求超时（15s）」 |

**即：第一轮辛苦构造的根因诊断，在产品里根本到不了用户眼前。**
这正是「前后端未贯通」最典型的形态 —— 两侧各自「正确」，拼起来是断的。

**修复**：

| 端点 | 修前 | 修后 | 理由 |
|---|---|---|---|
| `connect` | 默认 15s | **120s** | 后端最坏 ~60s 的两倍余量 |
| `/brokers/test` | 默认 15s | **120s** | 与 connect 同源（都要跑 `adapter.start()`） |
| `/brokers/auto-detect` | 默认 15s + retry | **60s + `retry:0`** | 实测全盘扫描 ~25s；重试会白跑两遍 |
| `/brokers/version-info` | 默认 15s | **60s** | 内部会探客户端目录（可能 spawn 子进程） |

**新增回归测试** `frontend-next/tests/brokerConnectBudget.test.ts`：用假时钟把预算钉死
（16s / 60s 处**不得** abort，120s 处才 abort 且文案须为「120s」）。实测输出：

```
connect 超时文案 = 请求超时（120s）—— 后端可能正忙或数据源较慢，可稍后重试
test    超时文案 = 请求超时（120s）…
auto-detect 超时文案 = 请求超时（60s）…
```

### 3.2 前端其余问题（P1-6 / P1-7）

| 问题 | 修前 | 修后 |

| 同一错误出现两次 | store 写 `error`（列表面板）+ 按钮写 `msg`（表单面板） | `store.connect` 不再写 `error`（返回值已携带原因） |

### 3.3 P1-3 / P1-4 / P1-9 语义纠偏

**P1-3（真实 bug）**：`datasource/manager_kline.py:64` 写着 `except BrokerError:`
但该模块**从未导入** `BrokerError`（反倒是 `registry.py` 导了却不用）⇒
一旦真有异常，`except` 自身抛 `NameError`，**把原始错误彻底掩盖**。
→ 在 `manager_kline` 补导入，`registry.py` 删除死导入，并把这条陷阱写进模块 docstring。

**P1-4**：`POST /brokers/{id}/connect` 的 `except Exception` 也返回 503。
非 `BrokerError` 的异常 = **平台自身缺陷**（`TypeError`/`NameError`/…），
报成「券商不可用」会把人引向重装客户端 / 联系券商。→ 改为 **500 + 异常类型**，
并同时 `log.exception` 留栈。

**P1-5**：`gateway/health.py::_reconnect` 恒 `min(2^n, 60)`，对券商授权类
**非自愈**根因会以 60s 周期无限重拉子进程（每次 spawn + 45s 重试 + 客户端日志刷
`not allowed`）。→ 在 `BrokerError` 上新增两个**基于文案**的派生属性（跨进程边界仍可用）：

```python
@property
def needs_action(self) -> bool:   # 命中「严格连接校验」「not allowed」「程序化交易」…
@property
def brief(self) -> str:            # 单行摘要（首行 + 限长）
```

命中即把退避上限提到 **300s** 并置 `health_status="needs_action"`；
`last_error` 统一改用 `brief_error()`（**单行**，不再在句中截断）。

### 3.6 第三轮新增发现：契约面与实际不符（5 处）

按「主体流程联通 / 核心链路不断链 / 无孤儿逻辑」逐条核对时，用四道静态门禁
（`check_api_contract_drift` / `check_execution_architecture` / `check_capability_coverage` /
`check_ws_consumption`）扫描，发现 **5 处**此前未被任何测试暴露的结构性问题
（⑨~⑫ 为「声明与实际不符」，⑬ 为「门禁说谎」）：

| # | 问题 | 性质 | 处置 |
|---|---|---|---|

| # | 失败用例 | 现象 | 根因 | 处置 |

### 3.8 第四轮（追加）：全量回归**卡死** ⇒ 挖出「启动备份静默冻死」（TD-25）

第三轮收尾时按 TM 正解（`CODEBUDDY_SAFE_DELETE_ENABLED=0`）重跑逐文件回归，结果
**卡死在第 49 个文件上超过 10 分钟**。这不是偶发：原始循环与之后的续跑**卡在同一处**。
用 py-spy dump 抓现场后，链条完整闭合（详见 `docs/TECH_DEBT.md` **TD-25**）：

| 环节 | 事实（证据） |
|---|---|
| 卡在哪 | `MainThread` 在 `TestClient.__enter__`（`starlette/testclient.py:698`）等 portal；portal 线程在 jobs reaper 的 `upsert` 里等 `_rw.write()`；**写锁持有者是备份线程**：`backup_to (core/db.py:455) → self._conn.backup()` |
| 为何等不到 | SQLite 备份 API 拿不到源库锁时返回 `SQLITE_BUSY`，而 CPython 的 `Connection.backup()` **每 0.25 s 无限重试且不回调 `progress`** ⇒ 调用方永远拿不回控制权 |
| 为何全进程停摆 | 旧实现是 `with _rw.write(): self._conn.backup(...)` ⇒ 进程级写锁被**无限期**持有；独立进程做 `BEGIN IMMEDIATE` 直接 `database is locked`，杀掉该进程后立即恢复 |
| 为何应用永远打不开 | `app/bootstrap/phase_misc.py` 启动阶段 `await asyncio.to_thread(backup_once, "startup")` —— 不占事件循环，但 **lifespan 在等它的结果** ⇒ 就绪广播与前端首屏全被拖死 |
| 为何偏偏这次爆 | 主库 **585 MB**、`keep=10`、**每次启动复制一份整库** ⇒ 11 分钟连写 **8 份 / 4.4 GB**，卷已 **98% 满**；且 `_r3d` 那轮「全绿」是假象——safe-delete 护栏（TD-23）把 `_prune()` 拦成 `SystemExit`，**备份压根没落盘**，关掉护栏后缺陷才现形 |

**处置与验收**

| 改动 | 文件 | 验收 |
|---|---|---|
| `backup_to()` 去掉进程级写锁；分块 `pages` + `progress` 墙钟中止（尽力而为）；≥64 MB 大库做磁盘可用空间预检；中止/失败清掉半份 `.tmp` | `backend/core/db.py` | 真实 585 MB 库：正常 **3.02 s / True**；`deadline_s=0.01` → **False**、**无 `.tmp` 残留**、无半份产物落位 |
| 启动备份改**独立 daemon 线程、不等结果** | `backend/gateway/db_backup.py` · `backend/app/bootstrap/phase_misc.py` | 开启备份时 `lifespan` **9.40 s** → `/ready` **200**，后台线程照常产出 585 MB 备份 |
| 周期/停机备份改 `_run_backup_bounded()`（自建 daemon 线程，**不用 `asyncio.to_thread`**） | `backend/gateway/db_backup.py` | **把 `backup_once` 换成永久阻塞**（模拟卡死）：`lifespan` **9.65 s** → `/ready` **200** ✔；卡死线程 `daemon=True`，进程可正常退出 |
| 3 道静态护栏防回归 | `backend/tests/test_db_backup_policy.py` | `46 passed`（含 `test_backup_to_never_holds_the_process_write_lock`、`test_startup_backup_never_blocks_readiness`） |

> **★ 独立记一条**：`asyncio.to_thread` 用的是默认 `ThreadPoolExecutor`，其线程**非 daemon**，
> `concurrent.futures` 在解释器退出时 `atexit` join 它们 ⇒ 备份卡死时 `asyncio.wait_for`
> **能**超时返回，**但进程仍然退不出去**（实测 `timeout 300` 强杀前一直不退出 = 用户点关闭关不掉）。
> **凡「可能无界阻塞」的活都不能丢给 `asyncio.to_thread`。**
>
> 另记：新写的护栏一开始**自己被自己的注释绊倒** —— 说明文字里逐字引用了被禁写法
> （`await asyncio.to_thread(db_backup.backup_once`）导致断言误报。修法是护栏只扫
> **剥掉注释与三引号字符串后的代码**（`_code_only()`）。**扫代码，别扫说明。**
