## 0. 结论摘要

**一句话结论：架构与后端内核已达工业级水位，但「最后一公里」（前后端字段契约、界面可信度、可观测性）尚未达标——目前是"能力工业级、交付准工业级"。**

| 维度 | 判定 | 依据 |
|---|---|---|
| 后端内核（下单/风控/幂等/WAL/行情总线） | ✅ 工业级 | 唯一入口 signal_router、风控强制、幂等 single_flight、WAL 先落盘、状态机完整、无绕过路径 |
| 数据源与降级语义 | ✅ 工业级 | 多源按链降级、显式 `degraded`+`degraded_reason`、绝不用空列表冒充无数据（3 处例外见 P0-4） |
| 接口规模与 MCP 开放度 | ✅ 工业级 | REST 215 / MCP 115 tools / WS 26 类事件，MCP 零 mock、admin 鉴权、默认仅本地监听 |
| 测试门禁 | ✅ 工业级 | 后端 1077 用例 + 前端 200 用例 + 覆盖率门禁 + 架构门禁，全绿 |
| **前后端字段契约** | ❌ **不达标** | 委托方向/已成交、五档盘口、订单状态词表三处系统性错配，**静默显示错误值且不报错** |
| **界面可信度** | ⚠️ 准达标 | K 线默认不复权且丢弃 stale 标记、金额精度丢失、危险操作用 `window.confirm` |
| **可观测性/告警** | ❌ 不达标 | 定时任务失败只 log.warning、无告警接入；部分端点吞异常成"假成功/假空态" |
| **文档** | ⚠️ 准达标 | 有 30+ 篇设计文档，但**无一份完整的接口清单与功能清单**（本文补上） |

**是否达到工业级**：核心交易链路是，**端到端交付不是**。按第 5 节 P0 修完即可跨过门槛。

## 0.2 关于「MCP 覆盖缺口」的更正：那是**刻意策略，不是遗漏**

第 2 节曾把 `signal` / `alerts` / `notifications` / `webhooks` / `api-keys` /
策略运行 没有 MCP 工具列为「覆盖缺口」。**这个措辞会误导后人去"补齐"，而补齐恰好
是在放大风险面** —— 复核 `app/capabilities.py` 后确认这是显式设计：

```python
# 执行 / 密钥 / 基础设施域：一律不自动暴露（保持人工确认护栏，不放大交易风险面）
_EXEC_DENY_DOMAINS = {"trade", "target-portfolio", "rebalance", "algo", "condition",
                      "limitup", "signal", "brokers", "api-keys", "webhooks",
                      "notifications", "alerts", "scheduler", "ws", ...}
```

配套规则：
- **写入型（POST/PUT/DELETE）一律不自动暴露**，由 `test_no_write_auto_exposed` 锁死；
- 需要人工确认的域（trade/algo/condition/limitup/signal…）即便 GET 也不自动暴露；
- `/api/v1/webhooks`、`/api/v1/api-keys` 还在 `_DENY_TOOL_PATHS` 里二次拦截。

**结论**：这些域的 MCP 缺口是护栏，不是缺陷。若确实需要让 Agent 读取告警/通知，
正确做法是**手工注册只读 tool**（与其它手工域一致）并单独评审，而不是把这些域
加进自动暴露名单。

### 0.3 更正：打包态启动 90 秒的真实原因（此前归因错误）

我曾判定「17 条 `C:/no_such_qmt/userdata_mini` 垃圾连接逐个超时 ⇒ 启动 90s」。
**这个归因是错的** —— 实测 `data/app.db` 中这 17 条 **active 全为 0**，
它们根本不会进入启动期的 `bridge.start()` 循环。

复测结果（同一台机器、同一份代码）：

| 场景 | 首次冷启动 | 二次及以后 |
|---|---|---|
| 打包态后端 EXE | ~90s | **10s** |
| 开发态 `python run.py` | — | **11s** |

真实原因是**首次冷启动的一次性开销**（PyInstaller 资源首次加载、eltdx 名称表
首次枚举 5574 只并写缓存、目录/缓存初始化），与垃圾连接无关。

不过由此加固了一条真实隐患（已修，见 0.4）：**若**这类无效路径连接处于 active，
每条都会烧掉一次 32s 的 `wait_for(bridge.start())` 超时，十几条就会把「打开软件」
变成等几分钟。这是防御性修复，不是本次 90s 的成因。

统一约定：
- 前缀 `/api/v1`；响应包恒为 `{code, message, data}`，**业务错误走 HTTP 200 + `code != 0`**（`code=503` 表示数据源/券商不可用）。

### 1.2 MCP：115 个 tools（0 resource / 0 prompt）

挂载点 `POST /mcp`（Streamable HTTP）。构成：

- **手工注册 56 个**（`mcp_server/__init__.py:48-69` + `tools/*.py`）：
  券商 3（list_brokers / list_broker_profiles / broker_status）、行情 6、交易 7、账户 2、分析 4、回测 3、再平衡 1、持仓 1、因子研究 6、参考 5、策略生成 2、目标组合 3、算法单 5、条件单 3、涨停 5。
- **自动暴露 59 个**（`mcp_server/auto_expose.py:117`）：遍历 `app/capabilities.py` 的 `agent_visible` GET 端点直接转 tool。

可用性质疑结论：**零 mock，全部真实调用**。`tools/__init__.py:25` 无连接时抛 `BrokerNotConnectedError` → 503，不造假。契约快照 `tests/contracts/mcp_tools.json`（115 条）可作回归基线。

**已知隐患**：`tools/trading.py:49` 的 `place_order` 带 `auto_confirm=True`，**绕过 TOTP 二次确认**，仅靠 instructions 文本约束（见 P1-6）。

**覆盖缺口（仅 REST 有、MCP 无）**：signal 实盘信号、alerts、notifications、webhooks、api-keys（`capabilities.py:38-43` 列入 deny）；策略运行 / 策略市场发布导入；选股仅 GET 暴露，`POST /market/screen/{classic,expr,nl}` 无 MCP；`/sync/subscribe` 无。

**可发现性**：后端有 `tools/list` 与 `/capabilities`；但**前端 `grep mcp` 零匹配**——界面无法查看或管理 MCP（见 P2-3）。

### 0.5 ★ 新发现并修复：MCP 端点 `POST /mcp` 返回 405（照文档配的客户端全接不上）

**这是本轮最有价值的发现**——它不是纸面审计能看出来的，而是打包态实测 MCP 协议时撞到的。

现象：

| 请求 | 修复前 | 修复后 |
|---|---|---|
| `POST /mcp` （无尾斜杠） | **405** | **200** |
| `POST /mcp/` | 200 | 200 |

为什么严重：**README、`GET /capabilities/mcp` 返回的 `endpoint`、根端点说明，三处全写成 `/mcp`**
（无斜杠）。也就是说「照文档配置的 MCP 客户端一律握手失败」，而 405 的报错
完全看不出「加个斜杠就好」。MCP 客户端通常不会自动补尾斜杠重试。
此前所有验证都只打到 `GET /api/v1/capabilities/mcp`（REST 自省），
**走的是另一条代码路径**，所以协议层一直没被发现是坏的。

修法（`app/main.py`）：ASGI 层把 `/mcp` 重写为 `/mcp/`，
**不用 307 重定向**——部分 MCP 客户端不跟随重定向，或对 3xx 直接判定接入失败。

新增 `scripts/verify_packaged_mcp.py`：按真实 MCP 协议
`initialize → notifications/initialized → tools/list → tools/call` 走一遍，

### 0.6 追加修复：对账「WAL 读失败」被报告成「无待核销委托」

系统性扫描「假空态」时发现的**资金相关**缺陷（扫描方法见下）。

`gateway/reconcile.py::_pending_from_wal` 原实现是 ``except: return {}``，于是
`reconcile()` 返回 ``{"checked": 0, "note": "无待核销委托"}`` ——
**与「真的没有待核销」完全无法区分**。WAL 是待核销委托的唯一真源，读不出来
（磁盘故障 / 文件损坏）时：委托可能一直卡在未核销状态，而系统每天报告「一切正常」。
启动日志里那句 `startup reconcile: {'checked': 0, 'note': '无待核销委托'}` 正是这个返回值，
看不出是成功还是故障。

- 新增 `WalReadError`，读取失败**抛错**；`reconcile` 转成 `{ok: False, error}`，
  成功路径统一带 `ok: True`；
- 路由层：`res["ok"] is False` → **503**，不得用 `HTTP 200 + code=0` 把「查不了」
  包装成一次成功的对账；
- 新增 3 条测试（WAL 坏 → `ok:False` 且**不得出现**「无待核销委托」字样；
  `wal=None` 属未配置不是故障；路由返回 503）。

**扫描「假空态」的正确方法**：用 **AST** 找 except 块里直接 `return []` / `{}` /
`ok([])`，不要用正则 —— 正则会把「`return err(...)` 之后紧跟的下一个函数
`return ok(...)`」大量误报（实测 38 条命中里有 36 条是噪声）。
扫描结论：`app/routes/` 已无残留；其余命中多为数据源/内部 helper 返回空，
由链路的 `degraded` 机制承接，两处已确认合理（诊断函数返回 None；
批量取行情失败项跳过但暴露 `served/requested` 计数）。

**顺带修掉一个基元级可访问性缺陷**：`FormRow` 的 label 与控件**没有关联**（几乎无调用方传
`htmlFor`）⇒ 读屏无法朗读、点标签无法聚焦。已在 `design/primitives/Input.tsx` 用 `useId()`
自动生成 id 并注入（仅当控件本身无 id 时）。共享基元改动，前端全量 210/210 无回归。

**修正既有测试**：`tests/test_system_jobkinds.py` 的 `system.*` JobKind 由 8 个断言为
**9** 个 —— 上一轮为「经典策略选股定时调度」新增 `system.classic_screen` 时漏同步该断言，
属**自己引入的失败**，全量跑测试才发现（ci_reconcile 只收集不执行，抓不到）。

## 8. 本地启动客户端实测（2026-09-19 续）：抓到 3 个真缺陷

按「本地启动客户端测试」实际拉起桌面壳（`npx electron .`），后端随之启动在
`http://127.0.0.1:21118`。**实测比静态审查有效得多** —— 三个缺陷里有两个是
「握手/清单全绿、一调用就炸」，静态审查与只跑单元门禁都发现不了。

### 8.1 ★ P0：MCP 自动暴露工具的依赖注入参数被当成普通入参（工具清单有，但调不通）

**现象**：协议层握手、`tools/list`（120 个工具）全部 PASS，但 `tools/call
get_alerts_rules` 返回 `'str' object has no attribute 'db'`。

**根因**：能力自省把 `ctx: AppContext = Depends(get_ctx)` **当成普通 string 参数**
收进了 `param_schema`，默认值是 `Depends` 对象；`auto_expose._make_tool_func` 按
类型规则把非字符串默认值压成空串 `""`，于是生成的工具把 `ctx=""` 原样传给 handler ——
**凡是用到 `ctx.db` / `ctx.broker_manager` 的自动工具全部调不通**。

**为什么之前没发现**（两道掩盖叠加）：
1. MCP 的错误是**带内**返回的：`result.isError = true` + content 里的
   `Error calling tool ...`，而 `tools/list` 与握手照样全绿；
2. `scripts/verify_packaged_mcp.py` 只检查「响应里有没有 `result`」，**不检查
   `isError`** —— 于是「工具在、一调就炸」被判成 PASS。这就是典型的**假通过**。

**修复**：
- `auto_expose._is_di_param` 识别注入项，**不进工具签名**，改在调用时由 `_DI` 表
  解析注入（同步/异步依赖都支持）。
- `verify_packaged_mcp.py`：① 逐个调用 `SAFE_CANDIDATES` 里**存在**的工具（不再只
  调第一个）；② `isError` 为真即判 FAIL；③ 候选里**必须包含一个依赖 ctx 的工具**
  （`get_alerts_rules` / `get_notifications`）作为这条缺陷的常驻探针。
- 新增 3 条测试锁死：签名不得含 `ctx`、调用必须真的拿到 AppContext、自动工具总数
  不得因单点异常崩塌。

**自己引入的回归（同轮发现并修掉）**：第一版用 `isinstance(d, Depends)` 判断注入项 ——
**新版 FastAPI 的 `Depends` 是函数不是类**，`isinstance` 直接抛
`TypeError: arg 2 must be a type`，而这段跑在工具注册循环里 ⇒ **整个自动暴露失败**，
工具数 120 → 68。改用鸭子类型（注入项的共同特征是带 `.dependency` 可调用属性）。
这条也说明：**护栏必须同时看数量**，否则「整体崩塌」和「少了几个」看不出区别。

### 8.2 ★ P1：GPU 进程不可用时客户端**闪退且无任何提示**

无 GPU 环境（虚拟机 / RDP / 远程桌面 / 驱动异常 —— 交易场景很常见）下，默认启动会走到
`FATAL: gpu_data_manager_impl_private.cc: GPU process isn't usable. Goodbye.`
**直接退出**：窗口一闪即没，日志只有几行 GPU 报错，用户无从排障。

仓库里其实**早有**一批降级开关（`disableHardwareAcceleration` + `swiftshader`），
但**只在显式传 `--disable-gpu` / `SAFE_MODE` 时才生效** —— 真正需要它的用户恰恰
不知道要传什么。

**修复**：`electron/main.cjs` 增加 GPU 崩溃自愈 —— 启动 12s 窗口内 GPU 子进程崩溃
2 次即 `app.relaunch({args:[...,"--disable-gpu"]})` 重启。该参数会让既有 `SAFE_MODE`
分支生效，因此**不会无限重启**（第二次已是安全模式）。实测日志：

```
[desktop] GPU 子进程崩溃 1/2: killed 1
[desktop] GPU 子进程崩溃 2/2: killed 1
[desktop] GPU 不可用 —— 自动以软件渲染（--disable-gpu）重启客户端
```

### 8.3 ★ P1：客户端列出**两条一模一样的连接**（且必有一条连不上）

客户端实际用的是 `userData/app.db`（**不是** `backend/data/app.db`），里面有两条

#### 顺带修掉一处「把不支持说成网络坏了」的误导文案

遍历时发现：券商**明明已连上**（`connected=true`），但 `GET /market/boards` 报
「板块榜获取失败：TDX 行情源暂不可用，请检查网络或连接券商」。

追下去是 `app/services/market/aggregates.py` 里三处**硬编码**的兜底文案：
`_first_supported` 拿不到数据时只返回 `(None, None)`（**原因全丢**），上层只能给一句
通用话术。而真实原因是 `_sup_chain("broker", "sector")` **刻意返回空链** ——
券商源声明的能力只有 `{quote, kline, kline_qfq, kline_hfq, instrument_detail}`，
本来就不含 `sector`，这与 TDX、与网络毫无关系。

**危害**：用户会去查网络、反复重连券商，而真正的答案是「换个数据源」。排查方向被彻底带偏。

**修复**：
- `DataSourceManager` 增加失败溯源 `_last_chain` / `_last_trace` + `last_failure_trace()`，
  记录每个候选源是「未注册 / 不支持该方法 / 熔断中 / 调用失败或返回空」；
- `aggregates._unavailable(label, source)` 据此分三类给出**可执行**的提示：
  - 空链 + `source=broker` → 「数据源 broker 不提供该能力…请改用 source=auto」；
  - 空链 + `source=auto` → 「当前无任何数据源声明该能力…检查插件是否安装」
    ⚠️ 这里**不能**说「请改用 source=auto」—— 用户已经在用了，自相矛盾的提示比不提示更糟；
  - 链非空但全失败 → 列出实际尝试过的源与各自原因。

实测三种 `source` 的返回：

```
auto    板块榜获取失败：当前无任何数据源声明该能力（券商源无此接口，且已注册补充源未声明该能力）。请检查数据源插件是否安装/启用。
broker  板块榜获取失败：数据源 broker 不提供该能力（券商源无此接口）。请改用 source=auto 走补充源，或连接/安装支持该能力的数据源。
```
