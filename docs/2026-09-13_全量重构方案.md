## 1. 决策基线

| # | 决策项 | 你的选择 | 落地含义 |
|---|--------|----------|----------|
| 1 | 前端工程策略 | **全新设计** | 新建独立工程 `frontend-next/`，旧 `frontend/` 冻结至切换完成 |
| 2 | 技术栈 | **全新设计、全新改造**（授权我出方案） | TS strict + Zustand + 设计令牌 + CSS Modules（§4.1） |
| 3 | K 线/图表 | **专业 K 线库 + ECharts 分工** | klinecharts 管 K 线/分时；ECharts 管资金流/板块/热力 |
| 4 | 导航布局 | **功能树移到顶部** | 6 大业务域收进顶部菜单栏，左栏改为数据面板（§4.4） |
| 5 | 前端功能面 | **移除策略回测 + 因子前端模块** | 前端不建这两个域的页面 |
| 6 | 后端功能面 | **回测/因子模块保留** | 后端端点与 MCP 工具不动，仅前端不暴露 |
| 7 | 数据源 | **移除 TDX** | 后端删除 tstdx/pytdx |

### 1.1 关于第 5、6 项的组合效果（重要）

「前端移除、后端保留」是一个**清晰且合理的分层**，它带来三个好处：

1. **零回归风险**：后端 `tools/backtest.py`、`tools/factor_backtest.py`、`/backtest/*`、`/research/*` 全部不动 → 不需要抽离内核，`tools/factor_backtest.py:11` 对 `tools/backtest.py` 的依赖**保持原样即可**
2. **能力不丢失**：回测与因子研究仍可通过 **MCP 工具 + REST API** 使用（面向 Agent 与脚本），只是不占用 UI
3. **前端更聚焦**：新前端专注于"专业交易终端"定位，界面信息密度与操作效率优先

> ⚠️ 唯一需注意：`/backtest/*` 与 `/research/*` 端点在前端无入口，但仍在 `/capabilities` 与 MCP 工具集中。需在 `docs` 中明确标注"仅 API/MCP 可用"，避免使用者困惑。

## 4. 阶段 2 详案：全新前端工程

### 4.1 技术栈选型

| 层 | 选型 | 理由 |
|----|------|------|
| 语言 | **TypeScript 5（strict）** | 现 128 文件仅 1 个 TS，类型体系形同虚设。金融终端状态与契约复杂，类型是必需品 |
| 构建 | Vite 5 | 产物仍输出到 `backend/static_next/`（灰度期） |
| UI 框架 | React 18 | 沿用，认知成本为零 |
| 状态 | **Zustand + 分片 store** | 替代现 6 个 Context + props drilling；selector 精准订阅对高频行情关键 |
| 样式 | **CSS 变量设计令牌 + CSS Modules** | 替代 1207 行全局 CSS；修正 `--bg3` → `--bg-3` |
| K 线/分时 | **klinecharts** | 内置画线/指标/多周期/十字光标联动——正是对标通达信的核心缺口 |
| 通用图表 | ECharts 5（按需引入） | 资金流/板块热力/相关性矩阵 |
| 表格 | **TanStack Virtual** | 行情表百万行虚拟滚动 + 增量更新 |
| 测试 | Vitest + Testing Library | 沿用 Vitest |
| 桌面壳 | Electron 多窗口 | 复用现 `main.cjs` 端口发现/托盘/自启/更新逻辑 |

### 4.4 导航布局：功能树移到顶部（你的提议）

**结论：赞成，且这正是通达信的做法。**

**为什么顶部更好**

| 维度 | 左侧功能树 | 顶部菜单栏 |
|------|-----------|-----------|
| 纵向空间 | 常驻占用（行情终端最宝贵的恰是垂直空间——多图叠加、K 线高度） | **完全释放**给图表与表格 |
| 层级承载 | 6 域 × N 页需逐级展开，深处易迷失 | 一级菜单 = 6 域，下拉 = 域内页，**恰好两层**，无需展开 |
| 肌肉记忆 | 与国内专业客户端不一致 | 与通达信/大智慧/东方财富**一致** |
| 左栏用途 | 被导航占据 | **让位给真实数据**（自选股列表、盘口、预警），左栏本身产生交易价值 |
| 与多 Tab 配合 | 导航与 Tab 双份"位置感"，冗余 | 菜单负责"打开什么"，Tab 负责"已打开什么"，职责清晰 |

**具体设计**

- **顶部一级菜单**：行情 / 研究 / 交易 / 账户 / 自动化 / 系统（6 项，对齐业务域）
- **下拉二级菜单**：域内页面；点击即在新 Tab 打开
- **工具条**（菜单栏下一行）：周期切换、画线工具、指标选择、联动开关、布局模板——这是通达信式的"上下文工具条"，随当前激活 Tab 的页面类型变化
- **左栏改为数据面板**：自选股列表 / 盘口 / 预警，可折叠、可切换内容，**不再承担导航**
- **全局搜索 + 命令面板兜底**：代码直达（输入 `600519` 回车开图）、`.` 唤起命令面板——专业客户端的核心效率来源，导航深度不再是瓶颈

> **前提**：顶部菜单的可用性依赖"快捷跳转"补齐。若只有菜单而没有代码直达/命令面板，高频操作会比侧边栏更慢。二者必须同批交付。

## 5. 核心流程贯通清单（前后端联通验收基准）

> 这是本方案的**验收主干**。每条流程必须端到端跑通：前端入口 → API → 后端链路 → 事件回推 → 前端呈现。带 ⚠️ 的是当前已知断点，阶段 1/2 必须闭合。

### 流程 1：冷启动 → 连接券商 → 实时行情

| 环节 | 实现 |
|------|------|
| 前端 | 启动 → 探活 `/live` → 未连接则引导至「连接管理」 |
| API | `GET /brokers/profiles` → `POST /brokers` → `POST /brokers/{id}/connect` |
| 后端 | `BrokerManager` → `XTQuantBridge` → adapter |
| 回推 | WS 首帧全量快照 |
| 断点 | 无 |

### 流程 2：标的检索 → 自选股 → K 线 → 联动

| 环节 | 实现 |
|------|------|
| API | `GET /market/search` → `GET /market/kline` |
| 回推 | `POST /sync/subscribe` + WS quotes |
| 断点 | ⚠️ 现前端每 Tab 各自 `useQuotes`（最多 24 订阅）；新前端须做**订阅聚合**（refcount） |

### 流程 3：手动下单全流程（含二次确认）★核心

| 环节 | 实现 |
|------|------|
| 前端 | `OrderTicketModal` → 预检 → 提交 → （大额）确认弹窗 |
| API | `POST /trade/precheck` → `POST /trade/order` → `POST /signal/confirm` |
| 后端 | `SignalRouter.route()` → 风控 → `ExecutionService` → 桥 → 柜台 |
| 回推 | WS `signal_pending` / `signal_live` / `risk.blocked` / 订单状态 |
| 断点 | ⚠️ **P0-5**：`trade.py:71` 传 `auto_confirm=True` → 大额分支永不触发。`/signal/confirm` 端点存在但主 UI 路径不用。**新前端必须走完整确认流** |

### 流程 4：算法交易 TWAP/VWAP

| 环节 | 实现 |
|------|------|
| API | `POST /algo/submit` → `GET /algo` → `POST /algo/{id}/pause|resume|cancel` |
| 后端 | `engines/algo.py` 拆单 → 逐片 `signal_router.submit` |
| 回推 | WAL 事件 + WS |
| 断点 | ⚠️ **P0-3** 无幂等键；**P1-2** 暂停态重启丢失 → 重启后自动恢复下单 |

### 流程 5：条件单 / 涨停监控（自动化触发）

| 环节 | 实现 |
|------|------|
| API | `/trade/conditions*`、`/limitup/pool`、`/limitup/start|stop|reset` |
| 后端 | 引擎触发 → `signal_router.submit(auto_confirm=True)` |
| 回推 | WS 事件 + 通知 |
| 断点 | ⚠️ **P0-3** 无幂等；涨停监控启动时不自动 `start()`，`_triggered` 不持久化 |

### 流程 6：多账户批量下单/撤单

| 环节 | 实现 |
|------|------|
| API | `POST /account/batch/order`、`/account/batch/cancel`、`/account/batch/reconnect` |
| 后端 | `gateway/batch_execution.py` |
| 断点 | ⚠️ **P1-5** 幂等仅 30s 窗口，跨窗口重试同 `batch_id` 会重复下单 |

### 流程 7：风控拦截 → 前端实时提示

| 环节 | 实现 |
|------|------|
| 后端 | `risk.check_order()` 拒绝 → `_emit({"type":"risk.blocked"})` |
| 回推 | WS `risk.blocked` |
| 断点 | ⚠️ **P0-2** 风控执行两次 → 额度翻倍消耗，正常单被误拦 |

### 流程 8：委托/成交/持仓 → 对账核销

| 环节 | 实现 |
|------|------|
| API | `GET /trade/orders|deals|positions`、`/reconcile/*`、`/wal/*` |
| 后端 | `OrderReconciler` 比对 WAL 与券商 |
| 断点 | ⚠️ **P0-1** WAL 写后 → 崩溃窗口内委托失联，对账查不到 |

### 流程 9：告警规则 → 通知 / 出站 Webhook

| 环节 | 实现 |
|------|------|
| API | `/alerts/rules*`、`/alerts/history`、`/webhooks*`、`/webhooks/deliveries` |
| 后端 | `alert_engine` → `notifier` → `webhook_out`（HMAC + 退避重试） |
| 断点 | 无（前端页面此前不可达，新架构已修复） |

### 流程 10：外部信号入站 → 路由 → 执行

| 环节 | 实现 |
|------|------|
| API | `POST /signal/webhook` → `GET|POST /signal/mode` |
| 后端 | `SignalRouter`（live/dry-run/paused） |
| 断点 | ⚠️ **P1-4** `webhook_secret=""` 默认即可实盘下单 |

### 流程贯通验收方式

- **端到端脚本**：每条流程写一个 `tests/e2e/flow_*.spec.ts`（新前端）+ 后端契约断言
- **WS 事件覆盖**：对照 `backend/tests/contracts/ws_events.json` 确认前端已消费全部事件类型
- **能力可达性**：遍历 `/capabilities`（212 条），确认每条都有前端入口或明确标注"仅 API/MCP"

### 13.2 修复 1 · K 线时间格式多源漂移（高优先级）

**现象**：日线图 X 轴标签全部显示同一天（`2026-09-13`），而数据实际横跨数月。

**根因**：`toTimestamp()` 只认 `YYYY-MM-DD`，构造 `new Date("20260817T00:00:00")`
得到 `Invalid Date`，落到 `Date.now()` 兜底 —— **所有 K 线共用同一个「当前时间」**。
连带失效：十字光标时间、`DataLoader` 的 `timestamp < timestamp` 翻页过滤。

**关键认识**：后端 `time` 字段**本就不是统一格式**，按数据源不同至少四种：

| 数据源 | 代码位置 | 输出 |
|---|---|---|
| eltdx / local_store | `eltdx_source.py:435,752` | `20260817` |
| akshare | `akshare_source.py:123` | `2026-08-17` |
| optional_sources | `optional_sources.py:56,139` | `2026-08-17 00:00:00` |
| public_sources | `public_sources.py:64,94` | `2026-08-17` |

**修复**：抽到 `src/shared/time.ts`，按「位数 + 分隔符」分支解析，覆盖全部已知格式；
解析失败返回 `NaN` 而**不再兜底 `Date.now()`**（兜底会让异常值堆在同一时刻，
产出「看起来正常、其实全错」的图表，比空图危险）。调用方过滤 `NaN`。
同时一律用**本地时间**构造，禁用 `new Date("2026-08-17")` ——
ECMAScript 规定无时间的日期串按 UTC 解析，GMT+8 下会整体错位一天。

**回归防护**：`tests/time.test.ts` 18 条用例，逐个来源格式钉死，
并含「不同日期必须得到不同时间戳」的原始缺陷回归。

### 14.1 P0-4 · 手动单接入大额 TOTP 二次确认

**改动**：`app/routes/trade.py` 手动下单从 `auto_confirm=True` 改为 `auto_confirm=False`。

**为什么这是 bug 而不是设计**：`auto_confirm` 的语义是「跳过人工 TOTP 挂起」，
它的目标用户是**已授权的自动化引擎**（algo / condition / limitup / strategy /
rebalance —— 用户启动引擎前已配置并授权，不该逐单再确认）。
手动单跟着传 `True` 的后果是 `SignalRouter.route()` 里

```python
if amount >= self.threshold and self.mode in ("live", "paper") and not auto_confirm:
```

这一条件**恒为假**（`threshold` 默认 `signal_confirm_threshold = 100000`），于是：

- 人工大额单的二次确认**从不触发**，TOTP 形同虚设；
- 前端 `Trade.tsx` 里整套 `pending_confirmation` / `confirm_token` / TOTP 输入框
  沦为**死代码**——不是前端没做，是后端永远不给它触发条件。

改后语义：手动单金额 ≥ 10 万且 mode ∈ {live, paper} → 返回
`pending_confirmation + confirm_token`，前端弹 TOTP 确认框，再调 `/signal/confirm` 执行；
小额单不受影响，照常直接下单；引擎单（各自仍传 `True`）行为完全不变。

**回归防护**：新增 `backend/tests/test_p0_manual_confirm.py`（6 条），
分两层锁死——路由层断言「必须以 `auto_confirm=False` 调用」，
语义层用真实 `SignalRouter` 断言「金额 ≥ 阈值确实挂起且**未产生真实委托**」、
「小额不挂起」、「引擎单仍跳过」。
已验证该测试在回退修复后**确实失败**（2 条路由层用例），恢复后全绿。

## 15. 两个既有后端测试失败的根治（预存失败清零）

两项失败均与 §14 的 P0-4 / TDX 改动无关：已用 `git stash` 对照确认，原始代码

恢复 → 通过」的因果闭环验证。

### 15.1 `test_datasource.py::test_kline_adjusted_chain_prefers_broker_then_falls_back`

- **现象**：broker 故障后期望降级到 eltdx，实测拿到 `None`。
- **根因**：`resolve_chain` 按真实 `importlib.util.find_spec` 过滤依赖——
  eltdx 未安装则其出链被过滤；而该用例注册的是 `TstdxSource` **假源**，未通过
  真实依赖判定，于是 eltdx 被链过滤掉，落库链拿不到任何数据。
- **修复**：`test_datasource.py` 中该用例包进 `force_deps()`（强制让目标源通过
  依赖判定），断言修正为「broker 失败 → 真实走到的下一可用源」。
- **验证**：回退 `force_deps` 后该用例复现失败，恢复后通过。

### 15.2 `test_market_contract.py::test_g3_snapshot_insert_and_replay`

- **现象**：`POST /market/moneyflow/snapshot` 返回 `data.inserted == 0`，断言
  `0 == 2` 失败。
- **根因（非产品 bug，是测试契约缺漏）**：快照端点离线无资金流源时真实返回
  `inserted: 0`（零 mock，绝不造假）；`_ready()` 只校验信封 `code`（离线亦为 0），
  于是**数据依赖的数量断言 `inserted == 2` 从未被 skip 守卫**——与同文件其他
  数据依赖断言（breadth / indices / board contributors 等的「离线 skip」纪律）
  自相矛盾。
- **修复**：拆分契约——信封 + **形状契约**（snapshot 的 `inserted/codes/ts`、
  replay 的 `code/rows/count`）**在线离线均校验**；数量断言（`inserted == 2`、
  `len(rows) >= 1`、逐行字段 `ts/inside/outside/net`）按 `inserted == 0` 显式
  `pytest.skip("离线无资金流源，快照/回放无数据；仅校验信封形状契约")`。
- **验证**：离线环境下该用例从「失败」转为「skip」，同文件其余 5 条仍通过；
  回退守卫后复现 `0 == 2`，恢复后 skip——因果关系闭环。

### 17.2 三处「没有照方案原文做」的设计取舍

方案原文给了目标，但直接照做会引入新问题。这三处按代码实况调整：

**① P0-2 没有把 ExecutionService 降为「纯执行器」**

方案写「只留 `SignalRouter` 一处；`ExecutionService` 降为纯执行器」。但
`ExecutionService.place_order` 还有**直连调用方**（`tools/trading.py:22` MCP 工具、
批量执行），若整体去掉风控，这些路径会变成「无风控裸单」—— 比双执更危险。

改法：加显式参数 `risk_checked`（默认 `False`），仅 `SignalRouter` 路径传 `True`
（它在 `route()` 里已校验并计数）。**单点执行达成，Mandatory Risk 不被削弱。**

**② P0-3 没有纯靠「内容自动生成幂等键」**

方案写「按 `source+code+side+vol+price+时间窗` 生成」。但 TWAP/VWAP 拆单各片的
`code/side/vol/price` **可能完全相同** —— 用 30s 窗口去重会把整轮拆单**吞成一单**，
造成严重欠量（比重复下单更难发现）。

改法：三级策略
- **显式键优先**：`algo:{aid}:{idx}`（含分片序号）、`limitup:{code}:{yyyymmdd}`、
  `rebalance:{code}:{direction}:{idx}` —— 天然唯一，可用长窗；
- **内容键兜底**：仅对白名单引擎来源生成，且用**短窗 2s 时间桶**，
  保证间隔超过窗口的正常拆单各自成立；
- **人工单/未知来源不去重**：白名单而非黑名单，宁可漏去重也绝不误吞正常下单。

**③ P0-7 保留了显式 opt-in 逃生通道**

未配置密钥即一律拒绝会直接阻断联调环境。改为默认拒绝 + `webhook_allow_insecure`
显式开启才回到旧行为，安全默认值与可用性兼得。

### 17.3 踩坑记录：模块级与函数级同名 import

新增模块级 `import uuid` 后，`_route_inner` 里残留的函数内 `import uuid`
使其被判定为**局部变量**，在另一分支访问时抛
`UnboundLocalError`（`test_p0_manual_confirm` 捕获到）。
**教训：把函数内 import 提升为模块级时，必须删除同名的函数内 import。**

### 18.3 本轮补齐：模拟盘（6 条）

核对暴露的最明显体验断裂：**后端 PaperEngine 能力完整（下单/持仓/成交/绩效/重置），
前端零入口** —— 用户在「外部信号」页能把模式切成 `paper`，下单后却无处查看结果。

新增「模拟盘」页（账户域）：`src/domains/account/Paper.tsx` +
`src/services/api/paper.ts`，接上全部 6 个 `/paper/*` 端点。

关键契约处理（逐字段核对 `paper.py` + `paper_engine.py`）：

- `POST /paper/reset` 返回的是**重置后的 account**（不是 `{ok:true}`），可直接回写概览；
- `/paper/account` 的 `total_return` 是小数（0.0123 = 1.23%），展示需 ×100；
- 成交记录主键是 `id` 不是 `trade_id`，`pnl` 仅卖出平仓有值；
- `marking_source=frozen` = **没拿到实时行情**，市值/浮亏退化为成本价 —— 页面显式
  告警，否则用户会误读「浮动盈亏 0 = 没亏」；
- 重置是破坏性操作，采用**两段式确认**，不依赖 `window.confirm`。
