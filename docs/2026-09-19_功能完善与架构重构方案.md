## 0. 一句话诊断

**这个项目的「执行侧」相当扎实，「呈现侧」存在系统性断层。**

风控、WAL 意图落盘、对账核销、幂等播种、假成功护栏、源链降级 —— 这些最容易出事的地方都做了且做得很细。但**任务跑完之后的结果、数据的覆盖情况、选股的命中明细、调度的真实状态、主题配置**，普遍**没有回到界面上**。

用户这一轮反馈的 8 个问题里，**有 6 个落在这个断层上**：

| 用户反馈 | 真实性质 |
|---|---|
| 仪表盘没有资产信息 | 呈现断层：后端 `/account/grid` 早有汇总+持仓，仪表盘只用了单账户的 `/account/status` |
| 密钥列表不能删除 | **感知**断层：删除功能完整存在，是两段式确认的**反馈不足**导致误解 |
| K 线图展示有问题 | 执行缺陷：券商路径漏传 `adjust`（复权口径造假）+ 图表每 tick 重建 |
| 定时自动选股看不到结果 | 呈现断层：命中只在 `runtime_jobs.result_json`，前端不渲染 `result` |
| 离线数据同步要完善界面 | 呈现断层：`coverage_report` 连 REST 端点都没有 |
| 背景色设置要完善 | 呈现+持久化断层：主色写死、后端无外观端点 |

所以这次重构的**主轴**不是「补功能」，而是**把执行结果接回界面**，同时借这个机会把架构上已经被打破的分层收回来。

关键事实（都有代码证据）：

## 3. 主体链路贯通性 + 本次问题的根因定位

### 3.1 K 线「展示有问题」—— 两个确切根因

**根因 A：券商取数漏传 `adjust`，导致「标着前复权、实为不复权」**

```python
# backend/tools/__init__.py:54-56
async def _fetch_broker(c: str, p: str, n: int):
    b = get_bridge(broker_id or None)
    return await b.call(b.gateway.get_kline, c, p, n)   # ← 只有 3 个参数，adjust 被丢弃
```

而 `xtquant_client/xtp/quotes.py:186` 的 `get_kline(..., adjust)` 是支持复权的。后果链：

1. `KLineChart.tsx:123` 默认请求 `qfq`；
2. auto 链先走 eltdx，**一旦 eltdx 失败**就落到券商原始价（未复权）；
3. 但 `gateway/kline_cache.py:403` 仍以 `adjust=qfq` 落库；
4. `market.py:374` 回包 `"adjust":"qfq"`；
5. `KLineChart.tsx:218/227` 角标显示「前复权」。

⇒ **用户看到未复权价却标着前复权**，除权日出现巨大跳空，形态与指标全失真。这是本项目**最严重的行情口径缺陷**。

**根因 B：图表每个行情 tick 都重建**

```tsx
// frontend-next/src/charts/KLineChart.tsx:120-121
indicators = ["MA"],          // ← 数组字面量默认值，每次 render 都是新引用
subIndicators = [],
...
// :214 effect 依赖含 indicators/subIndicators
```
组件又订阅了行情（`:130 useQuotesStore((st) => st.quotes[code])`），每个 tick 都重渲染 → effect 反复 `dispose` + `init` + 重新请求。表现即**闪断、重置、指标丢失**。
（`MarketData.tsx:24` 的 `?? ["MA"]`、`MarketWorkbench.tsx:192` 不传参，同样每次新建数组。）

**次要问题**：`KlineResponse.as_of`（`market.ts:19`）从未被渲染，用户看不到「数据截至哪天」；空数据 `callback([], false)`（`:169`）后画布全空，`charts.module.css:18` 的 `.overlay` 空状态样式**定义了但从未使用**。

### 3.2 交易日 / 非交易日展示

- 后端能力齐备：`gateway/trading_session.py:51-67`、`app/sync/calendar.py:126-147`（**已具备「最近 N 个交易日」**），经 `/health` 暴露 `trading_session{mode,active,trading_day}`（`health.py:46-51`）。
- 前端只用在了状态栏角标（`StatusBar.tsx:102-110` + `stores/session.ts:44-67`）。
- **缺口**：行情/K 线区域**没有「这条行情属于哪个交易日」的标注**；`referenceApi.calendar`（`system.ts:305`）与 `as_of` **均零调用**。
- 全项目唯一做对的是分时：`MinutesChart.tsx:138` 显示 `data.trading_date`（后端 `market.py:378-389` 在 date 为空时自动取最新交易日）—— **这是统一改法的样板**。

### 3.3 仪表盘资产

- 后端**已有** `GET /account/grid`（`account.py:193-238`）返回 `total_assets/total_cash/total_market_value/accounts/positions`；`GET /account/aggregate`（`:42-92`）同理。

- ⇒ 缺口是**没复用**，不是没实现。且前端求和的方式在多账户下天然错误。

### 3.4 「密钥列表不能删除」—— 是感知问题，不是功能问题

- 后端：`DELETE /api-keys/{kid}`（`apikeys.py:70`）+ `POST /api-keys/batch-delete`（`:79`）**都在**。
- 前端：`ApiKeys.tsx:204-206` 行内删除 + `:215-221` 批量删除**都在**；`services/api/system.ts:216-243` 7 个方法**全部被使用**。
- 真因：这四处（Alerts / Webhooks / **ApiKeys** / RuntimeJobs）此前是「点一下就删」，被统一改成了 `ConfirmButton` **两段式确认**（`ConfirmButton.tsx:78-90`：第一次点击仅 `setArmed(true)` 变成「确认删除」，3 秒未确认自动复原）。
- ⇒ **用户点一次按钮什么都没发生**，就判断为「不能删除」。**要修的是反馈，不是 CRUD。**

## 5. 重构方案

### 5.1 目标与原则

1. **主轴：把执行结果接回界面。** 所有「跑完就算完」的地方，都要有可见的出口。
2. **架构：渐进式收回分层，不做一次性搬迁。** 用「新建代码必须合规 + 存量只减不增」的护栏替代大爆炸式重写。
3. **契约：从手抄改为生成。** 前端类型从后端 OpenAPI 生成，手写层只保留薄封装。
4. **口径：一次只修一个真因。** 每项都要求「有证据 + 有回归测试 + 能实测证明」。
5. **不破坏既有能力。** 行情 5 个独立页保留（仅移出主菜单），调度默认时间变更不动用户已改过的配置。

### 5.2 目标架构

```
backend/
  core/          无依赖内核（config / db / clock / context / state）
  domain/        ★新增 领域层：实体、值对象、规则（纯逻辑，无 IO、无 SQL）
  repos/         ★新增 仓储层：**唯一允许写 SQL 的地方**（按聚合根分文件）
  services/      应用服务：编排 domain + repos + 外部适配器（现有 4 个扩展）
  gateway/       横切：auth / rate_limit / risk / execution / wal / kline_cache
  datasource/    数据源适配（保持）
  engines/       交易引擎（保持）
  app/routes/    只做：参数校验 → 调 service → 统一信封
```

**迁移策略（strangler）**：

| 步 | 动作 | 护栏 |
|---|---|---|
| 1 | 建 `repos/` 骨架，先搬**被多 route 复用**的表：`api_keys` `alert_rules` `schedules` `runtime_jobs` `local_bars` `kline_cache` `local_boards` | 新增测试 `test_no_new_raw_sql_in_routes.py`：统计 `app/routes/` 中 `ctx.db.query/execute` 出现次数，**设上限基线，只降不升** |
| 2 | 每个 route 因功能改动而触碰时，顺手把该处 SQL 搬进 repo | 同上，上限基线随每次下降而 `--update` |
| 3 | `domain/` 只承载**有真实规则**的聚合（涨跌停幅度、订单状态机、持仓盈亏口径），**不为了分层而分层** | 新增 `test_domain_has_no_io.py`：AST 扫描 `domain/` 禁 `sqlite3` / `ctx.db` / `requests` |
| 4 | 收敛「最新价提取」5 处 → `core/quote_fields.py::pick_last_price()` | 新增 `test_quote_field_unity.py`：AST 扫描禁止其它文件出现 `("price","last"` 这类键元组 |

**契约生成**：

- 后端 `scripts/gen_contracts.py` 增加 `--ts` 模式：从 `app.openapi()` 生成 `frontend-next/src/services/api/generated.ts`（request/response 类型）。
- `shared/types.ts` 中的 API 相关类型改为 `export type { ... } from "@/services/api/generated"`；**保留**纯前端类型（UI 状态等）。
- CI 增加 `gen_contracts.py --check`：不一致即失败（与 `ci_reconcile` 并列）。
- 手写层 `services/api/*.ts` 保留（负责路径拼接与薄转换），但**参数/返回类型必须来自 generated**。

**错误处理收敛**：

- 新增 `core/errors.py::swallow(exc, *, where, level)`：显式声明「这里允许吞」，并计数 + 结构化日志。
- 替换 `main.py:188-199`、`signal_router.py:103/495` 等处的裸 `except Exception: pass`。
- 新增测试：`app/` 与 `gateway/` 下不允许出现裸 `except Exception:\s*pass`。

**(I-3) 全量日线** ✅ **已实现**（2026-09-19）

> **方案前提已被实测推翻**：原判断「所有源都只按 `count` 取最近 N 根、没有 date-range」
> 只对**免费在线源**成立。券商渠道（迅投 `get_market_data(start_time=, end_time=)`
> 与 `download_history_data`）**本来就支持按日期区间取数** —— 也就是说「全量回补」
> 根本不需要靠「大 count 反复拉最近 N 根」去凑，直接**按自然年向前翻页**即可。
> 所以设计从「大 count + end 逼近」改成「逐年区间翻页」，代价从 O(年数 × 全量)
> 降到 O(年数 × 该年根数)。

设计（已落地）：

- `sync_runner` / `BarsSyncer` 新增 `mode: "incremental" | "full"`（默认 `incremental`）
  与 `full_years`（默认 12）。**非法 mode 一律按 incremental 处理** —— 全量是几小时
  的作业，不能靠猜。
- **声明式区间能力**：新增 `DataSourceManager.get_kline_range()`，**只走**声明了
  `supports_kline_range` 的源。当前仅 `_BoundBrokerSource` 声明（在线源只接受
  `count`，把 `start/end` 传过去会被**静默忽略** ⇒ 逐年翻页会变成「同一批最近数据
  重复 12 遍」）。判据另加一层签名校验（`_accepts_kline_range`）：声明了但签名不收
  `start/end` 的源会被判为不支持 —— 否则 `src.get_kline(..., start=...)` 会在**协程
  创建处**抛 `TypeError`（在 `_call_source` 的 try 之外），整条链当场断掉而只剩一条
  debug 日志。
- `full` 语义（`bars.py::_fetch_full`）：按自然年**从今年往前**逐页取，遇到某年无数据
  （早于上市日）即停。从今年往前而不是从最早往今年：新股上市日未知，往前翻可以
  「遇空页就停」，页数最少。
- **断点续传用「数据即游标」**：不建「上次跑到第几个 code」的游标表（那种游标只在
  **正常退出**时才写对，崩一次就白跑），而是用 `local_store.earliest_dt_map()` 读
  「库里最早一根是哪天」—— 这本身就是事实，不需要额外状态，也不会与真实进度不一致。
  中断后重跑，已覆盖到目标起点的标的自动跳过。
- **绝不谎报**（三个新字段全部落库并上界面）：
  - `paged`：本次**是否真的按日期区间翻了页**。`mode=full` 而 `paged=false`
    ⇒ 当前环境没有支持区间的源，已退化为单次大 count，**历史并未补齐** ——
    这是最危险的一种「看起来成功了」（ok 满、状态成功、历史一根没多），
    界面必须明确否定它；
  - `as_of_min`：写入的最早一根 = 历史推到了哪一年（只报根数回答不了这件事）；
  - `skipped_complete`：因已补齐而跳过的标的数（断点续传的可见证据）。
- ⚠️ 连带修正：`sync_runner` 里「`total == 0` 即失败」的护栏必须**排除**
  `skipped_complete > 0` —— 第二次跑全量时所有标的都被跳过，`total` 合法为 0，
  否则重跑全量必报「股票池为空」的假失败。
- ⚠️ 命名冲突：落库 detail 里 `mode` 一直是**流的判别标签**（`"sync_bars"` /
  `"market.sync"`），而 `SyncSummary.mode` 是 `incremental|full`。两者混用会让界面
  把「全量回补」误判成普通增量，故同步模式落库键定为 **`sync_mode`**。
- 规模参考（已有实测）：窗口增量全市场 `total=5224`、`bars_written=1,630,066`、约
  7 分钟。**全量会显著更久**，因此断点续传 + 可见进度是硬要求。

### 8.2 ★ 本轮新发现的真实缺陷：券商日历覆盖区间被当成全集

写 `/market/session` 的测试时被**测试污染**暴露出来（单跑通过、整文件跑失败），根因不是测试问题：

- 券商 `get_trading_calendar()` 无参调用（`phase_broker.py:206`）返回 **19901219..20260918** —— 只到「最后一个已公布交易日」，**未来日期根本不在集合里**。
- 而 `TradingSession.is_trading_day` 原实现是 `key in self._calendar` ⇒ 区间外的日期一律判成「非交易日」。
- 后果：
  1. `next_trading_day(2026-09-19)` 走满 30 天扫描上限后返回 **20261020**（荒谬值）；
  2. 更严重 —— 客户端跨周末连续运行到周一，`is_active()` 整天为 `False`，**引擎一整天不轮询、行情停更且零报错**（`max` 仍是上周五）。
- 修复：`TradingSession` 记录 `calendar_span` 并新增 `covers()`；**区间内**信券商日历，**区间外**退回内置节假日表（覆盖 2024-2027），拿不到内置表再退周末规则。`is_trading_day_exact` 同步加覆盖判定。`stats()` 增暴露 `span` 便于排查。
- 护栏：`test_exact_judgement_ignores_calendar_outside_span`、`test_stale_calendar_does_not_idle_engines`。

> 教训：这仍然是「非空 ≠ 够新 / 有数据 ≠ 覆盖到」的同一族缺陷 —— 只是这次发生在**日历**而不是 K 线上。凡是「用一个集合的成员关系去回答一个集合可能没覆盖到的问题」，都必须先声明覆盖区间。
