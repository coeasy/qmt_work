- ⚠️ bash：set -e 下末句 `[[ … ]] && cmd` 与 `n=$(find 不存在|wc -l)`(配 pipefail) 静默 exit 1。
- ⚠️ Bash 工具里 `cmd &` 起的进程**随该次调用结束被回收** ⇒ 「起服务+curl+停服务」必须写在同一次 run_in_background 调用内。

## 数据/同步(跨轮硬知识)
- ⚠️★ **交易日格式唯一入口 `core/clock.bar_date()`**，落库一律 `YYYYMMDD`。各源原样形状
  （broker `20260825` / tencent `2026-09-18` / datetime）混存会让 `MAX(dt)` 失真
  （`-` 0x2D < `0` 0x30）、同日双行、区间过滤失效。非法日期返 `""`，绝不「修」成别的一天。
- ⚠️★ **「非空」≠「够新」**：源链「第一个非空即返回」，券商本地历史可能只到一年多前却照样非空
  ⇒ **永不降级**。同步/批量路径必须传 `get_kline(min_date=)` 新鲜度门槛（默认 10 自然日）。
- ⚠️★ **「假成功」四态全须封堵**：空转(total=0) / 假空态(对账 WAL) / 全陈旧(stale>=ok) /
  几乎全陈旧(stale>=ok×0.9)。共同点：任务 `status=done`+progress 100%，数据其实没动。
  判据永远是「数据有没有变」，不是「流程有没有跑完」。
- ⚠️ 免费公开接口**会被限流**（腾讯实测 `501 Not Implemented`，与 count 无关）⇒ 全市场批量
  必须节流（`_PublicSource._MIN_INTERVAL=0.3s`）且**分批**；并发 32 直接集体超时。
- ⚠️ 新浪只回不复权，按设计**不在 `kline_qfq` 链内**（让它进 = 不复权冒充复权）。
  腾讯限流时 qfq 无在线源可用，退回券商陈数据是**正确降级**。
- ⚠️ `params.get(x) or 默认` 会吞掉**空字符串**（falsy）：`adjust=""`（不复权）被静默改 qfq，
  新浪一次都没调用。区分「未传」只能用 `is None`。
- ⚠️★ **数据追不上的首选解法是「让券商补下载」，不是换在线源**：
  `xtquant_client/xtp/quotes.py` 的 `_warm_kline_cache` 曾只在**空结果**时预热，
  而 QMT 本地历史陈旧时 `get_market_data` **照样非空** ⇒ 预热永不触发 ⇒ 券商源永远吐陈数据。
  现已改为「**陈旧也预热**」+ 下载窗口从**最后一根**起算（默认回看 count 天够不着一年缺口）
  + `_WARM_MEMO` 同状态只试一次。券商渠道**无限流**、约 0.078 s/只（比在线源快 ~9 倍）、qfq 口径。
  实测全市场 5224 只 7 分钟，`stale` 5095→**4**。
- ⚠️ 免费公开源全市场量级**必然被限流**（腾讯 `501`、新浪 `456`），只适合小批量/交互，
  不能指望它做全市场同步。`_PublicSource._MIN_INTERVAL=0.3s` 只是降低被封概率，不是解药。
- ⚠️ akshare / baostock 是**可选依赖**，本机未安装 ⇒ `kline_qfq` 链实际只有 broker + tencent。
- ⚠️ 客户端库是 `userData/app.db`，不是 `backend/data/app.db`（后者供 `python run.py` 直跑）。
  客户端后端端口读 `userData/.qmt_work.port`（不是固定 8000）。
- ⚠️ 改了后端代码后**必须重启客户端**才生效（Electron 拉起的后端进程加载的是旧代码）。

## 数据源/降级（拿不到数据时怎么说话）
- ⚠️★ **绝不把「不支持」说成「网络坏了」**：`aggregates.py` 曾三处硬编码「TDX 行情源暂不可用，
  请检查网络或连接券商」，而真实原因常是 `_sup_chain("broker","sector")` **刻意返回空链**
  （券商能力={quote,kline,kline_qfq,kline_hfq,instrument_detail}，**不含 sector/etf_list**）。
  用户会去查网络、反复重连券商 ⇒ 排查方向被带偏。
- 失败原因唯一入口 `DataSourceManager.last_failure_trace()`（chain/tried）；`_first_supported`
  返回值只有 (None,None)，**原因全丢**，上层必须靠 trace 说话。trace 每次调用会重置。
- 文案唯一入口 `app/services/market/aggregates.py::_unavailable(label, source)`，三类分支：
  空链+指定源 / 空链+auto（**不得**提示「改用 source=auto」，用户已在用）/ 链非空全失败。
- 已知缺口（不冒进）：迅投 xtdata 真有板块接口，但券商源未实现 sector/etf_list ⇒ 连着券商
  也拿不到板块榜与 ETF 清单，只能靠 eltdx/sina/tencent 补充源。补齐需真券商逐项验证。
- ⚠️★ **券商有 `get_sector_stocks`（实测沪深A股 5224 只）但没有 `get_stock_list`**。
  凡是「需要股票池」的路径（选股 universe、日线同步 sync_stock_list）都必须**退化到券商板块成分**，
  否则纯券商环境恒空。入口：`DataSourceManager.get_sector_stocks` / `resolve_universe` / `BarsSyncer.sync_stock_list`。
  兜底数据**只有代码没名称**⇒ 不得回写股票列表（会把名称抹空）。
- ⚠️★ **空转绝不能报成功**：`sync_runner` 在 `total==0` 必须抛错。规律：「任务 done + 100% 但实际 0 写入」
  比直接失败危险得多（每天跑、数据没更新、界面显示完成，用户不看日志）。同类还有对账 WAL 假空态。
- 源名是 **eltdx** 不是 tdx（`source=tdx` → 「未注册的数据源」）。

## 任务运行时
- ⚠️★ 冲突判据是**底层数据资源**不是 kind：`RESOURCE_GROUP`（jobs.py）把
  `system.eod`/`sync_bars`/`rolling_repair`/`reconcile_bars`/`sync` 归为 `local_bars` 组同组互斥
  （EOD 内部本就含日线同步）。新增写库 kind 必须登记。
- 任务失败必须可感知：`JobRuntime.set_failure_hook`（装配层 phase_misc 注入 WS `system/job_failed`+notifier）；
  运行时刻意不直接依赖告警实现。钩子自身抛异常必须被吞掉。
- 成交去重唯一入口 `sync/__init__.py::deal_fingerprint(d)`：轮询路径与实时回报路径必须同键。

## MCP 暴露策略（改动前必读）
- ⚠️★ `app/capabilities.py::_EXEC_DENY_DOMAINS` 显式不自动暴露：trade/algo/condition/limitup/
  signal/brokers/api-keys/webhooks/notifications/alerts/scheduler…；写入型（POST/PUT/DELETE）
  永不自动暴露（`test_no_write_auto_exposed` 锁）。**MCP 覆盖缺口多为刻意护栏，不是缺陷**。
- 真要给 Agent 加能力 ⇒ 手工注册 tool（mcp_server/__init__.py），别改自动暴露名单。
- ⚠️★ MCP 端点在 `/mcp/`（有尾斜杠），`/mcp` 靠 main.py 的 ASGI 重写中间件别名。
  改挂载/路由后必须跑 `scripts/verify_packaged_mcp.py`（真协议握手+双真源比对）——
  **REST 自省能通不代表协议层能通**（曾 405 长期未被发现）。
- ⚠️ MCP `StreamableHTTPSessionManager.run()` 每实例只跑一次 ⇒ 测试必须复用
  conftest 会话级 `app_client`，自建 create_app()+TestClient 会 RuntimeError。
- 新端点若被 auto_expose 转成 tool，须跑 `scripts/gen_contracts.py` 刷新基线（MCP **120**）。
- 只读豁免：`_READ_ALLOWED_EXEC_DENY_DOMAINS = {alerts, notifications}` —— 执行域的 **GET** 可放开，
  写入型仍由 `test_no_write_auto_exposed` 锁。`test_read_only_exec_domain_exemption_is_bounded` 锁边界
  （豁免必须是拒绝域子集、绝不能混入 trade/algo/signal）。
- ⚠️★ **auto_expose 的依赖注入参数绝不能进工具签名**：能力自省把 `ctx: AppContext = Depends(get_ctx)`
  收进 `param_schema`（type=string），默认值被压成 `""` ⇒ `ctx=""` 传给 handler ⇒
  `'str' object has no attribute 'db'`，**凡用 ctx 的自动工具全调不通**。
  判注入项用鸭子类型 `hasattr(d,'dependency') and callable(d.dependency)`；
  **禁用 `isinstance(d, Depends)`**（新版 FastAPI 的 Depends 是函数不是类 ⇒ TypeError ⇒ 自动暴露整体崩）。
- ⚠️★ `scripts/verify_packaged_mcp.py` 曾**假通过**：只看「响应有没有 result」不看 `isError`；
  MCP 错误是**带内**的（isError=true），握手与 tools/list 照绿。现逐个调 SAFE_CANDIDATES 且 isError 即 FAIL，
  候选**必须含一个依赖 ctx 的工具**当常驻探针。

## 实测方法（比静态审查有效得多）
- ⚠️★ **全量 GET 端点遍历**：按 `GET /api/v1/capabilities` 自省出的清单逐条打运行中的客户端，
  按 code 分类 OK / DEGRADE(503 环境前提) / PARAM(4xx 占位参数) / BROKEN(5xx·异常)。
  脚本放 gitignored 的 `output/`，不入库。实测 0 结构性失败，但顺带挖出误导文案缺陷。

  静态审查与只跑单元门禁**发现不了**「清单全绿、一调用就炸」这类缺陷。

## 自动连接
- 唯一 backend/xtquant_client/autoconnect.py；开关 broker_auto_connect 默认 True 非阻断。
- ⚠️ 启动期无效路径连接（client_path 非空但 isdir 假）必须**跳过**而非等 32s 超时；
  判据唯一 `phase_broker.path_usable`（空路径算可用，勿误杀）。`has_intent` 亦排除之。
- ⚠️ 别拿「连接条数」当性能病因：真正会拖慢启动的是 **active** 的连接；先查 active 与阶段耗时日志。
- ⚠️★ `find_by_identity` 只拦**新建**重复，管不了库里**已有**的重复行 ⇒ `load_persisted()` 末尾跑
  `dedupe_identical()`：只认**一级身份**（券商+归一化路径+账号+账户类型；`userdata` vs `userdata_mini`
  是两种**模式**不算重复）；保留 active 那条并把被删者 active 意图**合并进保留者**；活跃指针改指保留者；
  异常只记日志**绝不拖垮启动**。测试 `tests/test_broker_dedupe.py`（8 条）。
- ⚠️★ 启动后自动连接守护判据 `_should_auto_connect(conns)`（phase_watchdogs.py 纯函数）：以「**有没有真正连上的连接**」为准，**不是**「连接列表是否为空」。全新安装→接；有 active 意图但没连上→**自愈**（覆盖「先开软件后开 QMT」）；非空且全 inactive→尊重手动断开。用「列表为空」是错的：存在任一条坏连接即永不介入 ⇒ 客户端开着也连不上。
- ⚠️★ 连接身份匹配 `find_by_identity`：一级精确 (broker_id+client_path+account)，二级「同客户端根+同账号」但**只放宽「根写法 ↔ 数据目录写法」**（`userdata` vs `userdata_mini` 是两种模式仍算不同）。持久化常写客户端根、探测给 userdata_mini，不归一就会重复建连。`repair_client_path()` 改路径必须重建 adapter/bridge（只改 cfg 不生效），仅在未连上时修。

## 桌面壳
- ⚠️ 窗口必须立刻建不能等后端(startBackend→createWindow→bootSequence)。
- CSP script-src 'self' 拦内联脚本(抽 public/theme-boot.js，须与 stores/ui.ts 规则一致)。
- ⚠️ 无 GPU 须 disableHardwareAcceleration + swiftshader；拖动区必须等应用页+传 --user-data-dir。
- ⚠️★ 降级开关**只在显式 `--disable-gpu`/SAFE_MODE/TEST_MODE 时生效** ⇒ 无 GPU 机器（VM/RDP/驱动异常）
  默认启动必崩 `FATAL: GPU process isn't usable. Goodbye.` 且**零提示**。
  已加自愈：启动 12s 内 GPU 子进程崩 2 次 ⇒ `app.relaunch({args:[...,'--disable-gpu']})`+`app.exit(0)`；
  该参数使 SAFE_MODE 生效故**不会无限重启**。
- ⚠️★ **客户端的连接库是 `app.getPath('userData')/app.db`，不是 `backend/data/app.db`**（dev 与打包态都是）。
  排查「界面看到什么」查错库会得出错误结论。后者是 `python run.py` 直跑用的。

## 选股（条件树 vs 经典策略）
- 条件树：app/screener/conditions.py，单股单值比较（字段仅 close/open/high/low/volume）。
- 经典策略：app/screener/classic.py（复刻 Sequoia-X 六策略）—— 需滚动极值/逐日涨跌/
  **横截面 RPS**，条件树表达不了，故独立成模块；行须带 close/change_pct 才与条件选股同构。
- ⚠️ 宽容只在叶子层：run_classic 对未知 id 返回 []（不让脏数据炸整轮），但
  **编排层(engine.scan_async / _classic_screen_runner)必须前置强校验 id**，
  否则用户传错名字只看到「零命中」，与「真的没票」无法区分（定时任务同理：必须失败留原因）。
- 路由：GET /market/screen 传 classic 时 conditions 可省（只回显）；
  GET /market/screen/strategies 驱动表单；POST /market/screen/classic 多策略批量。
- 界面：ScreenWorkbench 三 Tab（条件/公式/经典），经典模式把「命中分」列换成「命中明细」。

## 定时调度
- 默认调度 system_jobs.DEFAULT_SCHEDULES（固定 id，幂等播种，register_all 由 phase_misc 调）：
  15:30 sync_bars → 16:00 classic_screen → 18:30 EOD。**顺序即依赖**：选股排在日线更新前会拿昨天K线跑。
- ⚠️ 播种幂等三语义：首次建 / 二次零新建 / **用户改过的 cron 与 enabled 永不覆盖**（删掉则重建）。
- system.classic_screen 与手动选股共用 run_classic 内核 ⇒ 手动跑出的就是每天自动跑出的。
