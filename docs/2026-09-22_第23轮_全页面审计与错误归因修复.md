### 1.1 顺带发现的环境坑：`refs/remotes/*` 写入静默不落盘

`git branch -vv` 显示 `[origin/main: gone]`、`git rev-parse origin/main` 报 `ambiguous argument`，但 `git fetch origin --prune` 明明打印了 `* [new branch] main -> origin/main`。

## 3. 缺陷 D：策略回测空态把「没有作业」错误归因成「没连券商」

### 3.1 现场

打包态 0.3.0，状态栏同一时刻显示 **「券商 1/1 · 迅投XTQuant(bridge)」**（已连上），而页面空态写着：

> 还没有回测作业。回测基于券商真实历史 K 线，**需先连接券商**。

表单旁还挂着一条**常驻**提示：`未连接券商时回测会失败（K 线取不到）` —— 已连上也照挂。

### 3.2 根因

`GET /backtest/jobs` 读的是**本地作业表**，与券商**无关** —— 它不会因为没连券商就返空。所以这个列表为空**只有一个成因**：还没提交过作业。

券商只决定「提交能不能成功」，属于**前置条件**，不能拿来解释「列表为什么是空的」。两条文案把前置条件当成了空态成因 ⇒ 用户会去「连接管理」白跑一趟。

### 3.3 修法

- 提示条改为**条件渲染**（`!connected &&`），文案改成「未连接券商：回测依赖券商真实历史 K 线，现在提交会失败」；
- 空态按**已核实的状态**分叉：已连 ⇒「还没有回测作业。填好上方参数点「提交」即可创建。」；未连 ⇒ 如实说明成因 + 给「去连接」出口。

### 3.4 护栏（`frontend-next/tests/backtest.test.tsx`，5 → 7 条）

| 用例 | 断言 |
|---|---|
| 空列表 · 已连券商 | `queryByText(/需先连接券商/)` 为 null、`/未连接券商：回测依赖/` 为 null |
| 空列表 · 未连券商 | `getByText(/当前未连接券商/)` + `getByText("去连接")` 都在 |

两条护栏**可证伪**：把空态文案改回硬写版本，第一条必红。

## 4. 缺陷 E：仪表盘持仓面板同类的「成因糊在一起」

`domains/Dashboard.tsx` 的 `CrossAccountPositions`：

```tsx
emptyText="当前无持仓（或账户未连接）"     // ← 一个括号把两个成因糊在一起
```

括号里的「或」让用户无法判断到底是哪一种；更糟的是非空分支的「去连接」动作在**已连上**时仍然给出，是个**假出口**。

修法：`emptyText` 按 `connected.length > 0` 分叉（「当前账户无持仓」/「未连接券商：无法确认持仓，此处可能不完整」），`actionText` / `onAction` 改为 `gridLoading || connected.length > 0 ? undefined : ...`。

## 5. 优化一：`overview()` 三段取数改并发（改的是**结构正确性**，不是性能）

`backend/app/services/market/aggregates.py::overview()` 此前是顺序 await：

```
get_boards（预算 10s）→ get_quotes（10s）→ get_board_kline（8s）
```

三段**互不依赖**，改成 `asyncio.gather(..., return_exceptions=True)`，并**显式保住各自的错误语义**：

- `get_boards` 超时/失败 ⇒ 仍抛 `ServiceError(503)`（路由层转 err 信封）；
- `get_quotes` / `get_board_kline` 失败 ⇒ 静默退化（保持原行为），由「部分缺失」分支如实声明缺了哪一块。

### 5.1 ⚠️ 诚实记录：这次改的**不是**性能

| 场景 | 冷缓存耗时 |
|---|---|
| 改并发**前** | 7.988s |
| 改并发**后** | 7.974s |

几乎无差。分段 curl 计时（同一后端进程）才看清耗时分布：

| 分段 | 耗时 |
|---|---|
| `GET /market/boards?kind=stat` | 0.007s |
| `POST /market/quotes`（8 个指数） | **7.365s**（进程内首次；之后 2.4~4s） |
| `GET /market/board/kline` | 0.008s |

⇒ 耗时**几乎全在指数批量行情那一段**。所以这次并发改的是「将来某一段变慢时不再线性叠加」的**结构正确性**，**不是**当前这条链路的性能。这段结论已写进代码注释，避免下一轮被误导。

### 5.2 护栏（`backend/tests/test_batch_quotes.py`，17 → 19 条）

| 用例 | 可证伪点 |
|---|---|
| `test_overview_fetches_three_blocks_concurrently` | 三段各 `asyncio.sleep(0.30)`，断言 `elapsed < 0.60`；**退回顺序 await 就是 0.90 ⇒ 必然失败** |
| `test_overview_stat_failure_still_raises_503` | `get_boards` 抛 `RuntimeError("TDX 挂了")` ⇒ 断言 `ServiceError.code == 503` 且 message 含真实成因；**不得**静默返回空概览 |

## 6. 优化二：`overview` 缓存 10s → 60s

原值 10 秒，**前端默认传的也是 10**（`market.ts` 的 `ttl = 10`）⇒ 用户「切走页签再切回」几乎每次都要重新打源，而这条链路稳态就要 2.4~4s。

关键依据（**来自代码，不是推测**）：本页唯一新鲜度敏感的项是**指数最新价 / 涨跌幅**，而它由 `MarketStructure` 用 `useLiveQuotes` **实时叠加（WS 推送）**，不依赖这个快照；其余各项（涨跌家数 / 停板家数 / 成交均价 / 宽度趋势 / 两市成交额）都是慢变量。

改动三处，保持默认值一致：

| 文件 | 改动 |
|---|---|
| `frontend-next/src/services/api/market.ts` | `ttl = 10` → `ttl = 60` |
| `backend/app/routes/market.py` | 路由 `ttl: int = 10` → `60` |
| `backend/app/services/market/aggregates.py` | `overview(..., ttl: int = 10)` → `60` |

**影响面已核实**：`marketApi.overview()` 全站**只有 `MarketStructure.tsx` 一个调用方**（路由注释里提到的「顶部指数条」是历史状态，现走 `DataPanel`/`useDisplayQuotes`）。调用方仍可传 `ttl=0` 绕过缓存；页面另有「刷新」按钮。

**测试影响已核实**：现有 overview 测试要么显式传 `ttl=0`（`test_batch_quotes.py`），要么只断言字段形状（`test_market_contract.py`）；`test_index_name_fallback.py` 只在文档字符串里提到该端点，不实际调用。契约快照 `backend/tests/contracts/rest_endpoints.json` **不含** `ttl` 默认值。

## 8. 冷启动 8 秒：**归因校正**与下一轮落点

### 8.1 我上一轮的归因是**未经证实**的

上一轮我把它归给「券商桥接首次拉起」，依据是隔离实例实测 `source=broker` 冷 8.140s vs `source=tencent` 冷 0.688s。**这个对照并不能区分两种成因**：

1. 桥接子进程首次 spawn + XTQuant 初始化；
2. 券商报价路径本身每次调用就慢（超时 / 逐只 RPC）。

而且 `app/bootstrap/phase_broker.py::start_persisted_connections` 在启动期是 **`await`** 的（每条 32s 超时），若真走这条路，这 8 秒应该付在**启动期**而不是首个行情请求上。⇒ **原归因不成立，已撤回。**

### 8.2 用代码核到一条**静态可证**的线索（尚未实测确认）

`datasource/registry.py::DataSourceManager.get_quotes` 的 `_broker_batch`：

```python
results = await asyncio.gather(
    *[self.get_quote(c, "broker", conn_id) for c in todo], ...)
```

`asyncio.gather` 只并发了**等待**，每次 `get_quote` 各发一条跨进程 RPC（`BridgeAdapter.get_quote` → `_rpc("get_quote", [code])`）⇒ **N 只标的 = N 次 RPC**。取 8 个指数就是 8 次。

而桥接侧**已有批量接口**：`BridgeAdapter.get_full_tick(codes)` → `_rpc("get_full_tick", [list(codes)])`，一次就能拿全。

### 8.3 ⚠️ 为什么本轮**没有**动手改

**不能**把 `_broker_batch` 直接换成批量 RPC：`self.get_quote()` 除取价之外还做了**名称兜底 / 板块分类 / 详情合并**（`_merge_quote` 那段）。直接批量取原始 tick 会**静默丢掉这些字段**（指数名会退化成代码 —— 正是 `test_index_name_fallback.py` 锁死过的那类回归）。

正确做法是「批量只用于取原始 tick，逐只归一化照旧」，属关键报价路径的**重构**，且需要**真券商环境**验证；本环境不允许连真券商 ⇒ 不在无验证条件的情况下收尾落地。

已在 `registry.py::_broker_batch` 现场留下精确注释（含上述证据、风险与「尚未定论」的声明），作为下一轮的首要落点。
