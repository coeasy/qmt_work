## 4. 不合理之处

### 4.1 🔴 架构层

| # | 问题 | 影响 | 严重度 |
|---|---|---|---|
| A1 | **main.py 655 行 God File**：lifespan 手动按序挂接 20+ 引擎，启动逻辑与业务逻辑耦合 | 新增引擎需改 main.py，极易遗漏停机顺序 | 🔴 高 |
| A2 | **同步/异步混用**：routes 中 203 个 async def + 少量 sync def；bridge_client.py 用 asyncio.wait_for 包同步调用 | 桥接子进程 IPC 阻塞事件循环时，整个 API 卡死 | 🟡 中 |
| A3 | **响应信封不统一**：trade.py 的 positions/orders/deals 曾直接返回裸列表（已修复为 envelope_ok），但 reference.py/market.py 的 L2 也有同类问题 | 前端 _req 要求 {code:0,data}，裸列表导致界面空白 | 🔴 高 |
| A4 | **DB 表冗余**：5 张表完全无代码引用（broker_profiles/comparisons/llm_config/rebalance_orders/sync_state） | 迁移膨胀、维护负担 | 🟢 低 |
| A5 | **策略信号三处独立实现**：backtest.py(_signals)、strategy_runtime.py(_ma_signal等)、strategy_gen.py(on_bar) 各自实现 MA/MACD/RSI | 逻辑不一致风险、维护重复 | 🟡 中 |
| A6 | **tools/ 与 gateway/ 职责模糊**：algo/condition_order 是引擎但放 tools/；reconcile 在 gateway/ 和 tools/ 各有一份 | 新人难以定位模块 | 🟡 中 |
| A7 | **sync/__init__.py 606 行**：SyncEngine + WSManager 混在同一文件 | WS 管理与行情同步耦合 | 🟢 低 |

## 7. 全量重构方案

### 7.1 重构总则

| 原则 | 说明 |
|---|---|
| **零功能回退** | 重构不改变任何对外 API 契约（REST 端点 / MCP 工具 / WS 消息格式） |
| **渐进提交** | 每个重构批次独立 git commit，可单独回滚 |
| **测试先行** | 每个重构批次先补/改测试，再改代码 |
| **不新增功能** | 纯架构优化，功能增强放后续迭代 |

### 7.2 重构项清单

#### R1: main.py lifespan 拆分 [P0]

**目标**：main.py 从 655 行 → ~80 行（仅 FastAPI 构建 + include_router）

**方案**：
```
app/
  main.py              # ~80行：FastAPI 构建 + lifespan 调用
```
