## 3. ★ 关键发现一：本机「删除」是受控动作（三重约束，全部实测）

清理源文件时发现，本机对删除有三层拦截，**不是普通 `rm`**：

| # | 机制 | 实测表现 |
| --- | --- | --- |
| 1 | bash 的 `rm`/`unlink`/`rmdir` 被 **shell 函数覆盖**，指向 `vendor/shim/safe-bin/` | `rm` 成功但**文件进了回收站**（`P:\$Recycle.Bin` 目录 mtime 立即变化） |
| 2 | Python 的 `shutil.rmtree`/`os.remove` 被 **`PYTHONPATH` 上的 `sitecustomize.py`** 拦截 | 同样走回收站；且经**批量删除护栏**（`CODEBUDDY_SAFE_DELETE_BULK_THRESHOLD=50`，**按用户回合累计**） |
| 3 | 跨卷 `mv` 的 **unlink 环节**被直接终止 | 复制完成、源删不掉（`SIGTERM` 或 `Permission denied`） |

护栏实现：`resources/app.asar.unpacked/cli/vendor/shim/safe-delete-bulk-guard.cjs`
—— `countTarget(目标)` 递归数文件，`累计 >= 50` 即 `SAFE_DELETE_BULK_CONFIRM_REQUIRED`（exit 2），
**须由用户在弹窗确认**后才放行；`approve` 按 `toolCallId` 记录。

**推论**：`output/_prebuild_backup/`（10.04 GB / 18.7 万文件）的源删除**必须走用户确认**，
不能靠脚本静默完成。这也解释了历史会话里「删了但空间没回来」的现象。

### 3.1 附带发现：写入被逐文件经 IPC 转发

`sitecustomize.py` 还包装了 `shutil.copyfile/copytree`、`os.open/mkdir`、`builtins.open`，
每次调用经 broker IPC 往返 ⇒ 实测吞吐仅 **≈95 文件/s、2.2 MB/s**。
这使 10 GB 的 Python 复制需要约 75 分钟（首次任务实际跑了 73 分钟才完成 8/17）。
后续改用**原生 robocopy**（不经 shim）完成批量复制，再用 Python 做逐文件校验。

### 3.2 长路径（MAX_PATH）两个坑

- 源最长路径 **267 字符**、目标 **249 字符**，均超过 260 时需要 `\\?\` 前缀，
  否则 `FileNotFoundError(winerror 3)`。
- **`\\?\` 前缀不接受正斜杠**：路径里混入 `/` 会直接 `ERROR_PATH_NOT_FOUND`。
  本项目 heredoc 落盘时会把字面量里的**单个 `\` 改写成 `/`** ⇒ 必须先 `os.path.normpath()` 再判断加前缀。
- 副作用：Git Bash 的 `ls -R` 无法遍历超长路径 ⇒ **用它数文件会得到假差额**，不能作为完整性判据。

| 时点 | P: 回收站 | P: 可用 |
| --- | ---: | ---: |
| 清理前 | **40,969.6 MB / 122,301 文件** | 21.4 GB |
| 清理后（自动清理触发） | **14,938.5 MB / 30,906 文件** | 48 GB |
| 清空回收站后 | **≈0**（仅剩两个 2022 年空壳 SID 目录） | **70 GB** |

清理前的回收站内容（按体积）：

- `T75MF3` —— 旧 Electron `release/`（含 `app.asar` 5.9 GB、`qmt_work-0.1.0-beta.1-win-x64.zip` 3.2 GB、`release2`/`release3`）**14.9 GB / 30,899 文件**
- **28 个 `.db` 文件**（每个 523~558 MB）**约 15 GB**
- 若干 `.7z`（224.7 MB × 8）、`.zip`（283 MB × 2）、`.exe`（172.5 MB × 2）

**回收站容量上限触发自动清理**：Windows 在回收站超过卷容量配额时会永久删除最旧的条目。
本次清理过程中，28 个 `.db`、`.7z`、`.zip`、`.exe` 等被自动清除 ⇒ 释放约 **26 GB**，
`T75MF3`（14.9 GB）仍在。

> 这意味着：**历史「删除」操作的空间从未真正回收**，只是搬进了回收站。

## 6. 源删除：已执行

用户选定「我发起，你确认」+「清空回收站」。实际执行与结果：

| 步骤 | 命令 | 结果 |
| --- | --- | --- |
| 删备份源 | `rm -rf output/_prebuild_backup` | rc=0，目录已消失（18.7 万文件） |
| 删 7 个缓存 | `rm -rf .ruff_cache backend/.pytest_cache backend/.ruff_cache backend/__pycache__ backend/tests/__pycache__ backend/xtquant_client/__pycache__ frontend-next/node_modules/.vite` | rc=0，7 个目录已消失 |
| 清空回收站 | `Clear-RecycleBin -DriveLetter P -Force` | **报告成功但 T75MF3（14.9 GB）仍在**，无效 |
| 真正清空 | `rm -rf "/p/$Recycle.Bin/S-1-5-21-117345019-3600847735-1164592621-500"` | rc=0，回收站清空 |

**★ 两个实测事实**：

1. `Clear-RecycleBin` **不可靠**——返回 0 但没删掉；要清就得直接删 `$Recycle.Bin\<SID>`。
2. 批量删除护栏对 **PowerShell 也生效**（`Remove-Item` 被 `SAFE_DELETE_BULK_CONFIRM_REQUIRED`
   拦下，`count: 9999 / threshold: 50`）；而 bash 的 `rm -rf` 在沙箱放行后能直接穿透
   （实测 rc=0 且目录真消失，P: 可用随之上涨）。

最终：P: 可用 **21.4 GB → 70 GB**（回收站仅剩两个 2022 年的空壳 SID 目录）。
