## 〇、结论先行

**一句话判断：qmt_work 的"交易与运维纵深"已超过三款客户端，"行情分析与选股广度"则存在结构性缺口——缺的不是页面数量，而是支撑这些页面的两个地基：本地数据仓与统一指标/选股引擎。**

| 维度 | 结论 | 依据 |
|---|---|---|
| 交易执行 / 风控 / 审计 / 对账 | ✅ **显著领先** | 三款客户端不具备（它们只做"下单"，不做算法单/条件单/WAL/审计链/多账户网格） |
| 多券商接入 + MCP/Agent | ✅ **独家** | 三款客户端是封闭生态，无 MCP |
| 工作区/分屏/keep-alive | ✅ **领先** | `workspace.jsx` 的分屏树 + LRU keep-alive，TDX 的自定义版面反而不如灵活 |
| K 线/图表专业度 | ❌ **明显落后** | 无缩放、无画线、无叠加、无对数坐标（TDX 二十年前的标配） |
| 选股能力 | ❌ **结构性缺失** | 无通用选股器。只有板块榜/涨停扫描/轮动热力图三个"专项视图" |
| 指标/公式体系 | ❌ **双份实现且不可扩展** | 后端 19 个 Python 因子 + 前端 7 个 JS 指标，各写各的，用户无法自定义 |
| 数据底座 | ⚠️ **旁路缓存而非主数据源** | K 线缓存是"过期即回源"的 TTL 旁路，非 TDX 式的"本地数据仓 + 增量补齐" |
| 自选股/板块体系 | ⚠️ **弱** | localStorage 存代码数组，两处独立读写，无命名分组、无动态板块 |

**最重要的一个判断**：2026 年这三家的竞争焦点已经从"功能多"转向"**自然语言 × AI Agent × 交易闭环**"（东财妙想、问财 HithinkGPT、大智慧 AI 小慧）。
qmt_work 恰好持有它们都没有的资产——**真实券商通道 + 原生 MCP**。但要让 Agent 发挥价值，必须先有**选股器**这个"AI 的落地点"，而选股器又必须先有**本地全市场数据仓**。
因此本方案的推进顺序是：**数据仓 → 指标引擎 → 选股器 → AI 闭环**，这是一条有硬依赖关系的主链，不能打乱。

## 一、现状深度盘点

### 1.1 代码规模与分层

| 层 | 目录 | 文件数 | 行数 | 定位 |
|---|---|---|---|---|
| 路由/装配 | `backend/app/` | 46 | 8,014 | FastAPI 路由（30 个模块）+ 数据源抽象 + 中间件 |
| 领域网关 | `backend/gateway/` | 24 | 4,573 | 风控/审计/限流/告警/对账/WAL/行情总线/K线缓存 |
| 工具与引擎 | `backend/tools/` | 23 | 5,766 | 回测/因子/算法单/策略运行时/再平衡/MCP 工具实现 |
| 券商适配 | `backend/xtquant_client/` | 15 | 5,356 | 多版本 xtquant 兼容 + 桥接子进程 + 连接管理 |
| 推送同步 | `backend/sync/` | 1 | 597 | 订阅聚合 + WS 扇出 |
| 回测队列 | `backend/backtest/` | 1 | 227 | 任务编排（Semaphore(2)） |
| MCP | `backend/mcp_server/` | 1 | 88 | FastMCP 装配（11 组 tool 注册） |
| **后端合计** | | **~111** | **33,096** | |
| 前端 | `frontend/src/` | 63 | 12,707 | React 18 + Vite 5 + ECharts 5.5，**无路由/无状态库/无 UI 库** |

**分层是清晰且健康的**：路由（薄）→ gateway（领域服务）→ tools（引擎）→ xtquant_client（适配）。
对比三款客户端的 C++ 单体，qmt_work 的分层可维护性更好。**问题不在分层，而在层内的实现密度与重复。**

### 1.2 后端骨架与装配

- 单一 `APIRouter(prefix="/api/v1")`（`app/routes/__init__.py:33`）聚合 30 个子模块。
- 启动 `app_lifespan`（`app/main.py:174-487`）**顺序装配 22 个组件**：DB → 券商注册表 → K线缓存 → WAL → 券商桥 → 交易日历 → 风控 → 备份 → 广播 → 行情总线 → 同步引擎 → 批量 → 健康检查 → 涨停监控 → 算法引擎 → 条件单 → 订单看门狗 → 信号路由 → WAL 重放 → 对账 → 回测队列 → 模拟盘 → 策略运行时 → 行情同步 → 资金流采集。
- MCP 挂载 `/mcp`（`main.py:619`），与 REST 共享同一 `RiskManager` 实例。

**评价**：组件齐全度超过三款客户端（它们没有审计链/WAL/对账/风控引擎）。但 300 行顺序装配 = **隐式依赖**，任何一个组件初始化失败都会拖垮整体，且无法单独测试。

### 1.3 数据源与数据契约

| 能力 | 券商 xtquant | eltdx（通达信公开源） |
|---|---|---|
| 实时报价 | ✅ | ✅ |
| K 线 | ✅ | ✅ |
| 全市场股票列表 | ❌ 返回 None | ✅ |
| **分时** | ❌ | ✅ |
| **板块/成分股/板块K线** | ❌ | ✅ |
| **ETF 清单/资金流/股本/涨跌停价/搜索** | ❌ | ✅ |

`DataSourceManager`（`app/datasource/registry.py`）已实现：
- 熔断（阈值 3 / 冷却 30s / 单源超时 8s）
- **不静默回退**（`source="broker"` 返回空链，绝不悄悄换源）—— 这个设计原则非常正确，符合"零 mock"铁律
- 周期契约单点（`periods.py`）：未知周期**抛错而非静默降级**

**评价**：多源路由的工程质量高于多数开源项目。主要问题是**能力高度不对称**——eltdx 承担了板块/ETF/资金流/搜索/分时的全部供给，一旦它不可用，这些页面全部 503。

### 1.4 缓存与持久化现状

| 缓存 | 位置 | 设计 |
|---|---|---|
| 端点级内存 TTL | `routes/market.py:277-302` | 上限 512 → 淘汰到 480，硬 TTL 3600s |
| K 线 SQLite | `gateway/kline_cache.py:99` | 热表 `kline_cache` + 归档 `kline_archive`（按年路由），日线 TTL 6h / 日内 60s |
| 名称/行业表 | `eltdx_source.py:37-38` | 磁盘 JSON，**无 TTL** |
| 行情总线 | `gateway/quote_bus.py:21/73` | 内存 / Redis 双模，引用计数 |
| DB schema | `app/db.py` | **v15**，30+ 表，审计 hash 链，WAL 模式 |

**关键判断**：这些缓存全部是"**旁路加速**"性质——过期即回源，回源失败即报错。
而 TDX 的模式是"**本地数据仓**"——本地数据是**主数据源**，网络只负责增量补齐，断网也能看全部历史行情和做全市场选股。
**这是二者最本质的架构差异，也是后续一切能力（秒开、离线、全市场扫描、选股器）的分水岭。**

### 1.5 前端骨架与数据流

| 层 | 实现 | 评价 |
|---|---|---|
| 页面注册 | `pagesRegistry.jsx`，29 个页面 / 9 个分组，全 `React.lazy` | ✅ 良好，单一真相来源 |
| 工作区 | `store/workspace.jsx`（546 行），useReducer + 分屏树 + keep-alive（MAX_ALIVE=8） | ✅ **领先于 TDX 自定义版面** |
| 实时行情 | `lib/quoteHub.jsx`（280 行），模块级单例 + 引用计数 + 退订宽限 60s | ✅ 设计正确 |
| 系统事件 | `hooks/useSystemWS.js`（161 行），模块级单例 | ⚠️ 与 quoteHub **同 endpoint 却是第二条连接** |
| 请求层 | `api.js`（308 行），约 160 个具名方法，统一 15s 超时 + GET 重试 1 次 | ⚠️ 无类型、无缓存层 |
| 数据获取 | `hooks/useMarket.js`（155 行）统一 K线/基本面；但列表/表单约 30 个组件各自 `useState+useEffect` | ⚠️ 半统一 |

**评价**：骨架（注册/工作区/推送）设计水准高；**页面层是重灾区**——巨型组件、重复实现、硬编码遍地。

### 1.6 已具备的护城河（必须守住，不要在对标中丢失）

1. 真实券商通道 + 零 mock 原则（未连接返回 503 引导，绝不造假）
2. 多券商统一接入 + ABI 多运行时桥接（独家）
3. 原生 MCP（11 组 tool，Cursor/Claude 直连）
4. 工业级运维：审计 hash 链、WAL、对账、风控引擎、Prometheus
5. 多账户网格 + 算法单 + 条件单 + 信号路由

## 二、三款客户端的能力模型解构

### 2.1 通达信：本地数据 + 公式系统 + 自定义板块

通达信是**零售端事实标准**，其产品力来自三根支柱：

| 支柱 | 具体形态 |
|---|---|
| **本地数据优先** | 行情存本地 `.day/.dat` 二进制；"盘后数据下载"是一等公民功能；选股/排序/指标计算**全部基于本地数据**，断网可用、扫描 5000 只秒级返回 |
| **公式系统** | 公式管理器（Ctrl+F）四类公式：技术指标、条件选股、交易系统、五彩K线；类 C 的 DSL（`MA5:=MA(C,5); 放量:=V>REF(V,1)*1.5; CROSS(MA5,MA20) AND 放量;`）；用户可自定义、导入导出 `.tni/.tne`；**未来函数检测** |
| **板块体系** | 行业/概念/地域/自定义板块；**动态板块**（条件选股 + 定时自动刷新，成分股自动增减）；板块全景报表（`.400`，可切当日/3日/5日/20日，看涨停家数/5日涨幅/板块净流入）；细分行业可扩到 127 个 |

其余标配：条件选股器（Ctrl+T，支持"全部条件相与/相或"、剔除 ST/停牌、选股入板块）、条件预警系统（价格/涨跌幅/指标条件，点播+全推两模式）、多股同列（4/9/16）、多周期、画线工具、自定义版面、扩展数据、盘后复盘。

**核心启示**：TDX 的一切流畅度来自"本地数据仓"；一切可扩展性来自"公式 DSL"。**这两件事 qmt_work 都没有。**

### 2.2 大智慧：Level-2 深度 + 资金流指标 + 主题投资

| 支柱 | 具体形态 |
|---|---|
| **L2 全息盘口** | 逐笔成交、买卖队列、撤单流、大单追踪 |
| **资金流指标体系** | DDX（大单动向）/ DDY（涨跌动因）/ DDZ（大单差分）——把"资金流"做成**可排序、可筛选的标准化指标**，这是它最被认可的能力 |
| **主题投资 / 机构监控** | 主题库、机构席位、龙虎榜深度 |

2026 年新增：AI 诊股小程序、AI 小慧（舆情总结/公告提炼/关联因子）、**AI 活跃度**（基于 L2 全息盘口挖掘中长期大资金每日活跃度，柱形图）、全链预警数据库。

**核心启示**：资金流不是"看个数字"，而是要做成**一级指标**（可排序、可筛选、可入选股条件）。qmt_work 目前只有 15 只硬编码 watchlist 的快照。

### 2.3 东方财富：数据广度 + 社区 + AI 闭环

| 支柱 | 具体形态 |
|---|---|
| **数据广度** | 4000+ 金融数据库：财务/研报/公告/股东/融资融券/龙虎榜/北向资金/产业链图谱；Choice 终端 |
| **社区** | 股吧，日均发帖超百万（散户情绪风向标） |
| **AI 闭环** | 妙想大模型（2025-03 备案）：智能问答、**自然语言选股**（"筛选股息率高于 3% 且现金流稳定的银行股"）、AI 投研助理、盘口异动/资金流向监控；**选股→盯盘→下单同一生态闭环** |

**核心启示**：2026 年的终局是"**自然语言 → 结构化筛选 → 直达下单**"。东财靠自研大模型 + 4000+ 数据库 + 东财证券牌照实现闭环。

### 2.4 三者共同的五条产品范式（本方案的对标基准）

| # | 范式 | qmt_work 现状 | 差距 |
|---|---|---|---|
| **F1** | **本地数据仓 + 增量补齐**（离线可用、秒开、全市场扫描） | TTL 旁路缓存，过期即回源 | ❌ 根本性差异 |
| **F2** | **公式/指标 DSL**（用户可扩展、可导入导出、可入选股条件） | 硬编码双份实现，不可扩展 | ❌ 缺失 |
| **F3** | **条件选股器 + 动态板块**（全市场筛选、定时刷新、结果入板块） | 无通用选股器；自选股是 localStorage 数组 | ❌ 缺失 |
| **F4** | **专业图表交互**（缩放、画线、多股同列、多窗口联动、模板） | 仅静态 K线 + 分时；无缩放/画线/叠加 | ❌ 缺失 |
| **F5** | **资金流/盘口为一级指标**（分级资金流可排序筛选 + L2 深度） | 15 只硬编码 watchlist；无分级 | ⚠️ 弱 |

## 四、差距根因分析

五条根因，按"解释力"排序：

**根因 1｜缓存被当作加速手段，而非数据源。**
TDX 的本地数据仓是**主数据源**，网络是补齐通道；qmt_work 的 `KlineCache` 是**旁路加速**，网络是主源。这一个设计选择的差异，直接决定了：能否离线、能否秒开、能否全市场扫描、能否做选股器。**这是全部能力差距的总闸门。**

**根因 2｜指标与因子各写一份，缺少统一表达式层。**
后端用 Python 算因子（研究用），前端用 JS 算指标（渲染用），两套代码、两套语义、无法复用、用户不可扩展。TDX 用一套公式 DSL 同时供给"指标显示/条件选股/交易系统/五彩K线"四个消费场景——**一份定义，四处复用**。

**根因 3｜页面是"按后端端点切分"，而不是"按用户任务切分"。**
29 个页面基本一一对应后端 REST 端点（有 boards 页、etfs 页、rotation 页、limitup 页……），但缺少"选股""复盘""盯盘"这类**任务型**入口。TDX 的 Ctrl+T 选股器跨越了数据、指标、板块三个后端域，是一个任务型入口。

**根因 4｜实时推送只接了行情，未接业务事件。**
`useSystemWS` 事件总线已存在，但 12 处仍在轮询（`Backtest` 甚至 800ms）。业务状态变化（订单/回测/账户/算法单）尚未事件化。

**根因 5｜前端缺少设计系统与组件层，导致每个页面各自造轮子。**
CSS 变量只有 10 个、无 spacing/typography 体系、无共享 UI 组件层 → 5 份金额格式化、5 份涨跌色、4 份 ECharts 模板。这是"页面数量增长后必然腐化"的结构性原因。

## 五、重构优化方案

### 总体路线（有硬依赖，顺序不可打乱）

```
P0 本地数据仓  ──►  P1 统一指标引擎  ──►  P2 选股器 + 动态板块  ──►  P3 AI 选股闭环（MCP）
      │                                                                      
      └──► P4 图表专业度（缩放/画线/联动，可并行）                              
      └──► P5 前端工程化（可全程并行，越早做后续越省力）                        
      └──► P6 后端架构治理（可全程并行）
```

### P0 · 本地行情数据仓（对标 F1）— **最高优先级，其余皆依赖它**

**目标**：把行情数据从"网络主源 + 本地旁路缓存"翻转为"**本地主源 + 网络增量补齐**"，实现离线可用、秒开、全市场扫描。

| 步骤 | 落点 | 内容 |
|---|---|---|
| P0-1 | 新增 `backend/app/datasource/local_store.py` | 本地行情仓：按 `(code, period)` 组织的**列式分区存储**（推荐 Parquet，或 SQLite 分区表）。核心 API：`coverage(code, period) -> (first_dt, last_dt, row_count)`、`read(code, period, start, end)`、`upsert(code, period, bars)` |
| P0-2 | 扩展 `gateway/market_sync.py`（现 597 行） | 全市场增量同步器：① 全市场代码表 + 名称 + 行业 + 概念（落 `instruments` 表）；② 全市场日线增量（按 `coverage` 只拉缺口段）；③ 板块清单 + 成分股；④ 支撑盘后自动跑 + 手动触发 + 进度上报 |
| P0-3 | 改造读路径 `tools/__init__.py:25 fetch_kline_cached` | 语义从"TTL 过期即回源"改为"**本地优先 + 缺口补齐**"：`read(local) → 计算缺口 → 仅拉缺口 → upsert → 合并返回`。回源失败时若本地有数据则**降级返回本地并标注 `stale: true + as_of`**（诚实标注，不违反零 mock 原则） |
| P0-4 | 统一"陈旧度"契约 | 所有行情响应统一携带 `{ source, as_of, stale, coverage }` 四元信息，前端可显式展示数据新鲜度 |
| P0-5 | 归档冷热分层 | 复用现有 `kline_archive` 思路：近 2 年热数据 SQLite/内存映射，更早 Parquet 冷存 |

**验收**：
- 全市场（~5400 只）日线首次全量同步 < 15 min；此后每日增量 < 60 s。
- 断网状态下 K 线、板块榜、ETF 清单全部可用（标注 `stale`）。
- 全市场日线扫描（如"5 日均线上穿 20 日均线"）端到端 < 3 s。

**风险**：同步任务的频率与源站限流（eltdx 0.12s/并发 6）需做**限速友好的调度**（低峰期全量、盘中仅增量 + 按优先级分片）。

### P1 · 统一指标/公式引擎（对标 F2）

**目标**：消灭"后端 19 个 Python 因子 + 前端 7 个 JS 指标"的双份实现，提供一套**用户可扩展**的指标定义。

| 步骤 | 落点 | 内容 |
|---|---|---|
| P1-1 | 新增 `backend/app/indicators/` 包 | ① `dsl.py`：指标表达式定义（AST 或 TDX 公式语法子集，支持 `MA(C,5)`/`REF(V,1)`/`CROSS(a,b)` 等）；② `registry.py`：指标注册表（内置指标全部改为 DSL 声明，替换 `tools/factors.py` 的硬编码）；③ `engine.py`：向量化执行器（pandas/numpy）；④ `futurize.py`：**未来函数检测**（TDX 的核心安全特性——用了未来函数的公式在实盘会失效） |
| P1-2 | 新增 `GET/POST /market/indicator` 端点 | 输入 `(code, period, indicators[], params)` → 返回与 K 线对齐的指标序列。**指标计算收敛到后端单点**，前端只渲染 |
| P1-3 | 前端 `MarketData.jsx:85-180` 的 7 个 calc 函数 | 全部删除，改为调用 `/market/indicator`。同时修复 `calcKDJ`/`calcWR` 的 O(n×period) 嵌套循环性能问题 |
| P1-4 | 指标管理 UI（新页面 `Indicators.jsx`） | 指标列表/新建（DSL 编辑 + 语法提示）/参数调优/校验/导入导出/未来函数标记 |
| P1-5 | 落库 `user_indicators` 表 | 用户自定义指标持久化（DB schema v16） |

**关键设计决策**：指标计算在**后端**而非前端。
理由：① 保证前后端语义唯一；② 指标可被选股器（P2）与 AI（P3）复用——这是 TDX "一份公式四处复用"的精髓；③ 前端省掉 O(n×period) 计算，大周期不再卡顿。
代价：每次切指标需一次请求 → 用 K 线同生命周期的缓存（指标结果随 bars 一并缓存，key 含 `(code, period, adjust, indicator_sig)`）。

**验收**：内置 19 个因子全部 DSL 化，数值与旧实现**逐一回归一致**（新旧对比测试）；自定义公式可保存/复用/导出；未来函数可被检测并告警。

### P2 · 条件选股器 + 动态板块（对标 F3）— **本方案商业价值最高项**

**目标**：补齐三款客户端的标配、也是 AI 的落地点。

| 步骤 | 落点 | 内容 |
|---|---|---|
| P2-1 | 新增 `POST /market/screen` 端点 | 条件树（AND/OR 嵌套）→ 在本地数据仓上向量化执行。条件类型：① 行情（涨跌幅/振幅/换手/量比/成交额/市值/连板数）；② 技术指标（复用 P1 引擎的全部指标）；③ 基本面（PE/PB/ROE/营收增速，来自 `reference`）；④ 板块归属（行业/概念/自定义板块）。输出：TopN + 排序 + 可选返回明细列 |
| P2-2 | 条件构建器（新页面 `Screener.jsx`） | 可视化 AND/OR 条件树（对标 TDX "全部条件相与/相或"）+ 内置模板（均线多头、放量突破、超跌反弹、涨停梯队）+ 结果表格（复用 P5 的虚拟表格）+ 一键"存为板块" |
| P2-3 | **动态板块** | 选股条件可保存为板块并**定时自动刷新**（对标 TDX 动态板块）。落 `user_screens` 表 + `rationale` 记录（为什么这只票在板块里——可解释性） |
| P2-4 | 自选股体系升级 | 现状：localStorage 数组、2 处独立读写（`BottomDock.jsx:24,55,61` / `QuoteBoard.jsx:8,104`）。改为：后端 `watchlists` 表 + 前端统一 store。支持**多命名分组**、拖拽排序、批量增删、导入导出（兼容 TDX `.blk` 格式）、跨设备 |
| P2-5 | 预警前端联动 | 后端 `AlertEngine` 已完备，补齐前端：预警面板（触发历史 + 实时弹窗/提醒）+ "从选股结果一键建预警" |

**验收**：
- 全市场 5400 只 × 3 个技术条件 + 2 个基本面条件，端到端 < 3 s（依赖 P0）。
- 选股结果可一键存为板块/建预警/批量加入自选。
- 动态板块盘中按设定频率自动更新成分。

### P3 · AI 选股闭环（对标东财妙想 / 问财）— **差异化杀手锏**

**目标**：把"自然语言 → 结构化筛选 → 直达下单"做成 qmt_work 独有的闭环。这是三款客户端**做不到**的（东财靠自有牌照闭环，问财/财搭子不对接交易账户，而 qmt_work 有真实券商通道 + 外部 LLM 可直连的 MCP）。

| 步骤 | 落点 | 内容 |
|---|---|---|
| P3-1 | MCP tool `screen_stocks` | 把 P2 的选股器暴露为 MCP 工具——**这是 AI 的落地点**。LLM 可直接构造条件树调用 |
| P3-2 | 自然语言 → 条件树 | `POST /market/screen/parse`：LLM 把"股息率高于 3% 且现金流稳定的银行股"解析为结构化条件树，**返回条件树供用户确认/编辑后再执行**（不黑箱执行，符合零 mock/可解释原则） |
| P3-3 | 选股结果卡片 | 结果不仅在表格里，还生成"结论卡"：命中数量、行业分布、Top5 列表、条件命中度拆解 |
| P3-4 | 一键下单 | 选股结果 → 目标持仓（`target_portfolio` 已具备差量同步）→ 风控预检（`precheck`）→ 二次确认 → 执行。**闭环终点** |
| P3-5 | 决策留痕 | LLM 生成的条件树 + prompt 摘要写入审计链（`db.audit`），与既有审计体系打通 |

**关键原则**：AI 只做"**条件生成**"，不做"直接下单"。所有执行必须经 ① 用户确认条件树 ② 风控预检 ③ 二次确认。这与现有 `SignalRouter` 的三模式（live/dry-run/paused）设计一脉相承。

## 八、风险与约束

| 风险 | 说明 | 应对 |
|---|---|---|
| **源站限流** | P0 全市场同步受 eltdx 限流（0.12s/并发 6）约束；激进同步可能触发封禁 | 低峰期全量 + 盘中增量；分片优先级（先指数/成分股/自选，后长尾）；同步进度可观测 + 可中断 |
| **回测语义漂移** | P6-1 合并双内核可能改变既有回测数值 | **先锁一致性测试基线**（新旧内核同策略同数据对比报告），再动刀 |
| **零 mock 原则** | P0 的"降级返回本地陈旧数据"必须与造假划清界限 | 强制：所有降级响应必须携带 `stale: true` + `as_of` 时间戳 + `source`，前端显式展示"数据截至 X，未取得最新行情" |
| **AI 可解释性** | P3 若让 LLM 直接下单，风险不可控 | AI 只生成条件树 → 用户确认 → 风控预检 → 二次确认；条件树与 prompt 摘要入审计链 |
| **存储膨胀** | 全市场日线 + 分钟线本地化后体积增长 | 冷热分层（近 2 年热 / 更早 Parquet 冷存）；分钟线按需拉取不全量落盘；提供容量配额与清理策略 |
| **工作量** | 主线 P0→P3 约 12 周，加并行项合计 5-6 个月 | 严格按依赖顺序，避免"同时开工全部"；每阶段独立可交付、可验收 |
| **不要在对标中丢失护城河** | 对标的是"终端产品力"，不是要变成 TDX | 真实券商通道 + 零 mock + MCP + 审计/风控/对账，这五项在任何重构中都必须守住 |
