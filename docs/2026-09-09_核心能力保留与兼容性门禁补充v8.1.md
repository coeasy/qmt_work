# QMT Work 核心能力保留与兼容性门禁补充 V8.1

> 日期：2026-09-09  
> 仓库：`coeasy/qmt_work`  
> 基线：V8「整体架构与数据平台重构规划总纲」  
> 状态：**V8 强制附录**。后续所有重构 Phase、插件化、Connector/Data Plane、前端、桌面、打包与发布改造都必须同时满足本文件；若发生冲突，以“核心能力不回退 + 安全语义不降低”为硬约束。

---

# 1. 核心原则：重构只能换内部实现，不能丢平台能力

QMT Work 当前已经不是单一 QMT 包装器，而是同时提供 MCP、REST、WebSocket、多账户统一管理、交易执行、回测、风控、任务、通知、审计等能力的完整本地量化平台。

因此后续架构升级必须遵守：

> **Preserve Capability, Replace Coupling.**

也就是：

- 可以重构内部目录；
- 可以引入 AppContext / Ports / Adapters；
- 可以把 QMT 降为 Connector；
- 可以把行情改造成多 Provider Data Plane；
- 可以升级 Scheduler / Plugin Runtime；
- 可以重写某一模块内部实现；

但不能：

- 删除现有对外能力；
- 降低已有协议兼容性；
- 让原来可以完成的业务闭环失效；
- 以“解耦”为理由把功能暂时砍掉；
- 以“插件化”为理由把稳定能力变成未实现占位接口；
- 以“统一架构”为理由降低实时性、安全性或多账户能力。

正确方式是：

```text
旧能力
  ↓
先锁 Contract / Regression Gate
  ↓
建立新 Application Service / Port
  ↓
双轨迁移
  ↓
新实现达到同等或更强能力
  ↓
删除旧内部实现
```

而不是：

```text
先删旧实现
→ 再慢慢补功能
```

# 2. 一级不可回退能力清单

以下能力列为 **Tier-0 Core Capability Baseline**。

| 核心能力 | 当前用户价值 | 重构后要求 |
| --- | --- | --- |
| MCP 接口 | FastMCP Streamable HTTP，Cursor / Claude Desktop 等 MCP Client 可直连 | 保留 Streamable HTTP、工具发现、调用、错误语义与客户端兼容；内部改为调用统一 Application Service |
| REST API | FastAPI `/api/v1/*`，覆盖账户、行情、下单、回测、再平衡、风控、配置等 | 路径和核心请求/响应 Contract 原则上保持兼容；需要破坏性变化时走版本化/弃用期 |
| WebSocket 实时推送 | 行情、账户、订单、成交、Algo、Condition、连接状态、对账等实时事件 | 保留单上游订阅、多客户端扇出、事件重放/重连和有界背压 |
| 多账户网格 | 多券商/多账户统一资产、持仓、订单、成交看板 | 保留并增强；不能退回“单活跃账户”模型 |
| 批量交易 | 跨账户批量下单 / 批量撤单 | 保留；内部必须统一走 ExecutionService，不允许绕过 Risk/WAL/Audit |
| 批量运维 | 批量重连、连接状态统一管理 | 保留并迁入 ConnectionSupervisor |
| 多 Broker/多账户 | 多券商、多账户、多客户端版本 | 保留并扩展为多 Connector Platform |
| 行情/研究 | 行情、K线、指标、选股、因子、回测、策略研究 | 无 QMT 也必须继续可用，并由多行情源增强 |
| Paper/Dry Run | 模拟盘、dry_run、安全验证 | 保留，且与 live 共享策略/执行 Contract |
| 风控 | Mandatory Risk、额度、频率、价格偏离、标的限制等 | 保留且加强，任何入口都不能绕过 |
| WAL / Audit / Reconcile | 委托可追踪、崩溃恢复、对账核销、审计 | 保留且升级为 Execution Core 基础设施 |
| API Key / Scope / Rate Limit | 外部系统安全访问 REST/MCP | 保留，多客户端/插件化不能降低安全边界 |

# 3. MCP：必须作为一等入口保留

当前 MCP 不是附属功能，而是平台的一等交互入口。

重构后目标：

```text
Cursor / Claude Desktop / Other MCP Client
                 ↓
        FastMCP Streamable HTTP
                 ↓
             MCP Adapter
                 ↓
         Application Services
        / Capability Registry
                 ↓
    Data / Research / Execution Core
```

## 3.1 必须保留

- Streamable HTTP Transport；
- MCP 工具发现；
- 参数 Schema；
- 可读工具调用；
- 交易/写操作的安全确认边界；
- 错误返回可解释性；
- MCP Server 生命周期与 FastAPI 生命周期一致；
- Cursor、Claude Desktop 等标准 MCP Client 可接入。

## 3.2 MCP 不再拥有独立业务实现

未来禁止：

```text
MCP Tool
  ↓
直接 Broker / DB / gateway.place_order
```

统一改为：

```text
MCP Tool
  ↓
Application Command / Query
  ↓
ExecutionService / MarketService / ResearchService
```

REST 与 MCP 只是 Adapter 不同，业务语义必须相同。

## 3.3 MCP 兼容性门禁

CI 至少增加：

```text
MCP server boot smoke
MCP tool list contract
read-only tool invocation contract
trade tool permission contract
MCP ↔ REST semantic parity
Streamable HTTP handshake smoke
```

# 4. REST API：保留 `/api/v1/*` 作为稳定平台接口

FastAPI REST API 是前端、外部程序和自动化工具的重要契约。

重构后仍保留：

```text
/api/v1/account/*
/api/v1/market/*
/api/v1/trade/*
/api/v1/backtest/*
/api/v1/rebalance/*
/api/v1/target-portfolio/*
/api/v1/algo/*
/api/v1/signal/*
/api/v1/config/*
/api/v1/runtime/*
/api/v1/brokers/*
...
```

## 4.1 API 兼容原则

内部可以从：

```text
route → state → gateway
```

迁移成：

```text
route
  ↓
Application Service
  ↓
Port
  ↓
Adapter
```

但外部 REST Contract 不应因此被随意破坏。

需要破坏性改动时：

```text
旧 Contract
  ↓
Deprecated
  ↓
兼容窗口
  ↓
新版本 API
```

禁止一次提交直接删除主接口。

## 4.2 必须继续保留的网关能力

- OpenAPI；
- API Key；
- scope；
- rate limit；
- request id；
- 统一响应 Envelope；
- 审计；
- 健康检查；
- `/live`；
- `/ready`；
- metrics。

# 5. WebSocket：保留“上游一次订阅 + 多客户端扇出”

这是当前架构非常有价值的能力，不能在 Data Plane 重构中退化成“每个浏览器连接都向行情源单独订阅”。

目标保持：

```text
Market Provider / Broker Quote Stream
                ↓
          Subscription Manager
                ↓
             QuoteBus
                ↓
         Event / WS Manager
       ┌────────┼────────┐
       ▼        ▼        ▼
   Client A  Client B  Client C
```

## 5.1 引用计数语义必须保留

同一标的多个消费者：

```text
consumer A subscribe 600519
consumer B subscribe 600519
```

上游只应该建立一次真实订阅。

最后一个消费者退出后才释放上游订阅。

## 5.2 多 Provider 后不能破坏该机制

未来变成：

```text
QuoteSubscriptionKey = provider + market + instrument + channel
```

而不是简单按 `code`。

这样允许：

- QMT 实时流；
- 其他 Provider 实时流；
- 多账户共用同一行情；
- 多前端窗口共享；
- 多进程通过 Redis QuoteBus 共享。

## 5.3 WS 必须保留的事件类型

至少包括：

```text
quote / quotes
account
order
trade/deal
broker.connected
broker.disconnected
algo
condition
risk
reconcile
system
scheduler/job progress
```

允许增加版本化 Event Envelope，但不能让已存在核心事件在迁移后消失。

## 5.4 实时性门禁

增加：

```text
N clients -> 1 upstream subscription
unsubscribe reference count
fan-out integrity
slow consumer isolation
bounded queue/backpressure
reconnect replay
provider disconnect/recover
```

# 6. 多账户网格：必须从“页面功能”提升为 Domain Capability

当前多账户网格已经提供：

```text
/account/grid
/account/batch/order
/account/batch/cancel
/account/batch/reconnect
```

以及前端跨券商/跨账户统一看板。

这些不能因为后续改成 Connector Platform 而消失。

相反，应升级成正式的：

```text
AccountAggregationService
PortfolioAggregationService
BatchExecutionService
ConnectionSupervisor
```

## 6.1 多账户统一看板

必须继续支持：

- 所有已配置账户；
- 已连接/未连接状态；
- 账户资产；
- 可用资金；
- 市值；
- 持仓数量；
- 委托数量；
- 成交数量；
- 每账户错误状态；
- 跨账户总资产；
- 跨账户持仓矩阵。

## 6.2 不能退回 activeBroker-only

`active connection` 可以继续用于某些默认操作，但不能成为多账户 Core 的唯一上下文。

未来应明确：

```text
Default Connection != Only Connection
```

所有 Account/Portfolio Aggregation 都必须能跨 Connector 工作。

## 6.3 批量下单保留，但安全主链重写

保留用户能力：

```text
多账户逐笔订单
多账户广播订单
批量确认
逐账户结果
部分成功/部分失败
```

但内部必须从当前各自调用方式迁移到：

```text
BatchOrderCommand
      ↓
BatchExecutionService
      ↓
for each OrderIntent
      ↓
ExecutionService
      ↓
Risk / Pricing / Permission / Idempotency / WAL / Audit
      ↓
ExecutionPort
```

因此：

> **“保留批量下单”不等于“保留现在的直接 gateway.place_order 或固定假价格风控”。**

能力必须保留，安全问题必须修复。

## 6.4 批量撤单

同样统一：

```text
BatchCancelCommand
  ↓
ExecutionService.cancel(...)
  ↓
Connector
```

保留逐账户结果和部分失败语义。

## 6.5 批量重连

迁移到：

```text
ConnectionSupervisor.reconnect_many()
```

需要：

- 并发上限；
- timeout；
- per-connector runtime lock；
- 逐连接状态；
- 不因一个连接失败击穿整批；
- WS 实时反馈。

| Capability | Phase 前 | Phase 后 | Gate |
| --- | --- | --- | --- |
| REST boot | pass | 必须 pass | API smoke |
| OpenAPI | pass | 必须 pass | schema diff |
| MCP Streamable HTTP | pass | 必须 pass | MCP smoke |
| MCP tool list | pass | 必须 pass | contract snapshot |
| WS connect | pass | 必须 pass | WS smoke |
| quote fanout | pass | 必须 pass | subscription test |
| multi-account grid | pass | 必须 pass | REST + UI contract |
| batch order | pass | 必须 pass，且安全语义增强 | Execution contract |
| batch cancel | pass | 必须 pass | Execution contract |

# 11. API / MCP / WS 三入口统一业务语义

长期目标不是维护三套系统，而是：

```text
                   Application Layer
                / Command + Query Bus
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
      REST              MCP              WS
  Request/Command    Tool Adapter      Event Adapter
```

其中：

- REST：主要承担同步 Command / Query；
- MCP：Agent/AI Client 适配；
- WS：Server Push / Event Stream；
- 三者共用 Canonical Model、Permission、Execution 和 Data Service。

这样既保留现有入口，也降低后续语义漂移。

# 12. 前端不能因为 Data-First 改造而丢失多账户体验

V8 提出的 Platform-First 是正确的，但需要明确：

```text
PlatformProvider
 ├── DataProvider
 ├── CapabilityProvider
 ├── QuoteProvider
 ├── TradingConnectionProvider
 ├── MultiAccountProvider
 ├── SchedulerProvider
 └── WorkspaceProvider
```

`TradingConnectionProvider` 可为空，支持纯研究模式；

但一旦存在多个交易连接：

```text
MultiAccountProvider
```

必须同时支持多个，不应重新退化成只有 `activeId` 的单连接页面模型。

主界面最终至少显示：

```text
数据源状态
历史数据同步状态
交易连接数
已连接账户数
总资产摘要（有权限时）
任务状态
系统健康
```

# 16. 最终兼容性验收场景

## 场景 A：MCP Client

```text
启动 QMT Work
→ Cursor / Claude Desktop 连接 MCP Streamable HTTP
→ 获取工具列表
→ 查询行情/账户/研究能力
→ 写操作正确受 Permission/Risk 控制
```

成功。

## 场景 B：REST Client

旧有 `/api/v1/*` 主要 Contract 在重构后继续可用；发生升级的接口有清晰版本/弃用策略。

## 场景 C：三个前端窗口同时看同一股票

```text
3 clients subscribe 600519
→ 上游行情订阅 1 次
→ QuoteBus fan-out 3 份
→ 退出 2 个仍保持订阅
→ 最后 1 个退出才真正退订
```

成功。

## 场景 D：多账户

```text
QMT Account A
PTrade Account B
Other Account C
      ↓
/account/grid
      ↓
统一资产/持仓矩阵
```

成功。

## 场景 E：跨 Connector 批量下单

```text
Batch Command
→ 3 OrderIntent
→ 每一笔独立 Pricing/Risk/Permission/Idempotency/WAL/Audit
→ 不同 ExecutionPort
→ 聚合结果
```

成功。

## 场景 F：没有交易连接

MCP、REST、WS、行情、数据同步、选股、因子、回测、任务中心仍正常；只有真实账户/交易 Capability 显示 unavailable。

# 17. 最终硬约束

后续任何重构都必须同时满足：

1. **核心能力不减少。**
2. **外部 Contract 不静默破坏。**
3. **交易安全不降低。**
4. **多账户不能退回单账户。**
5. **实时行情不能退回每客户端重复订阅。**
6. **MCP / REST / WS 都必须继续作为平台一等接口。**
7. **QMT 解耦是解除依赖，不是删除 QMT 深度能力。**
8. **插件化是增加扩展性，不是把 Core 功能掏空。**
9. **新架构必须覆盖旧业务闭环后，旧实现才能删除。**
10. **每一项迁移都必须配对应 regression gate。**

---

# 18. 一句话原则

> **QMT Work 的重构目标不是“做一个更干净但功能更少的新系统”，而是在保留并锁死 MCP、REST、WebSocket、多账户、多连接、批量交易、研究、风控与审计等现有核心能力的前提下，把底层升级成可插拔、多行情源、多交易 Connector、可持续演进的平台架构。**
