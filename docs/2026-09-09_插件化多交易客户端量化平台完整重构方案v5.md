# QMT Work 插件化多交易客户端量化平台完整重构方案 V5

> 日期：2026-09-09  
> 仓库：`coeasy/qmt_work`  
> 基线：`main`，在 V4“多交易客户端平台”方案基础上继续演进  
> 目标：将 QMT Work 从“支持多交易客户端的模块化单体”升级为“内核稳定、能力可插拔、运行时可隔离、权限可治理、可独立安装/升级/回滚”的插件化量化交易平台。

---

# 1. 最终结论

## 1.1 后续可以插件化，而且应该现在就把插件边界设计进去

当前项目已经具备多处插件化雏形：

- `xtquant_client.registry` 已经有 Broker/Connector Profile、能力声明和热插拔档案；
- `datasource.registry.DataSourceManager` 已经用 `plugins: name -> DataSource` 管理补充数据源，并具备路由、超时、熔断与自动回退；
- `app.capabilities` 已经形成 REST 能力自描述和风险分级；
- `mcp_server.auto_expose` 已经根据 Capability Registry 自动生成只读 MCP Tool；
- `frontend/src/pagesRegistry.jsx` 已经是页面、菜单、命令面板的单一注册源；
- Strategy Market 已经具备 bundle/import/export/install 的产品雏形；
- QMT Runtime 的 in-process / bridge 已经证明“能力通过独立运行时承载”在工程上可行。

因此插件化并不是从零开始。

但这些扩展点目前是**各自独立的局部注册机制**，还没有统一为平台级 Plugin Runtime：

```text
Broker Registry       一套
DataSource plugins    一套
REST Capability       一套
MCP auto expose       一套
Frontend pages        一套
Strategy Market       一套
PyInstaller hidden imports 又一套
```

如果继续分别扩展，未来 5～10 个交易客户端、多个行情源、策略/指标/通知/UI 扩展加入后，会重新形成大量源码级耦合。

因此 V5 的核心目标是：

> **把现有各类“注册表”统一收敛到 Plugin Platform，但不把资金安全边界也做成可任意替换的插件。**

# 2. 插件化不是“所有东西都可替换”

量化交易平台与普通 IDE/内容应用不同，必须区分：

## 2.1 不可插件化替换的 Trusted Core

以下能力必须属于平台内核，第三方插件不能绕过、替换或关闭：

```text
Canonical Trading Model
ExecutionService 主链
基础 Risk Gate
Execution Mode (paused/paper/dry/live)
Idempotency
WAL
Reconcile
Audit
Permission / Identity
Plugin Permission Enforcement
Secret Store
Runtime Supervisor
Critical Event Journal
```

特别是：

```text
插件不能直接 Broker.place_order
插件不能直接访问真实券商 SDK 绕过 ExecutionService
插件不能通过自定义 Risk Plugin 关闭基础风控
插件不能直接改 WAL / Audit
```

插件只能提交：

```text
OrderIntent
```

然后由内核执行：

```text
Plugin / UI / REST / MCP / Strategy
               │
               ▼
           OrderIntent
               │
               ▼
        ExecutionService
               │
       Validation / Pricing
               │
             Risk
               │
      Mode / Permission / TOTP
               │
       Idempotency / WAL
               │
               ▼
         ExecutionPort
               │
               ▼
          Connector Plugin
```

这条链是 V5 的最高优先级架构红线。

# 3. 插件类型重新分类

建议不要只有一个模糊的 `Plugin` 概念，而是定义标准 Extension Kind。

## 3.1 Connector Plugin

用于接入交易客户端、券商 SDK 或远程交易服务：

```text
QMT / XTQuant
PTrade
同花顺量化
掘金 / GM
REST Broker
FIX Gateway
自研交易服务
```

可实现：

```text
ExecutionPort
OrderQueryPort
AccountPort
PositionPort
QuotePort
HistoryPort
ReferenceDataPort
EventStreamPort
```

QMT 最终应成为平台的第一个参考 Connector，而不是 Core 的特殊分支。

## 3.2 DataSource Plugin

用于：

```text
行情
K线
财务
板块
资讯
基本面
另类数据
```

当前 `DataSourceManager._plugins` 是这个方向最成熟的雏形，后续只需要从“进程内对象注册”升级成“Plugin Registry + Runtime + Capability”。

## 3.3 Strategy Plugin

策略只负责：

```text
Market/Event Input
        ↓
Decision
        ↓
Signal / OrderIntent
```

不得拥有 Broker 原始交易对象。

当前 Strategy Market 的“直接写 QMT mpython 目录”应逐步降级为 **QMT Exporter**，平台原生策略插件不应与某个交易客户端绑定。

## 3.4 Indicator / Factor / Research Plugin

包括：

```text
Indicator
Factor
Screening operator
Formula function
Research model
Backtest metric
Report exporter
```

这是最适合优先开放给第三方的低风险插件类型。

## 3.5 Algo Plugin

TWAP/VWAP/POV/Iceberg 等可扩展。

但是 Algo Plugin 只能产生子 `OrderIntent`：

```text
Parent Intent
    ↓
Algo Plugin
    ↓
Child Intents
    ↓
ExecutionService
```

不能直接向 Connector 下单。

## 3.6 Risk Extension Plugin

允许增加更严格的风控：

```text
Core Mandatory Risk
        AND
Risk Extension A
        AND
Risk Extension B
```

禁止：

```text
plugin override Core Risk = allow
```

插件只能“额外拒绝/收紧”，不能放宽基础门禁。

## 3.7 Notification / Integration Plugin

包括：

```text
钉钉
企微
飞书
邮件
Slack
Webhook
消息队列
数据导出
```

## 3.8 Automation Plugin

订阅平台 Event，产生动作/Intent：

```text
Event → Rule → Command/Intent
```

同样不得绕开命令总线和 ExecutionService。

## 3.9 MCP / Agent Extension

可以增加 Agent 的查询和分析能力。

默认：

```text
Read Capability → 可自动注册
Write Capability → 必须显式声明权限
Trade Capability → 必须人工/策略授权 + ExecutionService
```

继续保留当前“只自动暴露 GET/低风险能力”的安全原则。

## 3.10 UI Extension

用于增加：

```text
页面
菜单项
命令
状态栏组件
详情面板
设置面板
```

但 UI 插件需要特别区分可信级别，不能简单把第三方 JS 注入现有 React 同源上下文。

# 4. 插件信任分级

建议正式引入 Trust Tier。

## Tier 0：Core

平台内核，随主程序发布。

## Tier 1：Built-in First-party Plugin

官方内置插件：

```text
qmt-connector
builtin-market-data
builtin-indicators
builtin-notifier
```

它们使用 Plugin SDK 和 Manifest，但可以随 Core 打包。

这样可以先完成架构统一，不必第一天就把 QMT 从安装包拆出去。

## Tier 2：Signed First-party / Trusted Partner Plugin

独立安装和升级，经过签名验证；默认独立进程，可按白名单启用更高权限。

## Tier 3：Third-party Plugin

默认独立 Runtime，最小权限，只能通过 Plugin Host API 访问平台能力。

## Tier 4：Untrusted User Code

任意 Python/JS 用户代码不能因为“放到子进程”就宣称安全。

必须明确：

> **普通 Python 子进程只是故障隔离和依赖隔离，不是安全沙箱。**

真正运行不可信代码需要额外 OS 安全边界，例如：

```text
Windows restricted token / AppContainer / Job Object
独立低权限用户
容器 / VM
远程 Worker
```

在没有实现真正 OS Sandbox 前，平台不应把任意第三方 Python 标记为“安全沙箱插件”。

# 6. Plugin Manifest 作为插件 SSOT

所有插件必须有声明式 Manifest，禁止靠扫描 Python 类猜能力。

建议：

```yaml
schema_version: 1
id: qmt.connector.xtquant
name: QMT XTQuant Connector
version: 1.0.0
publisher: qmt-work
kind: connector

host_api: ">=1.0,<2.0"
plugin_sdk: ">=1.0,<2.0"

platforms:
  - windows-x64

runtime:
  type: python-subprocess
  python_abis: [cp38, cp39, cp310, cp311, cp312]

entrypoints:
  lifecycle: qmt_plugin.lifecycle:create
  execution: qmt_plugin.execution:create
  account: qmt_plugin.account:create
  quote: qmt_plugin.market:create

capabilities:
  - execution.submit
  - execution.cancel
  - account.read
  - position.read
  - market.quote
  - market.history

permissions:
  - platform.account.read
  - platform.trade.intent
  - filesystem.client_path
  - process.vendor_client.inspect

config_schema: config.schema.json

ui:
  settings_schema: settings.schema.json

artifacts:
  sha256: "..."
  signature: "..."
```

Core 启动和安装时首先验证 Manifest，不 import 插件实现来判断兼容性。

# 7. Plugin SDK 必须独立且稳定

新增：

```text
sdk/
  python/qmt_work_sdk/
  js/qmt-work-ui-sdk/
```

第三方插件只允许依赖 SDK：

```python
from qmt_work_sdk import QuotePort, PluginContext
```

禁止：

```python
from core.state import state
from app.main import app
from gateway.risk import ...
from xtquant_client.manager import ...
```

CI 架构门禁：

```text
external plugin importing backend internal package = FAIL
core importing concrete external plugin = FAIL
```

Plugin SDK 要独立版本化，并建立兼容矩阵：

```text
Host API
Plugin SDK
Canonical Model Schema
RPC Protocol
UI Contribution Protocol
```

# 8. 插件运行时：默认 out-of-process

第三方插件默认：

```text
Core
  │
  │ Local RPC
  ▼
Plugin Host
  │
  ▼
Plugin Runtime
```

运行模式：

```text
BuiltinInProcessRuntime
PythonSubprocessRuntime
NodeSubprocessRuntime
NativeProcessRuntime
HttpRemoteRuntime
```

只有 Tier 0 / Tier 1 才允许默认进程内加载。

## 8.1 为什么不让所有 Python 插件 import 到 Core

否则：

- 一个插件依赖冲突可以拖垮 FastAPI；
- 插件升级会污染主 Python 环境；
- Native DLL 冲突不可控；
- 任一 crash 可导致真实交易主进程退出；
- PyInstaller 必须预知所有 hidden imports；
- 无法真正独立安装/卸载。

因此外部插件应拥有自己的依赖环境。

# 10. RPC 协议

建议定义稳定的 Plugin Protocol：

```text
Hello
Manifest
Capabilities
Configure
Start
Stop
Health
Invoke
Subscribe
Event
Ack
```

所有请求带：

```text
request_id
plugin_id
protocol_version
deadline
trace_id
permission_context
```

第一阶段可以使用本地 JSON-RPC / framed stdio 或 Named Pipe；高频行情逐步切换成批量帧。

禁止每个 tick 做大量细粒度 RPC：

```text
Quote Plugin
   ↓ batch 20~100ms
QuoteBus
   ↓
Subscribers
```

必须有：

```text
backpressure
queue limit
batching
drop/coalesce policy
metrics
```

交易回报则不能简单丢弃，应进入关键事件链路。

# 11. Capability Registry 统一升级

当前 `app.capabilities` 已经是很好的基础，但它现在主要从 REST Route 反向推导能力。

V5 目标改为：

```text
Capability Registry = 平台能力 SSOT
```

能力来源：

```text
Core Application
Connector Plugin
DataSource Plugin
Research Plugin
Integration Plugin
```

然后由 Adapter 消费：

```text
Capability Registry
      ├── REST exposure
      ├── MCP exposure
      ├── UI visibility
      ├── Permission policy
      ├── Command Palette
      └── Diagnostics
```

而不是：

```text
REST Route
   ↓ scan
Capability
```

REST 只是 Capability 的一种 Adapter。




# 14. 插件配置、Secret 和 Storage

## 14.1 Config Schema

插件配置用 JSON Schema：

```text
manifest
   ↓
config_schema
   ↓
Frontend Dynamic Form
```

不再为每个 Connector 手写配置页面。

## 14.2 Secret

例如：

```text
API Token
Broker Password
Webhook Secret
```

Manifest 只声明字段，不保存值。

Secret 统一进入：

```text
SecretStore
```

插件通过受控 API 获取被授权 Secret。

## 14.3 Storage

第三方插件不应直接拿平台 SQLite 连接。

提供：

```text
PluginStorage
  namespace = plugin_id
```

或者插件自己的独立 SQLite：

```text
userData/plugin-data/<plugin_id>/plugin.db
```

这样卸载、备份、迁移、数据归属都更清楚。

# 16. Frontend Plugin Platform

当前 `pagesRegistry.jsx` 是很好的单一真相源，但仍是编译期静态注册。

建议升级为：

```text
ContributionRegistry
  ├── pages
  ├── menus
  ├── commands
  ├── statusWidgets
  ├── settingsPanels
  └── detailPanels
```

Core 页面也通过 ContributionRegistry 注册，这样官方与插件使用同一模型。

## 16.1 不建议直接加载任意第三方 React bundle 到主页面

原因：

如果第三方 JS 与主应用同 Origin 执行，它可以读取大量前端上下文；即使 Electron `nodeIntegration=false`，也不能把同源任意 JS 当安全插件。

因此 UI 分三级：

### A. Declarative UI Plugin（默认）

Manifest 声明：

```text
form
table
chart
metric
command
settings
```

Core 渲染标准组件。

这是第三方默认 UI 扩展方式。

### B. Isolated Web UI

插件页面运行在隔离 iframe / 独立 Origin，通过受控 Message Bridge 获取数据。

### C. Trusted React Extension

仅签名官方/合作插件允许编译或动态加载 React 扩展。

# 20. Build / Packaging 必须同步重构

当前 PyInstaller 通过大量 `hidden-import` 静态收集模块，这适合内置功能，不适合真正的运行时插件。

V5 建议拆成：

```text
Core Artifact
Plugin Artifact
Runtime Pack
Desktop Artifact
```

最终构建：

```text
Core Source
   ↓
locked Python env
   ↓
Core PyInstaller
   ↓
qmt-work-core

Plugin Source
   ↓
plugin contract tests
   ↓
qmtpkg

Runtime Packs
   ↓
cp38/cp39/... or vendor runtime

Frontend
   ↓
Core UI

Electron Builder
   ↓
Base Desktop Package
```

标准客户端只携带：

```text
Core + 必需 Built-in Plugins
```

# 30. Plugin API 与 REST/MCP 的关系

```text
      ↓
```

- 生命周期统一；
- 插件进程隔离可保持；
- 不需要运行时修改 FastAPI Python import 图；
- 插件关闭时端点可明确返回 unavailable。

官方 Built-in Plugin 可以有原生路由，但第三方默认走 Proxy。

# 31. 三轮方案检查

本 V5 在落盘前按三个角度重新审查。

## 第一轮：架构/扩展点检查

检查：

```text
Broker Registry

Capability Registry

Strategy Market
Frontend Page Registry
QMT Bridge Runtime
```

发现：

1. 项目已经有足够插件化基础，不需要引入完全独立的新体系；
2. 但现有注册表各自为政，需要统一为 Plugin Platform；
3. V4 Connector Platform 应成为 Plugin Platform 的一个子域，而不是另一套平行系统；
4. `BrokerAdapter` 拆 Port、Canonical Model、ExecutionService 仍然必须先做；
5. QMT 应先成为 Built-in Connector Plugin，再验证第二个独立 Connector。

### 第一轮修正

取消“每类插件单独造一套 Manager”的方案，统一：

```text

Capability Registry

```

各类型只提供不同 Extension Contract。

## 第二轮：交易安全/生命周期检查

检查：

```text
Execution path
Auth/Scope
Bootstrap
Shutdown
Global state
Bridge process lifecycle
MCP write boundary
```

发现：

1. 插件化会显著扩大真实交易攻击面；
2. localhost 信任不能被插件继承为“本地进程天然可信”；
3. 插件不能拿 Broker 原始对象；
4. Plugin Runtime 必须被 Supervisor 管理，否则 shutdown/reconnect 会继续碎片化；
5. Python 子进程不能被错误宣传成安全沙箱；
6. 插件风控只能收紧，不能覆盖 Mandatory Risk；
7. UI 插件任意 JS 不能默认与主应用同源执行。

### 第二轮修正

```text

Storage Namespace

Declarative UI / Isolated UI

```

检查：

```text
PyInstaller hidden imports
Electron package
Build Client
Release workflow
Frontend static lazy imports
Tests / capability drift gate
current main CI
```

发现：

1. 当前静态 PyInstaller 不能作为外部插件安装机制；
2. Core 与 Plugin 必须分开 Artifact；
3. Frontend 当前页面注册是静态编译期，第三方 UI 需要 Contribution Protocol；
4. Build Client / Release 应最终复用同一构建工作流；
5. 插件需要自己的 Contract Test Kit；
6. 当前 `main` 仍存在真实 CI/Build Client 红灯，不能在红色基线上大规模搬架构。

### 第三轮修正

最终实施顺序中增加 Phase 0，并把打包演进拆成：

```text

Desktop Package
```

# 37. 不建议做的事情

## 不要把整个 Core 改成插件

交易安全核心需要稳定边界。

## 不要现在拆微服务

Plugin Process 已经提供足够的依赖/故障隔离。

## 不要让插件直接修改 FastAPI 全局 Router

```text
permissions
signature
rollback
UI
```

## 不要把“子进程”当安全沙箱

默认 Declarative UI 或隔离页面。

## 不要让插件自由 pip install 到 Core

每插件独立 Runtime。

## 不要让 Risk Plugin 覆盖 Mandatory Risk

只能增加更严格约束。

# 41. 最终结论

QMT Work 后续**非常适合扩展成插件化平台**，而且 Connector、DataSource、Capability、MCP、Page Registry、Bridge Runtime 已经提供了良好的演进基础。

但正确目标不是：

> “任何 Python 文件都可以装进来运行”。

而是：

> **稳定 Core + 标准 SDK + Capability Ports + Manifest + 独立 Runtime + 最小权限 + 可审计生命周期 + 独立 Artifact + 原子升级回滚。**

V5 与 V4 不冲突：

```text
V4 Multi-Client Connector Architecture
              ↓
V5 Unified Plugin Platform
```

Connector 只是 Plugin Platform 中安全要求最高的一类插件。

因此后续所有架构重构，应以 V5 为长期总架构，以 V4 的 Canonical Model / Ports / ExecutionService 为第一阶段落地基础，而不是继续围绕 QMT 特例追加条件分支。
