## 1. P0-1：`routes/` 直写 SQL 收敛

**问题（可证）**：`app/routes/*.py` 里直接拼 SQL，绕过 `app/services` 层 ——
路由既做参数校验又做数据访问，SQL 无法被单测覆盖、无法被复用、改表结构要全仓 grep。

**动作**

1. 新增 5 个仓储模块：`app/services/{alerts,apikeys,audit,backtest,account}_store.py`。
   - `apikeys_store` **刻意只取需要的列**，用 `substr(key_hash,1,8) AS key_prefix`
     —— 绝不把完整 `key_hash` 返回给路由层（`SELECT *` 会把将来新增的敏感列一并带出）。
   - `alerts_store.delete_rules()` 对空 `ids` 早退，否则会拼出 `IN ()` 语法错误。
2. 两处**非 `ctx.db.` 形态**的漏网也被收敛（首轮 grep 只查了 `ctx.db.`）：
   - `market.py::dataset_snapshots` 的 `get_db().query(...)` → `DatasetSnapshotStore.list_recent()`；
   - `config.py::_count_cold_rows` 的 `sqlite3.connect(...)` → `cold_store.count_rows_readonly()`。
3. 路由内 `ctx.db.query("SELECT 1")`（探活）**下沉为** `core/db.py::DB.ping()`
   —— 否则裸 SQL 字面量会撞新门禁。
4. `check_execution_architecture.py` 新增 **Gate 2**：AST 扫描 `backend/app/routes/**/*.py`，
   拦三类：`ctx.db.{query,query_one,execute,executemany,executemany_in_txn}`、
   `sqlite3.connect(...)`、**裸 SQL 字面量**。
   - receiver 用 `_is_db_receiver()` 判定（`db`/`conn`/`cur`/`cursor`、`.db` 后缀、`get_db(`）；
   - **不拦** `insert`/`upsert`/`audit`/`verify_audit_chain`（结构化 API，不是裸 SQL）；
   - 裸 SQL 正则只匹配「以 SQL 关键字开头且带标识符」的字符串，避免误伤中文提示语；
   - **自检**：扫不到任何 `.py` 就报错（防「永远绿」）。

**验收判据与证据**

```bash
grep -rn "ctx\.db\.\(query\|execute\|executemany\|query_one\)" backend/app/routes/   # 递归归零
grep -rn "ctx.db.execute\|fetchall" backend/app/routes/*.py                          # 归零
python scripts/check_execution_architecture.py                                       # OK
```

**可证伪性**：8 类变异（`ctx.db.query` / `get_db().query` / `sqlite3.connect` / 裸 SQL
→ 期望红；`ctx.db.insert` + `ctx.db.audit` 对照组 → 期望绿）**全部符合预期**，源码字节级还原。

## 2. P0-2：`app/*` ↔ `core/*` 双命名空间冻结

**问题**：历史上 `app/db.py`、`app/config.py`、`app/state.py` 与 `core/*` 同名并存，
`from app.db import DB` 与 `from core.db import DB` 两条路径都能走通 —— 一旦某条路径被
单独修改，就会产生两个 `DB` 类。

**实测结论（比预期好）**：内核级 `app.*` 引用**已经是 0 处**；现存 391 处 `app.*` 导入
全部是 app 层子包（`routes` 87 / `runtime` 56 / `screener` 53 / `services` 29 …），属正常分层。

**动作**：新增 **Gate 3**，把「不新增」变成机器可查：
- `CORE_MODULES` **从 `core/*.py` 动态推导**（不是硬编码清单 —— 硬编码清单会随
  `core/` 增文件而失效）；
- ① 拦 `backend/app/<内核名>.py` **影子模块**；② 拦 `from app.<内核名>…` / `import app.<内核名>…`（报「应改为 `core.<名>`」）；
- 自检：推导不出内核清单就报错。

**为什么默认不换成新引擎**：旧接口有 3 条回归测试守着「`Σ w_i × 袖套收益`」的既有契约。
按项目纪律「**判断 ≠ 缺陷**」，契约本身不是错，改它属判断；所以新引擎**并存**、显式 opt-in。

### 6.2 顺带修掉的真实缺陷 TD-05：组合净值按**索引**加总

旧 `run_portfolio_backtest` 把各标的袖套净值按索引相加：

```python
tot += eq[t] if t < len(eq) else eq[-1]      # ← 旧实现
```

- 标的日期范围不一致时（次新股上市晚、长期停牌、取数根数不同），
  索引 `t` 在两只标的上对应**不同日期** ⇒ 组合净值曲线在真实日历上**不存在**，
  而夏普 / 最大回撤区间 / 月度分布**全部建立在它上面**。
- `eq[-1]` 填充更糟：把「这段没有数据」静默表述成「净值不变」。

**修法**：先 `align_panel()` 对齐再跑袖套，输出 `alignment`；
袖套求和契约保持不变；并加一条**净值序列长度一致性**断言
（长度不一致 = 净值与 K 线错帧，宁可报错也不给一条错的曲线）。

**行为级判据**（单看长度不够）：把 A 单独喂**对齐切片**重算，
收益必须与组合里的 A 分项**完全一致**：

```python
ref = run_backtest_vectorized("A.SH", aligned_a, "ma_cross", {...}, 1_000_000.0)
assert abs(out["per_symbol_metrics"]["A.SH"]["total_return"]
           - ref["metrics"]["total_return"]) < 1e-9
```

### 6.3 自检发现的缺陷 TD-06：`[:10]` 把分钟线压成一天

首版 `bar_date()` 用 `str(v)[:10]` 取日期键 —— `"2024-01-05 09:31:00"` 被截成
`"2024-01-05"`，一天内 240 根 bar 塌缩成同一天、**只剩最后一根**，
净值曲线凭空少 239 个点，**而没有任何地方会报错**。

**修法**：`_date_key()` 对带时间的值**保留到分钟**；同键多根的数量以
`n_collapsed_same_key` 显式报出。

### 6.4 引擎的三条硬不变量（真实数据上也成立）

| 不变量 | 含义 |
|--------|------|
| `final_equity == final_cash + Σ 持仓市值` | 净值定义自洽 |
| `Σ 分标的 total_pnl == Δequity` | 归因不丢钱（真实冷仓数据上误差 < 1 元） |
| `n_bars == |各标的交易日交集|` | 不 forward-fill、不混日期 |

### 6.5 验证

- 合成数据：等长 / 部分重叠 / 零重叠 / 分钟线 / 重复键 / 缺标的 / Σw>1 / 未知 rebalance / weekly 不可解析日期；
- **真实本地历史**：`backend/data/bars_cold.db` 的 `kline_archive`（31320 行 / 106 只）
  取 3 只真实标的跑通，恒等式成立；
- **变异验证 7/7 全红**（`scripts/verify_portfolio_falsifiable.py`），源码字节级还原：
  M1 分钟线压成一天 / M2 交集变并集 / M3 放行 Σw>1 / M4 去掉整手 / M5 资金不足误报通用原因 /
  M6 `rebalance=none` 变成每根都调 / M7 组合回退旧索引加总。

> ★ 变异脚本本身也踩了一次坑：**单独**把 `T = len(panel["dates"])` 改成 `max(lens)` 是
> **空操作** —— 对齐生效后各袖套长度恰好等于交集长度，两者恒等。所以 M7 必须是
> **组合回退**。这正是「变异锚点必须落在真正可执行的分支上」的又一个实例。

## 8. P1-5：前端 API ↔ 后端契约守卫

**问题**：`frontend-next/src/services/api/*.ts` 是**手工维护**的。后端改名/删端点时
前端不会编译报错 —— 只会在**运行时** 404，界面表现是「加载失败」这种最没有信息量的提示。

**动作**

- 新增 `scripts/check_api_contract_drift.py`：
  - 后端真源 = `backend/tests/contracts/rest_endpoints.json`
    （由 `tests/contracts/introspect.py` 从**运行中的 app** 导出，不是手写的，所以不会跟着前端一起漂）；
  - 前端真源 = `services/api/**/*.ts` 里 `http.<method><T>("<path>")` 的字面量；
  - 归一化：去 query、`${...}`→`{param}`、补 `/api/v1` 前缀、路径参数统一 `{param}`；
  - 判据：**前端调用的端点必须都在后端契约里**（反向不算失败 —— 硬要求覆盖只会逼人写假调用）；
  - **静态解析不到的调用点单独列出，不静默跳过** —— 否则「检查通过」可能只是因为解析不到；
  - 自检：`len(backend) < 50` 或 `len(frontend) < 20` ⇒ 判定检查失效并报错。
- 挂进 `scripts/ci_reconcile.py` 作为**第 4 项**契约（复用同一份判据逻辑，**不复制** ——
  复制一份就会出现「两份判据各自漂移」，那正是本门禁要防的病）。

**为什么放在 `ci_reconcile.py` 而不是另起一个 hook**：它和前三项是**同一类**问题 ——
「两处对同一事实的声明已经不一致，而没有任何编译期错误会提醒你」。分开放只会让
「跑门禁」变成「记得跑两个门禁」，而漏跑的那个永远不会有人发现。

**基线**：后端契约 **232** 端点 / 前端调用 **163** 端点 / 静态解析不到 **0** / 无漂移。

**可证伪性 4/4**（`scripts/verify_api_contract_falsifiable.py`，字节级还原）：
端点改名 / 方法错配 / 不存在的顶层段 ⇒ 红；仅改查询串 ⇒ 绿。

### 10.4 回归过程中发现并修掉的第三个问题：裸 `except: pass` 水位线零余量（TD-08）

全量回归中 `test_no_bare_except_pass.py` 报 `1 failed, 2 passed`，单文件复跑 10/10 全绿。
**没有当成 flake 放过**，查下去发现的是一个结构性问题：

- 水位线常量 `MAX_BARE_EXCEPT_PASS = 151` 是历史快照，而**工作区恰好 151**
  （`git show HEAD:` 口径是 **150**）；
- 多出的那 1 处来自**未提交的 R26 改动**：
  `app/services/market/kline_io.py::stop_moneyflow_collector` 里的
  `except (asyncio.CancelledError, Exception): pass` —— 正是这个护栏存在的意义，
  而它把最后一格余量吃掉了，于是**任何一次瞬时扰动都会让它变红，且与真实回归无法区分**。
- 处置：按护栏自身给出的处方改成 `swallow(exc, why="停机取消资金流采集循环…")`
  —— 停机路径仍不阻断，但静默失败变成可查日志。工作区回到 **150**，恢复 1 格余量。

**排除假设用的都是实验，不是猜**：并发跑变异脚本（425 次扫描，最大仍 151）、
影子模块存在、注入块追加、文件读放大（连续 60s 扫描未见任何单文件计数超真值）—— 均否。
那次瞬时超限的具体触发者**未复现**，已如实记入 TD-08 并给出再次出现时的判定流程。

> ★ 这条的价值在于：`1 failed` 的日志只写了「某文件 1 failed」，
> 如果按 flake 处理就会漏掉「水位线零余量 + 未提交改动吃掉最后一格」这件事。

## 13. 结论

§5 的 **P0 三项 + P1 五项全部闭环**，且每项都有机器可查的判据：
门禁新增 4 条规则 + 1 项契约，测试新增 2 个文件 / 33 条用例，变异验证合计 **19 类全红**。

比「清单打勾」更重要的是本轮**发现了三个静默缺陷**：
TD-05（组合净值日期混叠）、TD-06（分钟线被压成一天）、TD-08（裸 `except: pass` 水位线零余量）。
三者都满足「跑得通、有输出、无报错」，只有把「日期必须对齐」「时间轴键必须唯一」
「水位线必须有余量」写成**可证伪的断言**才会暴露 ——
而且 TD-08 是从一条 `1 failed` 的日志里挖出来的：
**按 flake 处理就永远发现不了**。这与方案文档结尾的判断一致 ——
**当前稀缺的不是再造功能，而是继续堵住历史债务并把它收敛成可追踪、可证伪的看板。**
