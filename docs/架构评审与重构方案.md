## 0. 摘要

### 0.1 一句话结论

**功能成熟度很高，工程纪律也少见地强；当前的主要风险不是“缺功能”，而是“真相不唯一、边界不清晰、关键状态机不完整”。**

项目已经具备一套完整的“真实券商 + 零 mock + 契约门禁 + 逐步降级”的工程体系，交易主链路（SignalRouter → 风控 → ExecutionService → WAL/审计 → 券商）也收口得相当好。但过去多轮快速演进留下了三类结构性债务：

1. **两代架构并存**：`xtquant_client`（旧）与 `connectors`（新）两套券商抽象、两套 K 线仓、两套构建脚本、两套部署实现；
2. **全局单例作为集成总线**：`AppContext` 49 个 `Any` 槽位，40 个生产模块直接取 `state`，测试靠快照/恢复维持顺序无关；
3. **边界普遍无类型**：254 个 REST 端点 **0 个 `response_model`**、75 个 `body: dict`，前端 648 行手写类型，契约只能靠测试与文档“看着”，不能靠编译器保证。

这三类问题不会立刻让功能坏掉，但会持续放大每一次改动的成本，并制造“假绿灯 / 假红灯”的土壤。

### 0.2 必须优先处理的 8 件事

| # | 事项 | 类型 | 为什么现在做 | 预估 |
|---|------|------|--------------|------|
| 1 | **订单超时/崩溃语义改为 `UNKNOWN`，并把 `WAL.unresolved_intents()` 接入对账** | 资金安全 P0 | 写前日志（intent）已落地，但超时/无委托号被写成 `intent_failed`（与拒单同义），而 `OrderReconciler` 只读 `order/submit/create`；真实柜台可能已接单却记为失败，用户重试会重复下单 | 3–5 人日 |

| 3 | **`auth_token` 加密落库 + 日志/导出脱敏** | 安全 P1 | 桥 token 可执行交易，当前与普通字段一样明文存 SQLite；LLM Key 已用 AES-GCM，口径不一致 | 1–2 人日 |
| 4 | **版本/许可证元数据单一真源** | 发布 P0 | `VERSION=0.5.4`，`backend/pyproject.toml` 仍 `0.4.9` 且 `license=Proprietary`，仓库 `LICENSE` 是 Apache-2.0 | 0.5 人日 |
| 5 | **统一构建编排：`.sh` / `.bat` 变成薄壳，逻辑进 Python** | 发布 P0 | 两份 574/560 行脚本重复全部步骤，TD-16/19/21 三次事故都源于此；每次改动要改两遍 | 4–6 人日 |

> **排序原则**：先修“会亏钱/会误导用户”的 P0，再做“让后续每次改动更便宜”的结构性改造。**不要**先做 `AppContext` 大重构或目录大搬迁——那会消耗大量时间，却不直接降低资金风险。

**关键事实**：

- 单进程、单 uvicorn worker；所有服务共享一个事件循环与一个 `state` 单例。
- 券商调用分两类：进程内 xtquant（旧 `BrokerAdapter`，同步）与大 QMT 跨进程桥（`BigQmtBridge`，同时实现 `adapter` 与 `bridge` 两套面）。
- 所有交易入口（REST / MCP / 算法 / 条件 / 涨停 / 策略 / 目标持仓）都收敛到 `SignalRouter`，这是本项目最值得保留的架构决策之一。

**关键事实**：

- `kline_cache`（展示/回测缓存）与 `local_bars`（选股离线仓）是**两套独立的 K 线存储**，各自有冷热/保留策略；
- `BarsSyncer` 的热路径写 `local_bars`，冷路径写 `kline_archive`；`KlineCache` 的热表是 `kline_cache`，冷仓也是 `kline_archive`；
- `market_sync._rollover()` 只把 `kline_cache` 的旧行搬入冷仓，**不处理 `local_bars`**；
- `BarsProvider` 的离线路径只读 `LocalStore`（`local_bars`），不读冷仓。

这会在第 2 节 A-05 展开。

### 1.5 五条关键链路

#### 1.5.1 启动

`app/main.py::create_app()` 构建 FastAPI 与中间件；lifespan 交给 `app/bootstrap/lifecycle.run_phases()`：

1. `phase_db`：初始化 SQLite、JobRuntime、API Key、通知、告警、runtime_config、KlineCache + 冷仓、WAL；
2. `phase_broker`：恢复持久化连接、自动发现/连接、刷新交易日历（**Optional**，失败降级不阻断 READY）；
3. `phase_engines`：行情总线、WS、算法/条件/涨停/模拟盘/策略运行时；
4. `phase_watchdogs`：健康巡检、委托超时看门狗、信号路由、定时任务；
5. `phase_replay`：WAL 算法单重放 + 启动对账；
6. `phase_misc`：行情定时维护、DB 备份、系统任务注册、默认调度。

停机按逆序执行（`app/bootstrap/shutdown.py`）。`Required` 阶段失败会阻断启动，`broker` 失败只降级——这是正确的取舍。

#### 1.5.2 下单

```
REST /trade/order ─┐
MCP place_order  ──┤
算法/条件/涨停/策略 ┴─→ SignalRouter.route()
                         ├─ mode=paper  → PaperEngine（本地撮合）
                         ├─ mode=dry_run→ 返回计划，不下单
                         └─ mode=live   → 风控（Mandatory Risk）
                                           → WAL intent（下单前落盘）
                                           → ExecutionService.place_order()
                                              ├─ 真实行情估价（市价单保护价）
                                              ├─ bridge.call_locked(gateway.place_order)
                                              │   或 ExecutionPort（QMT_USE_PORTS=1）
                                              └─ 审计
                                           → WAL order / intent_failed
                                           → WS 事件 + 通知
                                           → 定时对账
```

**做得好的地方**：所有入口统一到 `SignalRouter`；`risk_checked` 避免重复扣减频率/额度；WAL 先写 intent；`paper` 与 `live` 物理旁路；大额 TOTP 二次确认；幂等 `single_flight`。

**断点**：`WAL.unresolved_intents()` 没有被 `OrderReconciler` 消费；超时/无委托号被写成 `intent_failed`，而真实柜台可能已接单。详见 A-04 / D-01 / D-02。

#### 1.5.3 行情

```
券商回调 / TDX / eltdx / akshare
        │
        ├─ SyncEngine.on_event → latest_quotes 缓存
        │        ├─ WSManager.broadcast（按客户端订阅过滤）
        │        └─ QuoteBus.publish（当前无订阅者，仅引用计数在用）
        │
        └─ DataSourceManager（auto 链：broker → tdx → baostock → akshare）
                 ├─ KlineCache（kline_cache 热表 + kline_archive 冷仓）
                 └─ LocalStore（local_bars 离线仓）
```

**优点**：多客户端订阅同一标的只向券商订阅一次；断线重连补发 30s；数据源链有熔断/许可/能力校验；空结果与“不可用”分开归因。

**问题**：WS 广播对每个客户端顺序 `await send_text`，无队列/超时；慢客户端会拖住所有行情。`QuoteBus.publish/subscribe` 是未闭环的预留。

#### 1.5.4 数据同步 / EOD

```
ScheduleRunner（cron，next_run_at 落库）
   └─ JobRuntime（持久化队列、lease、checkpoint、reaper）
        ├─ system.sync_bars   → BarsSyncer（hot → local_bars；cold → kline_archive）
        ├─ system.sync_dataset→ DatasetSyncer（K 线委托 BarsSyncer；其他数据集自实现）
        ├─ system.eod         → calendar → universe → bars → quality → reconcile → snapshot
        └─ system.classic_screen 等

另有：
· gateway/market_sync.py：自己的 asyncio 循环，每日 16:00 刷新 KlineCache 热表 + 热窗滚动
· phase_watchdogs：健康/看门狗/定时任务循环
· engines：算法/条件/涨停/策略各自的后台循环
```

**问题**：时间触发有两套（ScheduleRunner 与 market_sync 自带循环）；行情刷新可能被 EOD 与 market_sync 各跑一次；31 个 `while True`、41 处 `create_task`（产品代码口径）没有统一任务注册表。

#### 1.5.5 大 QMT 部署

```
REST /qmt-agent/* ──→ app/routes/qmt_agent.py（1403 行）
CLI scripts/qmt_agent_deploy.py（44KB）
```

## 2. 架构设计评估

> 本章回答两个问题：**哪些设计是对的、必须保住**；**哪些不合理、为什么不合理**。第 3 章再下沉到具体代码细节。

### 2.1 先说对的：这些设计不要动

评审最容易犯的错，是把“我不熟悉的写法”当成“坏设计”。以下十项是项目真正的架构资产，重构时必须原样保留，任何“顺手简化”都可能造成资金或信任损失。

| # | 设计 | 位置 | 为什么是架构级正确 |
|---|------|------|--------------------|
| G-01 | **单一交易入口 `SignalRouter`** | `backend/gateway/signal_router.py` | live/paper/dry_run 三种模式共享同一条“校验 → 风控 → 执行 → 审计 → 事件”路径。模式是**策略**而非**分支**，所以模拟盘能真实暴露风控与序列化问题，而不是走一条“测试专用捷径” |
| G-02 | **Mandatory Risk + `risk_checked` 传递** | `gateway/execution.py`、`signal_router.py::_live` | 风控在 `route()` 做一次，执行层用 `risk_checked=True` 跳过二次校验。这个参数看似是“后门”，实际解决了“同一笔委托消耗两倍频率窗口/日额度”的真实 bug；注释明确写了原因，属于**有意为之的显式契约** |
| G-03 | **WAL 写前日志 + 幂等 + `client_order_id`** | `gateway/wal.py`、`gateway/execution.py` | 方向完全正确：先落盘“我打算下单”，再调用柜台，再用结果配对。这是从“尽力而为”走向“可恢复”的关键一步。当前问题不是方向错，而是**状态机只画了一半**（见 A-04） |
| G-04 | **6 阶段 bootstrap + Required/Optional 分层** | `backend/app/bootstrap/*` | `db → broker → engines → watchdogs → replay → misc` 顺序清晰；broker 失败只降级不阻断 READY，保证“没连券商也能看历史/改配置/读文档”。这是桌面端产品应有的可用性取舍 |
| G-05 | **零 mock 纪律** | 全局 | 未连接券商时返回引导文案，不返回假行情/假持仓。量化工具最怕“看起来有数据”，这条纪律保护了用户对系统的信任 |
| G-06 | **契约快照 + 可证伪门禁** | `backend/tests/contracts/*.json`、`scripts/check_*.py` | 不靠“大家记得更新文档”，而靠“CI 能证明你漏了”。`check_api_contract_drift` / `check_capability_coverage` / `check_ws_consumption` / `check_execution_architecture` 的组合，在同类项目里属于上游水平 |
| G-07 | **前端页面注册表 + 入口可断言** | `frontend-next/src/app/routes.tsx` | 46 个页面集中登记，`entryFrom` 让“隐藏页必须有入口”可被脚本验证。比散落的 `<Route>` 更容易做能力覆盖审计 |
| G-08 | **Electron 安全基线** | `frontend-next/electron/main.cjs` | `contextIsolation=true`、`nodeIntegration=false`、`sandbox=true`；`no-sandbox` 仅在 GPU 安全模式局部启用。桌面壳最容易图省事全开，这里没有 |
| G-09 | **大 QMT agent 单文件 + py3.6 门禁** | `backend/agent_bigqmt/BIGQMT_AGENT.py`、`scripts/check_bigqmt_agent_py36.py` | 单文件不是“不会拆”，而是 QMT 策略进程注入的**外部约束**；配套生成器与语法门禁说明团队理解这个约束。这是“约束驱动设计”的正例 |
| G-10 | **产物门禁** | `backend/build_exe.py`、`build_all.*` | 包内禁止 `master.key` / `app.db` / 运行期配置，`VERSION` 必须进包且一致。发布物一旦带密钥，后果不可逆；这道门禁价值极高 |

> **重构红线**：任何方案都不得以“简化”为由移除 G-01/G-02/G-03/G-06/G-10。可以改实现，不可以改语义。

### 2.2 五个根因：不合理的不是某一行代码，而是五种习惯

A-01…A-15 看着像十五个独立问题，实际只有五个根因。**只修表面问题，半年后会长出新的同类问题**；对准根因，才能判断哪些改造值得做、哪些是白费力气。

#### R-01 演进式叠加，缺少“收口 / 删除”阶段

**现象**：新方案上线时，旧方案不删，用开关并存；开关默认值长期停在旧路径。

**证据链**：

- 券商接入：`connectors/`（新 Port/Dialect/Transport）与 `xtquant_client/`（旧 adapter + ABI 桥）并存；灰度开关 `QMT_USE_PORTS` 默认 `"0"`（`gateway/execution.py:21`），即**生产默认仍走旧路径**，新架构只在测试与显式开启时被验证。
- 传输方式：`connectors/registry.py:47` 的 `RETIRED_PROFILES` 已把 `qmt.mini`、`qmt.big.direct`、`qmt.big.bridge.file/redis/zmq` 标为退役，但 `_PROFILES` 仍保留、前端仍可选。
- 门面：`gateway/easytrader_facade.py` 在生产代码中零引用，仅测试引用。
- 构建：`build_all.sh`（574 行）+ `build_all.bat`（560 行）+ `backend/build_exe.py` + `scripts/backend-build.mjs` + `package.json` scripts + `electron-builder.yml`，六处都能“构建”，但没有一处是唯一入口。
- 部署：`app/routes/qmt_agent.py`（1403 行）与 `scripts/qmt_agent_deploy.py`（44 KB）各实现一套 `_find_qmt_dir` / `_qmt_running` / `_atomic_write`，注释直接写“REST 侧独立实现”。

**机制**：每次需求都选择“新增一条路径 + 开关”，因为这样最快、最不容易碰坏存量。但没人负责“旧路径何时删”，于是开关变成永久分叉，验证成本翻倍，新人需要同时理解两套模型。

**代价**：

1. **验证不对称**：CI 跑的是新路径，生产跑的是旧路径；新路径“全绿”不代表用户那条路是通的。
2. **修复要改两遍**：同一个 bug 在 `connectors` 与 `xtquant_client` 各修一次，漏一处就是线上事故。
3. **认知负担**：读代码的人必须先判断“这个函数在当前开关下会不会被执行”，而这在静态阅读时几乎无法确定。

**判断**：这是**第一根因**。A-01、A-05、A-06、A-09、A-10 都是它的不同表现。

#### R-02 按“技术分层/文件”组织，而非按“领域/契约”组织

**现象**：目录按 `routes / gateway / engines / tools / datasource` 切，但业务概念（下单、行情、同步、部署）横跨 4–6 个目录，且底层反向依赖上层。

**证据链**：

- 包级循环依赖（AST 依赖图确认）：
  - `connectors/ports.py` → `xtquant_client.base.BrokerError`
  - `xtquant_client/manager.py` → `connectors.transport.TransportError`
  - `datasource/bound_broker.py` → `xtquant_client.base`
  - `gateway/market_sync.py:295` → `tools`
  - `tools/trading.py:7` → `gateway.execution`
  - `engines/paper_engine.py:17` → `tools.ashare`
- `app/routes/market.py`（891 行）在路由层里做 search / resolve / analysis / stock-info 的业务编排。
- `gateway/market_sync.py` 同时负责调度、拉取、归一化、落库、归档。
- `sync/__init__.py`（848 行）里 `SyncEngine` 同时负责行情扇出、账户快照、订单/成交事件、批量循环。

**机制**：早期文件少，“按技术层”最直观；功能变多后，新代码倾向放进“最近便的目录”，而不是“语义归属的领域”。缺少一个**只依赖协议、不依赖实现**的中间层，于是底层要引用上层的异常类型，形成环。

**代价**：无法单独测试/替换任一子系统；改一处要读六个目录；循环依赖让“抽包”永远排不上日程。

**判断**：这是**结构性根因**。A-03、A-07、A-12 属于此类。它不会立刻出错，但会让每一次“小改动”都变成跨层改动。

#### R-03 运行时用全局单例当集成总线

**现象**：`AppContext` 是 49 个 `Any` 字段的服务定位器，模块通过 `from core.state import state` 直接取，测试通过快照/恢复维持顺序无关。

**证据链**：

- `backend/core/context.py`：49 个 `AnnAssign`，类型全部 `Any`。
- 40 个生产文件 `from core.state import state`。
- `tests/contracts/appcontext_baseline.json` 固定 41 个文件；`scripts/check_appcontext.py` 以它为基线。
- 178 处 `Depends(get_ctx)`；93 处 `ctx.db`。
- `tests/conftest.py` 对 48 个键做快照/恢复。

**机制**：FastAPI 的 `Depends` 本来可以表达依赖，但 `get_ctx()` 返回同一个大对象，等于“依赖注入的形状 + 全局变量的实质”。测试为了避免顺序污染，只能整表快照/恢复——这是**设计缺陷的测试侧症状**。

**代价**：

1. 任何模块都能拿到任何服务，编译期/导入期都无法发现“越界依赖”；
2. 单测必须构造半个应用，跑得慢、易相互污染；
3. 49 个 `Any` 让 IDE 与类型检查完全失效，重构只能靠 grep。

**判断**：这是**可维护性根因**。不建议“一次性删除 AppContext”，而应“按领域收窄入口，逐步把可选依赖变成显式参数”。

#### R-04 边界无类型，契约靠“事后门禁 + 文档”守

**现象**：后端不声明响应模型，前端手写类型；参数不做范围约束；错误码语义靠约定。

**证据链**：

- 254 个 REST 端点，`response_model` 出现 **0 次**。
- `body: dict` **75 处**；全 app `BaseModel` 仅 11 处；`Query(` **0 处**。
- 前端 `shared/types.ts` 648 行手写接口类型。
- 503 语义双轨：156 处 `err(503)` 返回 HTTP 200 + body `code=503`，只有 `/ready` 用真实 HTTP 503；前端 `ApiError.brokerUnavailable` 用 `status === 503` 判断，对业务 503 永远为 false。
  —— **已修（2026-11-07）**：`code=503` 现返回真实 HTTP 503（详见 §3.7.3 与 TD-45）。

**机制**：早期用 `dict` 最快，`response_model` 会暴露“字段其实不稳定”的事实，于是没人补。契约快照记录的是**路径与参数名**，不记录**字段结构**，所以门禁只能抓“路径不存在”，抓不到“字段改名/类型变化”。

**代价**：后端改字段，前端在运行时才炸；OpenAPI 文档对客户端没有价值；MCP 工具与 REST 的入参约束各自维护。

**判断**：这是**边界质量根因**。A-08、D-05、D-06 属于此类。修复必须“写路径优先”，否则一次性补 254 个模型必然烂尾。

#### R-05 关键状态机缺少显式状态与单一所有者

**现象**：订单、K 线、后台任务这三类“有生命周期”的东西，都没有一个地方完整定义状态与转移。

**证据链**：

- **订单**：`intent` → 成功写 `order`，失败/异常/无委托号统一写 `intent_failed`；没有 `UNKNOWN` 态。而“无委托号”既可能是拒单，也可能是超时后柜台已接单。`OrderReconciler._pending_from_wal()` 只收 `op in ("order","submit","create")`（`gateway/reconcile.py:83`），**完全不读 `intent`**；`WAL.unresolved_intents()` 仅被测试调用。
- **K 线**：`gateway/kline_cache.py` 用 `kline_cache` + `kline_archive`；`datasource/local_store.py` 用 `local_bars`；`app/sync/bars.py` 热数据写 `local_bars`、冷数据写 `kline_archive`；`app/data/bars_provider.py::_local_batch` 只读 `LocalStore`；`gateway/market_sync.py::_rollover` 只归档 `kline_cache`。
- **任务**：`app/runtime/schedules.py`（ScheduleRunner）、`app/runtime/jobs.py`（JobRuntime）、`gateway/market_sync.py` 自带循环、`app/runtime/eod.py`、`phase_watchdogs`、各 engine 循环，共 31 个 `while True`、41 处 `create_task`，没有统一的生命周期/取消/健康上报。

**机制**：状态机是“隐式”的——状态藏在不同的表、不同的 op 字符串、不同的循环里。每加一个分支，就在某处 `if` 里补一笔，没人画完整转移图。

**代价**：**这是唯一会直接造成资金损失的根因**。订单“未知”被记成“失败”，用户重试 → 重复下单；对账看不到 intent → 永久失联；K 线两仓不一致 → 回测/选股结果不可复现。

**判断**：这是**风险根因**，优先级最高。A-04、A-05、A-06 属于此类。

### 2.3 架构问题逐条评估（A-01 … A-15）

> 每条统一给出：**结论 / 证据 / 影响 / 建议方向 / 优先级 / 工作量**。
> 优先级：P0 = 资金或产品安全，立即做；P1 = 结构性，1–2 个迭代内做；P2 = 改善型，排入常规。
> 工作量按“1 人熟悉代码后”的净开发时间估算，不含评审与回归等待。

#### A-01 双轨券商接入：新架构默认不生效，退役口径三处不一致

- **结论**：项目同时存在两代券商抽象，且**默认走旧的那一代**；退役标记只写在后端注册表里，前端与文档没有同步。
- **证据**：
  - `gateway/execution.py:21`：`_QMT_USE_PORTS = os.environ.get("QMT_USE_PORTS", "0")...`，默认关闭。
  - `gateway/execution.py:78`：未开启时直接走 `bridge.gateway.place_order` 旧路径。
  - `connectors/registry.py:47-53`：`RETIRED_PROFILES` 标记 5 个组合退役（mini、big.direct、bridge.file/redis/zmq）。
  - `xtquant_client/manager.py::_build_bigqmt_bridge`：bigQMT 走 `connectors`，mini 走 legacy adapter，同一个 manager 内两种装配。
  - `gateway/easytrader_facade.py`：生产零引用。
  - `connectors/bigqmt_closed_loop_channel.py`：仅测试引用。
- **影响**：
  1. CI 覆盖的新路径不是生产默认路径，**绿灯可信度打折**；
  2. 同一个柜台 bug 要修两遍；
  3. 用户按 UI 选择 `file` 桥，后端已判定其“策略进程禁文件读写”，属于**必然失败的选择**。
- **建议方向**：分三步收敛，不做大爆炸（详见 4.4.2）：
  1. 先把“退役”变成**三处一致**：registry、**新增** REST `/brokers/connectors`（当前缺失）、前端选项与文案；
  2. 新券商只允许 `connectors`，旧 adapter 保留只读兼容（查询/持仓），下单强制新路径；
  3. 观察一个版本后删除 `QMT_USE_PORTS` 开关与 `easytrader_facade`。
- **优先级**：P0（第 1 步，2–3 人日）+ P1（第 2–3 步，8–12 人日）
- **工作量**：10–15 人日

#### A-02 全局服务定位器 `AppContext`：49 个 `Any` 槽位，靠测试快照维持秩序

- **结论**：`AppContext` 已经从“启动期装配容器”退化为“运行期全局变量”，是模块边界失效的载体。
- **证据**：见 R-03 证据链（49 槽位 / 40 文件 / 178 Depends / 93 `ctx.db` / 48 键快照）。
- **影响**：
  1. 无法从签名看出依赖，改动影响面只能靠经验；
  2. 单测必须构造完整上下文，2746 用例被迫逐文件跑（见 A-14）；
  3. 新服务默认往 `AppContext` 加字段，**债务自动增长**。
- **建议方向**：
  - **止血**：新增字段必须带具体类型 + 在 `check_appcontext.py` 里登记“允许的消费者”，禁止新增 `Any`；
  - **收窄**：路由层优先用 `Depends(get_db)` / `Depends(get_manager)` 这类窄依赖，而不是 `get_ctx()`；
  - **分批迁移**：按域迁移（trade → market → sync → system），每批迁移后下调 baseline 文件数；
  - **不追求归零**：启动期装配仍可用容器，运行期禁止随意取。
- **优先级**：P1
- **工作量**：15–20 人日（分批，可与业务并行）

#### A-03 包级循环依赖与分层模糊

- **结论**：存在**真实的包级循环**（非仅“感觉耦合”），根因是缺少纯协议层。
- **证据**：6 条环，见 R-02。最典型的是 `connectors/ports.py` 反向 import `xtquant_client.base.BrokerError`——**新架构的端口定义依赖旧架构的异常类型**，这在架构上等于“新树嫁接到旧根”。
- **影响**：
  1. 无法把 `connectors` 单独打包/复用；
  2. import 顺序敏感，测试偶发失败难定位；
  3. “抽 contracts 包”这类改造会被环卡住。
- **建议方向**：
  1. 新建 `backend/contracts/`（纯 Python，无 I/O、无第三方 SDK）：`errors.py`（`BrokerError` 族）、`models.py`（`OrderSnapshot`/`Bar`/`Signal` 等 DTO）、`ports.py`（Protocol）；
  2. `connectors` 与 `xtquant_client` 都只依赖 `contracts`；
  3. 用 `import-linter` 或自写 AST 脚本加一条“禁止 contracts 反向依赖”的门禁。
- **优先级**：P1
- **工作量**：6–8 人日（含改 import 与回归）

#### A-04 订单状态机不完整：`UNKNOWN` 缺失，`intent` 未进入对账

- **结论**：**这是全项目风险最高的一处**。写前日志（intent）已经做了，但状态机把“未知”错误地归入“失败”，导致对账**主动忽略**最需要核对的委托。
- **证据**（已按工作区最新代码核对，比历史结论更精确）：
  - `gateway/signal_router.py::_live`：下单前 `_wal_intent(intent_id, sig)` ✅（P0-1 已落地）。
  - 拿到结果后：`if not oid or rstatus == "rejected":` → 统一 `_wal_append(WAL_OP_INTENT_FAILED, ...)`，返回 `ok=False`，reason 写“下单未确认（柜台未返回委托号，可能超时或拒单）”。
  - `gateway/wal.py:33-35`：只有 `intent` / `order` / `intent_failed` 三个 op，**没有 `intent_unknown`**。
  - `gateway/wal.py::unresolved_intents`：把 `order` 与 `intent_failed` 都视为“已配对”，因此**超时单不会出现在未决列表里**。
  - `gateway/reconcile.py:83`：`if op not in ("order", "submit", "create"): continue`，**从不读取 `intent`**；`unresolved_intents()` 仅测试引用。
- **影响**（按严重度排序）：
  1. **重复下单**：用户看到“失败”，重试；柜台实际已接单 → 双倍仓位。这是资金事故，不是体验问题。
  2. **对账盲区**：日终对账只核对“有 order_id 的记录”，超时单连“待核销”都算不上，日志里显示“无待核销委托”。
  3. **审计失真**：`intent_failed` 既表示“确定拒单”，又表示“结果未知”，事后无法区分。
- **建议方向**（详见 4.4.1）：
  1. 增加 `WAL_OP_INTENT_UNKNOWN`，只有**明确拒单**才写 `intent_failed`；超时/无委托号/网络异常写 `unknown`；
  2. `unresolved_intents()` 同时返回 `intent` 与 `intent_unknown`；
  3. `OrderReconciler._pending_from_wal()` 接收 intent，按 `client_order_id`/`intent_id` 去柜台查单，查不到才判定失败；
  4. 前端对 `unknown` 显示“结果待确认，请勿重复下单”，并禁用重复提交；
  5. 加回归：模拟“柜台超时但实际成交”，断言对账能认领、且不产生第二笔委托。
- **优先级**：P0
- **工作量**：3–5 人日

#### A-05 历史行情双仓：冷热割裂，读模型不唯一

- **结论**：K 线有**两套物理存储、两套读写路径**，且“冷数据归档”只对其中一套生效。
- **证据**：
  - `gateway/kline_cache.py`：`kline_cache` + `kline_archive`，负责图表/回测缓存与归档。
  - `datasource/local_store.py`：`local_bars`，`_local_batch` 只读它。
  - `app/sync/bars.py`：热数据写 `local_bars`，冷数据写 `kline_archive`。
  - `app/data/bars_provider.py::_local_batch`：只走 `LocalStore`。
  - `gateway/market_sync.py::_rollover`：只处理 `kline_cache`，不处理 `local_bars`。
- **影响**：
  1. 离线/选股在热窗口之外**看不到数据**（`local_bars` 没有归档）；
  2. 图表与选股对同一标的可能返回不同长度/不同复权口径；
  3. 回测结果不可复现——“上次能跑，这次少了一段”。
- **建议方向**：
  1. 定义唯一读模型 `BarRepository.get(code, period, start, end, adjust)`，内部决定热/冷；
  2. 短期不迁表：先做**读穿**（热查不到自动查冷），再统一归档任务；
  3. 中期合并为 `bars`（热）+ `bars_archive`（冷）两张表，或保留现表但只允许 Repository 访问；
  4. 增加一致性审计脚本（抽样比对两仓同一 code/period 的条数与最后一根时间）。
- **优先级**：P1
- **工作量**：15–20 人日

#### A-06 调度与后台任务多套并存

- **结论**：至少四套“定时/常驻”机制，各自管生命周期，缺少统一注册、取消与健康上报。
- **证据**：`app/runtime/schedules.py`、`app/runtime/jobs.py`、`gateway/market_sync.py` 自带循环、`app/runtime/eod.py`、`phase_watchdogs`、engines 内部循环；31 个 `while True`、41 处 `create_task`。
- **影响**：
  1. 关停时任务是否优雅退出不确定；
  2. 同一时刻可能两个同步任务并行写同一张表；
  3. 无法在 UI 上给出“后台任务总览”，排障靠日志拼。
- **建议方向**：
  1. 保留 `JobRuntime` 作为唯一执行器，`ScheduleRunner` 只负责“到点投递”；
  2. `market_sync` / `eod` 改为注册 Job，不自建循环；
  3. 所有 Job 必须声明 `name / timeout / 互斥键 / 是否可并发`；
  4. 增加 `/jobs` 只读总览（已在部分路由存在，需统一数据源）。
- **优先级**：P1
- **工作量**：8–12 人日

#### A-07 `SyncEngine` / `WSManager` 过大 + WS 无背压

- **结论**：`sync/__init__.py` 一个文件承担四种职责；`broadcast` 对每个客户端顺序 `await`，慢客户端会拖住所有人。
- **证据**：`sync/__init__.py` 848 行；`SyncEngine` 在 L49、`WSManager` 在 L656；`broadcast` 在 L825 对每个 `ws.send_text` 顺序 await，无队列、无超时、无丢弃策略。
- **影响**：
  1. 一个卡住的 WebSocket 连接会让行情广播整体延迟；
  2. 断线重连时无“补偿/快照”语义，只能等下一条；
  3. 无法单测“慢消费者”。
- **建议方向**：
  1. `broadcast` 改为“每客户端一个有界队列 + 独立 sender task”，满队列丢弃最旧并计数；
  2. 增加 `ws_dropped_total` / `ws_send_seconds` 指标；
  3. 把 `SyncEngine` 按“行情扇出 / 账户快照 / 订单成交事件”拆三个类，文件保留导出以兼容；
  4. 加“慢客户端不阻塞快客户端”的回归测试。
- **优先级**：P1
- **工作量**：6–8 人日

#### A-08 API 契约无类型：254 端点 0 响应模型

- **结论**：REST 边界事实上是“弱类型 RPC”，OpenAPI 对客户端几乎无信息量。
- **证据**：`response_model` 0 次；`body: dict` 75 处；`BaseModel` 全 app 11 处；`Query(` 0 处；前端 `shared/types.ts` 648 行手写。
- **影响**：
  1. 后端字段改名，前端运行时才炸；
  2. 参数无上下界（`limit=100000` 可直接打满内存）；
  3. MCP 工具与 REST 各自维护入参说明，易漂移。
- **建议方向**（详见 4.4.3）：
  1. **只先做写路径**（下单/撤单/配置/券商连接/部署），约 30 个端点；
  2. 用 Pydantic v2 模型 + `response_model`，读路径允许 `dict` 但必须有 `response_model_exclude_none` 之外的明确 schema；
  3. 从 OpenAPI 生成前端类型（`openapi-typescript`），替换 `shared/types.ts` 的手写部分；
  4. 加门禁：新增写端点若无 `response_model` 直接失败。
- **优先级**：P1
- **工作量**：10–15 人日（分批）

#### A-09 构建脚本双份，六处入口

- **结论**：`.sh` 与 `.bat` 各自实现完整流程，另有四个“也能构建”的入口；任何改动必须同步两遍。
- **证据**：`build_all.sh` 574 行、`build_all.bat` 560 行；`backend/build_exe.py`、`scripts/backend-build.mjs`、`package.json` scripts、`electron-builder.yml`。
- **影响**：TD-16/19/21 三次事故（行尾、括号、路径）都源于双份维护；本地与 CI 行为可能不一致。
- **建议方向**：`.sh`/`.bat` 只做“找 Python → 调 `scripts/` 下的 `build.py <target>`”；所有逻辑进 Python（跨平台、可单测）；CI 只调一个入口。
- **优先级**：P0（发布风险）
- **工作量**：4–6 人日

#### A-10 部署/诊断 REST 与 CLI 双份实现

- **结论**：同一套“找 QMT 目录 / 判进程 / 原子写 / 备份”的逻辑存在两份，注释承认是“独立实现”。
- **证据**：`app/routes/qmt_agent.py` 1403 行；`scripts/qmt_agent_deploy.py` 44,446 字节；重复 `_candidate_roots` / `_find_qmt_dir` / `_is_qmt_dir` / `_qmt_running` / `_strategy_dir` / `_atomic_write` / `_backup_if_exists`。
- **影响**：修一处漏一处；REST 与 CLI 对同一环境的判断可能不同；1403 行路由难以测试。
- **建议方向**：在 `backend/app/services/` 下新增 `qmt_agent_ops.py`（纯函数 + 显式参数），REST 与 CLI 都调用；路由只做参数校验与响应组装。
- **优先级**：P1
- **工作量**：5–7 人日

#### A-11 审计/异常/可观测性覆盖不均

- **结论**：写路径审计不是“默认动作”，异常处理大量静默降级。
- **证据**：130 个写端点，但路由层仅 42 处 `.audit(` 调用，多数写 handler 内没有显式审计（部分为只读 POST）；产品代码 812 处 `except Exception`，仅 26 处走 `swallow()`。
- **影响**：出事后无法回答“谁在什么时候改了什么”；静默 `return None` 让故障表现为“空数据”而非“报错”。
- **建议方向**：
  1. 审计改为**中间件/依赖**：写方法自动记录，handler 只补业务字段；
  2. `except Exception` 必须二选一：`swallow(reason=...)` 或 `raise`；新增 `check_broad_except.py` 门禁；
  3. 关键读路径（行情、持仓）失败要返回 `degraded=true`，不要返回空列表冒充“没有数据”。
- **优先级**：P1
- **工作量**：6–8 人日

#### A-12 前端缺服务端状态层与错误边界

- **结论**：每个页面自己 `useState + useEffect` 拉数据；没有统一缓存、去重、取消、重试；任一页面渲染异常会白屏整个壳。
- **证据**：无 `ErrorBoundary`；`useAsync` 无缓存/无 `AbortController`，失败时 `data: null`；520 个 `useState`（tsx）、76 个 `useEffect`、10 个 `setInterval`；`ScreenPanels.tsx` 1101 行、`Brokers.tsx` 1018 行。
- **影响**：
  1. 切页重新拉全量，行情页闪烁；
  2. 请求竞态导致“后发先至”的旧数据覆盖新数据；
  3. 单个组件异常 = 整个应用不可用。
- **建议方向**（详见 4.4.6）：
  1. 先加路由级 `ErrorBoundary`（1 人日，收益最高）；
  2. 引入 TanStack Query（或自写 100 行的 `useQuery`），统一 `staleTime/retry/abort`；
  3. `useAsync` 保留兼容，内部改为 query；
  4. 大组件按“容器 / 列表 / 表单 / 详情”拆分。
- **优先级**：P0（ErrorBoundary）+ P1（查询层）
- **工作量**：1 人日 + 8–12 人日

#### A-13 版本/许可证元数据不一致

- **结论**：三处版本、两处许可证口径不一致，属于“发布即错”的问题。
- **证据**：`VERSION=0.5.4`；`backend/pyproject.toml:3 version="0.4.9"`、`:7 license={text="Proprietary"}`；根 `LICENSE` 为 Apache-2.0；`README.md` 第 16 行仍写 `0.5.2`；`frontend-next/package.json` 为 `0.5.4`。
- **影响**：法务风险（许可证口径冲突）；用户/支持无法确认版本；`build_exe.py` 的版本校验只覆盖一部分。
- **建议方向**：`VERSION` 作为唯一真源；构建时注入 `pyproject` 与前端 `package.json`；CI 加“三处一致 + LICENSE 一致”门禁；README 版本号改为引用 `VERSION` 或由脚本生成。
- **优先级**：P0
- **工作量**：0.5 人日

#### A-14 测试体系：2746 用例，CI 逐文件跑 208 次

- **结论**：测试数量是资产，但运行方式与分层让反馈变慢，且“用例总数”是手写常量。
- **证据**：208 个 `test_*.py`、2746 用例；`scripts/ci_reconcile.py::EXPECTED_TESTS = 2746`；CI 逐文件调用 pytest；前端 CI 用 `npm test`（并行），README 要求 `test:serial`。
- **影响**：全量反馈以十分钟计；并行前端测试可能因共享状态偶发失败；新增/删除用例要手改常量。
- **建议方向**：
  1. 分层：`unit`（纯函数/模型，秒级）/ `integration`（临时 DB + fake bridge）/ `e2e`（真机，手动或 nightly）；
  2. CI 默认跑 `unit + integration` 一次进程，`e2e` 单独 job；
  3. `EXPECTED_TESTS` 改为“从 collect 结果生成快照”，或降级为“不少于 N”；
  4. 前端统一 `test:serial` 或修掉共享状态后并行。
- **优先级**：P1
- **工作量**：8–10 人日

#### A-15 文档与门禁过重，计数易漂移

- **结论**：文档密度是优势，但 `TECH_DEBT.md` 135 KB、手写计数、多个“审计脚本”让维护成本接近收益。
- **证据**：`TECH_DEBT.md` 135 KB；`ci_reconcile.py` 手写 `EXPECTED_TESTS/COMPONENTS/PAGES`；文档断链门禁已存在但仍需人工维护索引。
- **影响**：新人读不完；过期条目无人删；门禁红灯时先怀疑门禁本身。
- **建议方向**：
  1. `TECH_DEBT` 拆“活跃 / 已关闭 / 观察中”，关闭项折叠；
  2. 计数类断言改为“生成快照 + diff”，不手写数字；
  3. 文档索引由脚本校验（已有 `audit_doc_links.py`，扩展为“新文档必须在 README 索引中出现”）。
- **优先级**：P2
- **工作量**：3–4 人日

### 3.7 六个重点问题的代码级展开

> 其余条目按表格执行即可；这六条要么涉及资金安全，要么改动面大，需要先把“改成什么样”说清楚。
> **逐文件改动、代码骨架、测试清单与验收命令见第 7 章。**

#### 3.7.1 订单状态机：从“两态”补成“四态”

**现状**（`gateway/signal_router.py::_live`，已按工作区最新代码核对）：

```python
intent_id = uuid.uuid4().hex
self._wal_intent(intent_id, sig)          # 下单前写 intent ✅
try:
    res = await ExecutionService(...).place_order(...)
    oid = res.get("order_id")
    rstatus = res.get("status")
    if not oid or rstatus == "rejected":   # ← 两种语义被合并
        self._wal_append(WAL_OP_INTENT_FAILED, intent_id, {...})
        return {**res, "ok": False, ...}
    self._wal_append(WAL_OP_RESULT, str(oid), {"intent_id": intent_id, ...})
except Exception as exc:
    self._wal_append(WAL_OP_INTENT_FAILED, intent_id, {...})  # ← 网络异常也记“失败”
```

**问题不在“有没有写日志”，而在“写错了状态”**：`intent_failed` 在 `WAL.unresolved_intents()` 里被视为“已配对”，于是超时单被**主动移出**待核对集合。这比“没有 intent”更危险——它让对账产生假阴性。

**目标状态机**：

```
                 ┌──────────────┐
   决定下单 ────► │   INTENT     │  已落盘，尚未调用/正在调用柜台
                 └──────┬───────┘
                        │
        ┌───────────────┼────────────────┬──────────────────┐
        │ 明确拒单       │ 拿到委托号      │ 超时/无委托号/网络异常 │
        ▼               ▼                ▼                  │
 ┌─────────────┐  ┌───────────┐   ┌──────────────┐          │
 │ INTENT_FAILED│  │  ORDER    │   │ INTENT_UNKNOWN│         │
 │  （终态）    │  │ （待成交） │   │  （待核对）   │          │
 └─────────────┘  └─────┬─────┘   └──────┬───────┘          │
                        │ 对账/回报        │ 对账查柜台        │
                        ▼                 ▼                  │
                  ┌───────────┐   ┌──────────────┐           │
                  │ 终态集合   │   │ 查到→ORDER    │           │
                  │ 成交/撤单  │   │ 查不到→FAILED │           │
                  └───────────┘   └──────────────┘           │
```

**改动清单**：

1. `gateway/wal.py` 增加常量与语义：

```python
WAL_OP_INTENT = "intent"
WAL_OP_RESULT = "order"
WAL_OP_INTENT_FAILED = "intent_failed"     # 仅“确定失败”
WAL_OP_INTENT_UNKNOWN = "intent_unknown"   # 新增：结果未知，必须核对
```

2. `unresolved_intents()` 的 `resolved` 集合**只认** `order` 与 `intent_failed`；`intent_unknown` 必须继续留在未决列表。同时增加 `unknown_intents()` 供启动告警使用。

3. `signal_router._live` 分支改为：

```python
if rstatus == "rejected":
    op, reason = WAL_OP_INTENT_FAILED, res.get("reason") or "柜台拒单"
elif not oid:
    op, reason = WAL_OP_INTENT_UNKNOWN, "柜台未返回委托号，结果待确认"
else:
    ... 成功路径 ...
if op != WAL_OP_RESULT:
    self._wal_append(op, intent_id, {"intent_id": intent_id, "reason": reason, ...})
    return {**res, "ok": False, "status": "unknown" if op == WAL_OP_INTENT_UNKNOWN else "rejected",
            "retryable": op == WAL_OP_INTENT_FAILED, "intent_id": intent_id}
```

4. `except` 分支区分异常类型：`BrokerRejectedError` → `intent_failed`；`TimeoutError` / `ConnectionError` / 未知异常 → `intent_unknown`。**宁可多一次核对，不可少一次。**

5. `gateway/reconcile.py::_pending_from_wal`：

```python
if op in ("intent", "intent_unknown"):
    iid = str(rec.get("entity_id") or "")
    payload = rec.get("payload") or {}
    if iid:
        pending[f"intent:{iid}"] = {**payload, "wal_ts": rec.get("ts", 0), "kind": "intent"}
    continue
if op not in ("order", "submit", "create"):
    continue
```

6. 对账执行时，对 `kind == "intent"` 的记录按 `client_order_id`（若券商不支持则按 `code + side + volume + 时间窗`）查当日委托：

```python
match = broker_orders.get(payload.get("client_order_id")) or fuzzy_match(...)
if match:
    wal.append("order", str(match["order_id"]), {"intent_id": iid, ...})
else:
    wal.append("intent_failed", iid, {"reason": "柜台查无此单", ...})
```

7. 前端：`status === "unknown"` 时按钮文案改“结果待确认”，并禁用同一 `code/side` 的重复提交 30 秒（**仅前端禁用**，理由见下）；提供“去对账页查看”。

> **为什么不在路由层按 `code+side` 隐式拒绝**：`SignalRouter.route()` 的既有契约是“人工单不自动生成幂等键——人工重复下单是真实意图，去重会挡住合理操作”。若在路由层按内容拦截，会误伤“用户确实想再买一笔”的合法场景。正确做法是**显式幂等**：前端为一次下单会话生成 `client_order_id` 并在 unknown 重试时沿用；后端把它写进 intent，命中同一 key 的未决单直接返回原结果（`duplicated=true`），而不是新下一单。

**验证（必须新增的回归）**：

| 用例 | 构造 | 断言 |
|------|------|------|
| 超时但柜台已接单 | fake bridge `place_order` 抛 `TimeoutError`，但 `get_orders` 返回该单 | 对账后 WAL 有 `order` 配对；不产生第二笔 `intent`；UI 状态为 `unknown` |
| 明确拒单 | `place_order` 返回 `status="rejected"` | 写 `intent_failed`；`unresolved_intents()` 为空；`retryable=true` |
| 崩溃窗口 | 写 `intent` 后直接重启 | 启动对账能列出该 intent；查不到则写 `intent_failed` 并告警 |
| 同一 key 重试 | 带相同 `client_order_id` 再提交 | 返回原 `intent_id` + `duplicated=true`；WAL 中该 key 只有一条 `intent` |
| 不同 key 重试 | 不带 key、同 `code/side` 再提交 | **允许**（人工重复下单是真实意图）；WAL 产生第二条 intent |

#### 3.7.2 `auth_token` 加密落库与脱敏

**现状**：`xtquant_client/manager.py:729` 附近把桥 `auth_token` 与普通字段一起写入 `broker_connections`；`core/crypto.py` 已有 AES-GCM（LLM Key 在用）。

**改法**：

1. 写入：`enc = crypto.encrypt(token)`，存 `auth_token_enc`；保留 `auth_token` 列但写 `None`（迁移期兼容）。
2. 读取：`token = crypto.decrypt(row["auth_token_enc"]) if row.get("auth_token_enc") else row.get("auth_token")`。
3. 迁移：`db_migrations` 增加一版，逐行 `SELECT id, auth_token` → 加密 → `UPDATE`，迁移完成后再清空明文字段（**先写后清，可回滚**）。
4. 脱敏：所有 `to_dict()` / 审计 payload / 日志格式化统一走 `mask_secret(token)`，只保留后 4 位。
5. 门禁：`check_no_plaintext_secret.py` 扫描 `broker_connections` 写入点，禁止直接写 `auth_token`。

**风险**：`master.key` 丢失会导致 token 不可解——需要与现有 LLM Key 相同的“密钥丢失即重填”引导，不能静默失败。

#### 3.7.3 503 语义：把“传输失败”和“业务不可用”分开

**现状**：

- `middleware/envelope.py` 把所有响应包成 `{code, message, data}`；
- 156 处 `err(503, ...)` 返回 **HTTP 200** + body `code=503`；
- 只有 `/ready` 返回真实 HTTP 503；
- 前端 `ApiError.brokerUnavailable` 用 `response.status === 503` 判断 → 永远 false；
- README 写“未连接券商返回 HTTP 503” → 与实现不符。

> **已修（2026-11-07，D-12 / TD-45）**：`middleware/envelope.py::_promote_status()`
> 把 `code=503` 提升为真实 HTTP 503，body 一字不改；`400/404/409` 保持 HTTP 200。
> 三重闸门：仅 `/api/v1/` 前缀、仅原状态 200、仅 `_PROMOTE_CODES`。
>
> **与下表的一处偏离（有意）**：下表设计 body 用 `5030/4001` 这类**独立业务码**；
> 实际实现**保持 `body.code` 就是 HTTP 码（503/400）**，不引入新码段。
> 理由：全仓 155 处 `err(503)` 与大量前端/用例都按 `code===503` 判断，改成
> `5030` 是一次纯破坏性的契约迁移，收益为零。**分层靠 HTTP 状态码完成，
> body 语义不动** —— 这也是「先修一类」能安全落地的前提。

**决策**（不要两边都改，选一个真源）：

| 场景 | HTTP 状态 | body.code | 说明 |
|------|-----------|-----------|------|
| 券商未连接 / SDK 缺失 / 桥不可用 | **503** | `5030`（业务码） | 传输层语义正确，监控可告警，前端可判断 |
| 参数非法 | 400 | `4001` | |
| 未认证 | 401 | `4010` | |
| 权限不足 | 403 | `4030` | |
| 资源不存在 | 404 | `4040` | |
| 业务规则拒绝（风控/额度） | **200** | `4200` | 这是“请求成功但业务拒绝”，不是传输错误 |
| 未知异常 | 500 | `5000` | |

**实施**：

1. `envelope.py` 增加 `class ApiError(Exception)`，携带 `http_status` 与 `code`；中间件捕获后设置真实状态码，body 仍保持统一结构（前端解包逻辑不变）。
2. 把 `err(503)` 批量替换为 `raise BrokerUnavailable(...)`；用 AST 脚本统计替换进度，先做 `trade/market/broker` 三个模块。
3. 前端 `ApiError` 同时支持 `status` 与 `body.code`，过渡期两者都认。
4. README 与 `API接口文档.md` 的错误码表以此表为准。

#### 3.7.4 API 类型化：先写路径，后读路径，最后生成前端类型

**为什么不能一次全补**：254 个端点、字段命名不统一（`code` 既表示股票代码又表示错误码）、部分返回结构随券商变化。一次性补模型会产出大量 `dict[str, Any]` 的“假模型”，比没有更糟。

**三步法**：

**第一步（1 个迭代）— 写路径 30 个端点**

优先级：`trade`（下单/撤单/批量）→ `broker`（连接/断开/测试）→ `config`（保存/导入）→ `qmt_agent`（部署/下发）。

```python
class PlaceOrderRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")
    code: str = Field(pattern=r"^\d{6}\.(SH|SZ|BJ)$")
    side: Literal["buy", "sell"]
    volume: int = Field(gt=0, le=1_000_000)
    price: float = Field(gt=0)
    price_type: Literal["limit", "market"] = "limit"
    broker_id: str | None = None
    remark: str = Field(default="", max_length=64)

class PlaceOrderResponse(BaseModel):
    ok: bool
    order_id: str | None = None
    intent_id: str
    status: Literal["submitted", "rejected", "unknown"]
    mode: Literal["live", "paper", "dry_run"]
    reason: str | None = None
    retryable: bool = False
```

**第二步（2 个迭代）— 读路径按域补**

每个域先定“稳定字段”，波动字段放 `extra: dict` 并标注 `deprecated`。不要追求 100%。

**第三步 — 前端类型生成**

```json
// package.json
"scripts": { "gen:api": "openapi-typescript http://127.0.0.1:8000/openapi.json -o src/shared/api-schema.d.ts" }
```

`shared/types.ts` 保留“UI 派生类型”（如 `PositionRow` 含格式化字段），API 原始类型改为从 schema 取：

```ts
import type { components } from "@/shared/api-schema";
export type PositionDTO = components["schemas"]["Position"];
```

**门禁**：`check_api_types.py` 对新增写端点断言 `response_model` 非空；对 `body: dict` 新增行直接失败（存量登记豁免清单，只减不增）。

#### 3.7.5 历史行情：`BarRepository` 读穿方案

**现状问题**（A-05）：`local_bars` 与 `kline_cache/kline_archive` 两套；`LocalStore` 只读热；`_rollover` 只归档 `kline_cache`。

**目标接口**（先加不改表）：

```python
class BarRepository:
    def __init__(self, hot: LocalStore, cold: ColdStore, cache: KlineCache): ...

    async def get_bars(
        self, code: str, period: str, start: str, end: str,
        adjust: str = "none", *, limit: int | None = None,
    ) -> list[Bar]:
        """唯一读入口：热 → 缓存 → 冷，逐层读穿；返回按时间升序、去重。"""
```

**读穿顺序与理由**：

1. `local_bars`（热，最新，写入最频繁）；
2. `kline_cache`（图表用，可能含未落 `local_bars` 的实时聚合）；
3. `kline_archive`（冷，历史全量）。

三层都可能重叠，统一按 `(code, period, ts)` 去重，**以热为准**。

**写入收敛**：

- 新增 `BarWriter.write(bars)`：只写 `local_bars`，并更新 `sync_watermark`；
- 归档 Job 每天把 `local_bars` 中 `ts < today - N` 的记录搬到 `kline_archive`，搬完删除热表旧数据；
- `kline_cache` 降级为“进程内/短期缓存”，不再作为长期真源；
- 过渡期双写，读走 Repository，写保持现状，**先统一读、再统一写**。

**一致性审计**（可作为 CI nightly）：

```sql
-- 抽样 100 个 code，比对两仓条数与最后一根时间
SELECT code, period, COUNT(*) AS n, MAX(ts) AS last_ts FROM local_bars GROUP BY code, period;
SELECT code, period, COUNT(*) AS n, MAX(ts) AS last_ts FROM kline_archive GROUP BY code, period;
```

差异超过阈值（如 5%）输出报告，不自动修——**先看见，再决定**。

#### 3.7.6 退役传输：让后端成为唯一真源

**现状**：`connectors/registry.py` 已定义 `RETIRED_PROFILES`，但前端 `Brokers.tsx` 仍把 `bridgeFile` 标“推荐”，且没有 `qmt.big.closed` 选项。

**改法**：

1. **新增** `GET /brokers/connectors`（当前不存在；`/brokers/profiles` 返回的是券商类型，不含传输方式），结构如下：

```json
{
  "key": "qmt.big.bridge.file",
  "label": "文件桥",
  "available": false,
  "retired": true,
  "retirement_notice": "策略进程禁文件读写（PermissionError: Forbidden FileIO）",
  "recommended": false
}
```

2. 前端**不再硬编码选项**，用返回列表渲染；`retired=true` 的项禁用 + 显示原因 + 不显示“推荐”角标。
3. 默认选中第一个 `available && recommended` 的项；若没有，显示“当前环境无可用接入方式”并给排查链接。
4. 补 `qmt.big.closed`（闭环通道）入口，与后端 `bigqmt_closed_loop_channel` 对齐。
5. 门禁：`check_capability_coverage.py` 增加“后端 connector 必须在前端有对应项或登记豁免”。

**验收**：在未安装 QMT 的机器上打开券商页，不应出现任何“推荐文件桥”的文案；点击退役项应看到具体原因，而不是连接后才报错。

## 4. 优化改进与重构方案

### 4.1 原则：先止血，再通血管，最后换器官

这套方案的总体策略是**绞杀者模式（Strangler Fig）**：新结构在旁边长出来，读路径先切、写路径后切，旧结构在无人使用后删除。**不做一次性大重构**，原因很现实：

- 项目有 2746 个用例、17 道 CI 门禁，大改会让门禁全红，团队无法判断“是真坏了还是预期变化”；
- 交易系统不能在“半重构”状态发布；
- 现有功能是资产，重构的第一目标是**不破坏它**。

六条具体原则：

| # | 原则 | 落地方式 | 反例（不要这样做） |
|---|------|----------|--------------------|
| P-01 | **先加护栏，再改代码** | 新规则先写成可执行门禁（脚本/测试），再改实现 | 先大改 `AppContext`，改完发现没测试能证明没坏 |
| P-02 | **单一真源** | 版本、连接器能力、K 线、任务调度各只有一个所有者 | 前后端各维护一份连接器列表 |
| P-03 | **显式状态机** | 订单/同步/任务必须有状态枚举 + 转移表 + 非法转移断言 | 用 `if not oid or rejected` 合并两种语义 |
| P-04 | **读先写后** | 新读模型先上线（读穿/双读比对），确认一致后再切写 | 直接迁表，出问题无法回滚 |
| P-05 | **小步可回滚** | 每个 PR 可独立回滚；数据库迁移先加列后删列 | 一个 PR 同时改表结构 + 业务逻辑 + 前端 |
| P-06 | **删除也是交付** | 每个 Phase 必须包含“删掉了什么” | 只加开关不收口，两年后三套并存 |

### 4.2 目标架构：模块化单体，不引入微服务

**结论先行**：这个产品是**桌面单机 + 单用户/小团队**形态，引入微服务、消息队列、独立数据库只会增加部署负担，不解决任何当前问题。目标架构仍是**模块化单体**，但把“边界”从“目录约定”变成“依赖规则 + 类型契约”。

```
┌──────────────────────────────────────────────────────────────────┐
│  表现层                                                           │
│  React SPA（pages / domains / components）                        │
│  ↕ HTTP(JSON, typed)   ↕ WS(typed events)                        │
├──────────────────────────────────────────────────────────────────┤
│  接口层  app/api/                                                │
│  routes（薄）→ schemas（Pydantic 请求/响应）→ deps（窄依赖）        │
├──────────────────────────────────────────────────────────────────┤
│  应用服务层  app/services/                                        │
│  TradeService · MarketService · SyncService · BrokerService       │
│  QmtAgentOps · ConfigService · ResearchService                    │
│  （编排用例；不碰 SQL、不碰 SDK；可被 REST 与 MCP 共用）             │
├──────────────────────────────────────────────────────────────────┤
│  领域层  backend/domain/（新增，纯 Python）                        │
│  OrderStateMachine · RiskPolicy · BarQuery · Signal · Position     │
│  只依赖 contracts；无 I/O、无框架、可 100% 单测                     │
├──────────────────────────────────────────────────────────────────┤
│  基础设施层  backend/infra/（逐步迁移）                             │
│  broker/（connectors + xtquant_client 适配）                       │
│  storage/（SQLite / WAL / BarRepository）                         │
│  runtime/（JobRuntime / Scheduler / WS Hub）                      │
├──────────────────────────────────────────────────────────────────┤
│  契约层  backend/contracts/（新增，零依赖）                         │
│  errors.py · models.py（DTO）· ports.py（Protocol）               │
└──────────────────────────────────────────────────────────────────┘
```

**依赖规则（可用 `import-linter` 强制）**：

1. `contracts` 不依赖任何内部包（只允许标准库 + `typing`）；
2. `domain` 只依赖 `contracts`；
3. `infra` 依赖 `contracts` + `domain`，**不依赖** `app/api`；
4. `app/services` 依赖 `domain` + `infra` 的**端口**，不直接 import 具体实现；
5. `app/api` 依赖 `services` + `schemas`，不直接 import `infra` 具体类；
6. `mcp_server` 与 `routes` 同级，都调 `services`。

> **迁移现实**：不可能一次到位。做法是“新代码进新目录，旧代码逐步搬”，`import-linter` 只对**新增文件**生效，存量在 baseline 里登记，只减不增。

**为什么不引入的东西**（明确写出来，避免反复讨论）：

| 方案 | 不采用的理由 |
|------|--------------|
| 微服务 | 单机桌面应用，进程间通信成本 > 收益；部署从“一个 exe”变成“多个服务”是倒退 |
| 消息队列（Kafka/RabbitMQ） | 单进程内 `asyncio.Queue` 足够；持久化已由 WAL 承担 |
| ORM（SQLAlchemy） | 现有 SQL 直写 + 迁移脚本可控；引 ORM 会带来 N+1 与隐式事务，收益不明确 |
| 全量 async SQLite 驱动 | SQLite 写是串行的，换 async 驱动不提升吞吐；应做“单 writer + 短事务” |
| 前端微前端 | 46 个页面、单团队，拆分只增加构建复杂度 |

### 4.4 六个重点改造的实施方案

#### 4.4.1 订单状态机与对账闭环（Phase 0，P0）

**目标**：任何一笔“已决定下单”的委托，最终都能落到一个**确定状态**；在确定之前，系统不得提示用户“失败可重试”。

**实施顺序**（每步可独立合并）：

| 步骤 | 改动 | 文件 | 验收 |
|------|------|------|------|
| 1 | 增加 `WAL_OP_INTENT_UNKNOWN`，`unresolved_intents()` 只认 `order`/`intent_failed` 为已配对 | `gateway/wal.py` | 单测：写 intent + unknown，未决列表包含它；写 intent + failed，未决列表为空 |
| 2 | `_live` 分支拆分“拒单/无委托号/异常类型”，返回 `status` 与 `retryable` | `gateway/signal_router.py` | 单测覆盖 4 种返回 |
| 3 | `OrderReconciler._pending_from_wal()` 接收 `intent`/`intent_unknown` | `gateway/reconcile.py` | 单测：仅 intent 记录也会进入 pending |
| 4 | 对账执行增加“按 client_order_id 查柜台 → 命中写 order / 未命中写 failed” | `gateway/reconcile.py` | 集成测试：fake bridge 超时但 get_orders 有单 |
| 5 | intent 记录 `client_order_id`；`route()` 命中“同 key 且未决”时直接返回原结果 | `gateway/signal_router.py`、`gateway/wal.py` | 接口测试：同 key 重试返回 `duplicated=true`，不产生第二笔 intent |
| 6 | 前端按钮态与提示 | `domains/trade/*` | 手工：unknown 时按钮禁用、文案正确 |

**回滚点**：第 1–2 步可单独回滚（只影响 WAL 语义，旧记录仍可读）；第 3–4 步回滚后对账退回“只看 order”，不会更坏；第 5 步是纯前端/路由保护，可单独关。

**不要做的事**：

- 不要为了“状态完整”引入 8 个状态（`PENDING_NEW/PARTIAL/...`）——当前柜台回报能力不支持，会造出一堆永远到不了的状态；
- 不要把 `intent_unknown` 写进主库订单表——WAL 是唯一真源，主库只存“已确认”的订单；
- 不要在 `except Exception` 里统一写 unknown——`BrokerRejectedError` 必须写 failed，否则对账会去查一笔根本不存在的单。

#### 4.4.2 券商接入收敛（Phase 1，P0→P1）

**目标**：一个环境下只有**一条**可执行的接入路径；退役路径在 UI 上不可选，在代码里不可达（或明确标注 legacy read-only）。

**三阶段**：

**阶段 A（Phase 0，2–3 人日）— 口径一致**

1. `connectors/registry.py::describe()` 已返回 `retired/retirement_notice`，确认 REST `/brokers/connectors` 原样透出；
2. 前端改为**数据驱动**渲染（见 3.7.6），删除硬编码 `bridgeFile 推荐`；
3. 文档（README、券商接入指南）同步“哪些方式已退役”；
4. 门禁：`check_capability_coverage.py` 覆盖 connector 项。

**阶段 B（Phase 1，5–8 人日）— 写路径单轨**

1. `ExecutionService.place_order` 中，`QMT_USE_PORTS=0` 的 legacy 分支改为**仅允许查询/撤单**，下单直接报“请升级到端口层”；
2. `BrokerManager._build_bigqmt_bridge` 统一走 `connectors`；mini 的 legacy adapter 保留只读；
3. 用 fake bridge 跑“新旧双跑一致性”测试（已有 `test_execution_ports_gray.py` 可扩展）；
4. 默认值 `QMT_USE_PORTS` 改为 `"1"`，保留关闭能力一个版本。

**阶段 C（Phase 2，3–5 人日）— 删除**

1. 删除 `QMT_USE_PORTS` 开关与 legacy 下单分支；
2. 删除 `gateway/easytrader_facade.py`（先确认无测试依赖，或迁移测试）；

4. 更新 `docs/` 与前端文案。

**风险**：miniQMT 已于 2026-10-23 关停，若仍有用户依赖旧路径，阶段 B 的“只读保留”是必要的过渡；**不要在阶段 B 直接删代码**。

#### 4.4.3 API 契约类型化（Phase 1，P1）

**目标**：新增/修改接口时，字段变化能在**编译期或 CI** 被发现，而不是用户点出来。

**分批策略**（按“改动频率 × 资金相关度”排序）：

| 批次 | 范围 | 端点数 | 产出 |
|------|------|--------|------|
| B1 | `trade` 下单/撤单/批量、`broker` 连接/断开/测试 | ~15 | `schemas/trade.py`、`schemas/broker.py`；前端类型生成接入 |
| B2 | `config` 保存/导入/导出、`qmt_agent` 部署/下发 | ~15 | `schemas/config.py`、`schemas/qmt_agent.py` |
| B3 | `market` 行情/K 线/搜索 | ~30 | `schemas/market.py`；大响应保留 `dict` 但给 `TypedDict` |
| B4 | 其余读接口 | ~190 | 只补 `response_model` 的“外层壳”，字段用 `dict` 并标注 `x-unstable` |

**工程配套**：

1. 在 `scripts/` 下新增 `gen_openapi.py`：启动 app（不连券商）导出 `openapi.json`，纳入仓库；
2. CI 增加 `openapi-diff`：PR 中字段删除/类型变化必须显式标注 `BREAKING`；
3. 前端 `npm run gen:api` 生成 `api-schema.d.ts`；`shared/types.ts` 只保留 UI 派生类型；
4. 新门禁 `check_api_types.py`：新增写端点无 `response_model` → 失败；`body: dict` 新增 → 失败。

**度量**：`response_model` 覆盖率从 0% → B1 完成后 6% → B4 完成后 60%（读接口允许例外），但**写接口必须 100%**。

#### 4.4.4 构建/部署单一真源（Phase 0–1，P0）

**目标**：`build_all.sh` / `build_all.bat` 只做“找到 Python 并调用”，所有逻辑在 Python 里，只有一份。

**目标结构**：

```
scripts/
  build.py            # 唯一编排入口：build.py [backend|frontend|electron|all] --release
  build_steps/
    __init__.py
    backend.py        # PyInstaller 调用、产物校验
    frontend.py       # vite build、类型检查
    electron.py       # electron-builder 调用
    verify.py         # 版本一致、产物无密钥、文件完整性
  qmt_agent_ops.py    # 部署/诊断共用逻辑（REST + CLI 都调）
```

**改造步骤**：

1. 把 `build_all.sh` 的步骤按“平台无关 / 平台相关”分类；平台相关的只有“找 Python 路径”“复制/权限”两类；
2. 逐段迁移到 `build.py`，每迁一段，让 `.sh` 调它，**保持行为不变**；
3. `.bat` 同样改为薄壳（`py -3 scripts\build.py %*`）；
4. 全部迁完后，删除 `.sh/.bat` 里的重复逻辑，只留 10 行以内；
5. CI 改为调用统一入口（在 `scripts/` 目录下执行 `python build.py all --release`）；
6. `verify.py` 统一校验：`VERSION` == `pyproject` == `package.json` == 产物内版本；包内无 `master.key`/`app.db`/`*.log`。

**回滚**：迁移期间 `.sh` 仍可直接执行原逻辑（保留 `--legacy` 分支一个版本）；出问题改回调用旧脚本即可。

**顺带解决**：A-13 版本一致性、D-34 产物版本校验，都放进 `verify.py`。

#### 4.4.5 历史行情单一读模型（Phase 2，P1）

**目标**：所有“读历史 K 线”的代码只依赖 `BarRepository`，不再直接 SQL 查两张表。

**步骤**：

| 步骤 | 内容 | 验收 |
|------|------|------|
| 1 | 在 `backend/app/data/` 下新增 `bar_repository.py`，实现热→缓存→冷读穿 + 去重 + 排序 | 单测：三层各放一部分数据，能拼成完整序列 |
| 2 | `bars_provider`、图表路由、回测入口改为调 Repository | 同一请求返回结果与旧实现逐条一致（录制对比） |
| 3 | 增加“双读比对”开关：旧路径与新路径都跑，不一致只告警不阻断 | 灰度 1 周，差异率 < 0.1% |
| 4 | 归档 Job 统一：`local_bars` 冷数据搬 `kline_archive`，更新 `sync_watermark` | 连续 3 天无堆积、无重复 |
| 5 | 删除 `LocalStore` 的直读方法（或标 `@deprecated` 并加门禁） | `grep "FROM local_bars"` 只剩 Repository |

**关键设计**：

```python
@dataclass(frozen=True)
class BarQuery:
    code: str
    period: Literal["1m", "5m", "15m", "30m", "60m", "1d"]
    start: date
    end: date
    adjust: Literal["none", "qfq", "hfq"] = "none"

class BarRepository(Protocol):
    async def query(self, q: BarQuery) -> list[Bar]: ...
    async def coverage(self, code: str, period: str) -> Coverage: ...  # 供 UI 显示“数据范围”
```

`coverage()` 很重要：前端可以显示“本地数据 2018-01-01 ~ 2026-11-03”，用户不会再问“为什么回测没数据”。

#### 4.4.6 前端服务端状态与错误边界（Phase 0 + Phase 3）

**Phase 0（1 人日）— 错误边界**

1. `src/app/ErrorBoundary.tsx`：`componentDidCatch` 上报（本地日志 + 可选后端 `/client-errors`），展示“重试 / 回首页 / 复制诊断信息”；
2. 路由级包裹每个 `page`，面板级再包一层（行情面板崩了不影响下单面板）；
3. `main.tsx` 外层兜底，防止 Electron 白屏无提示。

**Phase 3（8–12 人日）— 查询层**

1. 选型：TanStack Query（成熟、体积可接受）或自写 `useQuery`（约 150 行，可控）。**建议 TanStack Query**，因为需要缓存、去重、重试、取消、乐观更新，自写会重复造轮子；
2. 迁移顺序：`quotes`（高频）→ `positions/orders`（资金相关）→ `system/config`（低频）；
3. 约定：
   - `queryKey` 统一 `[domain, resource, params]`；
   - 行情类 `staleTime: 1s` + WS 推送时 `setQueryData`；
   - 持仓/订单 `staleTime: 0`，但 `refetchOnWindowFocus: true`；
   - 所有 mutation 走 `useMutation` + 统一错误 toast；
4. `useAsync` 保留为兼容层，内部改为 `useQuery`，逐步删除调用点；
5. `setInterval` 收口到 `usePolling(fn, ms, {enabled})`，组件卸载自动清理。

**验收**：切页 10 次，行情请求数从“每次 1 次”降为“缓存命中”；断网后恢复，页面能自动重试且不闪烁；任一页面抛错，壳仍可用。

### 4.5 门禁调整：加三道，改两道，删一道

| 动作 | 门禁 | 说明 |
|------|------|------|
| **新增** | `check_api_types.py` | 写端点必须有 `response_model`；`body: dict` 只减不增 |
| **新增** | `check_wal_state.py` | 断言 `intent_failed` 只在“明确拒单”路径出现；`intent_unknown` 必须能被 `unresolved_intents` 返回 |
| **新增** | `check_version_consistency.py` | `VERSION` / `pyproject` / `package.json` / 产物版本四处一致 |
| **调整** | `check_appcontext.py` | 从“文件数基线”改为“禁止新增 `Any` 字段 + 新文件必须用窄依赖” |
| **调整** | `ci_reconcile.py` | `EXPECTED_TESTS` 改为“collect 快照”，允许增加、删除需显式更新快照 |
| **删除/降级** | `check_broad_except.py`（拟新增后再评估） | 先用“只统计不阻断”模式跑一个版本，避免一次性 812 处全红 |

> 门禁的设计原则：**只拦“新增的坏”，不拦“存量的坏”**。存量用 baseline 登记，每月下调一次，否则改造第一天就会全红，团队会习惯性忽略红灯。

### 4.6 风险与回滚

| 风险 | 触发场景 | 缓解 | 回滚 |
|------|----------|------|------|
| 订单状态改造引入新 bug | Phase 0 第 1–4 步 | 全部改动带 fake bridge 回归；先在 paper 模式跑一周 | 回滚 WAL 常量与 `_live` 分支，旧记录仍可读（新增 op 不被旧代码识别，会被忽略而非报错） |
| 连接器收敛导致某环境无法下单 | 阶段 B 关闭 legacy 下单 | 保留 `QMT_USE_PORTS=0` 逃生开关一个版本；发布说明明确 | 置回 `0` 即可恢复旧路径 |
| K 线读模型不一致 | Phase 2 切换读路径 | 双读比对灰度；差异率阈值；保留旧实现一个版本 | 关闭 `BAR_REPOSITORY_V2` 开关 |
| 构建脚本迁移导致发布失败 | Phase 1 | `.sh` 保留 `--legacy`；CI 同时跑新旧产物比对 | 改回旧脚本调用 |
| 前端查询层引入渲染抖动 | Phase 3 | 按域迁移；每域迁移后跑视觉回归 | 单域回退到 `useAsync` |
| AppContext 收窄导致启动失败 | Phase 3 | 只改“读取方式”，不改装配顺序；每批跑全量启动测试 | 恢复 `get_ctx()` 调用 |

### 4.7 明确不做的事（防止范围蔓延）

1. **不拆微服务、不引入 MQ、不换数据库**——单机桌面形态不支持这些复杂度。
2. **不做全量目录搬迁**——`gateway/engines/tools` 的目录名保留，只在新代码中引入 `domain/services/infra`；搬迁留给“下次改到该文件时顺手做”。
3. **不把 `BIGQMT_AGENT.py` 拆多文件**——QMT 注入约束，拆了就无法部署。
4. **不把所有 SQL 改 async/ORM**——收益低、风险高；只做“单 writer + 短事务”。
5. **不用 `pytest.mark.flaky` 掩盖不稳定用例**——不稳定用例要么修，要么删，要么标 `quarantine` 并限期处理。
6. **不为“架构纯洁”重写前端**——现有设计系统与页面是资产，只加查询层与边界。
7. **不在 Phase 0 动 `AppContext`**——它不是资金风险，先做会挤占 P0 的时间。

## 5. 优先级与排期

### 5.1 影响 / 工作量矩阵

```
影响
 高 │  A-04 订单UNKNOWN      A-05 双K线仓
    │  D-07 auth_token        A-01 券商双轨
```

### 5.3 并行建议

**可以并行**：

- 后端交易安全（S1）与前端 ErrorBoundary/退役 UI（S2 的前端部分）——不同文件；
- 构建脚本（S3）与 API 类型化（S4）——不同目录；
- K 线读模型（S6/S7）与 WS 背压（S8）——不同子系统。

**不要并行**：

- 两个 PR 同时改 `signal_router.py` / `reconciler.py`；

- 同时改 `Brokers.tsx` 与 connector 后端（容易互相等待）。

**协调机制**：每个 Sprint 指定一个“文件所有权”清单，跨清单改动需提前一天打招呼。

```python
# 常量区（现有 WAL_OP_INTENT / WAL_OP_RESULT / WAL_OP_INTENT_FAILED 之后）
WAL_OP_INTENT_UNKNOWN = "intent_unknown"   # 已发出请求，但未拿到确定结果

def unresolved_intents(self) -> list[dict]:
    """已写 intent、无**确定**结果的记录。

    配对规则变更（P0-1）：
      - ``order``          → 已配对（拿到委托号）
      - ``intent_failed``  → 已配对（明确拒单）
      - ``intent_unknown`` → **不配对**，必须继续留在未决列表
    """
    records = self.all_records()
    resolved: set[str] = set()
    for rec in records:
        if rec.get("op") in (WAL_OP_RESULT, WAL_OP_INTENT_FAILED):
            iid = (rec.get("payload") or {}).get("intent_id")
            if iid:
                resolved.add(str(iid))
    out = []
    for rec in records:
        if rec.get("op") not in (WAL_OP_INTENT, WAL_OP_INTENT_UNKNOWN):
            continue
        iid = str(rec.get("entity_id") or "")
        if not iid:
            continue
        # unknown 记录本身可能已被后续 order 配对（对账认领成功）
        if iid in resolved:
            continue
        out.append(rec)
    return out

def find_intent_by_key(self, client_order_id: str) -> dict | None:
    """按 client_order_id 找最近的未决 intent（供重复提交短路）。"""
    if not client_order_id:
        return None
    latest = None
    for rec in self.all_records():
        if rec.get("op") not in (WAL_OP_INTENT, WAL_OP_INTENT_UNKNOWN):
            continue
        if str((rec.get("payload") or {}).get("client_order_id") or "") != client_order_id:
            continue
        latest = rec
    return latest
```

**注意**：`find_intent_by_key` 返回的可能是已配对的旧记录，调用方必须再查“是否已有 `order`/`intent_failed` 配对”，或直接复用 `unresolved_intents()` 的结果集做索引。**不要**只按 op 判断，否则会把已完成的历史单当成未决。

```python
# core/db.py
def _backfill_broker_tokens(self) -> None:
    """把历史明文 token 加密到 auth_token_enc；幂等，失败不阻断启动。"""
    from core.crypto import encrypt_plain
    try:
        rows = self._conn.execute(
            "SELECT conn_id, auth_token FROM broker_connections "
            "WHERE COALESCE(auth_token,'') <> '' AND COALESCE(auth_token_enc,'') = ''"
        ).fetchall()
    except sqlite3.Error:
        return
    for conn_id, token in rows:
        try:
            enc = encrypt_plain(str(token))
        except Exception as exc:          # 密钥缺失/损坏：保留明文，记录告警
            log.warning("token 加密失败 conn=%s: %s", conn_id, exc)
            continue
        with _rw.write():
            self._conn.execute(
                "UPDATE broker_connections SET auth_token_enc=? WHERE conn_id=?",
                (enc, conn_id))
            self._conn.commit()
```

#### 7.5.3 门禁脚本骨架

在 `scripts/` 下新增 `check_version_consistency.py`：

```python
"""版本/许可证一致性门禁：VERSION / pyproject / package.json / 产物。"""
from pathlib import Path
import json, re, sys, zipfile

ROOT = Path(__file__).resolve().parents[1]

def read_version() -> str:
    return (ROOT / "VERSION").read_text(encoding="utf-8").strip()

def pyproject_version() -> str:
    text = (ROOT / "backend" / "pyproject.toml").read_text(encoding="utf-8")
    m = re.search(r'^version\s*=\s*"([^"]+)"', text, re.M)
    return m.group(1) if m else ""

def package_version() -> str:
    data = json.loads((ROOT / "frontend-next" / "package.json").read_text(encoding="utf-8"))
    return str(data.get("version") or "")

def main() -> int:
    want = read_version()
    errors = []
    if pyproject_version() not in ("", want):     # 动态版本时为空，允许
        errors.append(f"backend/pyproject.toml={pyproject_version()} != VERSION={want}")
    if package_version() != want:
        errors.append(f"frontend-next/package.json={package_version()} != VERSION={want}")
    # 许可证：pyproject 声明的 SPDX 必须与根 LICENSE 首行一致
    lic = (ROOT / "LICENSE").read_text(encoding="utf-8", errors="replace").splitlines()[0]
    py = (ROOT / "backend" / "pyproject.toml").read_text(encoding="utf-8")
    if "Apache-2.0" in lic and "Apache-2.0" not in py:
        errors.append("LICENSE 为 Apache-2.0，但 pyproject 未声明同一许可证")
    for e in errors:
        print("FAIL:", e)
    print("OK" if not errors else f"{len(errors)} 处不一致")
    return 0 if not errors else 1

if __name__ == "__main__":
    sys.exit(main())
```

**许可证是产品决策，不是工程决策**：如果产品确实要闭源，应把根 `LICENSE` 改为专有许可并同步 `THIRD_PARTY_LICENSES.md`；如果沿用 Apache-2.0，则 `pyproject` 必须一致。**两者不能同时存在**——这是法务风险，不是风格问题。

### 7.6 P0-5：路由级 `ErrorBoundary`

#### 7.6.1 组件骨架

在 `frontend-next/src/app/` 下新增 `ErrorBoundary.tsx`：

```tsx
import { Component, type ErrorInfo, type ReactNode } from "react";

type Props = { children: ReactNode; scope?: string };
type State = { error: Error | null };

export class ErrorBoundary extends Component<Props, State> {
  state: State = { error: null };

  static getDerivedStateFromError(error: Error): State {
    return { error };
  }

  componentDidCatch(error: Error, info: ErrorInfo) {
    // 本地留痕 + 可选上报；不要在这里 throw
    console.error(`[${this.props.scope ?? "app"}] render error`, error, info.componentStack);
  }

  private reset = () => this.setState({ error: null });

  render() {
    if (!this.state.error) return this.props.children;
    return (
      <div role="alert" style={{ padding: 24, color: "var(--text)" }}>
        <h3 style={{ margin: "0 0 8px" }}>这个面板出错了</h3>
        <p style={{ color: "var(--text-faint)", margin: "0 0 12px" }}>
          {this.props.scope ? `范围：${this.props.scope}。` : ""}
          其他面板不受影响，可以重试或回到首页。
        </p>
        <pre style={{ maxHeight: 160, overflow: "auto", fontSize: 12 }}>
          {this.state.error.message}
        </pre>
        <button type="button" onClick={this.reset}>重试</button>
        <button type="button" onClick={() => { window.location.hash = ""; }}>
          回首页
        </button>
        <button
          type="button"
          onClick={() => navigator.clipboard?.writeText(
            `${this.state.error.message}\n${this.state.error.stack ?? ""}`)}
        >
          复制诊断
        </button>
      </div>
    );
  }
}
```

#### 7.6.2 两个接入点

| 位置 | 包法 | 效果 |
|------|------|------|
| `frontend-next/src/main.tsx` | `<ErrorBoundary scope="app"><App /></ErrorBoundary>` | 壳级兜底，防止整窗白屏 |
| `frontend-next/src/shell/Workspace/PaneTree.tsx`（`<Suspense>` 内） | `<ErrorBoundary key={node.pageKey} scope={node.pageKey}><def.comp {...props} /></ErrorBoundary>` | 单窗格崩溃不影响其他窗格；`key` 保证切页自动重置 |

**为什么用 `key`**：不加 `key` 时，边界 state 会跨页面保留，用户切到另一页仍看到上一页的错误。`key={node.pageKey}` 让每次换页都重建边界。

#### 7.6.3 验收

- 在任一页面组件里临时 `throw new Error("boom")`：该窗格显示错误卡片，其他窗格与标题栏/状态栏正常；
- 点击“重试”能重新渲染；切换页面后错误状态清空；
- 前端单测：渲染一个抛错子组件，断言错误文案出现且不冒泡到外层。
