# QMT Work 项目架构审计与优化重构方案 V3

> 日期：2026-09-09  
> 适用仓库：`coeasy/qmt_work`  
> 基线：当前 `main` 架构与近期重构结果  
> 目标：在不降低真实交易安全门禁、不破坏 QMT/XTQuant 运行兼容、不以大规模搬目录替代架构治理的前提下，将项目收敛为边界清晰、行为一致、可测试、可演进的本地优先量化工作台。

---

## 1. 文档结论摘要

QMT Work 已经不再是简单的 QMT API 包装层，而是逐步演化成一个完整的本地优先量化工作台，当前能力已经覆盖：

- 多券商 / 多连接管理；
- QMT / XTQuant Runtime 自动发现与 Python ABI 兼容；
- In-Process / Bridge 双运行模式；
- REST API / WebSocket / MCP Agent 接口；
- 行情与本地数据源抽象；
- 指标、公式 DSL、选股、因子研究；
- 向量化回测与参数优化；
- 模拟盘、实盘、条件单、算法单、策略自动执行；
- 风控、幂等、WAL、Reconcile、审计、通知；
- React + Electron 桌面工作台。

近期已经完成一批正确方向的架构整理，包括：

- `core/` 基础能力下沉；
- `datasource/` 从 `app/` 提升为顶层包；
- Strategy / Algo / Condition / Paper 等逐步归位 `engines/`；
- WebSocket、事件总线、DB 并发、审计身份、密钥安全等能力加强；
- 因子研究、行情、同步等模块逐步解除对 `app` 包的反向依赖。

但当前已经进入一个新的阶段：**不能再以“继续移动目录”作为重构主线，而应从物理分层切换为行为边界重构。**

本方案将后续主线收敛为：

> **恢复 CI 真实绿线 → 统一 ExecutionService → 生命周期/Ready → AppContext → Runtime 平台化 → Legacy Shim 清零 → 依赖锁定 → God File 拆分 → 前端类型化。**

其中最高优先级不是代码行数，而是**所有真实交易入口必须共享完全一致的执行、风控、模式、WAL、审计与幂等语义**。

---

## 2. 项目当前定位

建议正式把项目定位为：

> **QMT Work = Modular Quant Trading Workstation**
>
> 一个本地优先、支持多券商 Runtime、多数据源、策略研究、回测、自动交易、Agent/MCP 和桌面终端的一体化量化工作台。

它不是单纯的：

- QMT SDK Wrapper；
- Web 交易面板；
- MCP Server；
- 回测库；
- Electron 壳。

而是这些能力的统一宿主。

因此最适合的总体架构不是立即拆微服务，而是：

> **强边界 Modular Monolith（模块化单体）**。

原因：

1. QMT / XTQuant 强依赖 Windows 本地客户端；
2. Broker Runtime 涉及 Python ABI、进程发现和本地桥接；
3. 风控、执行、行情、审计之间需要低延迟和强一致行为；
4. 桌面 Electron 场景天然适合单机服务编排；
5. 过早微服务化会显著增加网络故障、部署、状态同步和调试成本。

---

## 3. 当前整体架构

当前代码可以抽象为以下 8 个层次：

| 层 | 当前模块 | 主要职责 |
|---|---|---|
| Desktop | `frontend/electron` | Electron 生命周期、拉起 Python 后端、窗口与进程管理 |
| Web UI | `frontend/src` | React/Vite/ECharts，行情、交易、账户、研究、回测、设置 |
| REST API | `backend/app/routes` | FastAPI HTTP 接口 |
| Agent API | `backend/mcp_server` + `backend/tools` | MCP Tools、Agent 可调用能力 |
| Engine | `backend/engines` | Strategy、Algo、Condition、LimitUp、Paper 等 |
| Trading Infra | `backend/gateway` | Risk、Signal、WAL、Reconcile、Audit、RateLimit、Webhook 等 |
| Broker Runtime | `backend/xtquant_client` | QMT 发现、Runtime ABI、Bridge、Broker Adapter |
| Core/Data | `backend/core` + `backend/datasource` | 配置、状态、DB、密钥、数据源、本地 Store |

当前依赖方向已经比旧版本合理，但仍存在入口不统一、Service Locator、平台语义泄漏和兼容层残留问题。

## 4. 主要功能域梳理

### 4.1 券商 Runtime 与多连接

核心链路：

```text
QMT/券商客户端发现
        ↓
XTQuant 路径解析
        ↓
Python ABI 探测
        ↓
Runtime Resolver
   ┌────┴────┐
   ↓         ↓
in_process  bridge
   └────┬────┘
        ↓
Broker Adapter / Gateway
        ↓
BrokerManager
```

当前优势：

- 支持券商 SDK 与主后端 Python 版本不一致；
- Bridge 模式降低 ABI 冲突；
- 多券商、多连接模型已经具备基础；
- Broker Adapter 正在形成统一 Contract。

后续重点不应继续堆兼容判断，而应把平台路径、ABI 探测、Runtime 选择彻底纯函数化和可测试化。

### 4.2 行情与数据平台

当前数据层已经从“券商行情读取”扩展成：

```text
Broker/QMT
TDX/optional source
Local Store
History Sync
Instrument Registry
Period Normalization
Fallback/Degrade
```

这意味着 `datasource` 应成为独立基础设施边界，不应再依附 FastAPI `app`。

### 4.3 交易与风险管理

已经具备：

- RiskManager；
- SignalRouter；
- Paper / Dry-run / Live / Paused 模式；
- TOTP / 实盘确认；
- 幂等控制；
- WAL；
- Reconcile；
- Audit；
- Notifier / Webhook；
- Order Watchdog；
- Trading Session。

这些能力是未来 `ExecutionService` 的基础。

### 4.4 策略、指标、因子与回测

当前已经覆盖：

- 指标注册中心；
- Formula / DSL；
- 常见技术指标；
- Vectorized Backtest；
- 参数搜索；
- Factor Research；
- Screener；
- Natural Language Screen；
- Strategy Runtime；
- Strategy Market。

建议继续保持“研究计算层”和“实盘执行层”分离，禁止研究模块直接拥有 Broker 下单能力。

### 4.5 自动化执行 Engine

当前包括：

- StrategyRuntime；
- AlgoEngine；
- ConditionOrderEngine；
- LimitUpMonitor；
- PaperEngine。

后续这些 Engine 应只负责：

> **什么时候产生交易意图（Intent）**，而不是负责真实订单的最终执行。

最终所有 Intent 必须交给统一 ExecutionService。

### 4.6 REST / MCP / WebSocket

目前项目同时有三类外部接口：

```text
React / External Client / Agent
          │
          ├── REST
          ├── WebSocket
          └── MCP
```

MCP 当前只自动暴露 Agent Visible 的 GET 只读端点，这一安全原则应保留。

写入型能力必须明确走交易命令入口，不能由 REST、MCP 或 Engine 分别维护各自交易逻辑。

## 5. 当前高优先级问题

## P0-1：交易入口实际上尚未真正统一

这是当前最重要的架构问题。

当前 Strategy Runtime 已经向统一 SignalRouter 收敛，但仍存在其他入口直接调用 Broker Gateway 的情况，例如：

```text
REST /trade/order
    ↓
RiskManager
    ↓
Gateway.place_order
```

以及：

```text
MCP place_order
    ↓
RiskManager
    ↓
Gateway.place_order
```

这意味着不同入口可能拥有不同的：

- 行情价格获取规则；
- 风控价格语义；
- 幂等窗口；
- Paper / Dry / Live 模式；
- TOTP / 确认策略；
- WAL 行为；
- 审计来源；
- 通知行为；
- 失败恢复规则。

特别需要禁止“没有真实市价时使用固定假价格完成风险检查”的逻辑。

### 目标

所有订单必须形成统一命令：

```text
OrderIntent
    ↓
ExecutionService
    ↓
Validation
    ↓
Pricing
    ↓
Risk
    ↓
Execution Mode
    ↓
Idempotency
    ↓
WAL
    ↓
BrokerPort
    ↓
Audit / Notify / Reconcile
```

### 硬门禁

除以下位置外，仓库不得直接调用真实 `place_order`：

- ExecutionService；
- Broker Adapter 内部实现。

REST、MCP、Strategy、Algo、Condition、Rebalance、TargetPosition 全部禁止直连 Broker 下单。

## P0-2：启动生命周期与 Readiness 语义不一致

当前后端启动已经存在多阶段 bootstrap，但部分阶段异常可能只记录日志后继续启动。

与此同时，后端已经有 `/live`、`/ready`、`/health` 的基础能力，但 Electron 后端探测仍需要明确改为真正的 readiness。

### 推荐语义

| Endpoint | 语义 |
|---|---|
| `/live` | Python 进程是否存活 |
| `/ready` | 核心依赖是否准备好，可以正式接受请求 |
| `/health` | 所有组件详细状态，包括 degraded 信息 |

### Required Bootstrap

以下失败必须阻止 READY：

- Settings；
- DB；
- Migration；
- AppContext；
- ExecutionService；
- 必需路由/协议初始化。

### Optional Bootstrap

以下失败允许 READY + DEGRADED：

- Broker 自动连接；
- Redis；
- 外部补充行情；
- Notifier；
- Cache Warmup。

### Electron

Electron 必须：

```text
spawn backend
    ↓
/live
    ↓
/ready == 200
    ↓
打开主界面
```

不能再使用 `/docs` 是否能访问作为“系统已经准备好”的判断。

## P0-3：当前 Main CI 处于真实红灯状态

当前重构不能继续以大范围目录移动为优先，原因是主干存在真实门禁失败。

当前已确认问题类型包括：

1. Frontend CI `setup-node` 缓存路径与 `frontend/package-lock.json` 不匹配；
2. `app.crypto → core.crypto` 迁移后测试仍依赖旧私有实现；
3. Runtime selector 测试把宿主 Python ABI 与目标 Runtime 语义混在一起；
4. Linux runner 使用 `os.path` 解析 Windows 路径；
5. Ruff 在近期目录迁移后仍有存量问题未收尾。

### 原则

在 main 恢复绿色之前：

- 不继续大规模移动目录；
- 不降低 Ruff/Test/Build 门禁；
- 不通过 skip 掩盖 Runtime 问题；
- 不修改测试预期去迁就错误实现；
- 先修真实行为，再恢复 CI。

## 6. P1 架构问题

### 6.1 全局 AppState / Service Locator 过重

当前大量模块通过全局 `state` 获取：

- DB；
- BrokerManager；
- Risk；
- Gateway；
- Sync；
- Backtest；
- WS；
- Engine；
- Cache。

这种模式短期方便，但会导致：

- 测试状态污染；
- 生命周期不清晰；
- teardown 困难；
- 组件依赖无法静态分析；
- 多 App 实例困难；
- 隐式耦合扩大。

### 目标

```python
@dataclass
class AppContext:
    db: Database
    broker_manager: BrokerManager
    risk: RiskManager
    execution: ExecutionService
    quote_bus: QuoteBus
    sync: SyncService
    ...
```

生命周期：

```text
create_app()
   ↓
create_context()
   ↓
app.state.ctx
   ↓
FastAPI Depends / explicit constructor injection
```

最终门禁：

- module-level mutable service instance = 0；
- class-level mutable AppState = 0；
- 新业务模块禁止直接 import 全局 `state`。

### 6.2 Windows Runtime/路径语义泄漏到宿主 OS

当前 Runtime / Discovery 中部分逻辑仍依赖：

- `os.path`；
- `sys.executable`；
- `os.name`；
- 当前 runner 的平台状态。

这使得 Linux CI 难以正确测试 Windows 路径和 Runtime 决策。

### 重构目标

```text
RuntimeResolver
 ├── RuntimePolicy
 ├── ABIProbe
 ├── RuntimeDiscovery
 ├── PlatformPaths
 └── RuntimeLauncher
```

Windows 路径语义使用：

```python
PureWindowsPath(...)
```

核心 Runtime 选择改为纯输入：

```python
select_runtime(
    broker_abis,
    host_abi,
    bundled_runtimes,
    system_runtimes,
    platform,
)
```

而不是函数内部读取宿主环境后再推导行为。

### 6.3 Python 依赖不可复现

当前生产依赖大量使用下限约束：

```text
fastapi>=...
pydantic>=...
numpy>=...
pandas>=...
pytest
```

对以下项目风险较高：

- FastMCP；
- PyInstaller；
- Pandas/Numpy；
- Starlette/httpx；
- Runtime Bridge；
- Electron 打包。

### 推荐

优先：

```text
pyproject.toml
uv.lock
```

依赖组：

```text
runtime
broker
research
test
dev
build
optional-eltdx
```

CI 统一：

```bash
uv sync --frozen
```

依赖升级通过专门 PR 完成，不允许 CI 每次隐式漂移到 PyPI 新版本。

### 6.4 Legacy Compatibility Shim 未完成退出

近期已经形成：

```text
app.config     → core.config
app.crypto     → core.crypto
app.db         → core.db
app.state      → core.state
app.datasource → datasource
```

但生产代码和测试仍存在旧路径依赖。

建议明确四阶段：

```text
A. 新模块成为唯一 SSOT
B. 旧模块仅 re-export public API
C. CI 禁止生产代码继续 import 旧路径
D. 删除 shim
```

不要长期维护“双实现 + 转发层”。

### 6.5 本机 Loopback 免鉴权安全边界需要加强

桌面软件为了方便允许 loopback 访问是合理的，但本项目具有真实下单能力，因此：

> `localhost` 本身不应等价于“完全可信”。

建议 Electron 启动 backend 时生成一次性/会话级 Desktop Session Credential：

```text
localhost + valid desktop session token = trusted desktop client
```

远程 API Key / Scope / RateLimit 体系继续保留。

## 7. P2 可维护性问题

### 7.1 God File

当前部分文件已经承担过多职责，例如：

- 行情源实现；
- XTQuant 环境发现；
- Bridge Client；
- Market Routes；
- Datasource Registry；
- Strategy Runtime；
- Algo Engine；
- Condition Engine。

但拆分原则不能是“文件超过 N 行就拆”。

必须按职责边界拆，例如：

```text
xtquant_client/runtime/
  abi.py
  discovery.py
  policy.py
  resolver.py
  launcher.py
```

而不是把一个 2000 行文件机械切成 4 个 500 行文件。

### 7.2 前端 Feature 边界不清

建议逐步调整为：

```text
frontend/src/
  app/
    router/
    providers/

  features/
    market/
    trading/
    broker/
    accounts/
    strategy/
    backtest/
    research/
    settings/

  shared/
    api/
    ws/
    events/
    ui/
    types/
```

优先改造高风险交易领域，而不是一次性全站 TypeScript 化。

### 7.3 API Contract 仍依赖人工同步

FastAPI 已经天然生成 OpenAPI。

推荐：

```text
FastAPI OpenAPI
      ↓
Generated TS Types / Client
      ↓
Frontend
```

优先类型化：

- Trade；
- Broker；
- Account；
- Strategy Execution；
- Risk / Precheck。

## 9. ExecutionService 详细设计

这是 V3 最核心的重构。

### 9.1 输入统一成 OrderIntent

```text
OrderIntent
  source
  broker_id
  account_id
  symbol
  side
  order_type
  quantity
  limit_price
  strategy_id
  remark
  idempotency_key
  metadata
```

`source` 明确区分：

- manual_rest；
- manual_ui；
- mcp；
- strategy；
- algo；
- condition；
- rebalance；
- target_position。

### 9.2 Execution Pipeline

```text
normalize intent
    ↓
resolve broker/account
    ↓
resolve market price if needed
    ↓
validate instrument/session
    ↓
risk precheck
    ↓
execution-mode policy
    ↓
auth/confirm policy
    ↓
idempotency
    ↓
WAL append
    ↓
broker submit
    ↓
WAL commit/update
    ↓
audit
    ↓
notify/event
    ↓
reconcile tracking
```

### 9.3 市价单规则

禁止任何固定价格占位完成风险检查。

必须：

1. 获取真实可用 quote；
2. 获取失败时根据 source/policy 明确拒绝或采用保守估值；
3. 保守估值规则必须写入统一 PricingPolicy；
4. 所有入口行为完全一致。

### 9.4 幂等

统一幂等层，不允许 REST 一套 5s、MCP 一套 30s、Engine 再一套实现。

推荐：

```text
IdempotencyService
  explicit client key
  deterministic fingerprint
  in-flight singleflight
  durable order mapping when needed
```

## 10. CI / 架构门禁设计

V3 重构必须“每改一个行为，就增加一个阻止回退的门禁”。

### 10.1 交易入口门禁

AST/静态扫描：

```text
非 ExecutionService / BrokerAdapter 直接 place_order = 0
```

### 10.2 Legacy Import 门禁

逐阶段禁止：

```text
from app.crypto...
from app.db...
from app.config...
from app.state...
from app.datasource...
```

允许兼容 shim 自身和专门 compatibility test。

### 10.3 Runtime 门禁

Ubuntu：

- pure runtime resolver tests；
- path parser tests；
- API / data / research tests。

Windows：

- Windows path semantics；
- QMT discovery mock/probe；
- bridge startup；
- PyInstaller smoke；
- Electron startup smoke。

### 10.4 Readiness 门禁

自动测试：

- required phase 失败 `/ready` 必须 503；
- optional phase 失败 `/ready` 可 200 但 health 必须 degraded；
- Electron 只在 ready 后加载主工作区。

### 10.5 API Contract 门禁

生成 OpenAPI 后验证：

- schema 可生成；
- TS client 无 diff 或已提交；
- Trade/Account/Broker 请求响应类型一致。

### 10.6 依赖门禁

- 锁文件必须存在；
- CI `--frozen`；
- 锁文件变化必须显式出现在 PR diff；
- optional research-only license 依赖不得进入默认商用 runtime。

## 11. 推荐实施阶段

## Phase 0：恢复 Main 真实绿线

目标：停止结构继续漂移，先建立可信基线。

任务：

1. 修 Frontend CI lockfile/cache path；
2. 修 Crypto shim / test contract；

## 14. 不建议做的事情

### 不建议 1：现在直接拆微服务

当前 Broker/Runtime/Execution 是本地低延迟强耦合场景，微服务会增加复杂度而非降低复杂度。

### 不建议 2：一次性全仓库重命名

当前 main 尚需恢复真实门禁，继续大规模移动目录只会扩大回归面。

### 不建议 3：先机械拆大文件

业务入口尚未统一前拆文件，会把一个逻辑问题扩散成多个文件中的分布式问题。

### 不建议 4：立即替换 SQLite

Electron 本地 profile 使用 SQLite 非常合理。只有真正进入长期远程多用户服务时，再新增 PostgreSQL Repository 实现。

### 不建议 5：直接全前端 TypeScript 化

优先交易、券商、账户、策略执行等高风险模块，逐步覆盖即可。
