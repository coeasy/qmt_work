# QMT Work 多交易客户端平台架构完整重构方案 V4

> 日期：2026-09-09  
> 仓库：`coeasy/qmt_work`  
> 目标：从“以 QMT/XTQuant 为核心、预留其他适配器”的工作台，升级为“QMT 只是首个 Connector，后续可持续接入多类交易客户端、券商 SDK、远程交易服务和多资产交易通道”的统一量化交易平台。

---

# 1. 核心结论

当前架构已经具备多客户端的雏形，但还没有真正完成“多交易客户端平台化”。

现有 `BrokerAdapter` 已经声明支持 QMT、同花顺、PTrade、掘金等统一实现方向，Registry 也已经预留 `ths / ptrade / juejin` Profile；但当前基础设施仍然明显围绕 XTQuant/QMT 构建：

- `BrokerAdapter` 是一个过大的胖接口，同时绑定行情、交易、账户、参考数据、L2、生命周期；
- `BrokerManager` 中仍包含 QMT 路径发现、`xtquant` SDK 探测、MiniQMT/完整版判断等专有逻辑；
- `XTQuantBridge` 仍是 Manager 的直接组成部分；
- Runtime Resolver 主要围绕 Python ABI + XTQuant；
- Connection 与 Broker、Client、Account 等概念没有完全拆开；
- 能力协商已有雏形，但尚未真正成为前端、Execution、数据层的统一决策依据；
- 其他客户端适配器目前主要还是接口占位，而不是可独立安装、运行、升级、验证的 Connector。

因此后续需要的不是继续往 `xtquant_client/adapters/` 里添加更多类，而是完成一次**平台级架构重构**：

> **QMT/XTQuant 从“系统基础架构”降级为一个 Connector 实现；系统核心只认识标准化的 Port、Capability、Canonical Model、Connection 和 Execution。**

建议的最终定位：

> **QMT Work = Multi-Client Quant Trading Platform**
>
> 本地优先、桌面优先，同时支持多券商客户端、多 SDK、多账户、多资产、多 Runtime、多数据源和 Agent/MCP 的模块化量化交易平台。

# 2. 当前多客户端架构的真实状态

当前大致结构：

```text
React / REST / MCP / Strategy / Algo / Condition
                       │
                       ▼
                 app / tools / engines
                       │
                       ▼
                   BrokerManager
                       │
                       ▼
                  BrokerAdapter
          ┌────────────┼────────────┐
          ▼            ▼            ▼
      XTQuant       THS(planned)  PTrade(planned)
          │                         │
          ▼                         ▼
   XTPQuantAdapter             ExternalAdapter
          │
     ┌────┴────┐
     ▼         ▼
 in-process  Bridge
```

这一结构已经比“代码直接依赖 xtquant”好很多，但依然存在三个关键问题：

1. **抽象粒度不正确**：`BrokerAdapter` 把所有能力捆绑在一个接口中；
2. **Manager 泄漏供应商实现**：通用连接管理器知道 QMT 路径、ABI、xtquant；
3. **扩展方式仍偏源码式**：新增客户端仍然倾向于修改 Registry + 增加 Python 类 + 修改 PyInstaller hidden imports。

如果继续按当前方式扩展 5～10 个客户端，会迅速出现：

```text
BrokerManager if/else 膨胀
Registry profile 膨胀
PyInstaller hidden-import 膨胀
各客户端特殊参数散落
前端券商连接页大量条件判断
不同客户端订单/账户/行情字段差异不断泄漏到业务层
```

因此现在是完成平台化边界的最佳时间点。

# 3. 目标：QMT 只是 Connector，不再是 Core

重构后的原则：

```text
Core/Application 不 import xtquant_client
Core/Application 不知道 QMT userdata_mini
Core/Application 不知道 Python ABI
Core/Application 不知道 gm / ptrade / ths SDK
Core/Application 不知道某客户端是进程内、子进程、HTTP 还是 Native DLL
```

这些全部属于：

```text
infrastructure/connectors/<connector>/
```

目标依赖方向：

```text
                  ┌──────────────────────┐
                  │ UI / REST / MCP / WS │
                  └──────────┬───────────┘
                             ▼
                  ┌──────────────────────┐

                  └──────────┬───────────┘
                             ▼
                 ┌────────────────────────┐
                 │ Canonical Domain Model │
                 └───────────┬────────────┘
                             ▼
               ┌─────────────────────────────┐
               │            Ports            │
               │ Execution / Account / Quote │
               │ History / Reference / Event │

                            ▼
               ┌─────────────────────────────┐
               │      Connector Runtime      │
               │ Registry / Supervisor / IPC │

       ┌────────────────────┼─────────────────────┐
       ▼                    ▼                     ▼
  QMT Connector        PTrade Connector       GM Connector
  XTQuant/Bridge       SDK/Remote API         SDK/API
       │                    │                     │
       ▼                    ▼                     ▼

```

# 4. 第一项关键重构：拆掉胖 `BrokerAdapter`

当前 `BrokerAdapter` 同时承担：

- connect / close；
- quote / tick / kline；
- stock list / sector / calendar；
- account / cash / positions；
- orders / deals；
- place/cancel order；
- L2；
- callbacks。

这对 QMT 单体系方便，但对多客户端并不合理。

原因：不同客户端可能只支持部分能力，例如：

```text
Client A：交易 + 账户，不提供行情
Client B：行情很好，但不支持交易
Client C：支持股票，不支持期权
Client D：只提供 HTTP API，无本地客户端
Client E：只能在指定 Python 版本子进程运行
Client F：一个连接可挂多个账户
```

因此改成 Capability Ports。

## 4.1 建议的 Port

```text
ConnectorLifecycle
ConnectionHealthPort

ExecutionPort
OrderQueryPort
AccountPort
PositionPort

QuotePort
MarketDepthPort
HistoryPort
ReferenceDataPort

EventStreamPort
```

Python 形态示意：

```python
class ExecutionPort(Protocol):
    def submit_order(self, order: CanonicalOrderRequest) -> CanonicalOrder: ...
    def cancel_order(self, request: CancelRequest) -> CancelResult: ...

class AccountPort(Protocol):
    def accounts(self) -> list[TradingAccount]: ...
    def balances(self, account_id: str) -> AccountBalance: ...
    def positions(self, account_id: str) -> list[Position]: ...

class MarketDataPort(Protocol):
    def quote(self, instrument: InstrumentId) -> Quote: ...
    def subscribe(self, instruments: list[InstrumentId], handler): ...
```

一个 Connector 可以实现多个 Port：

```text
QMTConnector
 ├── ConnectorLifecycle
 ├── ExecutionPort
 ├── AccountPort
 ├── QuotePort
 ├── HistoryPort
 ├── ReferenceDataPort
 └── EventStreamPort
```

而行情源可以只实现：

```text
TDXConnector
 ├── QuotePort
 ├── HistoryPort
 └── ReferenceDataPort
```

这样“行情供应商”和“真实交易客户端”彻底解耦。

# 5. 第二项关键重构：建立 Canonical Trading Model

多客户端最大的长期成本不是连接方式，而是**语义不一致**。

必须建立平台自己的标准模型，所有 Connector 只负责双向转换。

## 5.1 Instrument

```text
InstrumentId
  symbol
  exchange
  asset_class
  currency
```

禁止核心业务长期使用模糊字符串：

```text
000001.SZ
SH600000
600000.SH
SZSE.000001
```

Connector 内部负责转换。

## 5.2 Order

建议统一：

```text
OrderRequest
  client_order_id
  account_id
  instrument
  side
  position_effect
  order_type
  time_in_force
  quantity
  limit_price
  stop_price
  source
  strategy_id
  metadata
```

标准枚举：

```text
Side
  BUY / SELL

OrderType
  MARKET
  LIMIT
  BEST
  STOP
  STOP_LIMIT
  FAK
  FOK
  OTHER

PositionEffect
  OPEN
  CLOSE
  CLOSE_TODAY
  AUTO
```

股票、期货、期权、信用账户的差异不能继续通过 `direction="buy"` + `price_type="limit"` 承载。

## 5.3 标准状态

```text
OrderStatus
  NEW
  ACCEPTED
  PARTIALLY_FILLED
  FILLED
  CANCEL_PENDING
  CANCELED
  REJECTED
  EXPIRED
  UNKNOWN
```

每个 Connector 建立 Vendor Mapping：

```text
vendor status → canonical status
canonical order type → vendor order type
```

核心系统不接触供应商状态码。

# 6. 第三项关键重构：Broker / Client / Connector / Account 解耦

当前模型容易把以下概念混在一起：

```text
券商
客户端
SDK
连接
资金账户
Runtime
```

未来必须明确：

## Broker

业务品牌/券商实体，例如：某证券公司。

## Client Family

软件/协议体系：

```text
QMT
PTrade
THS Quant
GM
Other REST Broker
```

## Connector

平台里的实现插件：

```text
qmt-xtquant
ptrade-sdk
gm-api
ths-quant
```

## Connection

一个 Connector 的运行实例：

```text
connection_id
connector_id
runtime_id
endpoint/client_path
health
```

## TradingAccount

独立账户：

```text
account_id
broker_id
account_type
market
```

关系应该支持：

```text
1 Connector Instance
       │
       ├── Account A
       ├── Account B
       └── Account C
```

不能假设：

```text
1 Connection = 1 Account
```

# 7. 第四项关键重构：从 Broker Registry 升级为 Connector Registry

当前 Registry 是很好的起点，但未来不应仅注册券商名字。

建议引入：

```text
ConnectorManifest
```

示例：

```yaml
id: qmt-xtquant
name: QMT / XTQuant
version: 1.0.0
vendor: qmt-work
transport: subprocess
runtime:
  type: python
  supported_abis: [cp38, cp39, cp310, cp311, cp312]
capabilities:
  execution: true
  account: true
  positions: true
  quote: true
  history: true
  l2: optional
asset_classes:
  - stock
  - credit
  - option
  - futures
config_schema: qmt.schema.json
```

其他 Connector 无需遵循 QMT 的 Runtime：

```yaml
id: broker-rest
transport: http
runtime:
  type: none
```

或者：

```yaml
id: vendor-native
transport: native
runtime:
  type: native-dll
```

Registry 负责：

```text
discover
install
validate
load manifest
create runtime
probe capabilities
version compatibility
upgrade
uninstall
```

而不应该负责具体 QMT ABI 选择。

# 8. 第五项关键重构：Connector Runtime Platform

后续不同客户端的最大现实问题，是 Runtime 千差万别。

需要统一运行模型。

建议：

```text
ConnectorRuntime
 ├── InProcessPythonRuntime
 ├── PythonSubprocessRuntime
 ├── NativeProcessRuntime
 ├── HttpRuntime
 └── ExternalServiceRuntime
```

其中 QMT 当前的 ABI/Bridge 能力变成：

```text
QmtRuntimeProvider
      ↓
PythonSubprocessRuntime
```

而不是整个系统的 Runtime 模型。

## 8.1 RuntimeSupervisor

统一管理：

```text
STARTING
READY
DEGRADED
RECONNECTING
STOPPING
STOPPED
FAILED
```

职责：

- 拉起/关闭 Connector；
- 心跳；
- backoff reconnect；
- child process tree；
- crash diagnostics；
- stdout/stderr；
- runtime PID；
- 资源回收；
- capability probe。

`BrokerManager` 不再直接处理 QMT `userdata_mini` 和 xtquant 路径。

---

# 9. 第六项关键重构：ConnectionSupervisor 取代当前 BrokerManager 的供应商逻辑

目标：

```text
ConnectionSupervisor
  │
  ├─ ConnectorRegistry
  ├─ RuntimeSupervisor
  ├─ ConnectionRepository
  ├─ CapabilityRegistry
  └─ HealthMonitor
```

只处理标准连接生命周期。

QMT 的：

```text
client_path 校验
userdata_mini
xtquant discovery
ABI probe
Bridge
```

全部移动到：

```text
connectors/qmt/
```

PTrade/GM/THS 分别拥有自己的 discovery/runtime/config。

# 10. 第七项关键重构：ExecutionService 必须独立于客户端

这是所有交易客户端共享的资金安全边界。

最终链路：

```text
UI
REST
MCP
Strategy
Algo
Condition
Rebalance
       │
       ▼
   OrderIntent
       │
       ▼
 ExecutionService
       │
       ├─ InstrumentNormalizer
       ├─ PricingPolicy
       ├─ SessionPolicy
       ├─ RiskManager
       ├─ PermissionPolicy
       ├─ ExecutionMode
       ├─ Idempotency
       ├─ WAL
       └─ Audit
       │
       ▼
ExecutionPort
       │
 ┌─────┼────────────┐
 ▼     ▼            ▼
QMT  PTrade        GM
```

核心要求：

> 新增任何客户端都不能重新实现一遍风控、幂等、实盘确认和 WAL。

Connector 只负责：

```text
canonical request
      ↓
vendor request
      ↓
vendor SDK
      ↓
vendor result
      ↓
canonical result
```

# 11. 第八项关键重构：行情与交易来源解耦

当前 `BrokerAdapter` 容易让系统形成：

```text
下单用哪个 Broker
行情也必须来自哪个 Broker
```

后续不应该如此。

建议：

```text
MarketDataRouter
```

允许：

```text
交易：QMT
实时行情：QMT
历史行情：本地数据库
参考数据：独立数据源
```

或者：

```text
交易：PTrade
实时行情：独立行情 Connector
历史行情：QMT / TDX / Local
```

路由策略：

```text
preferred provider
fallback provider
quality
latency
freshness
capability
```

这样新增交易客户端不要求它必须实现完整行情系统。

# 12. 第九项关键重构：Capability 必须成为平台核心机制

现有 capabilities 应升级为强类型能力模型。

示例：

```text
ExecutionCapabilities
  market_order
  limit_order
  cancel
  batch_order
  credit
  futures
  options

MarketDataCapabilities
  snapshot
  depth_5
  l2
  tick
  kline
  subscribe

AccountCapabilities
  cash
  positions
  orders
  trades
  multi_account
```

所有业务使用：

```text
capability check
      ↓
允许功能 / 降级 / 禁用
```

而不是：

```python
if broker_id == "xxx":
```

硬门禁：

> application/frontend 中基于 `broker_id/adapter_id` 判断业务行为的新增代码 = 0。

# 13. 前端也必须升级为 Capability-Driven UI

目前“券商连接页”未来应升级为“交易客户端/连接中心”。

前端不硬编码每个客户端表单，而由 Connector Schema 驱动。

```text
GET /connectors
      ↓
ConnectorManifest
      ↓
config_schema
      ↓
Dynamic Connection Form
```

例如 QMT 自动显示：

```text
客户端路径
极速版/完整版
账户
Runtime 诊断
```

HTTP Broker 显示：

```text
Endpoint
API Key
Account
```

GM Connector 显示自己的字段。

连接后前端依据 capability 动态启用：

```text
L2
信用交易
期权
算法单
条件单
多账户
```

不支持的功能直接隐藏/禁用并解释原因。

# 14. MCP / REST / Strategy 同样不能知道具体客户端

未来所有入口只接受：

```text
connection_id
account_id
instrument
```

不接受 QMT 专用概念作为核心协议的一部分。

例如：

```text
POST /api/v1/orders
```

而不是把 QMT SDK 参数直接暴露给用户。

MCP 同理：

```text

```

Connector 的 vendor-specific 高级功能如确实必须暴露，放入：

```text
connector extensions
```

不能污染统一核心协议。

# 18. 客户端打包机制也需要同步模块化

多客户端以后，不能把所有 SDK/Runtime 永久打入一个巨大 Electron 安装包。

目标：

```text
QMT Work Core
  ├── Desktop
  ├── FastAPI Core
  ├── Trading Application
  └── Builtin QMT Connector

Optional Connector Packs
  ├── QMT Runtime Pack cp38
  ├── QMT Runtime Pack cp39
  ├── PTrade Connector
  ├── GM Connector
  └── Other Connector
```

提供两类产品：

## Standard

```text
Core + 常用 Connector
```

## Full Offline

```text
Core + 全部官方 Runtime/Connector Packs
```

这样解决：

- 安装包无限增大；
- 不同 SDK 许可证隔离；
- Runtime 版本独立升级；
- Connector 缺陷可独立修复；
- 不需要每新增一个客户端就完整发布桌面主程序。

# 20. 迁移策略：不能一次性推倒

## Phase 0：恢复当前 Main 全部门禁

在新架构大改前先恢复：

```text
CI green
Build Client green
Frontend green
Backend green
Ruff green
```

禁止降低门禁。

## Phase 1：建立 Canonical Models

新增：

```text
InstrumentId
OrderRequest
Order
Trade
Position
Account
Quote
Capabilities
```

先保持旧 Adapter 可以通过 compatibility mapper 工作。

## Phase 2：建立 Ports

新增：

```text
ExecutionPort
AccountPort
MarketDataPort
HistoryPort
ReferenceDataPort
EventStreamPort
```

旧 `BrokerAdapter` 暂时作为 Compatibility Facade。

## Phase 3：ExecutionService 全入口统一

完成：

```text
REST
MCP
Strategy
Algo
Condition
TargetPosition
Rebalance
```

## Phase 4：Connector Registry / Manifest

# 21. 架构门禁

必须增加自动化检查。

## Gate 1

Core/Application 中：

```text
import xtquant_client = 0
```

## Gate 2

Application 中：

```text
broker_id / adapter_id vendor conditional = 0
```

## Gate 3

非 ExecutionService / ExecutionPort Adapter：

```text
direct vendor place_order = 0
```

## Gate 4

Connector 专属字段不得进入 Canonical Domain Model。

## Gate 5

新增 Connector 必须通过统一 Contract Suite：

```text
lifecycle
health
capabilities
account normalization
order normalization
cancel semantics
error mapping
event mapping
shutdown
```

测试替身仅用于协议不变量；真实 Connector 仍需对应 SDK/客户端的集成 smoke gate，禁止用 mock 代替真实接入验收。

## Gate 6

每个 Connector 必须声明：

```text
supported asset classes
supported order types
account types
runtime type
required permissions
supported versions
```

未声明能力不得推断为支持。

# 28. 推荐实施顺序

最终建议顺序：

```text
1. 恢复当前 CI / Build Client 绿线
2. Canonical Trading Models
3. 拆 BrokerAdapter → Capability Ports
4. ExecutionService 全入口统一
5. ConnectorManifest / ConnectorRegistry
6. RuntimeSupervisor / ConnectionSupervisor
7. QMT 迁移为第一个正式 Connector
8. MarketDataRouter 与交易来源解耦
9. AppContext / 生命周期统一
10. 前端 Capability-Driven Connection Center
11. OpenAPI/WS 类型化
12. 接入第二个真实交易客户端做架构验收
13. Connector Pack / Runtime Pack 模块化发布
14. 清除 XTQuant/QMT 在通用层的遗留语义
15. 扩展更多客户端与资产类型
```

核心原则：

> **先把 QMT 从 Core 中剥离成标准 Connector，再接第二个客户端。不要在现有 QMT-centric 结构上继续堆更多 adapter。**

这会显著降低未来每接入一种交易客户端的边际成本，并保证所有客户端共享同一套风控、执行、审计、恢复、前端和 Agent 能力。
