# qmt_work 项目功能 / 架构梳理与优化改进方案

> 版本：v0.3.4（单一真源为仓库根 `VERSION`）
> 梳理基线：`main` 分支当前代码（已含 V10 重构、第 25 轮全链路审计与 24 处修复）
> 日期：2026-09-25
> 说明：本文基于代码实况梳理，面向「项目主要功能、架构分层、实现细节」三件事，并在第 25 轮审计之后的基础上给出**下一步**优化方向。凡引用路径均以当前仓库为准，与旧方案快照（v1~v11 系列）可能不同。

## 0. 结论摘要（先看这里）

- **定位**：基于 QMT / XTQuant 等多券商 SDK 的**本地量化 Agent 平台**，同一进程承载 Web 界面 + MCP + FastAPI REST + WebSocket 四套入口，可打包为 Windows 桌面客户端（EXE）。
- **规模**：后端 397 个 `.py` 文件 / 约 8.1 万行；前端 119 个 `.ts/.tsx` / 约 2.7 万行；REST 34 路由模块（217 端点）、MCP 116 工具、WS 26 类事件；后端测试 152 个 `test_*.py`（1625 passed）、前端 vitest 48 文件 458 用例。
- **质量水位**：历经 25 轮迭代，工程化程度高——分层清晰（`core/` 无依赖内核 → `engines/` → `app/` 装配层 + `gateway/` 横切），零 mock 铁律，四大门禁进 CI，契约计数用脚本硬核对。
- **核心待改进**（本文第 5 章，均为**当前代码可证**的债务，非臆测）：
  1. 分层纪律仍有破口：多个 `routes/` 模块直接写 SQL（`alerts.py` / `apikeys.py` 等），绕过了 services 层；
  2. `app/*` 与 `core/*` 双真源的历史残留引用（187 处 `from app.*` vs 169 处 `from core.*`），虽已清 shim 但命名收敛未完；
  3. 超大文件集中（`datasource/registry.py` 64KB、`routes/market.py` 54KB、`tests/test_unit.py` 102KB 等），单文件职责过载；
  4. 已知 flake 测试与「仍未决」事项散落在各轮报告，未集中收敛成一个待办看板；
  5. 多标的组合回测、批量 RPC 等能力缺口已识别但受真券商环境约束暂缓。
- **本文交付**：一份按「功能 → 架构 → 实现细节 → 优化方案（P0/P1/P2 + 工作量）」组织的落地方案，可据此进入下一轮（R26+）执行。

## 1. 项目主要功能

### 1.1 能力定位一句话

> 在本地拉起一个「多券商 + 多数据源 + Agent 可安全编排」的量化平台：数据面可脱离 QMT 独立运行，交易面在真实券商 SDK 上统一收敛，AI（MCP）只读能力全开、写能力走两阶段确认。

### 1.4 零 mock 铁律（全项目的关键设计约束）

- 未连接券商时，行情 / 交易 / 账户端点返回 **HTTP 503** + 可操作引导；
- 券商可用但被业务规则拒绝（风控 / 拒单 / 非交易时段）返回 **HTTP 400** + 真实原因；
- **绝不把失败包成 `code=0`**——避免拒单被前端显示成「已报」（假成功）。
- 第 25 轮把「一律 503」滥用列为高危并系统性拆分（见 2.4 / 3.3）。

### 2.2 后端分层（V10 确立的依赖规则）

| 层 | 职责 | 目录 | 依赖约束 |
|----|------|------|----------|
| **内核** | 无业务依赖的基础能力：配置 / 数据库 / 时钟 / 加密 / 路径 | `core/` | **禁止反向 import app/engines** |
| **引擎** | 交易执行类引擎（SignalRouter 是唯一意图入口） | `engines/` | 依赖 core + datasource + xtquant_client |
| **装配层** | FastAPI 工厂 / 路由（只做参数校验与编排）/ 服务 | `app/routes/`、`app/services/` | 业务下沉 engines/tools |
| **横切** | 鉴权 / 风控 / 脱敏 / 限流 / 审计 / 缓存 / 指标 | `gateway/` | 中间件与可复用横切 |
| **券商连接** | BrokerAdapter / Manager / 桥接子进程 / 适配器 / registry | `xtquant_client/` | **不得 import app** |
| **数据面** | provider_catalog、能力契约链、降级、冷热存储 | `datasource/` | 独立 |
| **外部协议** | MCP / 连接器契约 / 插件 / 同步 | `mcp_server/`、`connectors/`、`plugins/`、`sync/` | 契约化 |

### 2.3 前端架构

```
frontend-next/src/
├─ main.tsx / App.tsx / app/routes.tsx   # 入口 + 页面注册表（PAGES 单一真源）
├─ services/api/                         # 类型化 REST 客户端（与后端契约一一对应）
├─ services/ws.ts                        # WebSocket 订阅 / 事件分派
├─ stores/                               # zustand：workspace / quotes / broker / watchlist / session / ui
├─ shell/                                # 多窗格工作台：Workspace / 命令面板 / 快捷键 / 菜单 / 状态栏
├─ domains/                              # 页面级组件（market/research/trading/account/automation/system）
├─ design/                               # 设计系统基元
├─ charts/ · shared/                     # 图表封装 + 通用工具
└─ electron/                             # 桌面壳（端口发现 + 托盘 + 开机自启 + 自动更新）
```

- **状态**：zustand；workspace 实现多 Tab + LRU keep-alive + 可拖拽分栏，区分「已打开」与「活跃渲染」。
- **路由**：`routes.tsx` 是菜单 / 命令面板 / 工作区的单一真源，`menu:false` 页面强制声明 `entryFrom`。
- **构建**：Vite `base="/"`，`outDir` → `backend/static/`，由 FastAPI 同源托管；桌面端同源加载。

### 2.4 后端启动与生命周期

- `run.py`：端口自动扫描（默认 21118，占用 +1 最多 10 次）+ 单实例锁（`.qmt_work.lock`）+ 端口锁定持久化 `.qmt_work.port`。
- `main.py`：`create_app()` 工厂；`combined_lifespan` = MCP lifespan + 应用 lifespan。
- `app/bootstrap/`：分 6 相位启动——`phase_db / phase_engines / phase_broker / phase_replay / phase_watchdogs / phase_misc`，`lifecycle.run_phases` 为唯一编排真源；shutdown 逆序关闭。
- 第 25 轮：optional 相位「慢」也会阻断启动的问题已修（启动预算 + 并发 + 交后台）；启动期无效路径连接护栏已加。

## 3. 实现细节（关键链路）

### 3.1 统一数据面（`datasource/`）

- **能力契约链**：`provider_catalog.resolve_chain(capability)` 按能力解析数据源链（V11 R6），替代旧的「注册顺序副产物」。
- **降级策略**：`auto` 模式按链回退（broker → eltdx → baostock → akshare）；`commercial_mode=true` 时链路求值跳过 Research-Only 源（eltdx）。
- **本地兜底**：`eltdx_utils.lookup_name` 提供 O(1) 无网络的中文名 / 行业兜底（刻意函数内 import 规避循环导入）。
- **冷仓**：`cold_store.py` + `local_store.py` 提供历史 K 线本地化与增量。

### 3.2 券商连接与 xtquant 桥接

- **BrokerAdapter 抽象**：`xtquant_client/base.py` 基类，迅投系适配器在 `adapters/` 继承；registry 用 `BrokerProfile` 声明档案。
- **多运行时桥接**：xtquant 的 C 扩展按 CPython 小版本编译，主后端版本不匹配时自动经「桥接子进程」加载；`tools/fetch_runtimes.py` 下载捆绑运行时；`/brokers/test` 给出三条可操作修复路径。
- **ABI 兼容**：无匹配解释器时返回 `runtime_mode: bridge` 与运行时来源。

### 3.3 交易执行与「503/400 归因」红线

第 25 轮专项审计了全部 60+ 处 `err(503`，确立唯一可证伪的判定：

- **正确 503**：引擎 / 数据库 / 数据源 / 风控未初始化、`BrokerError`、`MSG_NO_BROKER`、数据源全部返空。
- **应 400**：风控熔断 / 超限额 / 可用资金不足 / 参数非法 / 未知连接 id（404）。
- 已修：`signal.py`、`target_portfolio.py` 按 `broker_unavailable` 标志分流；`broker.py::connect` 拆开 `KeyError→404` 与 `BrokerError→503`。

### 3.4 风控 / 审计 / 对账

- `gateway/risk.py::RiskManager`：单笔 / 比例 / 频率 / 日级熔断 / 黑白名单 / 价格偏离。
- `core/auth_identity.py`：审计 hash 链（不可篡改）。
- `gateway/reconcile.py`：委托对账核销 + WAL 统计 / 归档 / 轮转，写销失败累计 `writeoff_failed`（不再被 `except: pass` 吞掉）。
- `gateway/idempotency.py`：下单幂等（防重复报单）。

### 3.5 MCP 与能力自描述

- **自动暴露**：`mcp_server/auto_expose.py` 按能力自描述注册表自动暴露只读端点；`_EXEC_DENY_DOMAINS` 拒绝写操作（下单 / 撤单等保留人工确认护栏）。
- **能力漂移门禁**：`scripts/check_capability_drift.py` 校验 REST agent-visible ↔ MCP 契约；契约基线固化在 `backend/tests/contracts/mcp_tools.json`（语义：基线 ⊆ 现网）。

### 3.6 前端工作区 / 事件订阅

- WS 订阅一次、多客户端扇出；断线重连补发最近 30s 行情。
- `Trade.tsx` 订阅 order/deal 回报事件，300ms 去抖自动刷新列表。
- 单例页（`MULTI_INSTANCE_PAGES` 之外）复用 `workspaceReducer.activate(state, tabId)`，漏传 tabId 会静默停留旧页（README FAQ 已记录）。

### 4.1 第 25 轮已修的 24 处（摘要，详见 `2026-09-23_第25轮_四遍审计与24处修复.md`）

- **H1** `mode` 别名不匹配 ⇒ 权重被当成股数 ⇒ 全仓清仓（未知 mode 直接报错，绝不静默走默认分支）。

## 5. 优化改进方案

> 原则：**先证伪、后改动**；每条改进给出可证伪的验收判据；不做「看起来能跑」的空洞优化；写操作保留人工护栏；每个任务单 PR 可回滚、带测试与门禁。
> 优先级：P0=当前可证的高风险/纪律破口，应立即收敛；P1=工程与体验优化；P2=能力扩展（多数需真券商环境，单独立项）。

### 5.1 P0 —— 分层纪律与双真源收敛（本轮应立即做）

| # | 问题（可证） | 改进动作 | 验收判据 |
|---|--------------|----------|----------|
| P0-1 | `routes/` 直写 SQL（`alerts.py` / `apikeys.py` 等）绕过了 services 层 | 把直写 SQL 收敛到 `core/db` 的仓储方法或新增 `app/services/*_store.py`，路由只做参数校验与编排 | `grep -rn "ctx.db.execute\|fetchall" app/routes/*.py` 归零；`check_execution_architecture.py` 新增「routes 不得直连 DB」规则 |
