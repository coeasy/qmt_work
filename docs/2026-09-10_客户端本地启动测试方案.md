# 客户端本地启动测试方案（2026-09-10）

> 目标：把「本地启动客户端看看有没有问题」从手工拼命令 + 凭经验判断，
> 变成**一条命令、可重复、有机器可读结论、失败能自我诊断**的验证链路。

## 一、入口

```bash
cd P:/github_public/qmt_work
<python> scripts/client_start_test.py --target auto      # 自动选（有打包客户端就测它）
<python> scripts/client_start_test.py --target dev       # 开发态 Electron（秒级，免重打包）
<python> scripts/client_start_test.py --target client    # 打包后的桌面客户端
<python> scripts/client_start_test.py --target backend   # 只测后端 EXE（无 GUI）
```

可选参数：`--timeout 90`（就绪等待上限秒数）、`--no-shot`（跳过截图）、`--port`。

**全程不删除任何文件**（只写自己的产物）。阶段 0 只清理**进程**；`port.txt` /
`window-ready.txt` / `startup-error.log` 等状态文件用「修改时间是否早于本次运行」
判定是否陈旧（`fresh()`），因此：
- 不会误用上次运行残留的端口文件把探测引到错误端口；
- 不会误把上次的 `window-ready.txt` 当成「本次页面已加载」；
- 不触发本环境的大范围删除护栏（早期版本删隔离 profile 时被拦过），
  脚本变成纯「只读 + 只写自己产物」的工具，随时可安全重复运行。

**必须 `dangerouslyDisableSandbox: true`**（要拉进程、写 `%APPDATA%`）。
产物：`output/client_test/report.json`、`client_window.png`、`<target>.log`。
退出码：全通过 0，任一失败 1。

## 二、七个阶段（单进程内跑完）

| 阶段 | 内容 | 关键判据 |
| --- | --- | --- |
| 0 清理 | 杀残留进程、删锁/端口/单实例/就绪标记文件 | 避免下次启动撞锁 |
| 1 启动 | 净化环境变量 + 隔离 `--user-data-dir` 启动 | 3 秒后进程仍存活（防「秒退」） |
| 2 就绪 | 等端口文件 → 轮询 `/api/v1/ready` | 200；记录启动耗时；进程已退则立刻失败 |
| 3 REST 冒烟 | 5 个核心端点 + 6 个券商依赖端点 | 核心=200；券商依赖=200 且业务码 ∈ {0,503} |
| 4 前端资源 | `GET /` 是 SPA 壳 + 首个 `/assets/*.js` 可加载 | 防止静态资源 404 |
| 5 WebSocket | 标准库手写握手 + 读首帧 | 101 + 首帧 snapshot |
| 6 窗口渲染 | 加载完成标记 / 崩溃扫描 / 窗口探测 / 截图 | 见下 |
| 7 停机 | `scheduler/shutdown` → 进程树强杀 | 零残留进程 |

第 6 阶段的四道判据（针对本项目历史上真实踩过的故障）：
1. **`did-finish-load` 标记**（`window-ready.txt`）——比猜窗口标题可靠；
2. **崩溃扫描**——日志里出现 `FATAL:` / `kFatalFailure` / `gpu_channel_manager` /
   `load FAILED` / `renderer process gone` 即失败；
3. **窗口探测**——可见 + 宽高 ≥ 200 + 排除 `Default IME`/`MSCTFIME UI`，取面积最大者；
4. **渲染质量**——截图字节数 + 采样「不同颜色数」，纯色即白/黑屏空窗。

## 三、设计约束（每一条都是踩坑换来的）

1. **必须在单次调用内跑完**：本工具环境会回收跨调用的后台进程，分步执行时
   端口文件写了但进程已死，冒烟必然假失败。
2. **必须净化环境变量**：宿主自身是 Electron 应用，会注入 `ELECTRON_RUN_AS_NODE=1`
   与 `NODE_OPTIONS`；桌面壳继承后以纯 Node 模式启动 → 无 TTY、**秒退 exit 0、零输出**，
   极易误判为「打包坏了」。
3. **必须绕代理**：沙箱内访问 `127.0.0.1` 会被 HTTP 代理拦截，表现为
   `HTTP 502 upstream connect failed` / `HTTP 000`。所有本地请求走空代理 opener。
4. **默认隔离 profile**：`--user-data-dir` 指向 `output/client_test/profile`，
   不污染用户真实客户端数据，也天然规避历史单实例锁残留。
5. **截图用 `PrintWindow`**：屏幕 DC 的 BitBlt 只能拿「屏幕上看得见的像素」，
   窗口被遮挡时会**截到遮挡者**（实测把工具窗口当成了客户端截图）。
6. **不删除任何文件**：陈旧状态文件靠 `fresh()`（修改时间是否早于本次运行）判定，
   而不是「启动前先删掉」。理由：删除隔离 profile 属于大范围删除，会触发本环境的
   安全护栏（实测被拦）；而功能上也不需要删。脚本因此是纯「只读 + 只写自己产物」。

### 无 GPU 会话崩溃：根因与正确开关

本机（远程/虚拟化会话，无可用 GPU）实测的崩溃链：

```
ERROR gpu_channel_manager  Failed to create GLES3 context, fallback to GLES2
ERROR gpu_channel_manager  ContextResult::kFatalFailure: Failed to create shared context for virtualization
FATAL gles2_cmd_decoder(2961)  Validating command decoder is not supported
→ 进程 exit 0x80000003（整个客户端被带走）
```

**顺序很关键**：`--in-process-gpu` 把 GPU 线程并进主进程，GPU 侧 FATAL 会连带
整个应用退出；`--disable-software-rasterizer` 又掐掉软件渲染兜底。**这两个都不能加**。

正确组合：`app.disableHardwareAcceleration()` + `--no-sandbox` + `--disable-gpu`
+ `--disable-gpu-compositing` + `--disable-features=Vulkan` + `--use-gl=swiftshader`
+ `--use-angle=swiftshader` + `--disable-crash-reporter`。

修复前后对比（同一环境、同一命令）：

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 进程存活 | t+5s 崩溃退出（0x80000003） | 稳定驻留 |
| 窗口 | 探测不到（进程已死） | t+6s 出现，1440x900，标题正确 |
| 日志 `FATAL` / `gpu_channel_manager` | 3 条 | **0 条** |
| 前端数据流 | 中断 | 正常（account/status、market/minutes 持续 200） |

## 六、两个「时好时坏」类故障的根因（值得单独记一笔）

### 1. GPU 降级开关把崩溃放大（见第四节）

### 2. ctypes 未声明签名 → 64 位句柄被当 32 位（截图随机失败）

`gdi32.CreateCompatibleDC` 实测返回 `0xfffffffff201149c` 这类**带高位**的 64 位句柄。
ctypes 默认把返回值当 C int、把入参当 C int，于是：

- 返回值被截断成负数再传给后续调用；
- 把大句柄当入参传给未声明签名的函数时抛
  `argument 1: OverflowError: int too long to convert`。

因为句柄的具体数值每次进程不同，表现为**开发态成功、打包客户端失败**的抖动
（同一份代码、同一时刻只差运行实例）。修法：在 `capture_screen._dlls()` 与
`client_start_test._win32()` 里**一次性声明全部 `argtypes`/`restype`**
（HDC/HBITMAP/HGDIOBJ/HWND 等），断言"句柄不再被截断"。
**教训：任何 ctypes 调 Win32 API 的地方都要显式声明签名，不要依赖默认 int 推断。**
