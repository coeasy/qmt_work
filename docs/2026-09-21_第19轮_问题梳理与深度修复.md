## 一、用户所报现象 = 两个独立缺陷叠加

现象：一打开「行情工作台」，K 线区域是一片白板，没有任何文字说明。

关键前提：**工作台默认标的是 `000001.SH`（上证指数）**
（`frontend-next/src/domains/market/MarketWorkbench.tsx:80` 的 `DEFAULT_WORKBENCH_CODE`）。

| 编号 | 缺陷 | 用户可见后果 |
|---|---|---|
| **A7** | eltdx 通用 `get_kline` **从来没给指数传 `kind="index"`** ⇒ 按个股布局解析指数字节流 ⇒ 抛 `ProtocolError` ⇒ 连续 3 次**熔断 30s** | 指数 K 线**恒空**；且一个指数请求把整个 eltdx 源打成不可用，连个股 K 线/分时/资金流一起遭殃 |
| **A8** | `/market/kline` 兜底条件 `not bars and not res.get("source")` 只接住「一个源都没应答」 | 「源都在、都正常应答、都返回空壳」时静默返回 `200 + count:0 + note:null` ⇒ 前端留白板**零提示** |

两者必须都修：只修 A7，A8 仍会在别的标的上静默；只修 A8，用户能读到原因但仍看不到图。

## 二、A7 —— eltdx 指数 K 线走错通道

### 2.1 根因

`eltdx` 的指数与个股走**两条不同的数据通道**：`cl.bars.get(..., kind="index")` vs
`kind="stock"`（默认）。本模块此前**只在 `get_board_kline`（`/market/indices` 用）里传过
`kind="index"`**，通用 `get_kline` 一次都没传。

猜错的后果**不是返回空，而是抛异常**：

```
数据源 eltdx 调用失败（已计入熔断）ProtocolError: invalid kline date: 30869201
数据源 eltdx 熔断（连续 3 次失败），冷却 30s
```

### 2.2 判定陷阱：代码前缀在不同交易所含义完全不同

| 代码 | 沪市 | 深市 |
|---|---|---|
| `000xxx` | **指数**（000001 上证指数 / 000300 沪深300） | **个股**（000001.SZ 平安银行、000002.SZ 万科A） |

所以「`code.startswith("000")` 就当指数」的写法**在沪市对、深市错**。而错的后果极不对称：

- 指数被当个股 ⇒ 报 `ProtocolError`（**可感知**）；
- **个股被当指数 ⇒ 取到指数的 K 线，或静默返回空**（**极难发现**）。

### 2.3 修法

1. `backend/datasource/eltdx_utils.py` 新增 `is_index_code()` —— **按交易所分别判定**，
   并独立于 `_get_index_name()` 里那份（那份只在**查名称**时用，误判无害，因此可以宽松；
   `kind` 判定直接决定取到谁的数据，必须严格）。
2. `backend/datasource/eltdx_source.py::get_kline` 传 `kind`；
3. 新增 `_bars_any_kind()`：kind 猜错时**就地换另一边重试一次**。这一层的价值不只是
   「拿到数据」，更是**不把自身可修复的错误上报成数据源故障**（异常不逃出 `_inner`
   ⇒ 不计入熔断）。

### 2.4 实证核对（不是靠猜前缀表）

`cl.codes.all_indices()` 是 eltdx 的**权威指数清单**。用它核对判定表：

```
权威指数条数 = 1678   （sh880 652 + sh881 467 + sz399 354 + sh000 200 + sh999 3 + bj899 2）
★ 漏判 = 0 条
★ 误判 = 0 / 5574 只个股
```

### 2.5 端到端验证（独立实例 + 真实 eltdx）

```
000001.SH => count=5 source=eltdx last=3949.91     ← 与已知正确的 /market/indices 值一致
000300.SH => count=5 source=eltdx last=4539.57
399001.SZ => count=5 source=eltdx last=13730.021
399006.SZ => count=5 source=eltdx last=3399.59
899050.BJ => count=5 source=eltdx last=1058.18
881101.SH => count=5 source=eltdx last=381.98      ← 通达信板块指数
（回归）000001.SZ => count=5 last=11.7             ← 平安银行，未被误判
（回归）600519.SH => count=5 last=1257.12
```

**熔断证据（决定性）**：整个验证过程日志里「熔断」出现 8 次，**全部来自 sina / tencent
公开源**（`TimeoutError` / `403 Forbidden`），**没有一条 eltdx** —— 改动前指数请求必然
把 eltdx 打成不可用。

## 三、A8 —— 空壳被静默

### 3.1 两种「空」必须分开

| 形态 | 语义 | 用户处置 |
|---|---|---|
| 源**都不可用**（抛异常 / 超时） | 「获取失败」 | 连券商 / 查网络 |
| 源**都在、都正常应答、但都返回空壳** | 「这份数据本身没有」 | 新上市 / 停牌 / 该周期无成交 / 源不覆盖 |

原条件 `not bars and not res.get("source")` **只接住前者**。而实测最常见的形态恰恰是后者：

```
GET /market/kline?code=000001.SH  →  {"source":"broker", "count":0, "bars":[]}
```

`res["source"]` 是 `"broker"`（真值）⇒ 兜底被整段跳过 ⇒ `200 + 0 根 + note:null`。

### 3.2 为什么是 200 + note，而不是 503

前端 `KLineChart.tsx`：

- `.catch()` 分支（网络 / 错误码）**只能显示一句通用猜测**「暂无 K 线数据（可能停牌或该周期无成交）」；
- `meta.note` 分支（第 375-379 行）能把**真实原因**写在画布上。

**错误归因必须落到用户看得见的地方**，不能退化成一句猜测。

### 3.3 为什么不用 `msvc._unavailable()`

两个原因：

1. 它的框架是「**获取失败**」—— 而此刻所有源都**成功应答**了。把「都成功了但没数据」
   说成「获取失败」会把排查方向带偏（本项目已因「把『不支持』说成『网络坏了』」吃过亏）；
2. 它读 `get_hub().last_failure_trace()` —— 那是一份**全局共享的「最近一次」**记录，
   并发下完全可能来自**另一个请求**的链路 ⇒ 文案张冠李戴。

故新增自洽的 `_kline_empty_note()`，只陈述本请求自己确知的事实。

### 3.4 修法与验证

兜底条件改为 `if not bars:`（先兜本地，本地也没有再按成因分叉文案）。
独立实例实测（无 eltdx 时）已复现 note：

```
000001.SH => code=0 count=0 source=broker
  note=行情源（broker）已正常应答，但没有 000001.SH 的日线 K 线，本地数据仓也没有该标的。
       可能原因：新上市 / 长期停牌 / 该周期无成交，或当前数据源不覆盖该标的。
```

## 四、A9a —— 财务数据解析形态不匹配（复发缺陷）

### 4.1 实测形态（100% 复现）

本机 QMT **只有旧接口 `get_financial_data`**（无 `get_stock_financial`），返回：

```python
{code: {指标名: DataFrame}}     # 键是指标名，每个指标各自一张表
```

**不是**文档假设的 `{报告期: {指标: 值}}`。

### 4.2 旧实现错在哪

把 `items[-1]` 当「最新一期」⇒

- `report_time = PARENT_NETPROFIT_YOY[:10]` = `"PARENT_NET"`（一个**字段名**冒充报告期）；
- `row` 是 DataFrame ⇒ `row.get("EPS")` 取不到 ⇒ **10 个指标全 null**。

界面上显示「报告期：PARENT_NET」+ 估值全空 —— 用户完全无从判断。

> 该缺陷 **2026-09-19 修过一次**（DataFrame 朝向问题），但只覆盖了「DataFrame」与
> 「`{报告期: {指标: 值}}`」两种形态，**没覆盖实测的第三种** ⇒ 复发。
> **教训：同一处缺陷复发，说明当时是按「已知形态」打补丁，而不是按「形态空间」收口。**

### 4.3 修法

新增 `_as_report_date()` / `_num_or_none()` / `_flatten_numbers()` / `_latest_from_table()` /
`_row_from_field_map()` / `_no_financial()`，并按「键集是否与指标名相交」分叉两种 dict 形态。

两条硬纪律：

- **`report_time` 只认真日期**（8 位数字 + `strptime` 校验），否则宁可留空 ——
  绝不透出「看起来像值、实际是字段名」的伪值；
- **NaN 必须转 `None`**：`round(float("nan"), 4)` 得 `nan`，json 编码成**裸 `NaN`**，
  那是**非法 JSON** ⇒ 浏览器 `JSON.parse` 抛错 ⇒ **整页数据全废**。

### 4.4 验证

真实 SDK + 生产适配器路径复跑：

```
{'code': '600519.SH', 'detail': '无财务数据：券商终端未返回该标的的财务指标。
  请在 QMT 客户端下载财务数据，或确认账号已开通财务数据权限。'}
```

`PARENT_NET` 消失，文案可操作。

## 五、A9c —— 估值的「假空缺」

### 5.1 现象

同一份 PE/PB：

- `/market/stock-info` 能从腾讯拿到 `pe_ttm=19.23 / pb=6.23`；
- `/market/analysis` 却说 `valuation: unavailable`。

因为 `_valuation()` 只认**券商财务接口** ⇒ 一个端点有、另一个说没有。

### 5.2 修法 + 一个自己踩到的坑

新增 `_valuation_metrics()` 作为**第二路**（券商财务缺位时用行情派生指标补齐）。

**踩到的坑**：行情源字段叫 `pe_ttm`（TTM 口径），而估值载荷字段叫 `pe`。
按同名填 ⇒ `pb` 同名碰巧填上（界面显示 6.23），**`pe` 一直空着**。

⇒ 新增显式映射表 `VALUATION_METRIC_MAP = {"pe_ttm": "pe", "pb": "pb"}`，**按映射填，不按同名填**。

### 5.3 验证（独立实例）

```
000001.SH => 不可用=[]  pe=17.22  pb=None   source=tencent
000300.SH => 不可用=[]  pe=13.5   pb=None   source=tencent
600519.SH => 不可用=[]  pe=19.23  pb=6.23   source=tencent
对照 stock-info：pe_ttm=17.22 / 19.23  ← 两个端点一致
```

两点说明：

- 指数 `pb=None` 是**如实**的 —— 腾讯对指数只给 `pe_ttm`，不给市净率；
- `performance` 维度**连带恢复**（此前指数日线在本地库 0 行 ⇒ 必然 unavailable；
  指数 K 线修好后 eltdx 能供给，该维度随之可用）。

## 六、A10 —— 基本面 6 维：一排 + 默认收起 + 点击展开

### 6.1 为什么要改

底部坞高度是从图表借来的（`panels.module.css::.dock { max-height: 42% }`），
6 块表格平铺会把 K 线压没；而 6 维里有好几维本来就没数据，等于白占空间。

### 6.2 设计要点（三条都是被测试逼出来的）

1. **「默认收起」必须同时锁两件事**：
   - 收起时明细单元格**不渲染**（不是靠 CSS 藏 —— 那样仍占 DOM，且 `textContent` 断言会假通过）；
   - 收起时**仍看得见每维状态**（标题 + 可用性角标 + **摘要**）。
2. **摘要不是装饰**：不可用时**优先说原因**（「券商无财务数据」/「数据源不含资金流」），
   而不是一排破折号 —— 破折号不携带任何信息，等于把「默认收起」变成纯负担。
3. **展开区必须按 `availability` 收口**：后端在「这一维没拿到」时会返回
   **字段齐全但值全 null** 的对象（实测 `valuation: {report_time: null, eps: null, pe: null, ...}`），
   只看对象非空会渲染一整张破折号表格。

### 6.3 交互

- 一排 6 张可点卡片（`flex: 1 1 0; min-width: 118px`，不写死 6 列）；
- 点击展开该维明细，再点收起；点另一维则替换前一维（同时只开一个）；
- `aria-expanded` + `title`（「展开『估值』明细」/「收起『估值』明细」）；
- 展开估值时额外给出**来源可追溯**行：「估值来源：腾讯行情（行情源直接提供的 PE(TTM) / PB）」
  或「券商财务（由现价 ÷ 每股指标现算）」。

## 七、A11 —— 备份跳过判断的「同 tick 盲区」（本轮**新增**发现的真缺陷）

> 这一条不是用户报的，是**收尾跑全量测试时抓到的**：`test_real_write_after_checkpoint_still_backs_up`
> 变红。项目纪律是「**flaky 先当真缺陷查**」—— 查下去发现它确实是真缺陷。

### 7.1 现象与定位

失败点：`assert b.backup_once("原地 UPDATE") is not None` —— 一次**真写入**之后，
`backup_once` 却判定「已覆盖」并**跳过**。

探针（`output/_a5_probe3.py`，严格复刻测试时序）：

```
=== A) 不加 sleep，跑 6 轮 ===
  第1轮: 首次备份=ok 纯检查点跳过=ok 原地 UPDATE=★未备份 小 INSERT=ok 删一行=★未备份
  第2轮: 全过
  第3轮: 全过
  第4轮: ... 删一行=★未备份
  第5轮: 原地 UPDATE=★未备份 小 INSERT=★未备份 ...
  第6轮: 全过
=== B) 每次写后 sleep 20ms，跑 3 轮 ===
  全部 全过
=== C) 200 次连续追加写：mtime 未推进的次数 = 188
```

⇒ 6 轮里 **4 轮**出现「真写入却未触发备份」；加 20ms sleep 就全过。
**根因是时间精度，不是逻辑错。**

### 7.2 根因

A5 的归一化指纹在成功时**只认主库 `(size, mtime_ns)`**。而：

1. **原地 UPDATE / 小改动 ⇒ 主库 size 不变**；
2. **Windows 的文件时间按系统 tick 更新** —— 实测 200 次连续追加写里 **188 次 mtime 没推进**；
3. 两者叠加 ⇒ 指纹与上次备份**完全相同** ⇒ `_covered_by()` 判定「已覆盖」⇒ **静默跳过备份**。

风险方向是最坏的那种：**静默丢备份（不可恢复）**。

### 7.3 横向试过、被实测否掉的候选信号

| 候选 | A5（纯检查点不变） | A11（真写入必变） | 结论 |
|---|---|---|---|
| 主库 `(size, mtime_ns)` | ✓ | **✗**（同 tick 盲区） | 现状，不完备 |
| 主库 header change counter（offset 24） | ✓ | **✗**（实测**恒为 2**，WAL 模式下不动） | 死路 |
| `PRAGMA data_version`（**每次新建连接**） | ✓ | ✗（新连接恒从 1 开始） | **探针错**（见下） |
| `PRAGMA data_version`（**常驻连接**） | **✗**（连空操作检查点都算变化） | ✓ | 单独不可用 |
| `page_count` / `freelist_count` | ✓ | ✗ | 对原地写无感 |
| 主库首页 4096B 的 sha1 | ✓ | ✗ | 改的不是首页 |
| **归一化前 `-wal` 是否有帧** | **✓** | **✓** | ★ 采用 |

**两个「探针错」值得单独记**：

1. `data_version` 第一次被误判为无效，是因为探针**每次 `snap()` 都新建连接**
   —— 新连接的 `data_version` 恒从 1 开始。它的语义是「**同一连接**在两次读取之间，
   是否有**别的连接**提交过改动」⇒ 必须用**同一条常驻连接**读。
2. 前几个探针都在 `_normalize_wal()` **之后**才读 `-wal` ⇒ 恒为 0，**把证据销毁了**。
   正确次序是「**先读 `-wal`，再归一化，最后读主库**」。

### 7.4 修法

`backend/gateway/db_backup.py`：

- 新增 `_wal_size()`（**纯读**，不做归一化）；
- `_covered_by()` 在归一化**之前**先读 `pending = self._wal_size()`；
  `pending > 0` 且归一化成功（`cur["wal"] == [0]`）⇒ **必有新提交** ⇒ 判为「未覆盖」。

为什么这个信号成立且与文件时间无关：`_normalize_wal()` 会把已提交数据并回主库并把
`-wal` 归零，所以「归一化前 `-wal` > 0」⇔「自上次归一化以来确有提交」。
**空操作检查点不留帧** ⇒ A5 的跳过语义完好。

⚠️ 次序是这条修法的**全部要害**：读在归一化之后 ⇒ 恒为 0 ⇒ 修了等于没修。

### 7.5 验证

- 新增 3 条用例：`test_pending_wal_frames_force_backup_even_if_fingerprint_unchanged`
  （把 `_source_fingerprint()` 钉死成恒定值来模拟盲区 ⇒ 断言的是**机制**，
  不依赖「恰好同 tick」的时序巧合）、
  `test_noop_checkpoint_leaves_no_frames_so_pending_signal_does_not_misfire`（A5 反向护栏）、
  `test_wal_size_helper_does_not_normalize`（纯读，不得有副作用）。
- **可证伪性**：把补强条件短路掉 ⇒ 机制用例**必红**（实测 1 failed / 43 passed）。
- 修复后 `tests/test_db_backup_policy.py` **44 passed**。
