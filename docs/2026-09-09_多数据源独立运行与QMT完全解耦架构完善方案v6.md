# QMT Work 多数据源独立运行与 QMT 完全解耦架构完善方案 V6

> 日期：2026-09-09  
> 仓库：`coeasy/qmt_work`  
> 基线：V5「插件化多交易客户端量化平台」方案  
> 目标：让 QMT 成为可选的交易/行情 Connector，而不是平台主界面、行情、选股、研究、回测和策略设计的运行前提；即使完全没有安装或连接 QMT，用户仍可通过 tstdx、eltdx、BaoStock、新浪、腾讯以及后续其他数据源完成基础行情、数据同步、选股、指标、因子、研究、回测和模拟盘流程。

---

# 1. 最终结论

## 1.1 完全可行，而且应作为平台核心架构原则

后续正式原则调整为：

> **QMT 是 Provider / Connector 之一，不是 QMT Work 的宿主依赖。**

系统必须支持以下独立运行形态：

```text
模式 A：无 QMT、无交易客户端
  第三方行情源 / 本地数据仓
      ↓
  行情 / K线 / 标的检索
      ↓
  指标 / 条件选股 / NL选股
      ↓
  因子 / 研究 / 回测
      ↓
  策略设计 / 模拟盘

模式 B：无 QMT，但有其他交易 Connector
  第三方行情源
      +
  PTrade / GM / 其他交易通道
      ↓
  完整研究 + 实盘能力

模式 C：连接 QMT
  QMT 行情能力
      +
  QMT 交易能力
      +
  QMT Vendor Extension
      ↓
  完整能力
```

因此平台定位应进一步从：

```text
基于 QMT 的量化工作台
```

升级为：

```text
插件化多数据源、多交易连接量化平台
```

QMT 是首个重点支持的 Connector，但不是平台 Core。

---

# 2. 三轮现状检查结论

本方案是在 V5 基础上再次对当前 `main` 做三轮检查后形成。

## 2.1 第一轮：后端数据与选股链路

当前代码已经具备很好的无 QMT 基础。

### 已存在的正确能力

`datasource.registry.DataSourceManager` 已经支持：

- `broker` 作为一个数据源；
- `eltdx` 等第三方 DataSource；
- `source="auto"`；
- 数据源注册；
- 自动 fallback；
- 单源 timeout；
- circuit breaker；
- source 显式选择。

而 `BarsSyncer` 当前已经通过：

```text
get_hub().get_kline(..., source="auto")
```

获取 K 线，再落入 LocalStore。

股票列表也已经通过：

```text
get_stock_list(source="auto")
```

同步到 LocalStore。

因此从架构上已经存在：

```text
第三方 DataSource
       ↓
DataSourceManager
       ↓
BarsSyncer
       ↓
LocalStore
```

### 选股已经基本与 QMT 解耦

当前条件选股不是逐只股票请求 QMT，而是：

```text
LocalStore
   ↓
全市场股票列表
   ↓
本地 K 线
   ↓
Indicator Engine
   ↓
Screener Engine
```

因此只要第三方 DataSource 能把数据同步进入 LocalStore，选股就可以完全脱离 QMT。

自然语言选股也已经是离线规则解析：

```text
自然语言
  ↓
可编辑条件树
  ↓
Screener Engine
```

这些能力都不要求 QMT。

### 第一轮仍发现的耦合

`datasource.registry` 目前仍直接：

```python
from xtquant_client.base import BrokerError
```

并内置 `_BoundBrokerSource`，知道 `bridge.gateway` 调用形态。

这说明当前 datasource 虽然功能上支持多源，但**依赖边界仍未完全与 QMT/Broker 解耦**。

V6 必须把它修正为：

```text
Data Plane
   ↓
MarketDataPort
   ↓
任意 Provider
```

而不是：

```text
DataSourceManager
   ↓
xtquant_client
```

---

## 2.2 第二轮：前端主界面依赖

当前 `Screen.jsx` 的选股页面本身没有 BrokerContext/QMT 依赖，这是正确的。

但根 `App` 当前仍被：

```text
BrokerProvider
```

包裹。

而 `BrokerContext.jsx` 的设计注释仍把：

```text
当前活跃连接 conn_id
```

描述成前端所有 REST / 实时行情的全局连接来源。

这会造成产品和代码两层错误心智：

```text
先有 Broker
  ↓
才有行情
  ↓
才有主工作台
```

未来必须改成：

```text
PlatformContext
  ├── DataContext
  ├── CapabilityContext
  ├── TradingConnectionContext
  └── WorkspaceContext
```

其中：

```text
DataContext              永远可以存在
TradingConnectionContext 可以为空
```

主界面不能把“未连接交易客户端”理解成“平台未就绪”。

---

## 2.3 第三轮：统一数据契约与降级机制

当前项目已经存在：

```text
Quote
Bar
InstrumentInfo
StockInfo
BoardItem
Moneyflow
```

等标准模型。

同时已经存在 `DataResult`：

```text
results
source
as_of
stale
warnings
extra
```

并且明确约束：

```text
stale=True
必须有 as_of
必须有 source
```

项目还已有：

```text
远程源失败
  ↓
LocalStore fallback
  ↓
stale=True
source=local:sqlite
```

因此 V6 无需重新设计一套数据对象。

真正需要升级的是：

1. 标准模型成为所有 Provider 的强制边界；
2. DataResult 真正覆盖全部核心 Data Plane；
3. 数据源路由从“单个 auto_chain”升级成“按 Capability 路由”；
4. 数据来源、时效、质量、授权、限速都进入 Provider Manifest；
5. 前端只消费统一 Data API，不知道来源是 QMT、eltdx、BaoStock、新浪还是腾讯。

# 3. V6 核心架构：Data Plane 与 Execution Plane 正式分离

这是本轮最重要的架构升级。

最终系统不是“Broker 提供一切”，而是两条彼此独立的平面。

```text
                         QMT Work Core
                              │
                    Canonical Domain Model
                              │
          ┌───────────────────┴───────────────────┐
          │                                       │
          ▼                                       ▼
      DATA PLANE                            EXECUTION PLANE
          │                                       │
 MarketDataService                        ExecutionService
 ResearchDataService                     Risk / WAL / Audit
 InstrumentService                       Idempotency / Reconcile
          │                                       │
     DataRouter                              ExecutionPort
          │                                       │
 ┌────────┼────────┬────────┐          ┌──────────┼──────────┐
 ▼        ▼        ▼        ▼          ▼          ▼          ▼
eltdx   BaoStock  新浪     腾讯       QMT      PTrade      GM/Other
 ▼
tstdx / Other
```

QMT Connector 可以同时实现：

```text
Market Data Capability
+
Execution Capability
```

但平台不能假设数据和交易必须来自同一个 Connector。

例如完全合法的组合：

```text
实时行情：eltdx
历史数据：BaoStock
基础资料：其他 DataSource
交易：QMT
```

或者：

```text
行情：第三方公共数据源
交易：PTrade
```

或者：

```text
只有本地历史数据
无任何交易连接
```

平台都应正常运行。

# 4. 主界面必须变成 Data-First，而不是 Broker-First

## 4.1 当前需要纠正的状态模型

不要再用：

```text
activeBroker
```

作为平台全局最上层状态。

未来顶层应该是：

```text
PlatformCapabilityState
```

示例：

```json
{
  "platform_ready": true,
  "data": {
    "quote": true,
    "history": true,
    "instrument": true,
    "fundamental": false,
    "local_store": true
  },
  "execution": {
    "available": false,
    "connector": null
  }
}
```

这样：

```text
execution.available = false
```

只代表：

```text
不能实盘下单
```

不代表：

```text
行情页不能用
选股不能用
研究不能用
回测不能用
```

# 5. 页面能力必须按 Capability Gate，而不是 Broker Gate

未来页面按能力分级。

## 5.1 无 QMT、无交易连接仍可使用

只要本地仓或第三方数据源满足对应能力，就可用：

```text
仪表盘（研究模式）
行情快照
K线
报价牌（能力允许时）
标的搜索
市场结构
板块/ETF（数据源支持时）
技术指标
条件选股
自然语言选股
动态板块
因子计算
因子研究
回测
策略设计
策略市场
模拟盘
数据中心
任务中心
```

## 5.2 需要 Execution Connector 的能力

只有以下功能必须要求交易连接：

```text
真实账户
资金
真实持仓
实盘下单
撤单
订单查询
```

如果未连接执行 Connector：

```text

但执行按钮禁用

```

不能让整个主界面进入“未连接不可用”状态。

# 6. QMT 能力分成标准能力与 Vendor Extension

用户仍然应该能使用 QMT 的各种接口。

但要分成两层。

## 6.1 标准可移植能力

QMT 的通用能力映射到平台标准 Port：

```text
QuoteSnapshotPort
QuoteStreamPort
HistoricalBarsPort
InstrumentPort
AccountPort
PositionPort
ExecutionPort
OrderQueryPort
EventStreamPort
```

Core 只依赖这些标准接口。

## 6.2 QMT 专属能力

不能为了“完全解耦”而丢掉 QMT 特有功能。

例如 QMT 专属的高级接口，可以继续通过：

```text
QmtVendorExtension
```

暴露。

建议命名空间：

```text
/api/v1/connectors/qmt/extensions/*
```

或者内部 Capability ID：

```text
vendor.qmt.*
```

前端可以在：

```text
连接器 → QMT → 高级能力
```

中展示。

原则：

> **QMT 专属能力可以很多，但 Core 主流程不能 import 它。**

这样既保留“QMT 能用得深”，又保证“平台不依赖 QMT”。

# 7. DataSource 不应该继续是一个胖接口

V5 已要求拆 BrokerAdapter；V6 同样要求拆 DataSource。

当前一个 DataSource 同时假设：

```text
quote
kline
instrument detail
stock list
```

以后接入更多数据源后，这种假设会不成立。

不同 Provider 的能力可能完全不同。

因此建议拆成：

```text
QuoteSnapshotPort
QuoteStreamPort
HistoricalBarsPort
InstrumentDirectoryPort
InstrumentDetailPort
TradingCalendarPort
CorporateActionPort
FundamentalPort
FinancialStatementPort
BoardSectorPort
MoneyFlowPort
NewsPort
```

一个 Provider 实现自己真实支持的 Port。

例如：

```text
Provider A
  ├── QuoteSnapshot
  └── QuoteStream

Provider B
  ├── HistoricalBars
  ├── InstrumentDirectory
  └── FinancialStatement
```

平台不要求每个 Provider 填满所有接口，也禁止用假数据补齐不支持的能力。

# 8. tstdx / eltdx / BaoStock / 新浪 / 腾讯统一成为 Data Provider Plugin

这些数据源在架构层不要硬编码进 Core。

统一形态：

```text
plugins/data/<provider>/
```

每一个插件声明：

```text
ProviderManifest
```

示例结构：

```yaml
id: data.example
name: Example Data Provider
version: 1.0.0
kind: datasource

capabilities:
  quote.snapshot: true
  quote.stream: false
  market.history: true
  instrument.list: true
  instrument.detail: true
  fundamental: false

markets:
  - CN-A

freshness:
  quote: realtime
  history: eod

auth:
  required: false

rate_limit:
  managed: true

license:
  redistributable: false
```

具体 tstdx、eltdx、BaoStock、新浪、腾讯分别声明**实际能够提供的能力**，Core 不写死假设。

这点很重要：

> 不能因为某数据源今天支持某接口，就把这种供应商事实写成平台领域规则。

# 9. DataRouter 从单一 auto_chain 升级为按能力路由

当前：

```text
auto_chain = broker -> eltdx -> ...
```

对早期系统足够，但长期不够。

因为：

```text
最好的实时行情源
!=
最好的历史 K 线源
!=
最好的财务数据源
!=
最好的股票列表源
```

目标：

```text
CapabilityRouteTable
```

例如逻辑形态：

```text
quote.snapshot
  → Provider A → Provider B → Provider C

history.daily
  → LocalStore → Provider D → Provider A

instrument.list
  → LocalStore → Provider D

fundamental.statement
  → Provider E
```

实际具体顺序由：

```text
用户配置
Provider Manifest
健康状态
数据时效
授权状态
限流状态
```

共同决定，不在 Core 硬编码某个供应商优先级。

# 11. LocalStore 升级为平台 Data Hub

这是实现“不连 QMT 也能完整研究”的关键。

## 11.1 两条数据路径

需要明确区分：

### Live Path

用于：

```text
实时行情展示
最新价
盘口
实时策略输入
```

链路：

```text
Provider
  ↓
DataRouter
  ↓
QuoteBus
  ↓
Frontend / Strategy
```

### Research Path

用于：

```text
全市场选股
因子研究
回测
历史分析
```

链路：

```text
Provider
  ↓
Ingestion Job
  ↓
Normalize
  ↓
Quality Check
  ↓
LocalStore
  ↓
Screener / Factor / Backtest / Research
```

这两条链不能混成：

```text
选股时逐只调用新浪/腾讯/QMT
```

否则全市场几千只股票会产生：

```text
高延迟
公共接口限流
源不稳定
结果不可复现
```

正确做法仍然是当前已有方向：

> **先同步到 LocalStore，再本地全市场扫描。**

# 13. 数据质量应该成为一等能力

多数据源之后，最大的风险会从：

```text
没有数据
```

转变为：

```text
同一数据不同源不一致
```

所以需要：

```text
DataQualityService
```

负责：

```text
schema validation
时间连续性
OHLC 合法性
volume 单位
异常值
重复记录
缺失交易日
复权一致性
source drift
```

可选进一步支持：

```text
CrossSourceVerifier
```

对关键数据做多源对照。

注意：

研究用途可以允许明确标记的降级数据；

真实交易 Risk/Pricing 则必须使用 `PricingPolicy` 允许的高可信报价源，不能因为 DataRouter 能访问某公共网页行情，就自动用它作为实盘资金风控价格。

# 14. 实盘 Pricing 与普通行情必须隔离策略

这是多源后非常重要的安全边界。

不能做：

```text
任何可用行情源
  ↓
Risk Price
```

必须做：

```text
ExecutionService
      ↓
PricingPolicy
      ↓
Approved Pricing Source
```

例如策略逻辑：

```text
execution connector quote
或
被显式批准的低延迟可信 market provider
```

如果没有符合实盘风控等级的价格源：

```text
拒绝实盘订单
```

而不是降级到任意公共接口，也不是使用固定假价格。

# 21. QMT 断开时系统必须优雅降级

这是 V6 一个重要验收场景。

假设：

```text
09:30 QMT 正常
10:15 QMT 崩溃
```

系统不应：

```text
整个主界面失效
```

而应：

```text
Execution Connector = DEGRADED / OFFLINE
        ↓
立即禁止新的实盘执行
        ↓
交易页提示连接中断

同时：

DataRouter
  ↓
切换其他可用行情 Provider
  ↓
行情 / 选股 / 研究继续工作
```

这才是真正的功能解耦。

# 33. V6 最终定义

QMT Work 后续不应该被定义为：

> “需要先连接 QMT 才能使用的桌面交易软件”。

应该被定义为：

> **一个 Local-First、Data-First、Connector-Optional 的插件化量化平台。**

其核心研究链路：

```text
数据源
  ↓
标准化
  ↓
本地数据仓
  ↓
行情 / 指标 / 选股
  ↓
因子 / 研究 / 回测
  ↓
策略 / 模拟
```

与真实交易链路：

```text
OrderIntent
  ↓
ExecutionService
  ↓
Execution Connector
```

必须完全独立。

只有这样，QMT 才能同时满足两个目标：

1. **作为第一优先级交易客户端被深度支持，用户可以继续使用丰富的 QMT 专属接口；**
2. **又不会成为平台其他核心能力的单点依赖。**

这也是 V6 相对 V5 最重要的架构补全。
