# qmt_work 远程访问模式 · 对比分析与改进方案

> 决策问题：是否参考 Jupyter Notebook 模式，让客户端启动后同时支持第三方机器 Web 访问，本地免密、远程需密钥，客户端可配置/查看 Web 服务端口？
> 基线：v0.4.3 · 当前默认 `QMT_HOST=127.0.0.1`（严格单机），Electron 桌面壳加载 `http://127.0.0.1:<port>/`，CSP 白名单仅 `127.0.0.1:*`

---

## 一、当前部署形态（事实基线）

| 维度 | 现状 | 出处 |
|---|---|---|
| 后端默认绑定 | `127.0.0.1`（仅本机） | `core/config.py:58` `host = "127.0.0.1"` |
| 桌面壳加载地址 | `http://127.0.0.1:<port>/` | `electron/main.cjs:380,627,915` |
| CSP 白名单 | `default-src 'self' http://127.0.0.1:*` | `electron/main.cjs:497-502` |
| 启动自检 | 远程监听 + 默认密钥 = 拒绝启动 | `run.py:107-112` |
| loopback 免鉴权 | 本机请求免 API Key | `auth.py:60-63` |
| 限流豁免 | loopback 完全豁免 | `rate_limit.py:57-58` |
| 用户可改 `QMT_HOST=0.0.0.0` | 是（已有能力，但需手动改配置 + 自行设密钥） | `.env.example:6` |

**结论**：当前**已有**远程访问能力（改 `QMT_HOST` + 改 `api_key` 即可），但**没有产品化的"远程模式"**——用户需手改配置文件、手算端口、自行处理防火墙/反代/HTTPS，且无 UI 配置入口。

---

## 二、Jupyter Notebook 模式参考

Jupyter 的 `--no-browser` + token 模式核心特征：

| 特征 | Jupyter 实现 | 对 qmt_work 的可借鉴性 |
|---|---|---|
| 启动即输出 token + URL | 终端打印 `http://localhost:8888/?token=xxx` | 桌面壳可在「系统状态」页显示 |
| token = 随机生成 | 每次启动随机；可配置固定 | 复用 `api_key` 体系即可 |
| 本机免 token | `notebook_dir` 白名单 / `localhost` 免 | 复用 loopback 免鉴权 |
| 远程需 token | 首次访问输入；之后落 Cookie | 复用 `X-API-Key` 头 |
| 端口可配置 | `--port` / `--port-retries` | 已有（`QMT_PORT` + 自动 +1） |
| 无 GUI 也能跑 | `--no-browser` | 桌面壳可"最小化到托盘"近似 |

**关键差异**：Jupyter 是只读分析工具；qmt_work 是**可下单的实盘交易平台**——远程访问意味着他人可触发真实资金操作，风险等级完全不同。

---

## 三、两种方案对比分析

### 方案 A：默认严格单机（维持现状）

**设计**：`QMT_HOST` 默认 `127.0.0.1`；远程访问需用户手改配置 + 自行处理安全。

| 优点 | 缺点 |
|---|---|
| ✅ 攻击面最小（无可达网络路径） | ❌ 多设备协同不便（手机/平板看行情需另装 App） |
| ✅ 零误配置风险（不会"忘关远程"） | ❌ 服务器/无桌面会话场景无解（已知限制） |
| ✅ CSP / loopback 免鉴权 / 限流豁免口径一致 | ❌ 团队共享看盘需各自装客户端 |
| ✅ 已有安全基线无须扩展 | ❌ MCP 远程接入需 SSH 隧道（增加门槛） |
| ✅ 与"零 mock + 真实券商同机"硬约束天然契合 | ❌ 用户想远程时只能"裸开 0.0.0.0 + 默认密钥"被自检挡，体验差 |

### 方案 B：产品化"远程访问模式"（参考 Jupyter）

**设计**：新增 `QMT_REMOTE_ACCESS` 开关，启用后绑定 `0.0.0.0` + 强制随机密钥 + UI 配置入口 + 端口/密钥可见。

| 优点 | 缺点 |
|---|---|
| ✅ 多设备协同（手机浏览器看行情/持仓） | ❌ 攻击面扩大（任意网络可达 → 须 HTTPS/反代/防火墙） |
| ✅ 服务器/无桌面会话可用（浏览器访问） | ❌ 实盘下单远程触发 = 资金风险（须强二次确认） |
| ✅ 团队共享看盘无需各自装客户端 | ❌ CSP / loopback 口径需分叉（远程不豁免鉴权/限流） |
| ✅ MCP 远程接入无需隧道 | ❌ 用户可能误开远程 + 弱密钥 = 被接管 |
| ✅ 产品化体验（UI 一键开启/关闭） | ❌ 维护成本上升（远程模式独立测试矩阵） |
| ✅ 与 Jupyter 用户心智模型一致 | ❌ 桌面壳仍需同机（券商 SDK Windows 二进制依赖） |

## 四、关键风险深度分析

### R1 · 实盘下单的远程触发是核心风险

Jupyter 的 token 泄露 = 他人能跑你的代码（可接受）；qmt_work 的密钥泄露 = **他人能下真实委托、消耗真实资金**。这是**质变**的风险差异。

**缓解措施**（必须组合使用）：
1. 远程模式默认 `signal.mode=paper`（模拟盘），切 `live` 需二次确认；
2. 远程模式下大额下单强制 TOTP（已有 `QMT_TOTP_SECRET`）；
3. 远程模式下 `trade` scope 子密钥独立签发（不复用主密钥）。

### R2 · 桌面壳"同机"硬约束不变

即使开启远程访问，**Electron 桌面壳仍须与券商客户端同机**（xtquant 是 Windows 二进制）。"远程访问"指的是**第三方浏览器访问后端 HTTP 端口**，不是"远程跑桌面壳"。

### R3 · 网络可达性需用户侧处理

后端绑 `0.0.0.0` 只意味着"监听所有网卡"；第三方机器能否访问还取决于：
- Windows 防火墙放行端口；
- 路由器/NAT 端口转发（公网访问）；
- HTTPS 证书（明文 HTTP 传输密钥 = 中间人可截获）。

**结论**：产品化远程模式**只解决"后端绑定 + 鉴权"**这一层；网络可达性与 HTTPS 须文档引导用户自行处理（或提供"内网模式"与"公网模式"两档）。

### R4 · CSP 白名单需扩展

当前 CSP `default-src 'self' http://127.0.0.1:*`。远程模式下浏览器从 `http://<局域网IP>:<port>` 访问，CSP 须允许该 origin。若固定写死 `127.0.0.1`，远程访问会因 CSP 拦截静态资源。

## 五、最终改进方案：分级远程访问模式

**结论：有必要加入，但必须分级 + 默认安全。** 不是"开/关"二元，而是三档：

### 档位设计

| 档位 | 绑定 | 鉴权 | 适用场景 | 默认 |
|---|---|---|---|---|
| **L0 单机** | `127.0.0.1` | loopback 免 | 桌面壳同机使用 | ✅ 默认 |
| **L1 内网** | `0.0.0.0` | 远程强制 API Key + scope 分级 | 局域网内多设备看盘/团队共享 | 用户显式开启 |
| **L2 公网** | `0.0.0.0` | L1 + 强制 HTTPS + TOTP 强制 | 远程办公/公网访问 | 用户显式开启 + 引导 |

### 实现要点

| # | 动作 | 判据 |
|---|---|---|
| 1 | **新增 `QMT_REMOTE_ACCESS=off\|lan\|wan`** | 三档枚举；默认 `off` |
| 2 | **启动自检升级**：L1/L2 + 默认密钥 = 拒绝启动；L2 + 无 TOTP = 拒绝启动 | 复用 `run.py::_self_check` |
| 3 | **UI 配置入口**：「设置 → 远程访问」页：档位下拉 + 端口显示 + 密钥查看/重置 + TOTP 绑定 | 改档位需重启后端（或热重载配置） |
| 4 | **桌面壳状态可见**：托盘菜单/系统状态页显示「远程访问：关闭/内网(L1)/公网(L2）·端口 21118」 | 状态变更即时反映 |
| 5 | **CSP 动态化**：L1/L2 时 CSP 允许当前 `host:port` origin | 不再硬编码 `127.0.0.1` |
| 6 | **远程模式安全强化**：L1/L2 下 `signal.mode` 默认 `paper`；切 `live` 需 TOTP 二次确认 | 复用 `SignalRouter` 已有能力 |
| 7 | **密钥生成向导**：首次开 L1 时自动生成随机密钥（复用 `api_keys` 表）+ 显示一次 + 引导复制 | 不复用主密钥 |
| 8 | **限流分叉**：L1/L2 下 loopback 仍豁免，远程请求走限流 + 转发头检查（修 P1-5） | 复用 `auth.is_loopback` 逻辑 |
| 9 | **网络可达性引导**：L1 提示"请在 Windows 防火墙放行端口"；L2 提示"建议配置反向代理 + HTTPS" | 文档 + UI 提示 |
| 10 | **可证伪守卫**：`verify_remote_access_safety.py` —— 构造「L2 + 无 TOTP」必须报红；构造「L1 + 默认密钥」必须报红 | 2 例 + 终态对照 |

### 与既有安全基线的契合

- **loopback 免鉴权**：L0 维持；L1/L2 远程请求不豁免（已有 `auth.is_loopback` 转发头检查）
- **启动自检**：L1/L2 + 默认密钥 = 拒绝（已有 `run.py::_self_check` 扩展点）
- **scope 分级**：远程模式建议只签 `market` scope 子密钥（只读看盘）；`trade` scope 须额外显式授权
- **TOTP 二次确认**：L2 强制启用（已有 `totp.py`）
- **审计链哈希**：远程访问的所有操作都进审计链（已有 `db.audit`）

## 六、为什么不建议"默认只允许单机"

1. **用户已经在尝试远程**：`.env.example` 已列 `QMT_HOST=0.0.0.0`，README FAQ 有"端口被占用"条目，说明用户会改 host。当前缺产品化引导 ⇒ 用户裸开 `0.0.0.0` + 默认密钥被自检挡 ⇒ 体验差且不安全。
2. **服务器/无桌面会话**是已知限制（README 明列）。"桌面壳需桌面会话"在云服务器场景无解，但**后端 EXE + 浏览器访问**这条路径若产品化，可解锁"服务器部署 + 远程浏览器访问"场景。
3. **MCP 远程接入**：Cursor/Claude Desktop 直连 MCP 需后端可达；当前需 SSH 隧道。若 L1 内网模式可用，局域网内 MCP 接入零配置。
4. **多设备看盘**是真实需求：手机/平板浏览器看行情/持仓，比"各自装客户端"轻量得多。

## 七、分阶段落地

### 阶段 1（2 周）：L1 内网模式 MVP

- 新增 `QMT_REMOTE_ACCESS=off|lan` 开关
- 启动自检扩展：`lan` + 默认密钥 = 拒绝；`lan` 时绑定 `0.0.0.0`
- 「设置 → 远程访问」页：档位 + 端口 + 密钥查看
- CSP 动态化
- 可证伪守卫 2 例

### 阶段 2（3 周）：L2 公网模式 + 安全强化

- `QMT_REMOTE_ACCESS=wan` 档位
- L2 强制 TOTP；L2 默认 `signal.mode=paper`
- 网络可达性引导文档 + UI 提示
- 密钥生成向导（随机生成 + 显示一次）

### 阶段 3（4 周）：生态延伸

- MCP 远程接入零配置（L1 内网即用）
- 移动端只读视图（响应式布局适配手机浏览器）
- 反向代理 + HTTPS 配置文档与脚本

---

## 八、一句话决策

**有必要加入，但必须分级（L0/L1/L2）+ 默认 L0（单机）+ 远程模式安全强化（强制密钥/TOTP/paper 默认）。** 不做"开/关"二元，做"三档 + 默认最安全 + 用户显式升级"——既满足多设备/服务器/MCP 远程接入的真实需求，又不让"误开远程 + 弱密钥"成为资金风险入口。
