## 一、实测环境：起独立后端实例

- `QMT_DB_PATH` 必须是 **.db 文件路径**（不是目录），配合 `QMT_PORT` / `QMT_PORT_FILE`，
  这样测的是「新代码 + 新前端产物」，**不必重启用户正在看盘的客户端**。
- ⚠️★★ **`QMT_DB_PATH` 必须用相对路径**（先 `cd` 到仓库根）。
  Git Bash 会把 `/p/...` 这类绝对路径翻译成 **`\p\...`** —— 那是「当前盘根下的 `p\` 目录」，
  于是实例**在一个全新的空库上跑起来了，而且毫无报错**。症状极具误导性：
  「名称表查不到」「筛选没数据」「历史全是空的」，看起来像产品坏了，实际是测错了库。

  判据（一眼看穿）：

  ```bash
  QMT_DB_PATH=... python -c "from core.config import settings; print(repr(str(settings.db_path)))"
  #  错：'\\p\\github_public\\qmt_work\\output\\_live_db2\\app.db'   ← 前导 \p\ 就是铁证
  #  对：'P:/github_public/qmt_work/output/_live_db2/app.db' 或 'output/_live_db2/app.db'
  ```

  顺带：被翻译的路径会在盘根堆出 `P:\p\github_public\...` 垃圾目录树
  （本仓已有 `_direct_be` / `_static_build` / `preview` 等历史残留）。

- ⚠️★ **要用「用户真实库的副本」测，不要用空库**。空库会把一切都变成 DEGRADE / 空态，
  **分不清「真缺陷」和「本来就没数据」**。复制三样到 `output/_live_dbN/`：
  `app.db` + `app.db-wal`（最新数据在 wal 里）+ `stock_names.json`（名称表）。
  用户库位置：`%APPDATA%\qmt-work-frontend-next\app.db`（实测 1.15 GB）。
  注意：本 shell 里 `$APPDATA` 可能为空 ⇒ 写全路径
  `/c/Users/Administrator/AppData/Roaming/qmt-work-frontend-next/`。

- ⚠️ 锁文件（`.qmt_work.lock`）被独占、删不掉时，先找**持有者**：
  `netstat -ano | grep LISTENING` 取 PID → 强制结束该进程（本轮就是这么才删掉
  `output/_live_db` 的）；或直接**换一个新数据目录**（比纠缠删锁快得多）。

- ⚠️ `rm` 被 safe-delete 护栏接管、走 trash；**GB 级目录 trash 必然失败**
  （`SAFE_DELETE_FAIL_CLOSED`）。别反复换姿势绕（`cmd rmdir` / PowerShell
  `DeleteDirectory` 都会被拦）⇒ 把残留清单报给用户自己删。

- ⚠️ 真实库里存有持久化的券商配置 ⇒ 独立实例会**反复重连券商并失败**，启动与部分端点变慢。
  探针不要用固定超时。

- ⚠️ `QMT_PORT_FILE` 只有 `run.py` 会写；直接 `python -m uvicorn --port N` **不会写端口文件**，
  去读它必然读到空 ⇒ 误报「后端未就绪」。直接用已知端口探测。

## 二、股票名称表：唯一实现 + 三处同源失效

- 数据来源：`<数据目录>/stock_names.json`（真实安装实测 **7173 条**，如 `600000.SH -> 浦发银行`），
  由 eltdx 源维护、与之共用同一份缓存。
- 查询**唯一实现**：`datasource/eltdx_utils.py::lookup_name / lookup_names / reset_name_cache`
  （+ 内部 `_load_name_cache`）。`app/screener/universe.py::_fill_names` 已改为委托它。
- ⚠️★ 同一缺口造成**三处**静默失效（都不报错）：

  1. **选股「名称」列整列空白**：`names={}` 时 `name` 是 `""`，而空串绕过前端 `?? "--"`。
  2. **「排除 ST」一只都排不掉**：`_is_st(names.get(c, ""))` 恒 False，
     还报 `excluded_st=0`（看起来像「本来就没 ST」）。
  3. **涨停监控池把代码当名称**：`LimitUpMonitor.add` 曾是 `self._pool[code] = name or code`，
     而两个调用方（REST 路由 + MCP 工具）**都不传 name** ⇒
     `_limit_factor(code, name)` 的「名称含 ST ⇒ 5%」分支永不命中
     ⇒ **ST 股被按 10% 判涨停，而它 5% 就封板了 ⇒ 永远等不到触发**。

- 纪律：**查不到就留空**（零 mock），**绝不用代码或占位值冒充**；
  前端必须把空串显式渲染成 `—`（`?? "--"` 对 `""` 不生效）。
  实测修复后：`600000.SH → 浦发银行`、`600519.SH → 贵州茅台`、
  裸代码 `000001 → ""`（**不猜**：000001.SH 是上证指数、000001.SZ 是平安银行）。

## 三、门的顺序与归因（交易 / 账户域）

- ⚠️★ **参数校验必须在券商门之前**。`POST /trade/cancel` 曾把 `{}` 说成
  「未连接任何券商客户端：请到「券商连接」页添加并连接券商。」——
  把「参数没传」归因成「环境不可用」，排查方向被彻底带偏。

- ⚠️★ **券商门必须按执行模式分流**：`live` 才需要券商；`paper`（PaperEngine 本地撮合）与
  `dry_run`（只返回计划）**都不依赖券商**。已修 `/trade/order`、`/trade/cancel`、`/rebalance`。

- 反向纪律：`live` 无券商时的 `503` + 券商引导文案**一个字都不能改**（归因本来就对），
  修改后必须实测确认它没被放松。

- 撤单的账户安全保险：指定了 `conn_id` 却取不到该连接时**报 404，绝不静默回退到 active**
  （多账户下静默回退正是「撤错账户」的成因）。
  前端必须真的把 `conn_id` 传下去（`Positions.tsx` 传 `active?.conn_id` 并进依赖数组）——
  否则这道保险等于没接上（本项目反复出现的「能力存在但没人调用」）。

- 二次确认链路的两个静默死锁（已在 `docs/2026-09-19_...` 记过，此处只留判据）：
  ① 前后端字段名不一致（`totp` vs `totp_code`）⇒ 启用 TOTP 后大额单**永远确认不了**；
  ② `confirm()` 重跑风控漏传 `price_type` ⇒ 市价单被当限价单拒，而**取不到价恰是它进入挂起的原因**。
  凡「先挂起、后复检」的路径，复检**必须用原对象的全部字段**。

## 四、从 MEMORY.md 下放的子系统细则

### 数据 / 同步 / 任务运行时
- 运行记录必须落库：`sync_state` + `screen_runs`/`screen_picks`（双表）。只记成功 ⇒
  界面上「没跑」与「跑了失败」长得一样。
- `dataset_snapshots.batch_id` 必须与 `local_bars.batch_id` 一致：按 `provider_id='auto'`
  + ISO 时间戳回查恒 0 行 ⇒ 快照 `row_count=0` 却报 `complete`（自相矛盾）。
  空批次必须标 `quality=empty` + 写明原因。取「最新批次」按 `MAX(rowid)` 而非 `MAX(dt)`
  （全量回补会把很老的日期放进新批次）。

  按相位触发；迁移只改 `cron` 而不重算相位 ⇒ 按错时间跑（v27 把「先同步再选股」

  归入 `local_bars` 互斥组；手动 `screen` **刻意不进组**（用户发起、可见、可重跑）。
  新增写库/读库 kind 必须登记。
- `params.get(x) or 默认` 会吞掉空串 ⇒ 区分「未传」只能用 `is None`。
- 调度界面两个已知 bug：`RuntimeJobs.tsx:390` 传 `"catchup"`（后端只认 `catch_up`）⇒ 必 400；
  `:240` 读 `next_run/last_run`（后端返 `next_run_at/last_run_at`）⇒ 恒 `--`。

## 五、主库备份：占用闸门与跳过链（2026-09-20 实测修复）

### 缺陷：只有「份数」上限 ⇒ 11GB 常驻磁盘，且界面上一处都不提

备份是**整库全量复制**（`db.backup_to` 走 sqlite backup API）。
原实现只有 `keep=10`，而本机主库 1.14GB ⇒ **11.4GB** 常驻。
实测真实数据目录：

```
%APPDATA%\qmt-work-frontend-next\backups\   →  10 份 × 1.14GB = 11 GB
%APPDATA%\qmt-work-frontend-next\app.db.bak_bardate → 603 MB（未纳管的库副本）
C: 321GB 仅剩 47GB（已用 86%）
```

而 `gateway/db_backup.py::list_backups()` **零调用方**（docstring 写着「供运维接口
展示」，那个接口从来没建）⇒ 用户只能等磁盘满了才发现。磁盘满在本项目不是理论风险：
它会让同步写库失败、测试假失败。

### 修法（三层，缺一不可）

1. **体积闸门**：`db_backup_max_total_mb`（默认 4096）+ `db_backup_min_keep`
   （默认 2）。保留策略 = min(份数上限, 体积上限)，但**至少留 `min_keep` 份**。
   ⚠️ `min_keep` 是**地板**：预算比单份备份还小时，宁可超限也不许把备份删光 ——
   那等于静默关掉保护，比不设上限更危险。此时 `over_budget=true` 且
   `reclaimable_bytes=0` 是**合法状态**，界面必须如实讲清「受最少 N 份保护、
   需手工处理」，既不能承诺可回收，也不能说一切正常。
2. **跳过链**：源库指纹 = `app.db` 与 `app.db-wal` 各自的 `(size, mtime_ns)`，
   与上次成功备份完全一致则跳过。指纹落盘在 `backups/.last_backup.json`
   （点号开头、非 `.db`，不会被 `list_backups` 当备份）⇒ **跨进程有效**：
   客户端反复启停不再重复整库复制。
   被记录的那份备份若已被清理 ⇒ 覆盖关系失效 ⇒ 必须重新备份。
   ⚠️ **跳过 ≠ 失败**：`backup_once` 两种情况都返回 `None`，区分只能读
   `last_status["action"]`（created / skipped / failed / idle）。
3. **占用可见**：`stats()` 进 `/config/paths` 的 `db.backups`，界面在「数据目录」页
   主库那一栏下方展示占用 / 上限 / 最近一次结果 / 可回收量，并提供
   「立即备份」「清理旧备份」（后者走 `ConfirmModal`，删除不可逆）。

### ★★ 启动备份必须装在**最后一个**启动阶段（否则跳过永远不成立）

指纹是「某个时刻的物理形态」，所以**采指纹的那一刻库必须已经静止**。
启动阶段顺序是 `db → broker → engines → watchdogs → replay → misc`：把备份装在
`watchdogs`（第 4/6 个）时，它后面还有 `replay` / `misc` 在写库 ⇒
**指纹一记下来就已经过期**，于是每次启动都白复制一份 1GB+ 的主库
（实测：侧车 `wal=[1104192]` vs 实际 `wal=[1141272]`，永远对不上）。

已迁到最后一个阶段 `phase_misc`（`log.info("qmt_work started")` 之前）。
迁完实测：启动后侧车指纹与磁盘状态**完全一致**，第二次启动**不再复制**。

- 启动后库确实会静止（实测 14 秒内 `app.db` / `-wal` 大小纹丝不动），
  所以「在末尾采指纹」是可行且充分的。
- 护栏：`tests/test_db_backup_policy.py::test_db_backup_is_assembled_in_the_last_startup_phase`
  + `test_last_phase_really_is_last`（源码扫描）。往后追加启动阶段时后者会失败，
  提醒把备份再往后挪。
- ⚠️ 排查这类问题要看**侧车指纹 vs 磁盘实际值**，只看「有没有新备份」看不出原因。

### 三个容易写回去的顺序/细节坑

- ★★ **副作用必须发生在采指纹之前**。端点在备份成功后要写一条审计行，而
  **审计行本身就是写库**：若指纹先采，下一次调用必然认为「主库变了」⇒
  用户连点两次「立即备份」白复制两份整库（实测 1.14GB × 2）。
  故 `backup_once(reason, after_create=...)` 的回调在**落盘之后、采指纹之前**执行。
  跳过时**不写审计**（写了反而让下一次跳过失效）；失败必须留痕。
  ⚠️ 测这条必须让备份器盯**应用正在写的那个主库**，否则「审计行影响不到指纹」
  ⇒ 测试假通过（`_live_db_backup` fixture 就是为此存在）。
- ★ **备份文件名只到秒**（`app.YYYYMMDD_HHMMSS.db`），而同一秒内可以触发多次
  （启动 + 手动 + 关闭）⇒ 直接写同名文件会**静默覆盖**上一份备份，悄悄少一个
  还原点。必须 `_unique_name()` 重名加序号。
- ★ **同步重活必须丢线程**：1GB+ 的一致性复制要好几秒，`asyncio` 里直接调用会把
  事件循环（WS 广播 + 全部 HTTP）一起卡住。启动备份 / 周期备份 / 停机备份 /
  两个端点全部走 `asyncio.to_thread`。

### 挂载点

- `gateway/db_backup.py`：策略 + 指纹 + `stats()` / `prune_now()` /
  `stray_db_files()`（只上报未纳管副本，**绝不删**）。
- `core/context.py::AppContext.db_backup`（新槽位）：此前只存在
  `app.state._db_backup`（AppContext 之外的私有属性）⇒ 路由**没有任何途径**拿到它。
  占用类能力必须能被「读展示」的层拿到，否则等于不存在。
- 路由：`GET /config/paths` 的 `db.backups`；
  `POST /config/paths/db-backups/prune`、`POST /config/paths/db-backups/run`。
- 前端：`services/api/paths.ts`（`BackupStats` + `pathsApi.runBackup/pruneBackups`）、
  `domains/system/DataPaths.tsx`（导出 `backupOccupancyText` / `backupLastText` /
  `backupWarn` / `backupStrayText` / `canPruneBackups` 供单测）。
- 测试：`tests/test_db_backup_policy.py`（32 例）、
  `tests/dbBackupPanel.test.tsx`（19 例）。
- 实测：`output/_bkprobe2.py`（真协议、自起自停、**服务起来后再摆现场**）。
  ⚠️ 摆现场必须在启动之后：应用启动就会备份并按策略裁剪，事先摆好的「超上限」
  现场会被它顺手收拾干净 —— v1 探针因此报了 7 个假失败。


## 六、链路真伪与交易链路（2026-09-20 实测）

### ★★ 判「某条链路到底有没有生效」不能读代码

应用跑的是**它启动时那一份代码**。本轮实测客户端（08:23 起跑）与落库代码的提交时间
（10:50）错开，于是「看代码明明有落库」与「库里一行都没有」同时成立。判据必须三重取证：

1. **作业时间 vs 提交时间**：`runtime_jobs.finished_at` 与 `git log -1 --format=%cd <file>`。
2. **`result_json` 的键集**：落库版会多出 `run_id` / `saved` / `bar_date`。
   实测旧版键集 = `[strategies, scanned, total_hits, results, provider, degraded, degraded_reason]`
   ⇒ 缺 `run_id/saved/bar_date` = 落库版**从未生效**。
3. **目标表行数**：`screen_runs` / `screen_picks` / `sync_state` 实测全 0。

### 本轮修掉的三个缺陷

1. **前端新鲜度误判**（`AutoPicks.tsx`）：拿「今天」当基准 + `new Date().toISOString()`（**UTC**）
   ⇒ 周末/节假日必误报「行情未更新」。改为与后端 `expectDate`（最近交易日）比。
2. **下单提示条条件错**（`OrderForm.tsx`）：渲染条件是 `!connected`，而 mode 默认 `paper`
   ⇒ **连上券商时反而一声不响**（最危险：用户以为已报单）。改为 `orderExecutionNote(mode, connected)`
   返回「有结论就提示」。
3. **撤单 500**（`routes/trade.py`）：`PAPER-1` 被递给券商适配器 ⇒ `int()` ⇒ ValueError ⇒
   全局兜底 500「服务器内部错误」。改为**先按 `PAPER_ORDER_PREFIX` 拦下**（前缀唯一来源
   `engines/paper_engine.py`）并如实归因；柜台拒绝委托号形态 ⇒ `ValueError → 400`（不是 500）。
   ⚠️ 只拦**前缀**，不按模式一刀切 —— 用户可能刚从 live 切到 paper，券商那边还有真实挂单要撤。

### 探针纪律：不可证伪的断言 = 探针错

报 FAIL 之前先怀疑探针。本轮踩到三次**假失败**：

- 拿「今天」/`toISOString()`(UTC) 当新鲜判据。
- 把「启动备份必须 skipped」当不变式 —— 主库真变了就该 created。
- 把 `save_run` 的返回摘要当「来源标签」—— `source` 只存在 `screen_runs` 表里。

另：**「侧车指纹 == 磁盘指纹」在活进程上永不可断言**（订单看守 5s / 调度 30s / 账户快照持续写 WAL）。
可断言的是 `db` 文件指纹、`skip xor created`、`total_bytes <= max_total_bytes`、
连续两次调用 `created → skipped → skipped`。
