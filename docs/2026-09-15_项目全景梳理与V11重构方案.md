## 8.8 R4 已落地：`BarLite` 轻量视图（2026-09-15）

### 8.8.1 先测量再动手

在 117 万行真实库（6982 只 × ~168 根，`data/app.db` 462MB）上分离三段成本：

| 段 | 耗时 |
|----|------|
| SQL `fetchall()`（含 `sqlite3.Row` 物化） | 3586 ~ 3837 ms |
| Python 侧 canonical 选主 / 分组（不构造对象） | 826 ~ 843 ms |
| **`Bar` 构造（逐行 Pydantic 校验）** | **4449 ~ 5882 ms** |

构造方式对比（同为 1,173,722 次）：

| 方式 | 耗时 | 结论 |
|------|------|------|
| `Bar(**kw)`（现状） | 4901 ~ 5882 ms | 基准 |
| `Bar.model_validate(dict)` | 4174 ~ 5433 ms | 无显著收益 |
| `Bar.model_construct(**kw)` | **8277 ms** | **更慢**，排除（复现 09-14 结论） |
| `TypeAdapter(list[Bar]).validate_python([dict,...])` | 4174 ms | 仅快 ~15%，不足以抵消复杂度 |
| `TypeAdapter` 直喂 `sqlite3.Row` | ❌ 失败 | Pydantic 不把 `Row` 当 mapping，产出 117 万个校验错误 |
| `namedtuple` 位置实参 | 2067 ms | 可用 |
| **`__slots__` 类位置实参** | **1918 ms** | **采纳（约 3 倍快）** |

### 8.8.2 设计

- 新增 `datasource.models.BarLite`：**结构等价只读轻量视图**。字段集与 `Bar`
  完全一致（顺序也一致，位置实参构造依赖它），不做校验/强转。
- 三条铁律写入 docstring：① 字段集必须与 `Bar` 一致（测试钉住）；② **仅用于
  进程内批处理消费**，不得用于 API 响应 / 持久化 / 跨模块契约；③ 不做校验，
  调用方须保证必填列非空（`upsert_bars` 走 `Bar` 校验已保证）。
- `local_store._row_to_bar(row, lite=False)`：**单一函数体**按 `lite` 选目标类，
  取值列清单只有一份 → 结构上不可能漂移。
- `get_bars_batch(..., lite=False)` → `BarsProvider.get_bars_batch(..., lite=False)`
  → `screener.scan_async` 传 `lite=True`。**默认值全为 `False`，对外契约不变**。
- 在线路径仍返回 `Bar`（由 hub 构造，再转一道只增加成本）；两者字段同名同义，
  消费方按属性访问即可（选股链路无 `isinstance(Bar)` 依赖，已全仓核实）。
