#### 8.8.1 先测量再动手

在 117 万行真实库（6982 只 × ~168 根，`data/app.db` 462MB）上分离三段成本：

### 8.9 R4 已落地：批量取数的连接与消费方式（2026-09-15）

#### 8.9.1 起因：同类反模式审计

R4 剩余项里的「SQL 取数」原判「进一步压缩空间有限」。本轮做**同类缺陷审计**时发现，

```python
rows = self._db.execute(sql, params).fetchall()   # ← 旧实现
```

`DB.execute()` 是「**主连接 + 写锁**」，而 `fetchall()` 还在**锁外**跑在主连接上 ——
`core/db.py:276` 自己写着「回退路径：主连接上的读必须与写互斥（同连接写提交会打断读游标）」。
全仓 grep 确认这是**唯一**一处该反模式（其余 `.fetchall()` 均在锁内）。

#### 8.9.2 实测代价（3.2 万行小样，1 读者 + 1 写者，20s）

| 指标 | 旧实现 | 新实现 |
|---|---|---|
| 空载单次批量读 | 201.6 ms | 212.4 ms |
| **并发写负载下单次批量读** | **3925.1 ms** | **332.2 ms** |
| **相对空载劣化** | **19.5×** | **1.6×** |
| **20s 内读轮数** | **3** | **60** |
| 写者单次写入 p50 | 0.15 ms | 0.38 ms |
| **写者单次写入 p99** | **73.56 ms** | **1.55 ms** |
| 写者最大 | 122.44 ms | 45.62 ms |

根因：批量读与每一次写**共用一条主连接**，争抢同一把连接互斥量。

#### 8.9.3 改法

- 新增 `core.db.DB.readonly_conn()`：**独占只读连接**（`mode=ro`）上下文管理器，
  不占 `_rw` 读写锁、与写者互不阻塞；**分块循环外只开一次**；调用方**流式**消费游标。
  内存库 / 只读介质打不开只读连接时**降级主连接 + 写锁**（与 `query()` 回退同口径，语义安全）。
- `get_bars_batch` 改用该原语 + 游标流式消费（去掉 `fetchall` 的整批物化）。

### 8.10 R4 收尾：Canonical 选主规则统一（读侧 = 对账侧）（2026-09-15）

#### 8.10.1 起因：同一个问题，仓库里有**三份**实现、**三种**规则

§8.5 原记录该项为「`(provider_id='') DESC` 与逐只 `get_bars` 语义不一致」——**该表述有误**。
审计后实测：`get_bars`（SQL 窗口）与 `get_bars_batch`（`_canonical_key`）**完全一致**。
真正的分歧在**读侧与对账侧之间**：

| 位置 | 排序键 | 空 provider 位置 |
|------|--------|------------------|
| `local_store.get_bars`（SQL 窗口函数） | 质量状态 → `(provider_id='') DESC` → `provider_id` | **最优（排前）** |
| `local_store._canonical_key`（Python，复刻 SQL） | 同上 | **最优（排前）** |
| `quality.reconcile_bars`（Python） | `PROVIDER_QUALITY_RANK`（broker/qmt > eltdx > baostock > akshare） | **最差（999）** |

即：读侧「空 provider 优先 + 名字典序」，对账侧「provider 质量序 + 空最差」。
且两处 `local_store` docstring 写的是「优先具名 provider」，与**自身 SQL** 相反 —— 文档与代码也不一致。

#### 8.10.2 实测分歧（合成多源数据，`output/probe_canonical_rules.py` 可复现）

| 组 | 数据 | ① `get_bars` / ② `get_bars_batch` | ③ `reconcile_bars` | 一致? |
|----|------|-----------------------------------|--------------------|-------|
| A | `akshare`(30) vs `broker`(0)，同质量档 | `akshare`（名字典序在前） | `broker`（质量序更优） | ❌ |
| B | `''`(999) vs `broker`(0) | `''`（**空优先**） | `broker` | ❌ |
| C | 质量档不同（对照） | `broker` | `broker` | ✅ |

后果：一旦真有第二个数据源写入同一 `(code, dt)`，会出现
**「消费方读到的行」≠「对账侧标为 canonical 的行」** —— 两条链路对「这根 K 线的权威值」
给出不同答案。

#### 8.10.3 为什么一直是潜伏态（真实库实测）

| 指标 | 实测值 |
|------|--------|
| `local_bars` 总行数 | 1,173,744 |
| `provider_id` 为空的行数 | **0**（仅 broker / tencent / auto） |
| 同 `(code, period, adjust, dt)` 多源共存的组数 | **0** |

选主逻辑在真实数据上**根本不触发**（每组只有 1 行）。所以这是**潜伏地雷**而非现行 bug：
现在改，行为零变化；等第二个源落地再改，就要连带排查已污染的结果。

#### 8.10.4 决策

**统一到 provider 质量序**（用户确认）。理由：
① 这是架构文档已写明的规则（`quality.py` 模块 docstring）；
② 消除「读侧 ≠ 对账侧」这一矛盾 —— 两侧必须是同一行；
③ 空 provider = 未标注来源，不应压过具名数据源（原规则恰好相反）；
④ 真实数据上零行为变化，风险可控。

#### 8.10.5 改法：规则只允许有**一份**实现

- **规则落在 `quality.py`**（本就拥有 `PROVIDER_QUALITY_RANK`）：
  - `QUALITY_STATE_RANK`（`validated>complete>match>其他`）与 `PROVIDER_QUALITY_RANK` 并列；
  - `provider_rank(provider_id)` —— 未登记 / 空 → **999（最差）**；
  - `canonical_sort_key(quality_state, provider_id)` → `(质量状态档, provider 质量序, provider_id)`，
    **读侧与对账侧共用**。
- **`local_store` 导入复用**，不再自持一份：
  - `_canonical_key(row)` → 一行转发 `canonical_sort_key(...)`；
  - `get_bars` 的窗口 `ORDER BY` 改为 `_CANONICAL_ORDER_SQL`，而该片段由
    `_QUALITY_STATE_CASE_SQL` / `_PROVIDER_RANK_CASE_SQL` **程序化拼接生成**（遍历排名表），
    不是手写副本 —— 新增一个 provider 只需改 `quality.py` 一处，SQL 自动跟上。
- **`reconcile_bars` 的 tie-break 一并修正**：原为 `(_rank(provider_id), -close)`，
  即同档位下「**价高者胜**」——既与读侧的 provider 名升序不一致，也让 canonical 归属
  依赖价格。改为同一个 `canonical_sort_key`，tie-break 落在 `provider_id` 升序（确定性）。

#### 8.10.6 护栏（9 条，`backend/tests/test_canonical_selection.py`）

### 8.11 P1-2 已落地：双状态容器合一（`AppState ⊂ AppContext`）（2026-09-15）

#### 8.11.1 起因：三份槽位清单 + 快照语义

服务槽位（db / broker_manager / risk / ...）此前存在**三份**清单，必须人工保持一致：

| 位置 | 形态 | 角色 |
|------|------|------|
| `core/state.py` `AppState` | 模块级单例，类属性槽位 | bootstrap 各阶段**写**；engines / gateway / datasource 直接读 |
| `core/context.py` `AppContext` | dataclass | 启动时由 `build_from_state` 从 `AppState` **拷贝出的快照**，路由读 |
| `core/context.py` `_STATE_FIELDS` | 33 个名字的字面量元组 | 快照拷贝的白名单 |

且快照**不会随后续写入更新** —— 只有 `lifecycle_ready` / `lifecycle_stopping` 靠
`app/main.py` 里两段手工回同步代码维持（代码注释自己承认）。另：`AppContext.__getattr__`
对未知槽位**静默返回 None**（V10 迁移期兜底，迁移已完成却未撤）。

#### 8.11.2 实测：清单无漂移，但快照语义已经造成**两处静默失效**

机械比对三份清单：**完全一致**（`AppState` 33 槽位 = `AppContext` 33 对齐字段 =
`_STATE_FIELDS` 33 项，交集无缺无余），且 bootstrap 之外**没有**任何生产代码写
`state.X`。所以这不是「清单漂移」型 bug，而是**快照陈旧 + 静默兜底**型 bug：

| 端点 | 写入侧 | 读取侧 | 旧行为 |
|------|--------|--------|--------|
| `POST /api/v1/alerts/test` | `bootstrap/phase_db` 写 `state.alert_engine` | `routes/alerts.py` 读 `ctx.alert_engine` | 该名字**三份清单都没声明** → 读时经 `__getattr__` 兜底**恒为 None** → 端点**永远返回 503「告警引擎未初始化」** |
| `GET /api/v1/market/kline/sync-status` | `gateway/market_sync` 写 `state._market_sync_last` | `routes/market.py` 读 `ctx._market_sync_last` | 同上 → `last_run` **恒为 `null`** |

即：这两个端点在「静默降级」状态下运行了很久 —— 不报错、不告警，只是永远走兜底分支。
**这正是 `__getattr__` 静默 None 最危险的地方：它把「整条链路失效」伪装成「正常但为空」。**

#### 8.11.3 改法

- **槽位只定义一处**：`AppContext` 声明全部槽位（含 3 个运行期状态槽位与
  `alert_engine` / `order_watchdog`）；`core/state.py` 的 `AppState` 改为
  `@dataclass class AppState(AppContext)`，**只保留生命周期方法**
  （`begin_startup` / `mark_phase` / `mark_ready` / `begin_shutdown` / `require_bridge`）
  与 `state = AppState()` 单例。新增槽位只改 `core/context.py` 一处。
- **取消快照**：`app/main.py` 由 `ctx = build_from_state(state)` 改为 `ctx = state`
  —— 注册的就是单例本身，路由与引擎读写**同一对象**。于是：
  - `build_from_state` / `_STATE_FIELDS` 删除；
  - `mark_ready()` 与注册的**先后顺序不再重要**（旧实现必须 mark_ready 在前，否则
    `/ready` 恒 503）；
  - 停机时那两段手工回同步代码删除（`begin_shutdown()` 直接作用于同一对象）。
- **撤掉静默兜底**：删除 `AppContext.__getattr__`。未知槽位现在抛 `AttributeError`；
  取可选槽位请写 `getattr(ctx, name, None)`（该写法不受影响，`getattr` 自带默认值语义）。
- **保留可测性**：`AppContext()` 仍可独立实例化，`set_active_context(自建实例)` 仍可注入
  隔离上下文；`get_ctx()` 仍返回 `active_context()`。

### 8.12 P1-3 已落地：能力链统一（三套机制 → 单一入口）（2026-09-15）

#### 8.12.1 起因：原记录「链定义双份维护」低估了问题

§7.2 原记 P1-3 为「`_auto_chain` 与 `resolve_chain` 并存 → 链定义双份维护」。

#### 8.12.2 实测：三套机制 + 两套改链机制

| 机制 | 规则 | 谁在用 |
|------|------|--------|
| `_auto_candidates()` | 扁平 `_auto_chain`（**注册顺序**）+ 仅许可证过滤 | `get_quote` / `get_instrument_detail` / `get_minutes` / `get_stock_list` / `search_stocks` |
| `resolve_chain(cap)` | 能力契约链 + 注册 + **依赖** + 许可证 | 只有 `get_kline` |
| `_sup_chain()` | `resolve_chain("kline")` − broker | 8 个补充源方法（boards / etf_list / moneyflow / share_capital / price_limits …）——**用 kline 链解析非 kline 能力** |

两套改链机制各自只控制**一部分**路径，互不可见：

| 机制 | 暴露面 | 影响范围 |
|------|--------|----------|
| `DataSourceManager.set_auto_chain()` | 仅代码内 | 只影响扁平链（5 条路径） |
| `provider_catalog.set_override()` | `POST /api/v1/data/chain` | 只影响契约链（K 线 + `_sup_chain`） |

**确定性探针**（注入假补充源，不依赖网络）实测出三处硬事实：

| # | 事实 | 证据 |
|---|------|------|
| 1 | **改链 API 说谎** | `set_override('quote',['tencent'])` → API 回显 `resolved=['tencent']`，而 `get_quote` 仍取 `sina` —— 对 5 条路径**完全无效** |
| 2 | **顺序分歧** | 扁平链给 `sina` 优先、契约链给 `tencent` 优先；实际取 `sina`，而 `app/platform.py` 向 UI 宣告的是 `tencent` |
| 3 | **能力错配** | `_sup_chain` 给 `get_moneyflow` 的候选是 kline 链 `['tencent','sina']`，而 moneyflow 的真实链是 `(broker, eltdx, akshare)` —— **源集合不相交** |

#### 8.12.3 根因：`resolve_chain` 从不校验能力声明，而链成员是手写「期望」

`resolve_chain()` 只按 **契约链元组成员 + 注册态 + 依赖 + 许可证** 过滤，
**从不检查「该 provider 是否声明了该能力」**。而 `describe()` 用的是源自己声明的
`capabilities` —— 两套数据从未对账。逐源核对**真实方法集**后，实测出四类不一致：

| 类型 | 实例 |
|------|------|
| **链里有、声明无** | `kline` 链含 tencent/sina（按静态口径）；`sector`/`capital`/`price_limit` 链含 baostock；`fundamental` 链含 eltdx；`corporate_action` 无任何源实现 |
| **声明了、链里够不到** | sina/tencent 声明 `instrument_detail`，而该链只有 `(broker, eltdx, baostock, akshare)` —— 永远轮不到 |
| **静态目录 ≠ 实现** | broker 静态声明 14 个 / 实现 3 个；eltdx 13 / 4；akshare 13 / 5 |
| **声明幻觉 + 假实现** | baostock 声明 suspend/fundamental/index_constituent/dividend，akshare 声明 sector/fundamental/capital/suspend/moneyflow/calendar/dividend —— 两类**一个都没实现**；`_PublicSource.get_stock_list` 是 `raise`，`hasattr` 判不出来（探针一度被骗） |

> 该推断**不成立**。扁平链会去调 sina/tencent 的 `get_stock_list`，而它们是 `raise`，

#### 8.12.4 改法

1. **能力唯一真源 = `DataSource.capabilities`**（实现类自述）。新增 `_declared_map()`

2. **`resolve_chain(..., declared=)` 增加能力校验**（求值顺序 ④→⑤）：
   登记了声明的 provider 必须声明该能力才可入选。未登记时保持旧语义（渐进迁移）。
3. **链表与声明双向对齐**：逐源核对真实方法集后修正 10 处链成员；删除 `dividend`
   能力（无人实现）；新增 `minutes` / `etf_list` / `search` 三个能力 id，
   使「补充源专有方法」不再借道 kline 链。

   **只读 property**（返回真实生效链，`/market/sources` 展示随之对齐）；
   `set_auto_chain()` 降级为显式逃生口（`_auto_chain_override`，默认 None）。

6. **静态 `PROVIDER_CATALOG` 与实现对齐**（6 个描述符），消除「两套口径」。
7. **外部调用点跟进**：`source_policy.resolve_policy()` 增加 `declared` 透传；

#### 8.13.2 P1-4 真根因：**两类**进程级全局态泄漏（不是一个）

P1-4 原记录是「后端测试须逐文件跑」。R6 已实测更正为「**同进程全量 5 条顺序依赖假失败**」，
但根因未定位。R7 定位到**两类**独立泄漏，**缺一不可**：

#### 根因一：`set_active_context` 写全局却从不恢复

`core.context._ACTIVE` 是模块级全局；`active_context()` 在未注入时**新建空 `AppContext()`**。
多个用例在 teardown 里写 `set_active_context(AppContext())` / `set_active_context(None)`
—— 那是「换成空实例 / 置空」，**不是恢复**。而 `app_client` 是 `scope="session"`，
lifespan **只在首次使用时跑一次** → 此后所有用它的文件槽位全为 None。

**确定性复现（修复前）**：

```
appcontext_injection → paper        → ws_contract        = 3 failed
appcontext_injection → e2e_flows    → risk_regression    = 1 failed
```

（顺序关键：`app_client` 首次使用时才创建，故必须是「先用 app_client 的文件 →
改全局的污染者 → 再用 app_client 的文件」。）

**修法（单点结构修复，不逐个打补丁）**：

| 文件 | 改动 |
|------|------|
| `backend/core/context.py` | 新增 `active_context_or_none()`（区分「未注入」与「注入了空实例」，是保存/恢复的前提）；新增 `use_context(ctx)` 上下文管理器（`try/finally` **精确恢复**，含恢复为「未注入」）；`set_active_context` 签名放宽为 `AppContext \| None` 并补「裸调用会覆盖进程全局」的警告 |
| `backend/tests/conftest.py` | 新增 `autouse` 夹具 `_restore_active_context`：每用例前后精确恢复 |

#### 根因二：`core.state.state` 单例被 lifespan 就地改写且从不还原

`core.state.state` 是**模块级单例**（`AppState` 继承 `AppContext`，48 个槽位）。
`app_client` 的 lifespan 会**就地**写入 `broker_manager` / `db` / `risk` 等，
**且从不还原**。其中 `broker_manager` 是**真实 `BrokerManager` 且首个连接
`connected=True`** → 此后任何用例的 `BarsProvider._qmt_connected()` 都返回 `True`
→ `resolve_policy` 不再剔除 `broker`、`degraded` 恒为 `False` —— 与「无 QMT 时降级」
类断言的**自身前提**直接冲突。

**确定性复现（修复前，最小对）**：

```bash
pytest tests/test_appcontext_injection.py tests/test_screen_without_qmt.py -q
# → 1 failed（test_env2_commercial_no_eltdx_falls_to_baostock）
#   实测 report: fallback_tried=['broker:empty','eltdx:empty'], degraded=False
#   —— broker 没被剔除 ⇒ qmt_connected 被污染成 True
# 单独跑该文件 → 5 passed
```

**修法（同样单点）**：`backend/tests/conftest.py` 新增

- `pytest_configure`：在任何 fixture / 用例之前采集**干净基线**（必须在 lifespan 跑之前取，
  否则基线本身就是脏的）；
- `autouse` 夹具 `_restore_process_state`：用例**不用** `app_client` → 恢复到会话前干净基线；
  用例**用** `app_client` → 恢复到 lifespan 生效后的快照（由 `app_client` 夹具采集）。
  这样「用例的初始全局状态」只由它自己是否使用 `app_client` 决定，**与执行顺序无关**。

> **为什么不把 `app_client` 改成函数作用域**：lifespan 单次约 **9–12s**（6 阶段 bootstrap），
> 而使用它的用例有 **37 个** → 逐例重启将让全量从 ~90s 涨到 5 分钟以上。
> 故保留 session 作用域，改由「按需恢复到对应基线」解决隔离。

|---|---|---|
| 全量同进程 | `5 failed, 890 passed, 10 skipped` | **`910 passed, 10 skipped`（0 failed）** |

即「同进程全量」从**只能当差分兜底**升级为**可直接当验收命令**。

#### 8.13.9 **未纳入本轮**：时间戳格式统一（已定位，留作独立轮次）

审计 C 段还发现**时间戳格式有 ≥6 种变体**，且全部在产线可达：

| 写法 | 输出 | 时区 | 处数 |
|------|------|------|------|
| `datetime.now(timezone.utc).astimezone().isoformat(timespec="seconds")` | `2026-09-15T22:38:59+08:00` | 带偏移 ✅ | 5+ |
| `datetime.now().isoformat(timespec="seconds")` | `2026-09-15T22:38:59` | **裸值** ❌ | 2 |
| `time.strftime("%Y-%m-%dT%H:%M:%S")` | `2026-09-15T22:38:59` | **裸值** ❌ | ~30 |
| `time.strftime("%Y-%m-%dT%H:%M:%S%z")` | `2026-09-15T22:38:59+0800` | 非严格 ISO | 1 |
| `strftime("%Y-%m-%d %H:%M:%S")` | `2026-09-15 22:38:59` | **裸值 + 无 T** ❌ | 2 |

**为何本轮不做（已动手后主动回退）**：本轮曾完成 ~14 处迁移，但在做「消费者审计」时
发现**隐藏耦合**：

```python
# backend/engines/condition_order.py:290
if datetime.now() < datetime.fromisoformat(o["next_retry_at"]):
```

`next_retry_at` 若改成**带偏移**，与裸 `datetime.now()` 比较会直接抛
`TypeError: can't compare offset-naive and offset-aware datetimes` ——
即**这条路径会从「静默正确」变成「运行时崩溃」**。同类 `fromisoformat` 消费点共 7 处
（`condition_order`×3、`alert_engine`、`apikey`×2、`schedules`），需**逐字段**判定
「谁写、谁读、怎么比」，属于**独立重构**，不该塞进以修 bug 为主的 R7。
故本轮把该改动**整体回退**（`git checkout`，零残留），仅在此登记。

**影响评估**：所有变体编码的是**同一瞬间**（都是本地时区），前端 `shared/time.ts`
对两种形状都做了容错，SQLite 里 `ORDER BY` / 前缀比较仍单调 —— 故属**一致性债务**，
非功能缺陷。R8 若做，正确顺序是：先建 `core/clock.py`（`now_iso` / `to_iso`）→
再补一个「裸值按本机时区补齐」的解析助手 → 逐个消费点改造 → 用同一 `now_iso`
生成比较基准（保证两侧同口径）。

> **→ 已由 R8 落地（2026-09-16），见 §8.14。** 上面这份「正确顺序」被完整执行；
> 并且在做消费者审计时挖出了一处**真缺陷**（条件单永不到期），
> 证明 §8.13.9 当时把整件事判成「纯一致性债务」是**低估**了。

| 形态 | 产出 | 处数 | 定性 |
|------|------|------|------|

#### 8.14.2 canonical 形状怎么定的：既有约定，不是「哪个好看」

先问「canonical 取哪种形状」，而不是挑「最规范」的。三条硬证据一致指向
**「裸值 ISO 本地时间、秒精度、无偏移」**：

1. `core/db_migrations.py:624` 的列注释写着「ISO 本地时间」；
2. `schedules.timezone` 固定 `Asia/Shanghai`，`gateway/market_sync.py` 另有显式的
   「交易所时区时钟」`_sh_now()` —— 说明项目对「用哪个时钟」与「怎么格式化」是**分开**处理的；
3. 前端 `frontend-next/src/shared/time.ts` 明确禁止 `new Date("2026-08-17")`
   （ECMAScript 对纯日期串按 **UTC** 解析，会差一天）。

选它的**改动面小一个数量级**：只需改 **8 处**带偏移的偏离者，而不是把 **41 处**符合约定的
裸值生产者全改成 aware。

#### 8.14.3 唯一实现：`backend/core/clock.py`（新建，141 行）

| 导出 | 契约 |
|------|------|
| `FORMAT` | `"%Y-%m-%dT%H:%M:%S"` |
| `local_now() -> datetime` | **naive** 本地时间（与 `now_iso` 同口径） |
| `now_iso() -> str` | `2026-09-16T18:57:49`（无偏移、无微秒） |
| `today_str() -> str` | `2026-09-16` |
| `to_iso(dt) -> str` | aware 入参**先换算本地**再格式化；`None` → `""` |
| `parse_iso(s) -> datetime \| None` | 宽容解析 **6 种历史形状**，坏值 → `None`（**不抛、不兜底为「现在」**） |

`parse_iso` 的兜底是**返回 None 而不是 now()**：兜底为「现在」会让「过期判断」静默反转。

**与「交易所时区时钟」的区别（不要误统一）**：`gateway/market_sync.py::_sh_now()` 用
`ZoneInfo("Asia/Shanghai")` 解决的是**另一个问题**（EOD 触发该锚定哪个时区），
它的 tzdata 缺失回退分支**保留 `datetime.now()`**，不并入 `core/clock`。

#### 8.14.4 ★ 真缺陷：条件单**永不到期**（实测定证 + 因果验证）

`engines/condition_order.py::_is_expired` 旧实现：

```python
return datetime.now() > datetime.fromisoformat(expire_at)      # 旧
```

`expire_at` 一旦**带偏移**（`+08:00` / `+0800`），比较即抛
`TypeError: can't compare offset-naive and offset-aware datetimes`，
而调用方有 `except` 把它吞掉 → **恒返回「未过期」** → 条件单**永不到期、永不通知、永不清算**。

**实测定证**（脚本回退旧实现 → 跑回归用例 → 恢复）：

```
>>> 旧实现：1 failed
    AssertionError: '2020-01-01T23:59:59+08:00' 应判为已过期
    assert False is True  where False = _is_expired('2020-01-01T23:59:59+08:00')
>>> 新实现：1 passed
```

这正是 §8.13.3 那类「静默降级伪装成正常」。**判定「真缺陷 vs 一致性债务」的问法是**：
「这个形状冲突对**所有可能输入**都可接受吗？」带偏移的 `expire_at` 在存量库里确实存在
（V9 早期写的就是 aware），所以不可接受 ⇒ 真缺陷。

新实现：

```python
ts = parse_iso(expire_at)
if ts is None:
    return False
return local_now() > ts          # 两侧同口径（都 naive 本地）
```

#### 8.14.5 「同列两种形状」的三处现场缺陷

同一张表的同一语义列，由**两种形状**的代码写入 —— 这类问题不靠 grep 而靠**列级对账**发现：

| 位置 | 列 | 旧状 |
|------|----|------|
| `app/runtime/schedules.py` | `created_at` vs `updated_at` | `created_at` 走 SQLite `DEFAULT datetime('now','localtime')`（**空格形**），`updated_at` 走代码（**T 形**） |
| `app/runtime/jobs.py` | `created_at` | `:332` 用 `%z`（`+0800`）、`:503` 用裸值 —— **两处都写 `created_at`** |
| `gateway/apikey.py` | `expires_at` vs `last_used_at` | `expires_at` 用 `%z`、`last_used_at` 用裸值 |

`schedules.create()` 改为**显式写** `created_at`/`updated_at`（让 SQLite DEFAULT 永不生效）——
**不改表结构、零迁移风险**（`upsert` 按给定列 INSERT 即可）。

#### 8.14.6 消费点审计：为什么这次是**零行为变化**

§8.13.9 当初回退，就是因为没做这一步。R8 把 7 处 `fromisoformat` 消费点逐个判定
「谁写、谁读、怎么比」，结论是**零行为变化**：

| 消费者 | 旧写法 | 新写法 | 为什么等价 |
|--------|--------|--------|------------|
| `condition_order._is_expired` | `now() > fromisoformat(x)` | `local_now() > parse_iso(x)` | 裸值两侧同为本地 naive |
| `condition_order._end_of_day` | `fromisoformat(dt)` | `parse_iso(dt)` | 宽容解析是**超集** |
| `condition_order` 的 `next_retry_at` | `now() < fromisoformat(nra)` | `local_now() < parse_iso(nra)` | 同上 |
| `alert_engine._cooldown_ok` | `time.time() - fromisoformat(last).timestamp()` | `time.time() - parse_iso(last).timestamp()` | `timestamp()` 对「裸值本地」与「`+08:00`」得**同一数值** |
| `apikey._is_expired` ×2 | `datetime.datetime.fromisoformat(exp).timestamp()` | `parse_iso(exp).timestamp()` | 同上；**保持 fail-closed**（坏值 → 已过期） |
| `schedules._fire` | `fromisoformat(last_s)` | `parse_iso(last_s)` | 解析失败仍走「重算相位」分支 |

其余消费者一并核过：前端 `shared/time.ts` 的 `SEPARATED` 正则只取到秒、**忽略尾部偏移**；
SQLite 的 `ORDER BY ts` / `WHERE ts LIKE '…%'` 是**前缀比较**，形状不变即单调性不变。
⇒ 全部 62 处改动里，**只有 `_is_expired` 一处是行为修复**，其余是形状归一。

#### 8.14.9 ★ 顺带修好的 flaky：**进程级 monkeypatch 截走了后台循环**

```

E    At index 0 diff: 0.1 != 0.5
E    Left contains 276 more items, first extra item: 0.1
```

根因（探针抓调用栈确证）：`monkeypatch.setattr("gateway.webhook_out.asyncio.sleep", …)`
里的 `gateway.webhook_out.asyncio` **就是全局 asyncio 模块** ⇒ **进程级打桩**。

lifespan 跑在 **anyio 后台 portal 线程**、**全程存活**；它启动的后台循环里
`sync/__init__.py::_batch_loop` 有 **100ms 行情微批窗口**，被打桩后 `sleep(0)` 不再真正等待

**因果验证**：修好后 `30 passed`；把旧写法放回探针文件 → 护栏判红并精确指出
`tests/_guard_probe_tmp.py:55: gateway.webhook_out.asyncio.sleep`（探针已删）。

#### 8.14.10 ★ 客户端测试假阴性：被遮挡 → Chromium 不出帧（含一次**误诊更正**）

现象：`scripts/client_start_test.py --target dev` 从基线 `29/29` 掉到 **28/29**，
失败项 `[window] 窗口已实际渲染（非纯色空窗）`，**采样 18 色 / PNG 恒为 8450 bytes**
（多次连跑字节数完全一致）。

**⚠️ 先记一次误诊。** 本节最初把根因写成「`_win32()` 没声明 `SetWindowPos` 的
`argtypes`」，并按此「修好」、报了 `29/29`。下一轮复核时**同一失败复现**，
说明那次修法不成立 —— 当时的 `29/29` 只是桌面恰好没有窗口盖住它。
代价是多花一整轮。教训：**「改完绿了」不等于「根因找到了」**，
必须能把失败**稳定复现**再验证修法（见下方 A/B）。

排查链条（每步都用证据否掉一个假设）：

| 假设 | 证伪方式 | 结论 |
|------|----------|------|
| 截图抢跑（首帧没画完） | 固定 `sleep(0.8)` → **轮询 12.4s** | ❌ 仍 18 色 |
| 前端渲染失败 | `dev.log`：chunk 全 200、`window loaded`、WS 已连 | ❌ 页面没问题 |
| PrintWindow 取不到合成层 | 全屏抓图 + 按窗口矩形裁切 → 颜色数很高 | ✅ 内容在屏幕上 |
| 关掉 Windows「原生遮挡检测」即可 | 加 `--disable-features=CalculateNativeWinOcclusion` | ❌ 遮挡下仍恒 18 色 |
| 外部进程置顶即可 | `SetWindowPos(hwnd, HWND_TOPMOST, …)` | ❌ 返回 **1（成功）**，但 `WS_EX_TOPMOST` 仍 False、`WindowFromPoint` 仍返回遮挡者 |

**真根因**：Windows 的原生窗口遮挡检测判定客户端窗口被**完全遮挡**后，
Chromium 停止出帧、不再维护合成层；`PrintWindow(PW_RENDERFULLCONTENT)`
只能拿到**未合成的空白客户区**（客户区确实一个像素都没画 → PNG 高度可压、
字节数每次完全一致）。所以它是「同一份代码时红时绿」——
取决于运行时桌面上有没有窗口盖住客户端窗口。

**★ 决定性证据（自造遮挡窗口做 A/B）**：用 `CreateWindowExW` 造一个
**置顶且不透明**的窗口精确盖住客户端窗口，把失败**稳定复现**，再对比两种修法：

| 条件 | `topmost` | 采样颜色数 | 结果 |
|------|-----------|-----------|------|
| 遮挡 + 仅外部 `SetWindowPos(TOPMOST)` | `False` | `18`（连续 8 次） | **FAIL** |
| 遮挡 + **窗口所有者自己置顶** | `True` | `67` | **PASS 29/29** |

**修法**：让**窗口所有者**置顶 —— `frontend-next/electron/main.cjs` 的
`createWindow()` 里加一行 `if (TEST_MODE) win.setAlwaysOnTop(true);`。
生产环境不设 `QMT_CLIENT_TEST_MODE` ⇒ `TEST_MODE` 为假，**零影响**；
与既有 `window-ready.txt`、`--user-data-dir` 等测试钩子同一套路。

顺带修掉一个**真 bug**（不是本次失败的原因，但确实是错的）：`_win32()` /
`capture_screen._dlls()` 都写成「先 `ctypes.WinDLL(...)` 建新对象、再判模块级标志提前
return」。ctypes **每次调用都返回新的 CDLL 对象**、`argtypes` **不共享**
（实测 `a is b == False`、`b.SetWindowPos.argtypes is None`），于是「声明一次」只在
**第一次**调用生效，之后全部退化成「未声明签名」（64 位句柄会被截断、
`HWND_TOPMOST=-1` 会按 C `int` 传成 `0xFFFFFFFF`）。已改为**缓存并复用同一个 CDLL**，
并加护栏 `backend/tests/test_win32_binding.py`（2 条，做过「回退判红 → 还原复绿」因果验证）。

**结果**：`29/29` **连跑三次**（18.4s / 18.5s / 18.3s），采样恒 **68 色 / 39161 bytes**、
等待仅 1.0s。截图为真实界面（顶栏 `行情/研究/交易/账户/自动化/系统` + 连接管理页
「新增连接」表单 + `已有连接 (0)` + 状态栏「行情通道 已连接 · 订阅 4」「非交易时段」）。

#### 8.15.1 自选股「重影」= 同一个代码被渲染两遍（不是渲染问题）

截图放大后确认：每一行出现**两遍**（深色大字号 + 浅色小字号、纵向错位），
4 个代码看起来像 8 行。

**根因**：`frontend-next/src/shell/DataPanel.tsx` 的行结构是「名称槽 + 代码槽」两行，
名称槽写的是 `{q?.name ?? code}`。盘前无行情时 `q.name` 为空 → 名称槽回退成 code，
代码槽又是 `{code}` → **同一个代码渲染两次**；`.row` 高度固定 `26px`，
两行挤在一起重叠 → 视觉上就是「重影」。
`domains/market/MarketData.tsx` 头部有同款写法（并排重复）。

**修法**：新增 `shared/format.ts::namePair(name, code)`，**成对返回**
`[主标题, 副标题 | null]` —— 名称未知时主标题回退为代码、副标题为 `null`，
调用方跳过代码槽。把成对关系收进一个函数，让「只改一半」在结构上不可能。

**护栏**：`frontend-next/tests/format.test.ts` 新增 5 条，含一条**不变量**
——「副标题永远不等于主标题」（重影的充要条件）。

#### 8.15.3 ★ 隐藏性能坑：`discover()` 要 19.5 秒（cProfile 定位，非直觉）

自动探测接到页面后，用户要转 17 秒圈。`cProfile` 结果：

| 项 | 耗时 |
|----|------|
| `_scan_installed()` | **19.30s / 共 19.48s** |
| `nt.stat` 调用 **176,452 次** | **13.81s** ← 真凶 |
| `nt.listdir` 调用 24,669 次 | 2.20s |

根因：全盘 3 层扫描用 `os.listdir` + 逐个 `os.path.isdir`；
Windows 上 `os.path.isdir` 会对**每个路径单独 `stat`**。

**基准（同一份 22,447 个目录的 3 层扫描，先量再改）**：

| 写法 | 耗时 |
|------|------|
| `os.listdir` + `os.path.isdir` | **12.33s** |
| `os.scandir` + `entry.is_dir()` | **0.24s** |

**修法**（`backend/xtquant_client/discovery.py`）：
1. 全程 `os.scandir`，用 `ScandirEntry.is_dir()`（复用目录枚举已拿到的属性，不额外 stat）；
2. 新增 `_scan_children()`：**一次枚举同时返回「子项名 + 子目录路径」**，
   `_looks_like_client_root(d, entries)` 复用已枚举结果，省掉每个目录的第二次 listdir；
3. `_CLIENT_MARKER_SET = frozenset(_CLIENT_MARKERS)` 做 O(1) 查找；
   未提供 entries 时**边枚举边判定、命中即返回**；
4. `_add_root` 先查重再判定（原先对已收录的也白读一次目录）。

**结果：19.48s → 2.66s（7.3×）**，候选结果一个不少。
剩余约 1.5s 是「检查每个三级目录是否含标记」必须付出的枚举成本，属合理下限。

**护栏**：`test_looks_like_client_root_entries_argument_is_equivalent`
（锁死「传入 entries 与自行枚举结果必须一致」—— 两条路径分叉会**静默漏掉客户端**）、
`test_client_marker_set_matches_tuple`（防 `frozenset` 与元组漂移）。

⚠️ `discovery.py` 是 **`i/mixed` 行尾**（542 CRLF + 10 LF），
本轮改动走**字节级替换**（新代码写独立文件 → `replace('\n','\r\n')` →
`bytes.index()` 定位 → `b[:i] + new + b[j:]`），改后核对 CRLF/LF-only 计数
（542/10 → 543/10，与 +1 行一致）与 `git diff -U0` 的落点区间。

#### 8.15.4 测试工具改进：`--settle`（等待首帧之后的异步内容）
