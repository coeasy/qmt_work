## 2. 缺陷 A：打包态版本号恒为 `0.1.0`

### 2.1 怎么发现的

截图 `06-sysstatus.png` 时，界面「系统健康」显示 `v0.1.0` —— 而仓库根 `VERSION` 明明是 `0.2.0`。

### 2.2 证据链与根因

```
$ find .../resources/backend -name VERSION     # 空
$ grep _FALLBACK backend/app/version.py        # _FALLBACK = "0.1.0"
```

`backend/app/version.py` 是版本号的读取口，按两条候选路径找仓库根 `VERSION`：

```python
for base in (Path(__file__).resolve().parents[2],   # 仓库根（源码运行）
             Path(__file__).resolve().parents[1]):  # backend / _internal（打包形态）
    ...
return _FALLBACK   # ← 找不到就**静默回退** "0.1.0"
```

而 `backend/build_exe.py` 的 `DATAS` **从来没有包含过 `VERSION`** ⇒ 打包产物里没有该文件 ⇒ 两条路径都落空 ⇒ 版本恒为内置的 `0.1.0`。

### 2.3 危害（比「显示错一个数字」严重得多）

打包态下**所有**版本出口都是错的：

- 界面「系统 → 系统状态 / 系统健康」显示 `v0.1.0`；
- `GET /health`、`GET /ready`；
- FastAPI OpenAPI 的 `info.version`；
- release-manifest。

最要命的是**自动更新**：`electron-updater` 判断「有没有新版本」靠的就是版本比对 —— 一个恒为 `0.1.0` 的客户端，其更新判断从根上失去依据（永远认为自己比 Release 旧，或者反之）。用户也无法从界面确认自己装的是哪一版。

### 2.4 修法

1. `DATAS` 加入 `VERSION`，落点选 `.`（即 `_internal/`，正好命中 `parents[1]` 那条候选路径）：
   ```python
   _version_file = ROOT.parent / "VERSION"
   if _version_file.is_file():
       DATAS.append(f"{_version_file};.")
   ```
2. 构建期 **fail-fast 校验**（关键：让「没随包」变成红灯，而不是静默回退）：包内 `VERSION` 必须存在，且内容与源文件逐字一致，否则 `SystemExit`。

### 2.5 可证伪性

- 构建日志必须出现 `[version] 版本号随包核对通过：0.3.0`；
- 重新截图后，「系统状态」页显示的版本必须是 `0.3.0`（端到端证明，而不是只看构建日志）。

## 3. 缺陷 B：`build_all.sh --backend-only` 分支写反

### 3.1 症状

```
$ bash build_all.sh --force --backend-only
...
[build] 前端构建完成 → backend/static/
[build] 仅构建后端 EXE 完成          ← 打印了「完成」
```

但 `backend/dist/qmt_work/qmt_work.exe` 的时间戳**仍是上一轮的 09:26** —— PyInstaller 根本没跑。

### 3.2 根因

```bash
if [[ "$DESKTOP_ONLY" == false ]]; then
    if [[ "$BACKEND_ONLY" == false ]]; then     # ← 多包了这一层
        log "Step 2/3: 后端 EXE 打包（PyInstaller）"
        ...PyInstaller...
    fi
    if [[ "$BACKEND_ONLY" == true ]]; then
        log "仅构建后端 EXE 完成"                # ← 于是 --backend-only 直接在这里 exit 0
        exit 0
    fi
fi
```

契约（脚本头部文档）写的是「`--backend-only` 仅后端 EXE」，实现却是**跳过**后端 EXE 打包。

### 3.3 判据（供下次一眼识别）

`--backend-only` 的日志里**没有** `Step 2/3` 这一行，也没有 `build_exe.py` 的任何输出。有「完成」二字 ≠ 真的构建了。

### 3.4 危害

**静默复用旧产物**：`backend/dist/qmt_work/qmt_work.exe` 不变，而脚本退出码 0、日志有「完成」。本轮若不是顺手对比了时间戳，就会拿**上一轮的后端**去打出「新版本」的安装包。

### 3.5 修法

去掉那层条件 —— 只要不是 `--desktop-only`，Step 2 就必须执行；`--backend-only` 只决定「做完 Step 2 就停下，不进 Step 3（Electron）」。头部文档同步改为「Step 1 前端 + Step 2 PyInstaller，跳过 Electron」。

## 4. 缺陷 C：截图脚本收尾留下孤儿进程

### 4.1 症状

第二次运行 `build_all.sh` 时被直接拒绝：

```
[error] 后端 EXE 实例 正在运行（qmt_work.exe）。请先完全退出（托盘右键→退出，或任务管理器结束 qmt_work.exe），或用 --force 跳过
```

### 4.2 查证（不能按镜像名杀）

用 ctypes 探针（`output/_r22_probe_procs.py`）查证，得到：

```
qmt_work.exe 进程数 = 4
  pid=10108  ppid=14032  created=2026-09-22 02:33:58  age=30116s
      exe=P:\github_public\qmt_work\frontend-next\dist-electron\win-unpacked\qmt_work.exe
  ...（4 个全部同一镜像、同一秒启动、**无任何监听端口**）
```

4 个进程全部来自**上一轮构建的产物目录**、同一秒启动（典型的 Electron 进程树），且**没有任何 TCP 监听**（说明后端子进程已经死了，只剩一个空壳）。它们把 `win-unpacked/` 锁住 ⇒ `electron-builder` 无法重写该目录。

### 4.3 根因

`capture.mjs` 的 `finally` 里只有：

```js
try { process.kill(child.pid); } catch {}
```

`child.pid` 是 **Electron 主进程**。主进程被 `TerminateProcess` 后，它拉起的渲染 / GPU / utility 子进程，以及那个由 PyInstaller 打包出来的后端子进程（**也叫 `qmt_work.exe`**）全部变成孤儿继续活着。

### 4.4 修法

新增 `output/_r22_probe_procs.py`（ctypes 实现；本机 `taskkill` 被拒、`wmic` 被安全策略硬阻止），提供：

- `--tree <pid>`：按 `CreateToolhelp32Snapshot` 的父子关系收集**整棵子树**，先叶子后根终止，最后复核「0 个残留」；
- 终止护栏：**镜像必须位于 `dist-electron/win-unpacked/` 内**，否则拒绝 —— 绝不按镜像名杀（本项目踩过「把用户正开着的客户端静默杀掉」）。

`capture.mjs` 收尾改为调用它，并打印「进程树已清空 / 仍有残留」。

> 附带修掉一个探针自身的误判：`OpenProcess` 失败时原来一律当作「越权镜像」拒绝，而 `err=87`（进程已不存在）应当与「打不开」区分开 —— 否则「进程刚退出」会被误报成「越权」，护栏看起来在拦人，其实在说谎。

### 5.5 自动更新链路的闭环校验（缺陷 A 的真正后果）

缺陷 A 的要害是**自动更新**，所以不能只验「界面显示对了」。`electron-updater` 实际读的是
`latest.yml`，它必须同时满足下面几条，否则客户端会静默拒绝更新：

| 校验项 | 实测值 |
|---|---|
| `latest.yml` 的 `version` | `0.3.0` |
| `latest.yml` 的 `url` / `path` | `qmt_work-Setup-0.3.0.exe` |
| `latest.yml` 的 `size` | `236148822`（与磁盘文件一致） |
| `latest.yml` 的 `sha512` vs 安装包**真实摘要** | **一致**（逐块 sha512 后 base64 比对） |
| **安装后实际运行的那份** `VERSION` | `win-unpacked/resources/backend/qmt_work/_internal/VERSION` = `0.3.0` |

> 为什么要单列这一节：`sha512` 对不上时，更新会被**静默拒绝**，在客户端只表现为
> 「点检查更新没反应」，几乎无法归因；而 `latest.yml` 是 electron-builder 生成的、
> 要随安装包一起传到 Release 的**另一个文件**（很容易漏传）。所以发布前必须用真实文件复核一次。
