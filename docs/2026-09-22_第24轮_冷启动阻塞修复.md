# 第 24 轮：冷启动阻塞修复（optional 相位「慢」也会阻断启动）

- **日期**：2026-09-22（会话日）
- **起点 HEAD**：`3646216`（v0.3.2 已发布）
- **改动文件**：`backend/app/bootstrap/phase_broker.py`（核心）·
  `backend/tests/test_broker_path_guard.py` · `scripts/ci_reconcile.py` · `README.md`
- **一句话**：「optional 相位」只保证**失败**不阻断 READY，**不保证「慢」不阻断** ——
  客户端已安装但没启动时，一条持久连接就把整个 HTTP 服务堵了 **32s**。本轮把
  「等连接」改成「给总预算 + 并发 + 交后台」，实测 **32.01s → 8.00s**。

---

## §1 起因

第 23 轮做全页面审计时，我曾把「首个行情请求要等 8 秒」归因到「券商连接在首个
请求时才建立」。那次归因**已被自己撤回**（见 `2026-09-22_第23轮` §14 末）：因为
`phase_broker.start_persisted_connections` 在启动期就是 `await` 的，8 秒应该付在
**启动期**而不是首个请求上。

本轮改为**先把事实时间线摆出来，再谈归因**。

## §2 事实时间线（全部来自实测日志，非推断）

来源：`output/client_test/client.log`（`scripts/client_start_test.py --target client`
在 2026-09-23 08:37 那次启动留下的）。

```
08:37:35,273  WARNING  registry 未知券商 'generic'（按通用适配器处理）
08:38:05,303  ERROR    bridge 握手失败: _ping 调用超时 30.0s
08:38:07,284  INFO     bootstrap phase broker (optional) done in 32011ms
08:38:08,168  INFO     Application startup complete
```

三条关键事实：

1. **32s 付在启动期**（`bootstrap phase broker` 相位本身），不是首个请求；
2. 该相位在 `lifecycle.PHASE_LEVELS` 里被标注为 **optional**；
3. `Application startup complete` 出现在 32s **之后** —— uvicorn 是 lifespan
   启动返回后才开始收请求，**这 32s 里整个 HTTP 服务一个字都不回**。

第 3 条正是用户感知：「双击图标 → 窗口白着不动 → 以为打不开」。

### 现场取证（为什么这条连接会烧满 30s）

```
broker_connections: conn_id='2d6d2194aee3'  name='集中交易001（自动连接）'
                    broker_id='generic'  client_path='P:\stock\gd_qmt\userdata_mini'

```

`client_path` **目录存在**（客户端确实装了），于是 `path_usable()` 放行 ⇒ 真的去
`bridge.start()`；而 QMT 客户端进程当时没在跑（或没登录）⇒ `_ping` 在
`bridge_client._HANDSHAKE_TIMEOUT = 30.0` 上超时。

**这正是用户最常见的情形**：客户端装了、平时不常开；或者「先开我们的软件、后开
券商客户端」。此时每一条 `active` 连接都要陪跑满 30s。

## §3 根因：optional ≠ 非阻塞

`app/bootstrap/lifecycle.py`：

```python
for name, fn in phases:
    level = PHASE_LEVELS.get(name, "optional")
    results[name] = await fn(app)          # ← 顺序 await
```

`PHASE_LEVELS["broker"] = "optional"` 的语义是「**失败** → 记 error 状态并继续
（Degraded）」，注释也写着「QMT 失败不失去 READY」。

**但「失败不阻断」不等于「慢不阻断」**：`await fn(app)` 是顺序的，相位内部只要
不返回，后面的相位（engines / watchdogs / replay / misc）一个都轮不上，lifespan
不返回，uvicorn 不收请求。

> ★★ 判据（可复用到任何「optional 相位」）：问「这个相位最坏情况要花多久」，
> 而不是只问「它失败了会怎样」。**optional 只覆盖了错误路径，没有覆盖延迟路径。**

## §4 修法：启动预算 + 并发 + 交后台 + 出路闭环

全部落在 `backend/app/bootstrap/phase_broker.py`，四件事：

### 4.1 总预算（不是每条预算）

```python
STARTUP_CONNECT_BUDGET = 8.0     # 启动期给「持久连接」的总预算
CONNECT_HARD_TIMEOUT = 32.0      # 单条硬上限（后台继续跑时仍生效）
```

取值依据来自 `bridge_client` 的设计注释：客户端**已登录**时 `_ping` 5s 内返回；
**未登录**时 SDK 要 10~30s 才阻塞/异常。**8s 因此能干净切开「能连上」与「连不上」
两类** —— 既不误杀慢机器冷启动，也不再陪跑满 30s。

### 4.2 并发拉起（否则耗时随 N 线性增长）

```python
tasks = {asyncio.ensure_future(_start_one(c)): c for c in eligible}
done, pending = await asyncio.wait(set(tasks), timeout=budget)
```

N 条连接**共享同一份预算**。「17 条残留连接把启动拖到 ~90s」那种线性放大从此
在结构上不可能（叠加既有的 `path_usable` 早跳）。

### 4.3 交后台而不是取消

```python
def _hand_off_to_background(task, conn) -> None:
    _bg_start_tasks.add(task)          # ★ 强引用：asyncio 只持弱引用，否则会被 GC
    task.add_done_callback(_on_done)
```

**为什么是「交接」而不是「取消」**：`bridge.start()` 的真实工作在
`loop.run_in_executor(...)` 的**线程**里跑，取消协程**停不掉那个线程**，只会把
状态停在半路（`XTQuantBridge._started` 不会被置位、`_proc` 可能悬着）。让它自然
跑完（内部仍有 32s 硬上限）反而是**确定**的行为，与改动前完全一致。

### 4.4 出路闭环（每个非正常态都要给出路）

后台那条**真的连上**时，必须把进程级活跃指针补上，并重刷交易日历：

```python
if outcome == "started":
    _sync_active_bridge()                                   # state.bridge / state.gateway
    asyncio.get_running_loop().create_task(_refresh_trading_calendar())
```

否则「先开软件、后开客户端」会变成「连上了但 `state.bridge` 永远是 None」。

> 注：`_sync_active_bridge()` 也被 `setup()` 与 `_auto_connect_active` 分支复用，
> 三处赋值收敛成一个函数。

## §5 归因分离：慢 ≠ 失败

返回值由 3 类扩到 **4 类**，四类互不混淆：

| 键 | 语义 | 用户该做什么 |
|---|---|---|
| `started` | 预算内连上 | 无 |
| `failed` | 预算内**确定失败**（超时/异常），已写 `last_error` | 查 `last_error` |
| `skipped` | 客户端路径不存在 ⇒ 直接跳过 | 去「连接管理」修正/删除 |
| `deferred` | 预算内还没跑完 —— **不是失败**，已交后台自愈 | **什么都不用做** |

`deferred` 的 `last_error` 刻意写成出路而不是判决：

```
启动期 8s 内未连上（券商客户端可能未启动或未登录），已转入后台自动重连
```

> ★★ 若把「慢」记成「失败」，用户会跑去改配置/重装客户端 —— 而其实后台
> （`BrokerHealthMonitor._reconnect` 指数退避 + `phase_watchdogs` 的 30s 守卫）
> 会自动连上。**这是本项目的第 ①/⑤ 条铁律在启动期的具体化。**

## §6 实测（探针 A/B/C）

`output/_r24_coldstart_probe.py` —— 用**真实** `setup()` 代码路径，只桩掉券商传输层
（`bridge.start()` 慢/不返回）。安全护栏：`QMT_BROKER_AUTO_CONNECT=false` 关掉自动
探测，`broker_manager` 整个换成桩（`load_persisted` 一旦被调用即报错）⇒
**不读真库、不连真账户**。

```
[改动前] budget= 32.0s  delay=3600.0s  实测耗时= 32.01s  stats={'started':0,'failed':0,'skipped':0,'deferred':1}
[改动后] budget=  8.0s  delay=  10.0s  实测耗时=  8.00s  stats={'started':0,'failed':0,'skipped':0,'deferred':1}
------------------------------------------------------------------------------
启动阻塞：32.01s -> 8.00s（省 24.01s）
------------------------------------------------------------------------------
后台在跑的任务数 = 1
后台补连完成后 state.bridge = <_SlowBridge object at ...>
  补连完成时刻（相对本段开始）= 2.11s；connected=True
==============================================================================
PROBE RESULT: PASS
```

三条断言全部成立：

- **A** `budget=32.0` 复现改动前的等待时长（单连接时与旧实现等价）→ 32.01s；
- **B** 新默认 `budget=8.0` → 8.00s 返回，且 `deferred=1 / failed=0`（归因正确）；
- **C** 交后台那条在 8+2=10s 跑完，`state.bridge` 被**回调**补上（不是手工调用），
  即「出路闭环」真的通。

> 探针口径诚实说明：A 用的是**新代码 + 旧预算值**，不是旧代码本身。对「等待时长」
> 这个被测量而言两者等价（单连接、顺序/并发无差别）；旧代码的形状差异（少一个
> `deferred` 键、顺序 await）由 §7 的两轮变异单独证明。

## §9 顺带核实的两件事（结论，不是猜测）

### 9.1 `state.bridge` / `state.gateway` 是**只写**状态

全仓扫描（排除 `dist/`）：

```
backend/app/bootstrap/phase_watchdogs.py:91,92   ← 写
backend/app/bootstrap/phase_broker.py:175,176    ← 写
backend/app/bootstrap/phase_broker.py:198,199    ← 写

backend/tests/test_e2e_flows.py:349              ← 测试夹具写假 app
```

**除本模块的交易日历刷新外，没有任何业务代码读它** —— 所有真实消费者（
`engines/*`、`sync/`、`mcp_server/`、`app/platform.py`）都走
`broker_manager.active_bridge()`（动态取）。

这条核实很重要，它决定了「缩短启动预算」是否安全：**是安全的** —— 晚到的连接
不会让业务拿不到行情。但它也解释了为什么 §4.4 的「补同步 + 重刷日历」必须做：
不补的话，晚到连接会让**交易日历**永远停在「工作日」fallback。

### 9.2 自愈路径确实存在（所以「交后台」不是甩锅）

- `gateway/health.py::BrokerHealthMonitor._loop` 每 5s 检查全部连接；对
  `active and not connected` 创建 `_reconnect` 任务，退避
  `delay = min(2 ** reconnect_attempts, 60)`（首次 1s）；
- `app/bootstrap/phase_watchdogs.py::_broker_auto_connect_guard` 每 30s 复探本机
  运行中的客户端，并在接入后重同步 `state.bridge` / `state.gateway`。

两条路径都不依赖启动期那次尝试成功 ⇒ 「预算到点就交还后台」不会丢连接。

3. 第 4 行 = **交后台不取消、且回调真的跑了**：`09:25:43.791 + 10.0s ≈ 09:25:53.828`，
   与 `_ping` 30s 超时/硬上限 32s 无关，说明是后台任务自然结束并触发 done 回调。

### 12.4 与探针的互证

`output/_r24_coldstart_probe.py` 在**源码态**给出 `32.01s → 8.00s（省 24.01s）`；
打包态实测 `32011ms → 8015ms`（省 24.0s）⇒ 两态一致，修法不是只对探针有效。

**探针口径诚实说明**：探针 A（复现改前 32s）用的是**新代码 + 旧预算值**
（`budget=CONNECT_HARD_TIMEOUT`），不是「旧代码」——因为旧代码没有 budget 参数；
它复现的是「不加预算时会发生什么」，等价于改前行为。
