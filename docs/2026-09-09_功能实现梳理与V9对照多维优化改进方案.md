# 一、主要功能与详细实现盘点（现状画像）

## 1.1 平台入口

| 入口 | 实现 | 文件 |
| --- | --- | --- |
| REST | FastAPI `/api/v1/*`，30+ 路由组，envelope 中间件 + request_id | `backend/app/main.py`、`app/routes/` |
| MCP | FastMCP Streamable HTTP；`auto_expose` 把 REST 能力自动注册为 MCP 工具；`tools/` 提供 trading/backtest/factors/indicators/matching/metrics/analysis 等手工工具 | `backend/mcp_server/`、`backend/tools/` |
| WebSocket | `WSManager` 连接管理 + 心跳 + 最近窗口重放 + 广播；`SyncEngine` 推送行情/账户快照/订单/成交 | `backend/sync/__init__.py`、`app/routes/ws.py` |
| 桌面 | Electron 壳 spawn 后端 → 端口文件发现 → React 同源加载 | `frontend/electron/`、`backend/run.py` |

## 1.2 交易执行（现状）

- **多券商/多账户**：`BrokerManager`（`xtquant_client/manager.py`）管理多个 `Connection`（QMT/掘金/PTrade/同花顺适配器），活跃连接 + 按连接寻径，持久化到磁盘。
- **下单链**：`POST /trade/order` → 参数校验 → `state.risk.check_order` → `_call(b, b.gateway.place_order)` → audit；幂等靠 `single_flight(key, window=5s)`（显式 key 或内容哈希）。
- **统一信号入口**：`SignalRouter`（`gateway/signal_router.py`）支持 live/paper/dry_run 三模式物理旁路 + 大额 TOTP 二次确认 + 持久化模式。
- **批量交易**：`/account/grid`、`/account/batch/order|cancel|reconnect`（`app/routes/account.py`），逐单独立风控 + 逐连接下单。
- **高级交易引擎**：`AlgoEngine`（TWAP/VWAP/Iceberg/POV，WAL 记录）、`ConditionOrderEngine`（条件单/止损单，轮询触发 + 重试 + DB 持久化）、`StrategyRuntime`（策略机器人容器）、涨停监控。
- **交易安全网**：`RiskManager`（额度/频率/价格偏离/日亏熔断/标的黑白名单）、`WAL`（fsync worker + checkpoint + replay）、`OrderWatchdog`（卡单扫描撤单）、`OrderReconciler`（300s 周期对账核销）、`gateway/idempotency.py`。
- **模拟盘**：`PaperEngine` 实时行情虚拟撮合（佣金/印花税/涨跌停带校验），独立于真实券商。

## 1.3 数据面（现状）

- **数据源**：`DataSourceManager`（`datasource/registry.py`）+ 单一 `DataSource` ABC + `auto_chain` 顺序降级 + 熔断器；当前注册源：`broker`（绑定 QMT 连接）+ `EltdxSource`（通达信协议：股票列表/快照/K线/分时/板块/ETF/资金流/股本/涨跌停价/详情/搜索）。
- **本地存储**：`LocalStore`（SQLite：local_bars/stock_list/boards/meta）+ `KlineCache`（热数据缓存 + 周线重采样）+ `MarketSync`（收盘后热数据刷新 + 跨年归档）。
- **研究链**：screener（条件选股 + NL 选股）、indicators（注册表 + DSL）、factors（pandas 向量化）、backtest（任务队列 + 成本模型）、strategy_market。

## 1.4 调度与任务（现状）

- `JobRuntime`（`app/runtime/jobs.py`）：内存任务表 + 优先级 + 取消 + dispatcher loop；Runner：sync/screen/backtest。**无持久化、无 retry/misfire/lease，重启即丢**。
- 周期任务全是 `asyncio` loop（对账 300s、看门狗 5s、行情快照 5s、MarketSync 自维护 loop）。

## 1.5 运行期容器（现状）

- `core/state.py::AppState`：类属性单例，持有 ~25 个服务引用（Service Locator 模式）；`app/state.py` 仅是兼容 shim。
- 启动分 6 阶段（`app/bootstrap/phase_db → broker → engines → watchdogs → replay → misc`），shutdown 逆序。
- `run.py`：单实例文件锁 + 端口 +1 平滑改口 + 端口文件发现。

## 1.6 质量与 CI（现状）

- CI（`ci.yml`）：pytest 逐文件自动发现 + ruff（仅 F+E9 真实 bug 门禁）+ ESLint + Vitest + Vite build；另有数字核对（测试数/组件数 vs 文档）、License 门禁、能力漂移门禁（REST agent 可见 → MCP tool）、前端 className 差集门禁。
- 测试约 45 个文件，覆盖 contract/datasource/paper/quote_bus/rate_limit/runtime 等单测面。

# 二、已核实的 V9 差距（带代码证据）

以下为本次实码勘察**确认存在**的问题，全部与 V9 的判断一致：

## 2.1 【P0】LocalStore latest-N 错误（V9 §10.2）

`datasource/local_store.py::get_bars`：

```sql
ORDER BY dt ASC  LIMIT ?
```

→ "取最近 N 根"实际返回**最早 N 根**。所有依赖本地 K 线的研究/回测/指标在数据量 > N 时取到的是最旧数据。**这是正确性 bug，不是架构问题，应立即修复**（子查询 `SELECT dt FROM ... ORDER BY dt DESC LIMIT N` 再 ASC 输出）+ 回归测试。

## 2.2 【P0】显式 source 静默 fallback（V9 §8.3）

`datasource/registry.py::get_kline`：`source` 为**未知源名**时会落到 `for name in self._auto_chain` 的 auto 分支静默换源；显式指定已注册源但无数据时返回 None（正确），但未知源名不报错。违反"显式指定 source 不支持该能力必须返回明确错误"。

## 2.3 【P0】批量下单假价格风控（V9 §7、§24）

`app/routes/account.py::account_batch_order`：

```python
state.risk.check_order(o["code"], o["price"] if o["price"] > 0 else 100.0, ...)
```

市价/无价格批量单用 **100.0 固定假价格**通过风控——价格偏离校验、单日金额限额、持仓比例全部失真。V9 CI 门禁 `fake market risk price = 0` 正对此项。修复方向：复用 `_latest_price` provider；无行情时市价单走"最近价 + 偏移带"或显式拒绝。

## 2.4 【P1】执行语义分散（V9 §7）

下单逻辑分散在：`routes/trade.py`、`routes/account.py`（batch）、`tools/trading.py`（MCP）、`gateway/signal_router.py`（live/paper/dry_run）、`engines/algo.py`、`engines/condition_order.py`、`engines/strategy_runtime.py`。各处风控/审计/幂等/事件推送**手工重复拼装**，语义不完全一致（如 batch 用假价、trade/order 有 single_flight 而 condition/algo 路径各自实现 WAL）。V9 的 `OrderIntent → ExecutionService` 尚未建立。

## 2.5 【P1】JobRuntime 无持久化（V9 §14）

任务表纯内存，进程重启丢任务；无 catch-up——"每天自动同步历史数据"目前依赖进程常驻。V9 Phase 6 的 Durable JobRuntime + Schedule Store 完全未开工。

## 2.6 【P1】AppState Service Locator（V9 §18）

全局单例 + 循环 import 规避注释（core/state.py 自己注明"避免循环 import"）。测试隔离差（改 state 需手动复位）、生命周期不显式。

## 2.7 【P2】数据源单一注册 + 无 Provider Manifest（V9 §8）

auto_chain 目前实际只有 `broker + eltdx` 两源；无 Manifest（license/限流/新鲜度）、无能力声明（Provider 有没有某能力靠 `hasattr` 探测）。

## 2.8 【P2】前端 Broker-First（V9 §17）

顶层 `BrokerContext.jsx`，无 `CapabilityProvider`；未连券商时研究功能依赖 broker 的程度需逐页确认。

## 2.9 【P2】无 Dataset Snapshot / 复权版本 / Instrument Master（V9 §10/12/13）

LocalStore 的 bars 表无 provider/batch/checksum 溯源列；复权只有 `adjust` 字符串无版本；标的别名映射分散在各 Provider。

# 三、多维优化改进方案

以下按 **9 个维度**组织。每项标注：`(优先级 | 对应 V9 Phase | 新增=V9 未覆盖)`。

## 维度 A：交易执行正确性与安全（最高优先）

| # | 优化项 | 说明 | 优先级 |
| --- | --- | --- | --- |
| A1 | 修复 batch order 假价格风控 | 无价单复用 `risk.set_price_provider` 的最新价；取不到行情时市价单**拒绝**而非假价通过；补回归测试 | P0 / V9 Phase3 |
| A2 | 建立 `OrderIntent` + `ExecutionService` 统一主链 | 定义 dataclass OrderIntent(code, side, volume, price, price_type, mode, source, idem_key, conn_id, metadata)；ExecutionService 内置 Validation→Pricing→Risk→Mode 分流→Idempotency→WAL→Audit→Notify→ExecutionPort；先包一层适配现有 7 个入口（不重写），逐个切换 | P1 / V9 Phase3 |

# 四、调整后的实施路线（对 V9 23 章的执行建议）

V9 的 Phase 0→11 顺序总体正确，本文按"风险×收益"微调：

```
S0（本周可完成，全是小改）
  B1 latest-N 修复 + 测试
  B2 显式 source 修复 + 测试
  A1 假价格风控修复 + g1 门禁
  I2 日志文件治理
  → 一个 PR，独立合入，不依赖任何架构改动

S1（V9 Phase1 原样执行）
  E1 REST/WS 契约快照门禁（g6/g7）
  MCP smoke、batch/grid 回归、Risk/WAL/Audit 回归
  → 锁死能力基线，之后所有重构有安全网

S2（数据治理最小闭环 ≈ V9 Phase2 压缩）
  B3 溯源列 + B4 质量 Gate（四项）+ B5 Instrument Master + B6 日历 SSOT
  → 为 S4 EOD 同步提供地基

S3（ExecutionService ≈ V9 Phase3）
  A2 OrderIntent 主链 + A3 撤单幂等 + g4 门禁
  A4 Execution Port 薄抽象（为 Phase8 铺路）

S4（调度 + EOD 同步 ≈ V9 Phase6+7 合并推进）
  C1 持久 job 表 → C2 schedule+catch-up → C3 EOD JobKind → H3 coverage 看板
  → 这是"每日自动同步"用户价值兑现点，优先级高于前端/插件

S5（V9 Phase4+5）
  D1/D3 AppContext + /ready 分层；数据源 Manifest + 能力路由改造
  D2 循环 import 消除 + g5 门禁

S6（V9 Phase8/9/10/11 按原计划）
  Connector 平台化 → Plugin Kernel → 前端 Platform-First → 打包升级
  E2/E3/E4 契约工具随前端 Phase 一起做
```

**关键调整理由**：
1. V9 Phase6/7（调度+EOD）提到 Phase8 之前是正确的，但建议**与 Phase4/5 并行或前置**——"每天自动同步历史数据"是最高用户价值，且不依赖 AppContext 完成；
2. latest-N、假价格、静默 fallback 三个 P0 **不排队等 Phase**，立即修；
3. 契约快照门禁（E1/g6/g7）必须先于一切数据面/执行面改动，否则"能力不回退"没有机器裁判。

# 六、一句话总结

> 当前代码已具备 V9 要求的**能力面**九成以上，真正的差距集中在四处：**三个已核实的数据/风控正确性 P0 bug**、**执行主链尚未统一**、**调度无持久化**、**容器仍是 Service Locator**。修复顺序应是：先修 P0 bug（一两天量级）→ 契约门禁锁基线 → 数据治理地基 → ExecutionService → 调度+每日同步兑现价值 → 再做架构现代化（AppContext/Connector/Plugin/前端）。
